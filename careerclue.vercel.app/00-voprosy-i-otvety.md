## Базовый синтаксис

- **В:** Какие базовые типы часто забывают перечислить, отвечая на вопрос «какие типы есть в Go»?
  **О:** `float32`/`float64` и `complex64`/`complex128` — кандидаты обычно называют целые/bool/string/составные типы, но забывают числа с плавающей точкой и комплексные. Более полный ответ также упоминает дженерики (1.18+), именованные типы и `any`. *(ист. 1, 7, 15)*

- **В:** Можно ли объяснить недоступность переменной за пределами блока `{}` через работу сборщика мусора?
  **О:** Нет, это частая ошибочная линия рассуждения. Причина — чисто лексическая область видимости (решается компилятором статически), переменная может физически жить в памяти сколь угодно долго после выхода из блока (например через замыкание) — просто обратиться к ней по имени снаружи уже нельзя. *(ист. 67)*

- **В:** Из каких полей состоит внутренняя структура строки в Go, и есть ли там поле ёмкости (cap), как у слайса?
  **О:** Нет — `stringHeader` содержит только `Data` (указатель) и `Len` (длина), без `Cap`. Строки и слайсы не разделяют одну структуру, хотя выглядят похоже (указатель+длина). *(ист. 15)*

- **В:** В чём разница между `type X = Y` (алиас) и `type X Y` (новый тип)?
  **О:** `type X = Y` — просто другое имя того же типа, полностью взаимозаменяемое без приведения. `type X Y` (без `=`) создаёт новый, номинативно несовместимый тип — даже при идентичном представлении в памяти нужно явное приведение. *(ист. 42, 51)*

- **В:** Что дают дженерики (Go 1.18+) по сравнению с `any`/`interface{}`?
  **О:** Ошибки несовпадения типов ловятся на этапе компиляции, а не в рантайме, и не нужен type assertion внутри функции — компилятор уже знает конкретный тип на месте вызова. Ограничение (constraint) — интерфейс, описывающий разрешённые операции; `~T` в объединении означает «любой тип с базовым типом T», а не только сам T. *(ист. 48)*

- **В:** Если `type UserID int` и `type ProductID int` — можно ли присвоить значение одного типа переменной другого напрямую?
  **О:** Нет — Go использует номинативную (по имени) типизацию для явно объявленных типов, а не структурную; совпадение базового типа не даёт совместимости. Нужно явное приведение. *(ист. 19)*

- **В:** Почему `int8(127) + int8(1)` даёт `-128`, а не ошибку?
  **О:** Целые числа представлены в дополнительном коде (two's complement); арифметика по модулю 2^N молча «заворачивает» через границу диапазона без паники. *(ист. 7, 36)*

- **В:** Что происходит при явном приведении `int32(math.Pow(2, 31))`?
  **О:** Значение превышает `math.MaxInt32`, биты усекаются и переинтерпретируются как знаковое число — получается `-2147483648`. Приведение типов в Go никогда не паникует на переполнении, просто усекает биты; дробная часть float всегда отбрасывается, не округляется. *(ист. 12)*

- **В:** Чем различаются байт, руна и графема?
  **О:** `byte` (`uint8`) — единица хранения UTF-8; `rune` (`int32`) — один Unicode code point; графема — то, что пользователь воспринимает как «один символ» (может состоять из нескольких рун — например «é» как e+акцент это 2 руны, но 1 графема). Для графемно-осознанного подсчёта нужны сторонние библиотеки (`rivo/uniseg`). *(ист. 1, 7, 11)*

- **В:** Что вернут `len(s)` и `s[i]` для строки с кириллицей, и почему `s[0] == 'П'` не скомпилируется?
  **О:** `len(s)` — число байт, не символов (кириллица — 2 байта/руна). `s[i]` возвращает i-й байт (тип `byte`), а не символ — сравнение с `rune`-литералом `'П'` не пройдёт компиляцию из-за несовпадения типов. Для подсчёта рун — `utf8.RuneCountInString` (O(n), без аллокаций), а не `len([]rune(s))` (тоже O(n), но с аллокацией). *(ист. 1, 3, 7, 11, 23)*

- **В:** Безопасно ли резать строку по произвольным байтовым индексам (`s[0:3]`)?
  **О:** Нет — срез режет по байтовым смещениям, может разрезать многобайтовую руну пополам и дать невалидный UTF-8. Резать безопасно только по индексам из `for range` (никогда не паникует, заменяет плохую последовательность на `RuneError`). *(ист. 7, 11)*

- **В:** Почему `s[0] = 'H'` — ошибка компиляции, и как на самом деле изменить символ в строке?
  **О:** Строки неадресуемы для записи. Обходной путь — привести к `[]byte` (или `[]rune` для Unicode-safe изменения), изменить, привести обратно. Оба направления конвертации `string`↔`[]byte` **всегда** копируют данные — это не zero-copy, вопреки частому заблуждению. *(ист. 3, 11, 19)*

- **В:** Почему конкатенация строк в цикле через `+=` — плохая идея, и что использовать вместо неё?
  **О:** Это O(n²) — каждая операция копирует все предыдущие данные заново. Правильный инструмент — `strings.Builder` (амортизированная O(1), растит буфер ×2); с Go 1.20+ у него есть защита от копирования уже использованного `Builder` (паника при попытке). *(ист. 3, 11, 23)*

- **В:** Паникует ли деление на ноль в Go, и одинаково ли ведут себя целые и float?
  **О:** Для целых чисел `x/0` — паника в рантайме `runtime error: integer divide by zero` (кроме случая, когда оба операнда — константы: тогда это ошибка компиляции «division by zero», а не рантайм-паника). Для `float64`/`float32` деление на ноль не паникует вообще — возвращает `+Inf`, `-Inf` или `NaN` (для `0.0/0.0`) по стандарту IEEE 754. *(источник: t.me/go_interview_lib)*

## Управляющие конструкции

- **В:** Когда вычисляются аргументы отложенного вызова `defer fmt.Println(x)` — сразу или в момент фактического выполнения при выходе из функции?
  **О:** Сразу, в момент выполнения строки `defer`. Если нужно актуальное на момент выхода значение — нужно обернуть вызов в замыкание: `defer func() { fmt.Println(x) }()`. *(ист. 30)*

- **В:** В каком порядке выполняются несколько `defer` в одной функции?
  **О:** LIFO (как стек) — последний по коду `defer` выполняется первым при выходе. *(ист. 30)*

- **В:** Как правильно модифицировать возвращаемое значение функции по итогам `recover()`?
  **О:** Через именованные возвращаемые значения — они доступны и изменяемы внутри `defer`-функции уже после выполнения тела, но до фактического возврата: `func f() (err error) { defer func() { if r := recover(); r != nil { err = fmt.Errorf(...) } }() ... }`. *(ист. 30)*

- **В:** Поймает ли `recover()`, вызванный внутри вложенной (не напрямую defer-ной) функции, панику родительской функции?
  **О:** Нет — `recover()` перехватывает панику, только если вызван напрямую внутри той функции, что непосредственно зарегистрирована через `defer`, а не в промежуточной вложенной функции, вызванной из неё. Причина — `recover()` привязан к конкретному фрейму стека той функции, что передана в `defer`. *(ист. 72)*

- **В:** Что делает `fallthrough` в `switch`, и учитывает ли он условие следующего `case`?
  **О:** Безусловно передаёт исполнение в тело следующего по порядку `case` (не проверяя его условие вообще), в отличие от C/Java, где обычный `case` в Go уже не проваливается сам по себе (неявный `break` есть всегда). `fallthrough` обязан быть последним оператором в теле текущего `case` и не может стоять в последнем `case` блока или в `case` внутри `select`. *(источник: t.me/go_interview_lib)*

## Функции

- **В:** Что такое «голый» (naked) return, и почему он считается антипаттерном в длинных функциях?
  **О:** `return` без аргументов в функции с именованными возвращаемыми значениями — она просто возвращает их текущие значения. В короткой функции (буквально в несколько строк) это может быть читаемо, но в длинной функции с несколькими такими `return` по коду читателю приходится прокручивать вверх к сигнатуре, чтобы понять, что именно возвращается в каждой точке — это снижает читаемость и провоцирует случайные ошибки при рефакторинге (значение может быть переприсвоено где-то выше по коду и забыто). Именованные возвраты по-прежнему полезны ради документации сигнатуры и доступа к значению из `defer`/`recover`, но в теле функции рекомендуется всегда писать явный `return x, err`, а не голый `return`. *(источник: t.me/go_interview_lib)*

## Слайсы, массивы, map, struct

- **В:** Из скольких полей состоит заголовок слайса, и сколько байт он занимает на 64-битной платформе?
  **О:** Три поля (указатель, len, cap), по 8 байт каждое — итого 24 байта (`runtime.SliceHeader`); именно они копируются при передаче слайса по значению, а не сам базовый массив. *(ист. 3, 7, 8, 22)*

- **В:** Может ли размер массива быть переменной времени исполнения (`arr := [n]int{}`, где `n` — переменная)?
  **О:** Нет — размер массива обязан быть константой времени компиляции; `[8]byte` и `[16]byte` — разные, несовместимые типы именно из-за этого правила. *(ист. 51)*

- **В:** По какой точной формуле растёт cap слайса при `append` (сверено с исходником `runtime/slice.go`)?
  **О:** Порог — ровно 256 элементов. При `cap < 256` — удвоение (`newcap = 2×oldcap`). При `cap ≥ 256` — `newcap += (newcap + 3×256) >> 2`, что стремится к ×1.25. Комментарий в исходнике: «Transition from growing 2x for small slices to growing 1.25x for large slices». *(независимо сверено с исходником `runtime/slice.go`; ист. 3, 7, 15, 60)*

- **В:** Что случится, если взять срез из середины другого слайса и сделать `append` к новому при наличии свободной ёмкости?
  **О:** Запись пойдёт в тот же базовый массив, затирая данные, всё ещё видимые через оригинальный слайс. Защита — three-index slicing `s[low:high:max]` (принудительно ограничивает cap) или явный `copy()`. *(ист. 4, 7, 8)*

- **В:** Чем nil-слайс отличается от `[]int{}`, и как это проявляется в JSON?
  **О:** У обоих `len==0` и `cap==0`, но у nil-слайса указатель в заголовке — nil. `nil`-слайс маршалится в JSON как `null`, пустой — как `[]`. Проверять пустоту всегда через `len(s) == 0`, не `s == nil`. *(ист. 4, 12)*

- **В:** Можно ли получить доступ к элементу, записанному через `append` внутри функции, если снаружи `len` не изменился?
  **О:** Да, если ёмкости (cap) хватило без реаллокации — элемент физически записан в тот же базовый массив; получить к нему доступ снаружи можно явным ресайзом длины: `s[:cap(s)]`. *(ист. 21)*

- **В:** Что случится при коллизии двух случайных значений `float32`, используемых как ключи map?
  **О:** Второе значение молча перезапишет первое (обычное поведение map) — итоговый размер map может оказаться меньше ожидаемого без ошибки/паники. Практический вывод — избегать float как ключи map. *(ист. 21)*

- **В:** Безопасно ли читать из nil map? А писать?
  **О:** Чтение из nil map безопасно (возвращает zero value). Запись в nil map — паника в рантайме (`assignment to entry in nil map`), не ошибка компиляции. Map всегда нужно явно инициализировать через `make`/литерал перед записью. *(ист. 19)*

- **В:** Как устроена «классическая» (до Go 1.24) реализация map — бакеты, load factor, распределение бит хеша?
  **О:** Бакеты вместимостью 8 элементов, overflow-бакет при переполнении; порог load factor для роста — ~6.5 элементов **в среднем на бакет по всей таблице** (не 8 в одном бакете); эвакуация при росте — инкрементальная. Младшие биты хеша → номер бакета, старшие 8 бит (tophash) хранятся с элементом для быстрого сравнения без сравнения всего ключа. *(ист. 3, 7, 8, 25, 30, 42, 48)*

- **В:** Правда ли, что Go 1.24 сменил реализацию map на Swiss Tables — или это миф одного источника?
  **О:** Это подтверждённый факт. Официальные release notes Go 1.24: «a new builtin map implementation based on Swiss Tables» (open addressing), включено по умолчанию, откат — `GOEXPERIMENT=noswissmap`. Версия с классическими бакетами точна для Go ≤1.23, версия с Swiss Tables — для Go 1.24+; обе версии корректны, просто для разных эпох рантайма. *(независимо сверено с официальными release notes go.dev/doc/go1.24; ист. 3)*

- **В:** При какой доле удалённых записей запускается ресайз новой (Swiss Tables) реализации map?
  **О:** ⚠ Неподтверждено — кандидат на одном из собесов назвал ~20% tombstone-помеченных записей, интервьюер сам отметил это как непроверенное утверждение; официальные release notes Go не детализируют этот внутренний порог. *(ист. 74, 76)*

- **В:** Почему `&m[key]` для map — ошибка компиляции?
  **О:** При рехешировании бакеты перевыделяются и элементы физически перемещаются — сохранённый указатель стал бы висячим. Обходные пути — читать-изменять-записывать целиком, либо хранить в map указатели (`map[K]*V`). *(ист. 9, файл 05)*

- **В:** В каком порядке обходит map оператор `for range`, и меняется ли этот порядок между запусками?
  **О:** Порядок намеренно рандомизирован рантаймом **при каждом отдельном запуске `for range`**, а не один раз на жизнь программы — защита от случайной привязки кода к негарантированному порядку. Конкурентная модификация map без синхронизации — фатальная ошибка рантайма (`fatal error: concurrent map read and map write`), а не тихая гонка. *(ист. 3, 7, 8, 24)*

- **В:** Какие требования к типу ключа map?
  **О:** Ключ обязан быть сравнимым (comparable) — слайсы, map, функции нельзя. Указатели как ключи валидны, сравниваются по адресу, не по содержимому. *(ист. 23)*

- **В:** Как эффективно найти пересечение двух слайсов?
  **О:** Построить map из элементов первого слайса (O(n)), пройти по второму и проверить наличие в map (O(m)) — суммарно O(n+m) вместо наивного O(n·m), ценой O(n) памяти. *(ист. 17)*

- **В:** В чём опасность взятия маленького среза из очень большого слайса без явного копирования?
  **О:** Маленький срез продолжает держать живым указатель на весь базовый массив — весь большой массив не может быть собран GC, пока жив хоть один срез на него. Защита — явное копирование: `small := append([]T(nil), big[1000:1010]...)`. *(ист. 24)*

- **В:** Сжимается ли map обратно после массового `delete()` элементов?
  **О:** Нет — `delete()` освобождает слот, но не возвращает память ОС и не уменьшает число бакетов; если map когда-то выросла, память бакетов остаётся выделенной, пока жива сама map. *(ист. 34)*

- **В:** Как компилятор располагает поля структуры в памяти, и почему порядок объявления полей влияет на итоговый размер структуры?
  **О:** Поля идут строго в порядке объявления, но компилятор вставляет padding-байты между ними ради выравнивания (alignment) — каждый тип должен начинаться по адресу, кратному своему размеру. Чередование мелких (`bool`) и крупных (`int64`) полей увеличивает padding; сортировка от крупных к мелким минимизирует итоговый размер. Проверка — `unsafe.Sizeof()`. *(ист. 63)*

- **В:** Функция принимает слайс как `[]int` и делает `append` внутри — почему вызывающий код не видит добавленный элемент?
  **О:** Заголовок слайса передаётся по значению, и `append` (если не хватило вместимости — а иногда и в общем случае, поскольку меняются сразу len/ptr) пишет новое значение заголовка в локальную копию параметра, а не в переменную вызывающего кода. Изменение уже существующих *элементов* слайса видно снаружи (общий базовый массив), а вот переприсваивание самой переменной — нет. Чтобы функция могла надёжно расширить чужой слайс, ей нужен параметр `*[]int`, а не `[]int`. *(источник: habr.com/ru/companies/ru_mts/articles/909158/)*

- **В:** Что вернёт `new([]int)`, и чем это отличается от `make([]int, 0)`?
  **О:** `new([]int)` возвращает `*[]int` — указатель на nil-слайс (сам слайс внутри не инициализирован: `len==cap==0`, указатель на данные — nil). `make([]int, 0)` возвращает саму (не указатель) уже инициализированную структуру слайса с ненулевым внутренним указателем на пустой, но выделенный участок памяти. На практике `new` для слайсов почти не используется — идиоматичнее `make` либо просто `var s []int` (тоже даёт nil-слайс, но без лишнего уровня указателя). *(источник: t.me/go_interview_lib)*

## Указатели

- **В:** Передаёт ли Go что-либо «по ссылке» в принципе (включая передачу через канал)?
  **О:** Нет — в Go всегда передаётся по значению, вопрос лишь в том, *что именно* копируется: вся структура целиком или указатель (8 байт) на неё. Канал не «передаёт по ссылке», а просто кладёт в себя копию отправленного значения. *(ист. 5, 9)*

- **В:** Мутирует ли метод с value receiver оригинальную переменную?
  **О:** Нет, даже для примитивных типов-алиасов (`type Counter int`) — метод получает копию. Мутация возможна только через pointer receiver. *(ист. 9)*

- **В:** Копирует ли присвоение структуры данные внутри её слайс/map-полей?
  **О:** Нет — это shallow copy: дублируется только заголовок (указатель+len+cap для слайса), обе копии продолжают ссылаться на одни и те же исходные данные. `append`, если требует реаллокации, разрывает эту связь. *(ист. 9)*

- **В:** Чем `new(T)` отличается от `make(T, ...)`?
  **О:** `new(T)` работает для любого типа, возвращает `*T` на обнулённую память. `make` работает только для слайсов/map/каналов, возвращает саму инициализированную структуру `T` (не указатель) с уже выделенными внутренними буферами. *(ист. 9)*

- **В:** Если у типа `T` все методы объявлены с value receiver, а хотя бы один — с pointer receiver — кто удовлетворяет интерфейсу, `T` или только `*T`?
  **О:** Если все методы — value receiver, интерфейсу удовлетворяют и `T`, и `*T`. Если хотя бы один метод — pointer receiver, удовлетворяет только `*T`. *(ист. 9, 19)*

- **В:** Зависит ли размер указателя от размера типа, на который он указывает?
  **О:** Нет — указатель это всегда просто адрес (4 или 8 байт в зависимости от платформы), независимо от того, указывает он на `int8` или на мегабайтную структуру. *(ист. 20)*

- **В:** Гарантирует ли взятие адреса переменной (`&x`) её уход в кучу?
  **О:** Нет — компилятор решает через escape analysis, «убегает» ли переменная из функции; если нет, она может остаться на стеке, даже если её адрес был взят. Проверка — `go build -gcflags="-m"`. *(ист. 9)*

- **В:** Почему `User{}.SetName("X")` (вызов pointer-receiver метода на литерале) не компилируется?
  **О:** Временные значения (литералы, результат вызова функции) неадресуемы — нельзя взять `&` от них. Нужно сначала присвоить переменной: `u := User{}; u.SetName("X")`. *(ист. 9)*

- **В:** Что изменилось в Go 1.22 в поведении переменной цикла `for _, v := range ...` при взятии её адреса/захвате в замыкании?
  **О:** До 1.22 все итерации делили одну переменную — все указатели/замыкания видели одно (последнее) значение. С 1.22 на каждой итерации создаётся новая переменная — `&v` на разных итерациях указывает на разные ячейки с верными значениями. *(ист. 9)*

## Методы и интерфейсы

- **В:** Как проверяется соответствие типа интерфейсу — на этапе компиляции или в рантайме?
  **О:** Статически, на этапе компиляции. Реализация неявная (нет `implements`) — тип удовлетворяет, если имеет все нужные методы; лишние методы не мешают. *(ист. 1)*

- **В:** Из чего состоит внутреннее представление непустого интерфейсного значения, и чем оно отличается от представления пустого интерфейса (`any`)?
  **О:** Непустой интерфейс — пара `(itab, data)`: указатель на таблицу методов конкретного типа + указатель на данные. Пустой интерфейс (`any`, без методов) — пара «указатель на дескриптор типа (`*_type`), указатель на данные», без промежуточной таблицы методов вообще — диспетчеризировать нечего. *(ист. 1, 7, 67)*

- **В:** Когда сравнение двух значений `any` через `==` паникует, а не просто возвращает `false`?
  **О:** Если динамический тип хотя бы одного из значений несравним (слайс, map, функция) — паника `comparing uncomparable type`, а не `false`. Компилятор не может отследить это статически для `any`. Альтернатива для слайсов — `slices.Equal()`/`reflect.DeepEqual()`. *(ист. 19)*

- **В:** На стороне какого пакета идиоматично объявлять интерфейс — производителя или потребителя?
  **О:** Потребителя — пакет, который использует интерфейс (принимает как параметр), а не пакет, реализующий его. Реализующий тип вообще не обязан знать о существовании интерфейса благодаря неявному удовлетворению. *(ист. 23)*

- **В:** После успешной type assertion `ab.(BC)` к другому интерфейсу — какие методы доступны, только `BC` или все методы реального динамического типа?
  **О:** Только методы целевого интерфейса `BC`, даже если реальный динамический тип реализует значительно больше. Assertion срабатывает по динамическому типу, но статический тип переменной после присвоения — именно `BC`. *(ист. 41)*

- **В:** Если дочерняя структура через embedding содержит родительскую, и обе объявляют метод с одинаковым именем — чей метод выполнится при вызове на значении дочерней структуры?
  **О:** Метод самой дочерней структуры — он объявлен на «глубине 0» и перекрывает одноимённый продвинутый (promoted) метод встроенного поля на глубине 1. Метод родителя при этом никуда не девается — он всё ещё доступен через явное обращение к полю (`c.Parent.Метод()`). Это не полиморфизм/override как в ООП с наследованием: если переменная статически типизирована как `Parent`, вызов метода на ней всегда останется методом `Parent`, даже если внутри физически лежит embedded-часть значения типа `Child`. *(источник: habr.com/ru/articles/654569/)*

## Обработка ошибок, panic/recover

- **В:** В какой горутине работает `recover()`, и что будет, если паника случится в горутине без своего `defer`+`recover`?
  **О:** `recover()` работает только в той горутине, где произошла паника — каждая горутина, где возможна паника, нуждается в своём `defer`+`recover`. Необработанная паника в любой горутине убивает **весь процесс**, а не только эту горутину. *(ист. 15, 21)*

- **В:** Когда уместно использовать `panic`, а когда — обычный `error`?
  **О:** `panic` — для нарушения инвариантов программы (программистских ошибок). `error` — для ожидаемых, штатных сбоев (файл не найден, невалидные данные). Не стоит использовать panic как замену обработки ошибок в бизнес-коде. *(ист. 15, 21)*

- **В:** Чем `errors.Is` отличается от `errors.As`?
  **О:** `errors.Is(err, target)` проверяет, есть ли конкретное ожидаемое значение ошибки где-либо в цепочке оборачиваний (аналог `==`, но по всей цепочке). `errors.As(err, &target)` находит в цепочке ошибку конкретного типа и извлекает её (аналог type assertion, тоже по всей цепочке). *(ист. 22)*

- **В:** Какой глагол форматирования появился в Go 1.13 для оборачивания ошибки с сохранением цепочки?
  **О:** `%w` (в отличие от `%v`, который просто форматирует текст без структуры-обёртки). *(ист. 22)*

- **В:** Что рекомендуется передавать клиенту в JSON-ответе об ошибке — текст или код?
  **О:** Код ошибки (`ErrNotFound`, `ErrInvalidArgument` как отдельные сравниваемые значения, а не строки) — текст хрупок для тестов и локализации; локализация текста — на стороне клиента. Маппинг кода в HTTP-статус — в отдельном централизованном middleware. *(ист. 53)*

## Конкурентность

- **В:** Каков стартовый размер стека горутины, и до какого предела он растёт по умолчанию?
  **О:** Стартовый — 2 КБ; растёт динамически до ~1 ГБ по умолчанию (`debug.SetMaxStack`). Упереться в лимит — почти всегда признак неограниченной рекурсии. Практический ориентир — не больше 500 тыс.–1 млн горутин на инстанс с запасом по памяти. *(ист. 1, 5, 8, 10, 18, 21, 23)*

- **В:** Чем livelock отличается от deadlock, и чем starvation отличается от обоих?
  **О:** Deadlock — горутины намертво блокируются. Livelock — горутины не блокируются, а активно уступают друг другу ресурс по кругу, реально не продвигаясь (тратят CPU без результата). Starvation — одна горутина монополизирует ресурс, не давая остальным исполниться. *(ист. 18)*

- **В:** Какие 4 условия Коффмана необходимы одновременно для deadlock?
  **О:** (1) взаимное исключение, (2) удержание-и-ожидание, (3) отсутствие принудительного отбора ресурса, (4) циклическое ожидание. Разрушение любого одного предотвращает deadlock (фиксированный порядок захвата локов ломает условие 4). *(ист. 20)*

- **В:** Детектирует ли рантайм Go deadlock в общем случае?
  **О:** Нет — только частный случай полного deadlock всей программы (все горутины спят и некому их разбудить), с `fatal error: all goroutines are asleep - deadlock!`; локальный deadlock двух горутин при живых остальных не детектируется. *(ист. 20)*

- **В:** Что означают `G`, `M`, `P` в модели планировщика Go?
  **О:** G — горутина, M — поток ОС, P — логический процессор (число = `GOMAXPROCS`). У каждого P — своя локальная очередь (LRQ) плюс общая глобальная (GRQ). *(ист. 5, 8, 10, 23)*

- **В:** Как именно работает work stealing в планировщике Go?
  **О:** Когда локальная очередь P опустела — до 4 попыток увести горутины из чужой случайно выбранной локальной очереди, забирая половину. Локальный P всё равно проверяет глобальную очередь каждые ~61 тик, чтобы она не голодала. *(ист. 5, 8, 10, 23)*

- **В:** С какой версии Go появилась асинхронная превентивная многозадачность (preemption), и что было до неё?
  **О:** С Go 1.14 (через сигнал `SIGURG`). До этого переключение горутин происходило только в точках блокировки — «тяжёлый» вычислительный цикл без операций I/O мог надолго занять поток. *(ист. 5, 8, 10, 23, 29, 31)*

- **В:** Какие состояния может принимать горутина как конечный автомат?
  **О:** `_Gidle`, `_Grunnable`, `_Grunning`, `_Gsyscall`, `_Gwaiting`, `_Gdead`. *(ист. 29, 31)*

- **В:** Что решает механику normal/starvation mode `sync.Mutex` (сверено с исходником `internal/sync/mutex.go`)?
  **О:** В normal mode — active spinning, новая горутина может «обогнать» уже давно ждущую в очереди (не строгий FIFO по факту владения). Порог перехода в starvation mode — `starvationThresholdNs = 1e6` (ровно 1мс ожидания); в starvation mode — строгий FIFO-хендофф без обгона. *(независимо сверено с исходником `internal/sync/mutex.go`; ист. 23)*

- **В:** Паникует ли операция с nil-каналом, или блокируется навсегда?
  **О:** Блокируется навсегда (и чтение, и запись) — не паникует. Паника у канала возникает только при записи в уже закрытый канал или повторном `close()` закрытого. *(ист. 15, 17, 24, 74)*

- **В:** Что происходит при `select` с несколькими одновременно готовыми ветками?
  **О:** Go случайно выбирает одну из готовых веток равномерно, без приоритета по порядку записи в коде, и выполняет ровно её. *(ист. 19)*

- **В:** Как разбудить сразу все горутины, ждущие на канале, не зная их точного числа?
  **О:** `close(ch)` — чтение из закрытого канала атомарно возвращает `(нулевое значение, false)` всем ожидающим одновременно; встроенный примитив broadcast. Закрывать канал должен только отправитель. *(ист. 10)*

- **В:** Кто должен закрывать канал результатов в паттерне worker pool — сами воркеры или отдельная горутина?
  **О:** Отдельная координирующая горутина, которая только ждёт `wg.Wait()` и лишь затем закрывает канал (`go func() { wg.Wait(); close(results) }()`). Попытка закрыть силами воркеров приводит либо к панике `send on closed channel`, либо к преждевременному закрытию. *(ист. 5, 10, 57)*

- **В:** Какое минимальное количество коротких STW-пауз происходит за один цикл современного (трёхцветного, конкурентного) GC?
  **О:** Две — Sweep termination и Mark termination; основная фаза Mark выполняется конкурентно с программой, не блокируя её. *(ист. 34)*

- **В:** Каков актуальный ориентир по длительности каждой STW-паузы GC — <10мс или <100мкс?
  **О:** <100мкс — это подтверждённый, актуальный с Go 1.8 (2017) ориентир (историческое обсуждение Austin Clements, октябрь 2016: «typical worst-case stop-the-world times less than 100 microseconds»). <10мс — это честная историческая цифра для версий Go до 1.8, а не устаревший миф и не запасная перестраховка. Обе цифры реальны, просто для разных эпох рантайма. *(независимо сверено с историческим обсуждением go-dev/golang-dev; ист. 34, 38, 39, 42)*

- **В:** По какой формуле рассчитывается таргетируемый размер кучи для следующего цикла GC через `GOGC`?
  **О:** `Target = Live × (1 + GOGC/100)`. При дефолтном `GOGC=100` куча вправе вырасти вдвое от live-данных. Для абсолютного потолка памяти нужен `GOMEMLIMIT` (Go 1.19+), а не подбор `GOGC`. *(ист. 38, 39)*

- **В:** Сколько CPU одного логического процессора таргетирует фоновая маркировка GC в steady state?
  **О:** ~25% (1/4) — это именно таргет, а не жёсткая квота; при `GOMEMLIMIT` вблизи лимита GC игнорирует этот таргет и может занять почти всё доступное CPU. *(ист. 38, 39)*

- **В:** Привязаны ли объекты в `sync.Pool` к конкретному логическому процессору (P)?
  **О:** Да — per-P locality (с Go 1.13): горутина на одном P кладёт объект в `Put()`, горутина на другом P может его не найти при `Get()`. GC может полностью очистить пул на любом цикле; состояние объекта не сбрасывается автоматически — нужен явный `Reset()`. *(ист. 39, 43, 46)*

- **В:** Через какую структуру-обёртку горутина, заблокированная на канале, паркуется в очереди `sendq`/`recvq`?
  **О:** `sudog` — структура, привязывающая горутину к конкретной операции ожидания; горутина переходит в `_Gwaiting`, будится через `goready()`, переводящую её обратно в `_Grunnable`. *(ист. 17)*

- **В:** Какова алгоритмическая сложность локальной диспетчеризации горутины планировщиком — почему она ближе к O(1), чем у классического POSIX-планировщика ОС?
  **О:** Локальное извлечение из LRQ — lock-free кольцевой буфер, O(1). У планировщика Go нет единого сортируемого списка приоритетов (в отличие от POSIX, где O(log N) и выше) — горутины существуют в раздельных состояниях, планировщик реагирует только на события. *(ист. 38)*

- **В:** Почему координатор-горутина — предпочтительный способ реализовать самодельный `WaitGroup` на каналах, а не мьютекс+счётчик?
  **О:** Единоличное владение изменяемым состоянием одной горутиной автоматически устраняет саму возможность гонки данных — суть message-passing подхода CSP в противовес shared-memory с блокировками; мьютекс+счётчик страдает TOCTOU-гонкой между проверкой `count==0` и блокировкой на сигнальном канале. *(ист. 38)*

- **В:** Для какого паттерна доступа оптимален `sync.Map`, и правда ли, что он всегда быстрее `map`+`RWMutex`?
  **О:** Оптимален для (1) записал-однажды-читают-многие, и/или (2) разные горутины пишут каждая в свои непересекающиеся ключи. При частой конкурентной записи в одни и те же ключи обычная map+`RWMutex` зачастую не медленнее (а то и быстрее) `sync.Map`. *(ист. 54)*

- **В:** При каком примерно соотношении чтений к записям оправдан `RWMutex` вместо обычного `Mutex`?
  **О:** Примерно 10:1 или выше. И `Mutex`, и `RWMutex` — не реентерабельны (повторный `Lock()` той же горутиной — гарантированный deadlock). *(ист. 21, 24, 46)*

- **В:** Что добавляет `errgroup` поверх обычного `WaitGroup`?
  **О:** Сбор первой возникшей ошибки среди горутин группы, автоматическую отмену через встроенный `context` при первой ошибке (`errgroup.WithContext`), и (в новых версиях) `SetLimit(n)` для ограничения конкурентности группы. Паника внутри горутины группы не превращается в обычную ошибку автоматически — всё ещё нужен свой `defer`/`recover`. *(ист. 22, 42)*

- **В:** Почему `context.WithValue()` часто называют антипаттерном, и как правильно выбирать тип ключа для него?
  **О:** Неявность зависимости (не видна в сигнатуре функции) и отсутствие типобезопасности (значение — `any`, ошибка только в рантайме). Ключом должен быть неэкспортируемый именованный тип (`type ctxKey string`), а не голая строка — иначе два пакета с одинаковым строковым ключом рискуют затереть значения друг друга. *(ист. 42, 58)*

- **В:** Какой конкретный ориентир по ускорению `sync/atomic` относительно `sync.Mutex` для простого счётчика?
  **О:** Примерно в 2–3 раза быстрее — атомарная инструкция CPU не требует полноценного захвата/освобождения лока со всей его логикой (spin/starvation, очередь ожидающих). Преимущество актуально для одиночных примитивных значений, не для группы связанных полей. *(ист. 77)*

- **В:** Чем горутина принципиально отличается от потока ОС по тому, кто её планирует, размеру стека и практическому масштабу?
  **О:** Горутину планирует рантайм Go в userspace (модель M:N — много горутин на меньшее число потоков), поток ОС — ядро (модель 1:1). Стартовый стек горутины — ~2 КБ, растёт динамически до ~1 ГБ (64-бит) / ~250 МБ (32-бит); у потока ОС стек обычно фиксирован и занимает единицы мегабайт сразу. Переключение горутин — дешёвая операция в userspace без syscall, поэтому одновременно можно держать сотни тысяч – единицы миллионов горутин против практического предела в тысячи потоков ОС. *(источник: habr.com/ru/articles/670974/)*

- **В:** Какие есть штатные способы остановить горутину, если у неё нет метода вроде `Kill()`?
  **О:** Три: (1) завершение `main()` — обрывает разом все горутины программы без гарантий завершённости; (2) закрытие канала, который горутины слушают (`close(ch)`) — широковещательно будит всех ожидающих; (3) отмена через общий `context` — горутины проверяют `ctx.Done()`, обычно внутри `select`. Остановить горутину можно только кооперативно «изнутри», а не императивно снаружи. *(источник: habr.com/ru/articles/670974/)*

- **В:** Что делают `runtime.GOMAXPROCS(runtime.NumCPU())` и `runtime.Gosched()`?
  **О:** `runtime.GOMAXPROCS(runtime.NumCPU())` явно фиксирует число логических процессоров планировщика (P) равным числу ядер — это и есть значение по умолчанию, явный вызов нужен только если до этого кто-то его переопределил. `runtime.Gosched()` — горутина добровольно уступает текущий поток, вставая в конец очереди на выполнение, не блокируясь ни на чём; из-за вытесняющего планировщика с Go 1.14 в проде почти не требуется. *(источник: habr.com/ru/articles/670974/)*

- **В:** В чём разница между `context.Background()` и `context.TODO()`, если оба возвращают технически одинаковый контекст?
  **О:** Разница чисто смысловая. `Background()` — канонический корень дерева контекстов, с которого стартуют в точке входа (`main`, обработчик верхнего уровня). `TODO()` — временная заглушка для мест, где ещё не решено, какой контекст использовать, либо родительский контекст объективно неоткуда взять — сигнал «здесь чего-то не хватает», а не альтернативный полноценный корень. *(источник: habr.com/ru/articles/670974/)*

- **В:** Чем `context.WithCancel`, `WithDeadline` и `WithTimeout` отличаются друг от друга по моменту срабатывания отмены?
  **О:** `WithCancel(parent)` отменяется только вручную — вызывающий сам решает и зовёт `cancel()`. `WithDeadline(parent, t)` отменяется автоматически в конкретный момент времени `t`. `WithTimeout(parent, d)` отменяется автоматически через интервал `d` от текущего момента — по сути обёртка над `WithDeadline`. Все три возвращают функцию отмены, которую нужно вызывать (обычно через `defer`) даже при уже сработавшем дедлайне/таймауте — иначе связанные с контекстом ресурсы не освобождаются сразу. *(источник: habr.com/ru/articles/670974/)*

- **В:** Что делает `sync.Once`, и для чего его обычно применяют?
  **О:** `once.Do(f)` гарантирует, что функция `f` выполнится ровно один раз за весь жизненный цикл программы, даже при конкурентных вызовах `Do` из множества горутин одновременно — остальные вызовы дождутся завершения первого и не выполнят `f` повторно. Типичное применение — потокобезопасная ленивая инициализация синглтона или общего подключения без ручного мьютекса и флага «уже инициализировано». *(источник: habr.com/ru/articles/658623/)*

- **В:** Что такое `sync.Cond`, и почему условие после `Wait()` нужно перепроверять в цикле `for`, а не в `if`?
  **О:** `sync.Cond` — условная переменная поверх блокировки (обычно `*sync.Mutex`): `Wait()` атомарно освобождает лок и паркует горутину до сигнала, при пробуждении сама заново захватывает лок; `Signal()` будит одну ожидающую горутину, `Broadcast()` — все разом. Между пробуждением и повторным захватом лока условие могла успеть изменить другая горутина (или сработало паразитное пробуждение) — поэтому его нужно перепроверять в цикле `for`, а не считать сам факт пробуждения доказательством истинности условия. *(источник: habr.com/ru/articles/658623/)*

- **В:** Чем отличаются lock-free и wait-free алгоритмы, и к какой из категорий относится типичный CAS-цикл (`compare-and-swap` с ретраем)?
  **О:** Lock-free гарантирует, что **хотя бы одна** горутина из конкурирующих продвинется вперёд за конечное число шагов (глобальный прогресс), но конкретная горутина в теории может застрять в цикле ретраев сколь угодно долго при постоянном проигрыше гонки. Wait-free — более строгая гарантия: **каждая** отдельная горутина гарантированно завершает операцию за ограниченное число шагов независимо от поведения остальных. Типичный паттерн `for { old := atomic.Load(&x); n := f(old); if atomic.CompareAndSwap(&x, old, n) { break } }` — lock-free, но не wait-free: при высокой конкуренции отдельная горутина может проигрывать CAS многократно подряд. *(источник: t.me/go_interview_lib)*

- **В:** Почему для канала-сигнала («просто разбудить», без передачи полезных данных) идиоматично использовать `chan struct{}`, а не `chan bool`?
  **О:** `struct{}` — тип нулевого размера (0 байт), тогда как `bool` физически занимает память (хоть и 1 байт) и создаёт ложное впечатление, что переданное значение (`true`/`false`) само по себе что-то значит — хотя обычно важен только факт получения значения или закрытия канала. `chan struct{}` явно сигнализирует читателю кода: канал только для синхронизации, само значение смысла не несёт. *(источник: t.me/go_interview_lib)*

- **В:** Как `sync.WaitGroup` умещает счётчик задач и число ожидающих горутин в одно 64-битное слово, и зачем?
  **О:** Внутреннее состояние (счётчик добавленных через `Add`/невычтенных через `Done` задач и число горутин, заблокированных в `Wait()`) упаковано в одно `uint64`: старшие 32 бита — счётчик задач, младшие 32 бита — число ожидающих. Упаковка в одно слово сделана специально ради атомарности: обе величины можно менять одной атомарной инструкцией CPU (`atomic.Add`/CAS) без отдельного мьютекса. Отсюда и требование выравнивания `WaitGroup` на 64-битную границу на 32-битных платформах — иначе атомарная операция над 64-битным словом невозможна. *(источник: t.me/go_interview_lib)*

- **В:** Какой практический ориентир для выбора числа воркеров в пуле — одинаков ли он для CPU-bound и I/O-bound задач?
  **О:** Нет. Для CPU-bound задач (чистые вычисления без блокировок) оптимум обычно близок к `runtime.NumCPU()` — больше воркеров лишь увеличивает переключение контекста без выигрыша. Для I/O-bound задач (сеть, диск, ожидание ответа БД) воркеров может быть в разы или на порядки больше числа ядер, поскольку большую часть времени горутина не потребляет CPU, а простаивает в ожидании — ограничивающий фактор здесь не CPU, а число одновременных соединений/лимиты внешней системы, под которые и нужно подбирать размер пула. *(источник: t.me/go_interview_lib)*

## Generics

- **В:** Правда ли, что встроенные функции `min`/`max` в Go работают только с числами с плавающей точкой, а для целых чисел нужно писать свою реализацию?
  **О:** Это устаревшее утверждение. До Go 1.21 в стандартной библиотеке действительно были только `math.Min`/`math.Max`, и только для `float64`. Начиная с Go 1.21 появились **встроенные** (без импорта) функции `min`/`max`, работающие для любого упорядочиваемого типа — целых чисел, строк и float — через сравнение `<`/`>`, а не только через float. *(миф — habr.com/folko.gitbook.io; уточнено по официальным release notes tip.golang.org/doc/go1.21)*

## Стандартная библиотека

- **В:** Через какие интерфейсы в Go абстрагированы файлы, сеть, сжатие и кодирование?
  **О:** `io.Reader`/`io.Writer` из пакета `io` — не только «чтение/запись HTTP-запроса», как часто отвечают кандидаты узко. *(ист. 1)*

- **В:** Какая формула защищает от переполнения `int` при ручной реализации бинарного поиска?
  **О:** `low + (high-low)/2`, а не `(low+high)/2`. В stdlib есть готовая `sort.Search` вместо ручной реализации. *(ист. 3)*

- **В:** Правда ли, что скомпилированный Go-бинарник запускается на любой ОС без пересборки?
  **О:** Нет — бинарник платформозависим. «Кросс-компиляция» — это пересборка с другими `GOOS`/`GOARCH`, а не один универсальный бинарник. *(ист. 8)*

- **В:** Для чего нужен `math/rand` vs `crypto/rand`, и в чём проявляется «парадокс дней рождения» при генерации уникальных случайных чисел?
  **О:** `math/rand` — некриптографические случаи (детерминирован по seed); `crypto/rand` — обязателен, где случайность важна для безопасности (токены). При приближении запрашиваемого N к существенной доле пространства значений наивный цикл «генерируй-проверяй» становится неэффективным — эффективнее алгоритм Фишера-Йетса (равномерная перестановка за O(n)) и взять первые N. *(ист. 24)*

- **В:** Как перевести `int32` в байты с явным порядком байт, и что такое Big/Little Endian?
  **О:** `binary.BigEndian.PutUint32(buf, uint32(x))` / `binary.LittleEndian.PutUint32(...)` из `encoding/binary`. Big Endian — самый значимый байт первым (сетевой порядок); Little Endian — младший байт первым (нативный для x86). Несовпадение порядка у отправителя/получателя — источник трудноуловимых багов. *(ист. 63)*

- **В:** Чем `io.EOF` отличается от `io.ErrUnexpectedEOF`, и когда `io.ReadFull` вернёт именно второй?
  **О:** `io.EOF` — штатный сигнал «поток данных закончился ровно на границе» (не ошибка в смысле «что-то сломалось»). `io.ReadFull(r, buf)` требует прочитать ровно `len(buf)` байт: если поток закончился, не успев заполнить буфер полностью, но хотя бы один байт уже был прочитан — возвращается `io.ErrUnexpectedEOF` (данных оказалось меньше ожидаемого — уже нештатная ситуация); если не было прочитано вообще ни байта — возвращается обычный `io.EOF`. *(источник: t.me/go_interview_lib)*

- **В:** Что изменилось в Go 1.23 для `time.Ticker`/`time.Timer`, если забыть вызвать `Stop()`?
  **О:** До Go 1.23 забытый (не остановленный) `time.Ticker`/`time.Timer` держал живым весь связанный с ним объект (включая канал и всё, что через него достижимо) до явного `Stop()` — источник утечки памяти при частом создании таймеров без очистки. С Go 1.23 таймеры и тикеры, на которые больше нет ссылок из пользовательского кода, стали доступны для сборки GC даже без вызова `Stop()` — рантайм больше не держит на них скрытую сильную ссылку сам по себе. Явный `Stop()`/`defer ticker.Stop()` всё равно остаётся хорошей практикой (немедленно останавливает тикающий таймер), а не только подстраховкой от утечки. *(источник: t.me/go_interview_lib)*

## Тестирование

- **В:** Чем отличается мок от стаба?
  **О:** Мок проверяет поведение (что метод действительно был вызван нужное число раз с нужными аргументами), стаб просто возвращает заданные значения без проверки факта вызова. *(ист. 15)*

- **В:** Какие три уровня тестовых замен для HTTP-клиентского кода дают возрастающую гибкость?
  **О:** (1) fake-клиент с захардкоженными полями; (2) мок с программируемым полем-функцией (`DoFunc`); (3) `http.RoundTripper` на уровне транспорта. Отдельно — `httptest.Server` для интеграционных тестов с реальным HTTP-роундтрипом. *(ист. 33)*

- **В:** Что такое table-driven тесты, и как запустить каждый кейс как отдельный именованный подтест?
  **О:** Слайс структур-кейсов (входные данные + ожидаемый результат), каждый запускается через `t.Run(caseName, func(t *testing.T) {...})` — отдельный, независимо идентифицируемый в выводе тест на кейс. *(ист. 33)*

## HTTP / веб-сервер

- **В:** Что HTTP/2 добавляет поверх HTTP/1.1, и насколько типично сокращается объём заголовков через HPACK?
  **О:** Бинарный фрейминг, мультиплексирование нескольких запросов в одном TCP-соединении (без взаимной блокировки на уровне HTTP), сжатие заголовков HPACK (~85% сокращение), приоритизацию потоков, Server Push. HTTP/2 в Go включается автоматически при `ListenAndServeTLS`. *(ист. 36)*

- **В:** Что вернёт `client.Do()` при ошибке на уровне транспорта (не удалось установить соединение), и в чём частая ошибка при работе с этим случаем?
  **О:** `(nil, err)` — `resp` гарантированно nil. Обращение к `resp.Body.Close()` без предварительной проверки `err != nil` — паника на nil-указателе. Правильный порядок — сначала проверить ошибку. *(ист. 32, 33)*

- **В:** Почему одного `http.Client{Timeout: N}` часто недостаточно, и какие раздельные таймауты нужны через `http.Transport`?
  **О:** Общий таймаут покрывает весь цикл запроса разом и не различает, на каком этапе застряло (медленная отдача тела — Slowloris-подобная деградация выглядит так же, как обычная медленная сеть). Раздельные — `DialContext`/`net.Dialer.Timeout` (TCP), `TLSHandshakeTimeout`, `ResponseHeaderTimeout` (специально ловит зависание на заголовках). *(ист. 26)*

- **В:** Как правильно классифицировать HTTP-коды в retry-логике клиента?
  **О:** `429` — сигнал rate-limiting, уважать заголовок `Retry-After`, а не свой фиксированный график. `5xx` — обычно транзиентно, ретраить с backoff+джиттером. `4xx` кроме `429` — ошибка самого запроса, повторять бессмысленно. *(ист. 47)*

- **В:** Почему refresh-токен не обязан быть JWT, и как безопасно хранить access/refresh на клиенте?
  **О:** Refresh-токен практичнее делать непрозрачной случайной строкой, привязанной к записи в БД — это даёт возможность отзыва (нельзя для stateless JWT без доп. стораджа). Access — в памяти/заголовке `Authorization`; refresh — в cookie с `HttpOnly`+`Secure`+`SameSite=Strict`. Повторное использование уже инвалидированного refresh-токена — сигнал кражи, повод отозвать все сессии. *(ист. 26)*

- **В:** Какая типичная атака возможна при самодельной проверке JWT, если валидатор доверяет полю `alg` из самого токена?
  **О:** Algorithm substitution (alg confusion) — атакующий подменяет заявленный алгоритм на симметричный (HS256) и подписывает токен публичным ключом сервера как секретом HMAC. Защита — валидатор обязан жёстко зафиксировать ожидаемый алгоритм на своей стороне, игнорируя `alg` из токена. Сравнение подписи — константное время (`hmac.Equal()`), не обычный `==`. *(ист. 53)*

- **В:** Когда предпочтителен gRPC, а когда REST?
  **О:** gRPC — для внутреннего взаимодействия сервисов друг с другом (бинарный protobuf ×3-10 плотнее JSON, строгий типизированный контракт, HTTP/2). REST — для внешних API и там, где важна доступность для незнакомых с gRPC разработчиков. *(ист. 15, 22)*

- **В:** Как включить server reflection в gRPC, и почему это обычно отключают в проде?
  **О:** `reflection.Register(grpcServer)` в коде сервера — сервер сообщает список сервисов/методов без `.proto`-файлов на клиенте (используют `grpcurl`/`grpcui`). В проде обычно отключают — иначе утечка структуры внутреннего API постороннему с сетевым доступом, но без исходников. *(ист. 66)*

- **В:** Можно ли безопасно переиспользовать один `http.Client` из множества горутин одновременно, и почему рекомендуется создавать его один раз, а не на каждый запрос?
  **О:** Да, `http.Client` безопасен для конкурентного использования из многих горутин одновременно — предназначен именно для переиспользования. Создание нового `http.Client` (а точнее, нового `http.Transport` внутри него) на каждый запрос — частая ошибка производительности: `Transport` держит пул keep-alive TCP-соединений, переиспользуемых между запросами; создавая клиент заново каждый раз, теряется весь эффект от keep-alive — каждый запрос заново устанавливает TCP- (а для HTTPS — ещё и TLS-) соединение с нуля. *(источник: t.me/go_interview_lib)*

- **В:** Как защититься от SQL-инъекции и XSS в Go-обработчике, принимающем пользовательский ввод?
  **О:** От SQL-инъекции — только параметризованные запросы (плейсхолдеры `$1`/`?`, значения передаются отдельно от текста запроса через `database/sql`/драйвер), никогда конкатенация или `fmt.Sprintf` пользовательского ввода прямо в SQL-строку. От XSS — экранирование при выводе пользовательских данных в HTML; пакет `html/template` (в отличие от `text/template`) делает это автоматически с учётом контекста вставки (тело HTML, атрибут, URL, JS), тогда как `text/template` не экранирует ничего и не должен использоваться для генерации HTML из недоверенных данных. *(источник: t.me/go_interview_lib)*

- **В:** Чем интерфейс `http.Handler` отличается от типа `http.HandlerFunc`, и что произойдёт, если передать `nil` вторым аргументом в `http.ListenAndServe`?
  **О:** `http.Handler` — интерфейс с одним методом `ServeHTTP(w, r)`; `http.HandlerFunc` — тип-обёртка над обычной функцией с такой сигнатурой, которая сама реализует `ServeHTTP` (просто вызывая себя) — приём, позволяющий передавать обычные функции туда, где ожидается `Handler`, без отдельной структуры. `http.ListenAndServe(addr, nil)` с `nil` вторым аргументом использует `http.DefaultServeMux` — глобальный, пакетный экземпляр мультиплексора, куда пишут обработчики, зарегистрированные через `http.HandleFunc`/`http.Handle` в любом импортированном пакете процесса. На практике это считается плохой практикой в продакшн-коде (неявная глобальная регистрация, риск конфликта путей между независимыми пакетами, невозможность держать несколько независимых серверов в одном процессе) — явный `http.NewServeMux()` предпочтительнее. *(источник: t.me/go_interview_lib)*

## Идиомы и best practices

- **В:** Какие 7 категорий проблем чаще всего всплывают при переходе от «просто работающего» кода к продакшн-готовому?
  **О:** (1) жизненный цикл CGo-объектов, (2) лимиты уровня конкурентности, (3) обработка таймаутов/context, (4) очистка временных файлов, (5) мониторинг/метрики, (6) стратегии retry (экспоненциальный backoff), (7) circuit breaker. *(ист. 5, 33)*

- **В:** Зачем нужны флаги линковщика `-ldflags="-s -w"`, и какую цену за это платят?
  **О:** `-s` убирает таблицу символов, `-w` — отладочную информацию DWARF, уменьшая размер бинарника. Цена — потеря читаемых имён символов/полноценной отладки через `delve` на итоговом бинарнике (обычно приемлемо для прод-сборки). *(ист. 60)*

- **В:** Чем `go trace` (`runtime/trace`) отличается от `pprof`?
  **О:** `pprof` — агрегированная статистика (сколько времени/памяти суммарно ушло куда). `trace` строит подробную временную шкалу конкретного запуска (активность потоков/P, блокировка/пробуждение горутин, фазы GC) — для разбора конкретной аномалии, не для агрегата. *(ист. 43)*

- **В:** Каков типичный лимит размера одного PR, при котором качество ревью резко не деградирует?
  **О:** Порядка 400–500 строк diff — крупные PR снижают качество ревью просто из-за объёма, физически невозможного удержать в голове целиком. *(ист. 47)*

- **В:** Какие 5 критериев отличают «сильного» мидла от «слабого» на Go?
  **О:** (1) понимание внутреннего устройства базовых структур вместо «чёрного ящика»; (2) способность писать корректный конкурентный код самостоятельно; (3) осознанное управление моделью памяти; (4) зрелая обработка ошибок; (5) правильное управление ресурсами через `context`. *(ист. 64)*

- **В:** Чем императивный подход отличается от декларативного, и какие технологии — эталонные примеры каждого?
  **О:** Императивный описывает **как** достичь результата (пошаговые инструкции, сам Go/Python код). Декларативный описывает **что** нужно получить, оставляя решение о шагах исполнителю (SQL `SELECT`, Docker/Kubernetes-манифесты, Terraform). Go как императивный язык может строить декларативные абстракции поверх себя (билдер-паттерны, DSL на функциональных опциях). *(ист. 70)*

- **В:** Как принципы SOLID переносятся на Go, где нет классов и наследования?
  **О:** Без иерархии классов все пять всё равно применимы: Single Responsibility — пакет/тип решает одну узкую задачу (в духе Unix-философии); Open/Closed — код открыт для расширения через добавление новой реализации интерфейса и закрыт для модификации уже написанных; Liskov Substitution — переносится в требование к контракту интерфейса (реализация не должна нарушать ожидаемое поведение); Interface Segregation — маленькие интерфейсы на стороне потребителя лучше одного большого; Dependency Inversion — зависеть от интерфейсов, а не от конкретных реализаций, передавая их через конструктор. Interface Segregation и Dependency Inversion в Go часто получаются «бесплатно» просто из структурной типизации и идиомы «интерфейс объявляется у потребителя». *(источник: habr.com/ru/articles/658623/)*

- **В:** Что такое cache thrashing (ложное разделение кэш-линии, false sharing) в конкурентном Go-коде, и как его избежать?
  **О:** Когда несколько горутин на разных ядрах CPU часто пишут в разные переменные, физически расположенные в одной кэш-линии процессора (обычно 64 байта), каждая запись инвалидирует копию всей линии в кэше других ядер — несмотря на логическую независимость переменных, они начинают «состязаться» за кэш, резко деградируя производительность (кэш-линия непрерывно гоняется между ядрами). Типичное решение — явный padding между часто изменяемыми конкурентно полями структуры, чтобы они физически оказались в разных кэш-линиях. *(источник: t.me/go_interview_lib)*

- **В:** Чем директива сборки `//go:build` отличается от старой формы `// +build`, и что делает флаг `CGO_ENABLED=0`?
  **О:** `//go:build expr` (с Go 1.17) — новый, более читаемый синтаксис условий сборки на основе логических выражений (`&&`, `||`, `!`), проверяемый `gofmt`/`go vet`; `// +build tag1 tag2` — устаревшая форма (пробел между тегами = OR, отдельные строки = AND), которую `gofmt` автоматически конвертирует и до сих пор дублирует рядом с `//go:build` ради обратной совместимости со старым инструментарием. Обе директивы обязаны стоять до объявления `package`, с пустой строкой после, и не иметь над собой ничего, кроме комментариев. `CGO_ENABLED=0` при сборке отключает cgo — итоговый бинарник становится полностью статическим (без динамической линковки с libc), что важно для минимальных образов (`scratch`/`distroless`), но недоступны пакеты, реально зовущие C-код (например, некоторые способы DNS-резолвинга в `net` переключаются на чистый Go-резолвер). *(источник: t.me/go_interview_lib)*

- **В:** Чем `signal.NotifyContext` удобнее «ручной» связки `signal.Notify` + канал для graceful shutdown по `SIGINT`/`SIGTERM`?
  **О:** `ctx, stop := signal.NotifyContext(parent, os.Interrupt, syscall.SIGTERM)` сразу возвращает обычный `context.Context`, который отменяется при получении сигнала — код, уже умеющий реагировать на `ctx.Done()` (например `errgroup` или HTTP-сервер с `Shutdown(ctx)`), встраивается без отдельного канала сигналов и ручного `select`. Обязателен `defer stop()` — освобождает регистрацию обработчика сигнала, иначе она остаётся висеть до конца процесса. `signal.Notify(ch, ...)` — более низкоуровневый вариант: канал сигналов, регистрация сигналов и `select` пишутся вручную, вручную же транслируя получение сигнала в отмену контекста. *(источник: t.me/go_interview_lib)*

## Базы данных / инфраструктура / системный дизайн

- **В:** Проверяет ли `sql.Open` реальное подключение к БД?
  **О:** Нет — только инициализирует пул соединений. Для проверки нужен явный `PingContext`. *(ист. 5)*

- **В:** Какие 4 параметра настройки пула соединений есть в `database/sql`?
  **О:** `SetMaxOpenConns`, `SetMaxIdleConns`, `SetConnMaxLifetime`, `SetConnMaxIdleTime`. *(ист. 5)*

- **В:** В чём разница между liveness-пробой и readiness-пробой для БД-зависимого сервиса?
  **О:** Liveness — максимально дешёвая и быстрая (`SELECT 1`, просто «соединение живо»), не должна валидировать схему/бизнес-логику. Readiness — вправе быть строже (например проверка версии применённых миграций) — сервис не готов принимать трафик, если миграции ещё не применены. *(ист. 49)*

- **В:** Какие основные типы индексов БД существуют, и для чего каждый предназначен?
  **О:** B-tree/B+tree — индекс по умолчанию, O(log n), диапазонные запросы. Hash — O(1), только точное совпадение. GiST/R-tree — пространственные данные. GIN — полнотекстовый поиск/JSONB/массивы. Bitmap — низкая кардинальность, но плохо под конкурентной записью (OLAP). Покрывающий индекс (`INCLUDE`) — index-only scan без чтения таблицы. Частичный индекс — по подмножеству строк. BRIN — компактный для больших таблиц с физической корреляцией (временные ряды). *(ист. 37)*

- **В:** Чем `EXPLAIN` отличается от `EXPLAIN ANALYZE`?
  **О:** `EXPLAIN` — только план (что оптимизатор *собирается* делать, по оценке). `EXPLAIN ANALYZE` реально выполняет запрос и показывает и оценку, и фактические цифры — расхождение оценки и факта часто и есть источник проблемы. Для мутирующих запросов безопасно обернуть в `BEGIN; EXPLAIN ANALYZE ...; ROLLBACK;`. *(ист. 20, 22, 52)*

- **В:** В каком порядке идёт систематическая воронка диагностики медленной БД, от дешёвого к дорогому?
  **О:** (1) индексы, (2) оптимизация самих запросов, (3) тюнинг параметров СУБД, (4) HDD→SSD, (5) партиционирование, (6) репликация, (7) шардирование, (8) кэширование, (9) денормализация, (10) специализированное хранилище. *(ист. 56)*

- **В:** Что такое паттерн Idempotency Key, и как он реализуется в PostgreSQL атомарно?
  **О:** Клиент генерирует уникальный ID конкретной попытки операции (обычно UUID); сервер при первом получении выполняет операцию и сохраняет результат с этим ключом; при повторе — не выполняет заново, отдаёт сохранённый результат. В PostgreSQL — `INSERT ... ON CONFLICT (idempotency_key) DO NOTHING`. *(ист. 36)*

- **В:** Что такое multi-stage builds в Docker, и зачем они нужны?
  **О:** Один этап компилирует бинарник в полноценном образе с тулчейном, финальный образ — только бинарник поверх минимальной базы (`scratch`/`alpine`) — кардинально уменьшает размер конечного образа. *(ист. 35)*

- **В:** Чем readiness probe отличается от liveness probe в Kubernetes?
  **О:** Readiness — готов ли Pod принимать трафик прямо сейчас (временное исключение из балансировки без рестарта). Liveness — жив ли процесс вообще (при провале Kubernetes перезапускает контейнер). Частая путаница именно между этими двумя. *(ист. 35)*

- **В:** Кто именно принимает решение об откате канареечного релиза — DevOps/SRE или продуктовая команда?
  **О:** Инфраструктуру эксплуатирует DevOps/SRE, но пороговые значения метрик для остановки/отката задаёт инженерная/продуктовая команда сервиса, поскольку только она понимает бизнес-контекст критичности показателей. *(ист. 70)*

- **В:** Как СУБД PostgreSQL агрегация фильтруется через `WHERE` и `HAVING` — в чём разница?
  **О:** `WHERE` фильтрует исходные строки **до** группировки. `HAVING` фильтрует уже сгруппированные результаты (например `HAVING COUNT(*) > 5`) — потому что агрегированного значения ещё не существует на этапе `WHERE`. *(ист. 24)*

- **В:** Как выбрать порядок колонок в композитном индексе?
  **О:** Колонку с наибольшей селективностью — первой; B-tree индекс просматривается слева направо без «пропусков» середины, так что запрос по второй колонке без первой вообще не сможет эффективно использовать индекс. Неиспользуемые индексы находятся через `pg_stat_user_indexes` (`idx_scan = 0`). *(ист. 24)*

- **В:** В чём разница между `ON`-условием и `WHERE`-условием при `LEFT JOIN`, если условие ссылается на колонку из присоединённой таблицы?
  **О:** `ON`-условие не отсеивает строки, сохраняя `NULL` при отсутствии совпадения. `WHERE`-условие отсеивает `NULL`-строки — и `LEFT JOIN` фактически начинает вести себя как `INNER JOIN`, если `WHERE` ссылается на колонку правой таблицы. *(ист. 41)*

- **В:** Какие уровни изоляции транзакций есть в порядке возрастания строгости, и какой из них дефолт в PostgreSQL?
  **О:** Read Uncommitted (в PostgreSQL реально работает как Read Committed из-за MVCC), Read Committed (дефолт в PostgreSQL), Repeatable Read (возможны фантомные строки), Serializable (самый строгий, через SSI). *(ист. 20, 25)*

- **В:** Для точечного изменения баланса одного счёта в банковском сценарии — всегда ли правильнее взять Serializable/Repeatable Read?
  **О:** Нет — часто предпочтительнее Read Committed (дефолт) с явной блокировкой строки `SELECT ... FOR UPDATE` перед проверкой/обновлением — блокировка ложится точно на нужную строку, не вызывая ошибок сериализации (`40001`), которые пришлось бы перехватывать при более строгом уровне. Дополнительная защита — `CHECK (balance >= 0)` на уровне схемы. *(ист. 52)*

- **В:** Почему `GOMAXPROCS` может быть выставлен неверно внутри Kubernetes-контейнера с CPU-лимитом, и как это исправить?
  **О:** Рантайм Go по умолчанию видит **все** ядра хост-машины через `runtime.NumCPU()`, даже если контейнеру по cgroup выделена лишь часть — рантайм создаёт больше потоков, чем может параллельно исполняться под квотой, что приводит к CPU throttling. Решение — `go.uber.org/automaxprocs`, считывающая реальный cgroup-лимит. *(ист. 23)*

- **В:** Какие метрики однозначно указывают именно на CPU-throttling (а не общую нехватку ресурсов)?
  **О:** `container_cpu_cfs_throttled_periods_total` и `container_cpu_cfs_throttled_seconds_total` — рост при внешне невысокой средней загрузке CPU. *(ист. 43)*

- **В:** Чем отличается диагностика CPU-throttling от диагностики OOM Killer?
  **О:** Throttling (CFS-планировщик CPU) не убивает процесс, лишь замедляет. OOM Killer (подсистема памяти ядра) убивает процесс безвозвратно по показателю `oom_score` — в Kubernetes видно как `OOMKilled`. Разные уровни, разные метрики/логи для диагностики. *(ист. 43)*

- **В:** В чём принципиальная разница контейнера и виртуальной машины по механизму изоляции?
  **О:** ВМ эмулирует железо и запускает отдельную ОС целиком (сильная изоляция, гигабайты, минуты старта). Контейнер разделяет ядро ОС хоста (namespaces + cgroups) — мегабайты, секунды старта, но более слабая изоляция (общее ядро — поверхность атаки). *(ист. 20)*

- **В:** В каком порядке идёт структурированный протокол диагностики деградации распределённой системы «прод тормозит»?
  **О:** (1) метрики (~30 сек, локализовать аномальный сервис), (2) логи (~2 мин, агрегированный поиск паттернов), (3) трейсинг (конкретный проблемный span), (4) события инфраструктуры (корреляция с деплоями), (5) каскадные паттерны (circuit breaker/retry storm/bulkhead). От широкого и дешёвого к узкому и дорогому. *(ист. 30)*

- **В:** Гарантирует ли Kafka порядок сообщений по всему топику, или только в рамках партиции?
  **О:** Только в рамках одной партиции (монотонный offset). Чтобы связанные сообщения обрабатывались строго по порядку — задавать им одинаковый ключ (key), консистентное хеширование направит их в одну партицию. *(ист. 25)*

- **В:** Что делает `enable.idempotence=true` у продюсера Kafka?
  **О:** Присваивает сообщениям порядковые номера, защищая от дублей при повторных отправках после сетевого сбоя (retry продюсера не создаёт дублирующихся сообщений). *(ист. 25)*

- **В:** Как правильно обрабатывать сообщение Kafka, которое не удалось обработать — фатальная ошибка vs транзиентная?
  **О:** Фатальная (неразбираемый формат) — сразу в DLQ (Dead Letter Queue) с сохранением исходного контекста (топик/партиция/offset/текст ошибки/счётчик попыток). Транзиентная (сетевой таймаут) — ограниченное число ретраев (часто через отдельные retry-топики с растущей задержкой) перед уходом в DLQ. Offset коммитится только после успешной обработки или осознанной отправки в DLQ. *(ист. 68)*

- **В:** Как паттерн Transactional Outbox решает проблему двойной записи (dual write) между БД и Kafka?
  **О:** Событие и бизнес-изменение пишутся в одной локальной ACID-транзакции — бизнес-таблица обновляется и в ту же транзакцию добавляется строка в outbox-таблицу. Отдельный фоновый poller публикует их в Kafka. Для нескольких инстансов poller без дублирования — `SELECT ... FOR UPDATE SKIP LOCKED`. *(ист. 25, 68)*

- **В:** Чем `Histogram` отличается от `Summary` для метрики задержки, и почему `Histogram` обычно предпочтительнее?
  **О:** `Histogram` считает попадания в заранее заданные бакеты — позволяет агрегировать перцентили постфактум на сервере запросов, корректно суммируя данные с разных инстансов. `Summary` считает квантили уже на стороне клиента метрики — их нельзя корректно агрегировать между инстансами (нельзя усреднить уже посчитанные перцентили). *(ист. 69)*

- **В:** Как избежать «эффекта грозовой тучи» (cache stampede) при истечении TTL популярного ключа в Redis?
  **О:** Паттерн Lazy Read-Through + защита через Compare-And-Swap (`SET key value NX` — атомарная установка ключа-«замка», только один инстанс идёт в БД) — либо аналог `singleflight`/turnstile в масштабе распределённой системы. *(ист. 60)*

- **В:** Через какой механизм читатель PostgreSQL видит согласованный снэпшот данных, не блокируя писателей (и наоборот)?
  **О:** MVCC на уровне полей строки `xmin` (транзакция, создавшая версию) и `xmax` (транзакция, пометившая как устаревшую) — читающая транзакция видит только версии строк, чей `xmin` завершился раньше её снэпшота. Старые версии с неактуальным `xmax` остаются на диске до `VACUUM` (dead tuples). *(ист. 62)*

- **В:** Чем оптимистичная блокировка (поле `version`) отличается от пессимистичной (`SELECT ... FOR UPDATE`) с точки зрения масштабируемости?
  **О:** Оптимистичная лучше масштабируется при низкой реальной конкуренции (не держит лок впустую), но требует явного retry в прикладном коде при `RowsAffected() == 0`. Пессимистичная сразу выражает намерение через SQL, не требует retry-логики ценой худшей пропускной способности при высокой конкуренции. *(ист. 62)*

- **В:** Почему `float64`/`float32` — плохой выбор типа для денежных сумм, и что использовать вместо?
  **О:** Ошибки округления накапливаются на масштабе (пример: прибавление 0.1 миллион раз через float не даёт ровно 100000 из-за неточного двоичного представления десятичных дробей). Правильно — целочисленный тип в минимальных единицах валюты (`int64` в копейках/центах) либо `NUMERIC(19,4)`/`DECIMAL`. *(ист. 17, 21, 26)*

- **В:** Почему `time.Now().UnixNano()` — плохой способ генерировать ID транзакции под высокой нагрузкой, и какие альтернативы?
  **О:** Ограниченная гранулярность системных часов даёт реальные коллизии на высоком RPS, плюс не гарантирует уникальность между узлами. Альтернативы — ULID/KSUID (временная метка + криптографически случайная часть) или UUID v7 (сортируемый по времени вариант UUID). *(ист. 53)*

- **В:** Что проверяет паттерн Saga для распределённых «транзакций» через несколько сервисов, и чем оркестрация отличается от хореографии?
  **О:** Saga даёт только eventual consistency через компенсирующие действия вместо ACID-отката. Orchestration — центральный координатор явно вызывает шаги и знает, как их компенсировать (проще проследить, плотнее связанность). Choreography — децентрализовано, каждый сервис реагирует на события сам (слабее связанность, сложнее отлаживать). *(ист. 15)*

- **В:** Чем CQRS отличается от Event Sourcing, хотя они часто применяются вместе?
  **О:** CQRS — разделение модели записи и модели чтения на отдельные пути/хранилища. Event Sourcing — состояние хранится как последовательность неизменяемых событий, а не текущий снимок; текущее состояние вычисляется проигрыванием событий. Обе технологии типичны для финансовых/учётных доменов с требованием полного аудиторского следа. *(ист. 44)*

- **В:** Правда ли, что связка MongoDB+Elasticsearch означает «Elasticsearch хранит данные в MongoDB»?
  **О:** Нет — MongoDB (или любая БД) остаётся единственным источником истины, Elasticsearch — вторичная, денормализованная поисковая проекция с eventual consistency (обновляется отдельным конвейером синхронизации с задержкой), а не равноправное хранилище тех же данных. *(ист. 70)*

- **В:** Чем HLS/MPEG-DASH отличаются от RTMP и WebRTC в системном дизайне видеоплатформы, и почему они доминируют именно для видео по запросу (VoD)?
  **О:** HLS/DASH (поверх HTTP) — стандарт для VoD именно благодаря совместимости с обычным HTTP-CDN-кэшированием и встроенной поддержкой адаптивного битрейта. RTMP (поверх TCP) — легаси-протокол приёма потока от энкодера. WebRTC — для полностью интерактивных сценариев (видеозвонки), где задержка критичнее гарантированной доставки. *(ист. 75)*
