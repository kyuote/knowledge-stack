## Горутина vs поток ОС

Горутина — лёгкая единица исполнения, управляемая рантаймом Go, а не ОС. Стартовый размер стека — 2 КБ (у потока ОС обычно 1–8 МБ), стек растёт динамически, но не бесконечно — верхний предел роста стека одной горутины по умолчанию ~1 ГБ (настраивается через `debug.SetMaxStack`); упереться в этот лимит на практике — почти всегда признак неограниченной рекурсии, а не легитимной глубокой нагрузки. За счёт лёгкого старта на типичном железе можно держать миллионы горутин одновременно — на практике ограничение скорее ~1–5 млн на 16 ГБ RAM (с учётом ~2–4 КБ на стек горутины + метаданные); жёсткие пределы — объём виртуального адресного пространства, накладные расходы GC на сканирование стеков, конкуренция за планировщик. Практическая рекомендация — не превышать 500 тыс.–1 млн горутин на инстанс (под, если Kubernetes) с запасом по памяти, и использовать worker pool для контроля нагрузки, а не бесконтрольный спавн горутин; «утёкшая» (забытая, никогда не завершающаяся) горутина продолжает занимать свою долю памяти на стек, пока жив процесс — рост числа живых горутин со временем без выхода на плато при стабильной нагрузке — практический сигнал именно такой утечки. [14(доп.), 23] Конкретные ориентировочные цифры по производительности (порядки величин, не гарантия конкретного железа): создание горутины ~200 нс против ~10–100 мкс на поток ОС; переключение контекста горутины ~200 нс против ~1–10 мкс у потока ОС — разница на 1–2 порядка и объясняет разницу в достижимом количестве. Отдельная деталь по модели GMP: локальная очередь горутин (LRQ) у каждого P ограничена по размеру (по одному источнику — до **256** горутин), при переполнении часть перекладывается в глобальную очередь (GRQ). [1(кратко), 5, 8, 10, 18, 21]

## Race condition, deadlock, livelock, starvation — полный набор проблем shared-memory конкурентности

Помимо уже разобранной гонки данных (data race — минимум одна из конкурентных операций на общей памяти является записью, типичный пример — конкурентная запись в обычную map, что рантайм детектирует и роняет процессом с ошибкой, плюс `go run -race`/`go test -race` для статического обнаружения — детектор инструментирует каждый доступ к памяти для отслеживания конфликтующих чтений/записей, что стоит порядка **5–10× замедления** по времени выполнения и заметного роста потребления памяти, поэтому используется в CI/тестах, а не в проде) [51], стоит держать в голове ещё два термина, которые реже всплывают, но могут спросить отдельно: **livelock** — горутины не блокируются намертво (в отличие от deadlock), а активно уступают друг другу ресурс по кругу, реально не продвигаясь в работе (в отличие от deadlock тратят CPU, но результата нет); **starvation** («голодание») — одна горутина монополизирует ресурс/CPU, не давая остальным исполниться (не обязательно взаимная блокировка — может быть банальный дисбаланс приоритетов/захвата локов). Практическая рекомендация против deadlock (циклическое ожидание нескольких локов) — всегда захватывать несколько мьютексов в едином фиксированном порядке во всех местах кода, где они берутся вместе. [18]

Более формальный взгляд на deadlock — четыре условия Коффмана (Coffman conditions), выполнение всех четырёх одновременно необходимо для взаимной блокировки: (1) взаимное исключение (ресурс занят эксклюзивно одним потоком/горутиной); (2) удержание-и-ожидание (горутина держит один ресурс и одновременно ждёт другой); (3) отсутствие принудительного отбора ресурса (нельзя силой отобрать удерживаемый ресурс у горутины); (4) циклическое ожидание (цепочка горутин, где каждая ждёт ресурс, удерживаемый следующей по кругу). Разрушить любое из четырёх условий — способ предотвратить deadlock: фиксированный порядок захвата локов ломает условие (4); тайм-аут на попытку захвата — `TryLock` (метод `sync.Mutex`/`sync.RWMutex` с Go 1.18+, неблокирующая попытка захватить лок, возвращает `bool` успеха) в комбинации с ретраем — ослабляет условие (2), горутина не «зависает» вечно в ожидании. Сам рантайм Go **не** детектирует deadlock мьютексов в общем случае — обнаруживает лишь частный случай полного deadlock всей программы (все горутины спят и некому их разбудить), с ошибкой `fatal error: all goroutines are asleep - deadlock!`, но не любой локальный deadlock двух горутин при живых остальных. [20]

## Процессы vs потоки (фон перед GMP)

Поток исполняет код на ядре CPU, разделяя память с другими потоками процесса; процесс — загруженный бинарник, владеющий как минимум одним потоком. Механизмы межпроцессного взаимодействия (IPC): пайпы, сигналы, разделяемая память, сокеты, очереди сообщений — общее CS-знание, но часто спрашивают перед переходом к горутинам/GMP для проверки базы. Более детально: Unix domain sockets — низкая задержка для локального (в пределах одной машины) взаимодействия, дополнительно позволяют передавать между процессами файловые дескрипторы; именованные пайпы (FIFO) — как обычный пайп, но с именем в файловой системе, что позволяет взаимодействовать процессам без общего предка; разделяемая память + семафоры — самый быстрый вариант IPC (без копирования данных через ядро), но требует ручной, строгой синхронизации доступа (семафор координирует, кто сейчас пишет/читает); файлы на диске — простейший вариант, ценой задержки дисковых операций. [8, 29]

## `fork()` — системный вызов создания процесса (фон для сравнения с горутинами)

Классический CS-вопрос, всплывающий перед переходом к модели Go: `fork()` создаёт дочерний процесс — копию адресного пространства родителя. Возвращаемое значение отличает, в чьей «ветке» выполняется код: `< 0` — ошибка (процесс не создан), `== 0` — это дочерний процесс, `> 0` — это родительский процесс (значение — PID потомка). На практике полная копия памяти не происходит физически сразу — используется Copy-on-Write (страницы физически дублируются только при первой записи одним из процессов). Паттерн `fork()+exec()` — стандартный способ запуска нового бинарника из процесса на Unix-подобных системах. Архитектура prefork-сервера (заранее форкнутый пул процессов-воркеров, а не по процессу на запрос) исторически использовалась для параллельной обработки запросов до того, как лёгкие потоки/горутины стали основным инструментом — стоит уметь провести эту параллель на собесе (модель Go с горутинами решает ту же задачу параллельной обработки запросов на порядки дешевле по памяти и латентности создания). [20]

## Конкурентность vs параллелизм vs асинхронность

Конкурентность — архитектурное свойство работы с несколькими задачами (не обязательно физически одновременно, может быть переключение контекста). Параллелизм — задачи реально исполняются одновременно, нужно несколько ядер CPU. Асинхронность — про дизайн API: операция сразу возвращает управление, результат приходит позже (колбэк/канал/future). Все три комбинируются в реальных продакшн-системах одновременно. [5]

## Модель планировщика GMP и work stealing

G — горутина, M — поток ОС (machine), P — логический процессор, связывающий их (количество P по умолчанию = `GOMAXPROCS` = `runtime.NumCPU()`; `GOMAXPROCS=1` — конкурентность без параллелизма). У каждого P — своя локальная очередь горутин (LRQ), плюс есть глобальная очередь (GRQ). Work stealing: когда локальная очередь P опустела, он делает до **4 попыток** увести горутины из чужой (случайно выбранной) локальной очереди, забирая **половину** горутин оттуда — так избегается конкуренция за глобальную очередь. Чтобы глобальная очередь не голодала, локальный P всё равно проверяет её каждые **~61 тик** планировщика. Интеграция с netpoller: горутины, ждущие сети, «паркуются» отдельно, не блокируя поток ОС, и возвращаются в очередь, когда данные готовы. Syscall handoff: если горутина уходит в блокирующий системный вызов, её P «отдаётся» другому M, чтобы не простаивать. С Go 1.14 появилась асинхронная превентивная многозадачность (preemption, через сигнал `SIGURG`) — до этого переключение горутин происходило только в точках блокировки, из-за чего «тяжёлый» вычислительный цикл без операций ввода-вывода мог надолго занять поток. Практическое следствие: для CPU-bound задач не стоит создавать горутин больше, чем `GOMAXPROCS` (лишний оверхед переключения), для IO-bound — горутины дешёвые, их может быть значительно больше числа ядер. [5, 8, 10, 23]

Состояния горутины как конечного автомата (пригодится, если спросят про внутренности планировщика на уровне состояний, а не только очередей): `_Gidle` (только выделена, ещё не инициализирована), `_Grunnable` (готова к исполнению, ждёт своей очереди в LRQ/GRQ), `_Grunning` (реально исполняется на каком-то M), `_Gsyscall` (внутри блокирующего системного вызова — состояние, в котором и происходит уже описанный выше syscall handoff), `_Gwaiting` (заблокирована на канале/мьютексе/таймере — ожидает внешнего события, будится через `goready()`, см. выше), `_Gdead` (исполнение завершено, горутина ожидает переиспользования структуры). Переключение горутин (context switch) в кооперативной модели Go происходит в конкретных, заранее определённых точках, а не когда угодно: операции с каналами (отправка/приём/`select`), блокирующие системные вызовы, операции с примитивами `sync` (захват занятого мьютекса и т.п.), таймеры/`time.Sleep`, явный вызов `runtime.Gosched()`, safepoint'ы сборщика мусора, и — с Go 1.14 — асинхронные точки принудительной превентивной перекладки через сигнал `SIGURG` для горутин, слишком долго не отдающих управление добровольно (см. уже описанный async preemption выше). [29, 31]

## Гонки данных и инструменты синхронизации

Классическая задача: 1000 горутин инкрементят общий счётчик без синхронизации — две проблемы сразу: (1) гонка данных, потому что инкремент — три неатомарных шага (прочитать/увеличить/записать), часть обновлений теряется; (2) `main` может завершиться раньше, чем горутины успеют отработать (лечится `sync.WaitGroup`). Полный набор инструментов от гонок и для их устранения: паттерны confinement (данные не расшариваются, а передаются владением), каналы (модель CSP), примитивы `sync` (`Mutex`/`RWMutex`/`WaitGroup`/`Once`/`Cond`), атомарные операции (`sync/atomic`), отмена через `context`. У каждого — свои компромиссы по честности (fairness), производительности и семантике блокировки. Практическое правило: атомарные операции — для одиночных примитивных операций (счётчики, флаги, самый быстрый вариант); мьютекс — когда критическая секция состоит из нескольких связанных шагов. [4, 7, 10]

Дополнительные тактики против гонок и блокировок, помимо уже перечисленных: паттерн владения каналом (channel ownership) — только одна горутина «владеет» каналом на запись/закрытие, остальные только читают, что снимает саму возможность гонки за право закрыть канал; минимизация критической секции — держать под локом только то, что реально требует защиты, и как можно короче по времени (не выполнять внутри лока медленные операции вроде сетевых вызовов); `sync.Once` — гарантированно однократная инициализация (например синглтона/конфига) вне зависимости от того, сколько горутин одновременно в неё попытаются попасть. [20, 21]

## `RWMutex` вместо `Mutex` для операций чтения — практический пример упущения

На живом кодинге частая недоработка кандидата — защищать и чтение, и запись общей map через полный `Mutex`, хотя чтений обычно на порядки больше, чем записей (типичный сценарий — счётчик кликов, который часто читают и относительно редко обновляют) — правильнее `sync.RWMutex` с `RLock()` на чтение. Ещё одна типичная недоработка — гонка данных на отдельной вспомогательной переменной состояния (например, «дата последней очистки старых данных»), которую обновляет фоновая горутина, а читает горутина-обработчик запроса, без какой-либо синхронизации между ними — сам факт использования мьютекса для основной map не защищает соседние переменные состояния, если к ним обращаются напрямую в обход мьютекса. [16]

## Примитивы `sync` — полный список и детали

Полный список: `Mutex`, `RWMutex`, `Once`, `Cond`, `WaitGroup`, плюс `sync/atomic`, `sync.Map`, `sync.Pool` — частый пробел в ответах: кандидаты вспоминают только каналы/atomic/mutex/WaitGroup, забывая `RWMutex`, `Cond`, `Pool`, `sync.Map`. `Mutex`: в любой момент `Lock()` держит не более одной горутины, остальные блокируются до `Unlock()` (типичный пример — обернуть map в структуру с mutex, сама map не потокобезопасна). `RWMutex`: несколько читателей одновременно через `RLock()`, но запись через `Lock()` — эксклюзивна и блокирует всех; предпочтителен при большом перевесе чтений над записями. [7, 10]

**Механика spin/starvation ниже — сверена напрямую с актуальным исходником `internal/sync/mutex.go` (куда с Go 1.24 вынесена реальная реализация `sync.Mutex`) и подтверждена как точный факт, а не пересказ источника с оговоркой «требует проверки».** `sync.Mutex` реализован поверх атомарных операций и работает в двух режимах. В обычном режиме (normal mode) захват — это гонка «кто успел»: горутина, пытающаяся захватить занятый мьютекс, сначала недолго активно крутится в цикле (active spinning, через `runtime_canSpin`/`runtime_doSpin`), не уходя в полноценную блокировку — расчёт на то, что текущий держатель лока вот-вот его отпустит, и цикл дешевле полноценной блокировки/разблокировки потока; в это время **новая** горутина, только начавшая пытаться захватить лок, может «обогнать» уже давно ждущую в очереди — сам исходник описывает normal mode дословно так: «waiters are queued in FIFO order, but a woken up waiter does not own the mutex and competes with new arriving goroutines over the ownership» — то есть в обычном режиме порядок explicitly не FIFO по факту владения, хотя очередь ожидания формально FIFO. Порог перехода в starvation mode задан именованной константой в исходнике — **`starvationThresholdNs = 1e6`**, то есть ровно **1 миллисекунда** (это подтверждает уже стоявшую в конспекте цифру «~1 мс» как точную, а не приблизительную): если конкретная горутина ждёт лока дольше этого порога, мьютекс переключается в starvation mode, где, опять же дословно по исходнику, «ownership of the mutex is directly handed off from the unlocking goroutine to the waiter at the front of the queue; new arriving goroutines don't try to acquire the mutex even if it appears to be unlocked» — строгий FIFO-хендофф без обгона. Обратный переход в normal mode происходит, когда ожидающая горутина либо становится последней в очереди, либо успела прождать меньше 1 мс — то есть starvation mode это защитный, самоотключающийся режим, а не постоянное состояние. Отдельно стоит иметь в виду: Go 1.24 ввёл **новую** внутреннюю реализацию этого мьютекса рантайма («new runtime-internal mutex implementation» по официальным release notes, отключаемую флагом `GOEXPERIMENT=nospinbitmutex`) — но описанная выше механика spin/starvation осталась семантически той же в новой реализации, менялись детали низкоуровневого кодирования состояния, а не наблюдаемое поведение normal/starvation mode. [23; независимо сверено напрямую с исходником `internal/sync/mutex.go` и официальными release notes go.dev/doc/go1.24 — не источник из общей нумерации `_istochniki.md`]

Внутреннее представление `sync.Mutex` — не отдельная структура на каждый бит состояния, а одно целочисленное поле-состояние (`state`), разряды которого кодируют сразу несколько независимых флагов: занят ли лок (locked), разбужен ли ожидающий (woken, чтобы не будить сразу несколько горутин без нужды), находится ли мьютекс в starvation mode (см. выше), и счётчик числа ожидающих горутин — всё это поверх атомарных операций (`sync/atomic`), а не через отдельный примитив ОС на каждое поле; уже описанный выше spin-цикл — попытка не уходить в полноценную блокировку на уровне ОС, пока есть реальный шанс, что держатель лока вот-вот освободит его сам. [54]

Конкретный практический ориентир по производительности `sync/atomic` против `sync.Mutex` для простого счётчика — атомарные операции называют примерно в **2–3 раза быстрее** мьютекса именно на таком узком сценарии (инкремент/чтение одного целочисленного значения), поскольку атомарная инструкция CPU не требует полноценного захвата/освобождения лока со всей его логикой (spin/starvation mode, очередь ожидающих) — но преимущество актуально именно для одиночных примитивных значений; как только нужно атомарно менять больше одного связанного поля сразу — `sync/atomic` перестаёт быть простой заменой мьютекса (нужна атомарность именно всей группы полей разом, что `sync/atomic` в базовом виде не даёт). Практический пример применения — мониторинг доли ошибочных HTTP-ответов на живом сервисе через пару атомарных счётчиков (общее число запросов и число ошибок), инкрементируемых на каждый обработанный запрос без блокировок, с периодическим снятием и сбросом значений по `time.Ticker` (например раз в несколько секунд) для отправки метрики наружу — типичный low-overhead паттерн именно там, где нужен просто счётчик, а не сложное состояние. [77]

Уточнение к уже описанной выше таблице поведения nil/открытого/закрытого канала: типичная ошибка кандидатов — предположить, что операция с nil-каналом сразу **паникует**; на деле и чтение, и запись в nil-канал корректно **блокируются навсегда** (вечный deadlock при отсутствии других путей выполнения у горутины), а не паникуют — паника у канала возникает только при записи в уже **закрытый** канал или повторном `close()` закрытого канала, это принципиально другой случай. [74]

## `sync.Map` — для какого конкретно паттерна доступа он оптимален

Уточнение к уже упомянутому `sync.Map` (см. полный список примитивов `sync` выше): это не универсальная быстрая замена `map`+`RWMutex` на все случаи, а специализированная структура именно под два конкретных паттерна одновременно — (1) ключ, однажды записанный, дальше только читается многими горутинами (стабильный, редко меняющийся набор данных), и/или (2) **разные** горутины пишут каждая в свои непересекающиеся ключи, не конкурируя друг с другом за одни и те же записи. При частой конкурентной записи в одни и те же ключи из многих горутин обычная `map` + `sync.RWMutex` зачастую оказывается не медленнее (а то и быстрее) `sync.Map`, несмотря на интуитивное ожидание, что специализированная конкурентная структура обязана быть быстрее — стоит явно проговаривать этот нюанс на собесе, а не считать `sync.Map` универсально «более конкурентной» версией обычной map. [54]

## `sync.RWMutex` — когда оправдан оверхед по сравнению с обычным `Mutex`

Ориентировочное практическое правило (не жёсткая формула, скорее эвристика для собеса) — `RWMutex` оправдывает свой дополнительный оверхед по сравнению с обычным `Mutex`, когда соотношение чтений к записям примерно **10:1 или выше**; при близком к паритету соотношении чтений/записей накладные расходы на более сложную внутреннюю бухгалтерию `RWMutex` (отдельные счётчики читателей/писателей) могут не окупаться, и обычный `Mutex` оказывается не медленнее. И `Mutex`, и `RWMutex` — **не реентерабельны** (non-reentrant): повторный `Lock()` той же горутиной, уже держащей лок, — гарантированный deadlock, в отличие от, например, реентерабельных мьютексов в некоторых других языках. [21, 24] Проблема голодания писателя при преобладании читателей у `RWMutex` (см. также turnstile-паттерн выше для самодельной версии на каналах) имеет устоявшееся название — **writer starvation problem**: при непрерывном потоке новых читателей писатель, ожидающий эксклюзивного `Lock()`, теоретически может ждать неограниченно долго, если реализация не даёт писателю приоритета после того, как он встал в очередь; практическая рекомендация при преимущественно частой записи — просто `Mutex` вместо `RWMutex`, а не борьба с голоданием писателя поверх `RWMutex`. [46]

Практическая ловушка потокобезопасного кэша поверх map+`RWMutex`, которую часто упускают: если хранимые значения — указатели или содержат слайсы/map (то есть shallow-копируемые типы, см. файл 04), простой возврат значения из-под `RLock()` отдаёт вызывающей стороне доступ к тем же данным, что лежат внутри кэша — внешний код может изменить их в обход мьютекса, минуя всю защиту. Правильная практика — либо хранить в кэше только неизменяемые/значимые типы, либо явно делать глубокую копию значения **перед** возвратом из-под лока (ценой дополнительной аллокации на каждое чтение) — тот же класс проблемы, что и «нельзя мутировать данные снаружи защищённой структуры», но применительно именно к чтениям, а не только к записям. [34]

## Потокобезопасный кэш с TTL — конкурентный доступ, глубокое копирование и стратегия очистки

Ещё одна вариация уже разобранной выше задачи «кэш поверх map + `RWMutex`» (см. также готовые ловушки код-ревью такого кэша выше) — конкретно с TTL и с явным сценарием «прочитать профиль из кэша, изменить локально, опционально положить обратно»:

- **Проверка истечения TTL — по конкретному ключу, а не сканированием всего кэша при каждом чтении:** в `Get(key)` — вычислительно дёшево, O(1), сравнить сохранённую метку `expiresAt` конкретной записи с текущим временем (`time.Now().After(entry.expiresAt)`); полное сканирование всех записей кэша на предмет истёкших — отдельная, более редкая фоновая задача (периодическая горутина-уборщик), а не часть каждого запроса на чтение. Смешение этих двух ответственностей в одном месте (например пытаться чистить весь кэш при каждом обращении) — источник ненужных задержек на горячем пути чтения.
- **Возврат из кэша — всегда глубокая копия, а не совместно используемый указатель/слайс:** если хранимое значение (например профиль пользователя) содержит вложенные ссылочные поля (слайс заказов и т.п.), возврат значения напрямую из-под `RLock()` без глубокого копирования отдаёт вызывающей стороне доступ к тем самым данным, что лежат внутри кэша под защитой мьютекса — внешний код, получивший «свою» копию, на деле может конкурентно менять внутреннее состояние кэша в обход всей синхронизации (тот же класс проблемы, что уже отмечен выше для `RWMutex`-кэшей, но с уточнением: недостаточно скопировать сам верхнеуровневый объект — если он содержит слайс/map/указатель, нужна рекурсивная, а не поверхностная копия).
- **Отсутствие явного жизненного цикла** — типичный пробел реализации: нет конструктора, инициализирующего фоновую горутину очистки, и нет метода `Stop()`/`Close()` для её штатной остановки (без этого — утечка горутины, если экземпляр кэша должен быть уничтожен раньше, чем завершится процесс, см. уже описанный паттерн утечки горутин выше).
- **Граничные случаи, которые стоит явно обработать и проговорить** — пустой/некорректный ключ на вход, нулевой или отрицательный TTL (означает ли это «не кэшировать вообще» или «кэшировать навсегда»?) — оба варианта интерпретации валидны, но неявный выбор одного из них без документирования — источник багов у вызывающей стороны. [62]

За пределами стандартного `sync` часто спрашивают про `golang.org/x/sync/errgroup` — обёртку над `WaitGroup`, добавляющую: (а) сбор **первой** возникшей ошибки среди всех горутин группы (остальные ошибки после первой отбрасываются, а не копятся в слайс — если нужны все ошибки сразу, `errgroup` не подходит без доработки); (б) автоматическую отмену через встроенный `context` всех ещё не завершившихся горутин группы при первой ошибке (через `errgroup.WithContext`). Важный нюанс, который часто упускают на практике — паника внутри одной из горутин группы не превращается автоматически в обычную ошибку `errgroup`, ей всё равно нужен свой `defer`/`recover`, иначе она уронит процесс, как и в обычном ручном пуле горутин. Горутины, использующие переданный группой `context`, обязаны сами проверять его отмену в цикле (`select { case <-ctx.Done(): return ctx.Err() ... }`), `errgroup` не прерывает горутину принудительно — как и весь Go в целом, нет превентивной остановки горутины извне (см. выше). [22]

## Самодельные примитивы синхронизации на каналах — учебное упражнение и его границы

Частое задание на живом кодинге — реализовать примитив синхронизации «с нуля» через каналы, без пакета `sync`, чтобы проверить понимание механики, а не просто знание готового API:

- **Мьютекс на буферизованном канале ёмкостью 1**: канал как «жетон» — `Lock()` читает из канала (блокируется, если жетона нет), `Unlock()` кладёт жетон обратно. Работает, но с реальными ограничениями по сравнению с `sync.Mutex`: нет проверки владения (любая горутина может вызвать `Unlock()`, даже не державшая лок — в отличие от честной блокировки); нет гарантии честности/порядка (та же гонка «кто успел», что и в normal mode настоящего `sync.Mutex`, см. выше); не реентерабелен — повторный `Lock()` той же горутиной блокируется навсегда (deadlock), как и у настоящего `sync.Mutex`.
- **Читатель-писатель (RWMutex) на каналах с защитой от голодания писателя (turnstile-паттерн)**: наивная версия на двух каналах (один — «жетон записи», второй — счётчик читателей: первый читатель забирает жетон записи, последний — возвращает) сама по себе уязвима к голоданию писателя, если читатели прибывают непрерывным потоком, не давая счётчику дойти до нуля. Более надёжная версия добавляет «турникет» (turnstile) — дополнительный канал-шлагбаум, который писатель захватывает **до** попытки взять сам лок записи: захват турникета сразу блокирует вход новым читателям (даже если лок записи ещё не свободен от текущих читателей), гарантируя, что писатель рано или поздно получит лок, не дожидаясь бесконечно.
- **Атомарный счётчик на буферизованном канале ёмкостью 1**: тот же трюк «канал как контейнер под мьютексом» — прочитать текущее значение из канала, изменить, записать обратно; корректно, но не является настоящей атомарной операцией на уровне процессора — сравнение с реальными `sync/atomic` (`atomic.AddInt64` и т.п.): атомарные операции — это буквально одна CPU-инструкция (например `LOCK XADD` на x86) без переключения контекста горутины; канал-based версия физически включает операции отправки/приёма в рантайме планировщика — на порядки дороже по времени, чем одна атомарная инструкция, хотя и корректна с точки зрения безопасности. Практическая иерархия по производительности (от быстрого к медленному): `sync/atomic` (lock-free, одна инструкция) → `sync.Mutex` (блокировка на уровне ОС, но встроенная честность через starvation mode) → самодельные примитивы на каналах (чисто в духе CSP, полезны для понимания механики, но на порядок выше по латентности). [28]

## Семафор: реализация и готовое решение

Семафор можно реализовать через каналы (буферизованный канал как счётчик разрешений — идиоматичный подход в Go) или через atomic-примитивы — но чистый atomic не может блокировать горутину (нет «парковки» потока), для настоящей блокировки в конечном счёте нужен futex-подобный механизм на уровне ОС, который рантайм Go уже реализует внутри `sync.Mutex`/`sync.Cond`. Для продакшн-кода рекомендован готовый пакет `golang.org/x/sync/semaphore` (`Weighted`) — поддерживает взвешенные разрешения, интеграцию с `context` для отмены, и оптимизированный notifyList вместо самодельной реализации на каналах. [10]

Практическая опасность самодельной реализации на буферизованном канале: если внутри критической секции (между «взять слот» и «вернуть слот») происходит паника, а возврат слота (`<-sem`) не обёрнут в `defer` — слот теряется навсегда («утечка слота»), постепенно исчерпывая ёмкость семафора до полной блокировки всех последующих попыток захвата; правильно — всегда оборачивать освобождение слота в `defer` сразу после успешного захвата, а не расставлять его вручную по всем веткам выхода. Продакшн-паттерн для захвата с ограничением по времени — `sem.Acquire(ctx, n)` из `x/sync/semaphore` принимает `context`, что даёт отмену/таймаут захвата и защищает от вечного ожидания при недоступности слотов. [24]

## Управление жизненным циклом горутин: пауза/возобновление/остановка

В Go нет превентивного управления горутиной извне (нет аналога `thread.suspend/resume/kill`). Инструменты: `context.Context` — стандартный способ отмены; управляющие каналы — для паузы/возобновления по сигналу; `sync.Cond` — для высокочастотной паузы/возобновления (эффективнее по аллокациям, чем городить каналы под каждый сигнал). Асинхронный preemption с Go 1.14 (через `SIGURG`) решает проблему только для «зависшего» в тяжёлом CPU-bound цикле планировщика, а не для явной остановки конкретной горутины по требованию. [10]

## Утечка горутины из-за рассинхрона жизненного цикла — буфер маскирует, а не лечит

Типовой сценарий живого кодинга: функция запускает фоновую горутину с тяжёлой работой, результат которой пишется в небуферизованный канал; если вызывающая сторона уходит по таймауту раньше, чем фоновая горутина закончила — эта горутина блокируется на записи в канал навсегда (никто больше не читает) — классическая утечка. Частое, но **неполное** решение — просто сделать канал буферизованным (`make(chan Result, 1)`): формально устраняет блокировку записи (горутина запишет в буфер и завершится сама), но не устраняет корень проблемы — сама тяжёлая работа (`heavyWork`) всё равно продолжает выполняться и тратить ресурсы (CPU/сеть/память) уже никому не нужный результат, просто без видимой утечки горутин; под нагрузкой повторяющиеся таймауты всё равно накапливают одновременно исполняющиеся никому не нужные фоновые задачи. Правильное решение — распространение `context` внутрь фоновой работы: сама `heavyWork` обязана принимать `context.Context` и уважать его отмену (например через `http.NewRequestWithContext` для сетевых вызовов, либо явную проверку `ctx.Done()` в цикле вычислений), а горутина-обёртка при записи результата тоже слушает `ctx.Done()` через `select`, чтобы не блокироваться на записи, если вызывающая сторона уже ушла. Итог: буферизация лечит симптом (блокировку), `context`-пропагация лечит причину (ненужную работу и удержание ресурсов). [26]

## Конкурентная обработка N независимых задач без мьютекса — паттерн предвыделённого слайса по индексу

Альтернатива паттерну «горутины пишут в общий слайс под мьютексом»: заранее выделить результирующий слайс нужной длины (`results := make([]T, n)`), передать в каждую горутину не общий разделяемый счётчик, а её собственный фиксированный индекс результата, и писать результат напрямую по этому индексу (`results[i] = ...`) — поскольку каждая горутина пишет строго в свою, никем больше не используемую ячейку слайса, гонки данных не возникает в принципе, и `sync.Mutex` не нужен вообще; синхронизация по завершении всех горутин — через `sync.WaitGroup`. Работает, только когда индексы результатов известны заранее и не пересекаются между горутинами (типичный случай — параллельная обработка N URL/задач с уже известным порядком). [27]

## `time.Sleep` как способ «подождать» завершения горутин — антипаттерн

Частая ошибка новичка: запустить горутины и просто вызвать `time.Sleep(N)` в `main` в надежде, что этого времени хватит для их завершения. Проблема — никакой гарантии: планировщик не обязан вообще успеть запустить/выполнить горутины за произвольный фиксированный интервал (особенно под нагрузкой или на медленной машине), и даже если обычно «работает» в разработке — это гонка, которая рано или поздно проявится в проде недетерминированной потерей части результатов. Правильный инструмент — `sync.WaitGroup` или синхронизация через канал (результат/сигнал завершения), а не сон произвольной длины. [21]

## Направленные каналы (`chan<-`, `<-chan`) — ограничение прав на этапе компиляции

Тип канала можно сузить до «только отправка» (`chan<- T`) или «только приём» (`<-chan T`) в сигнатуре функции — компилятор не даст функции, принимающей `<-chan T`, вызвать по этому параметру `close()` или отправить в канал, и наоборот. Обычный двунаправленный `chan T` неявно преобразуется в любое из направленных представлений при передаче (но не обратно) — идиоматичный способ явно закрепить в сигнатуре, кто в конвейере имеет право писать/закрывать канал, а кто только потребляет (соответствует паттерну channel ownership выше) — типичный пример: функция-производитель принимает/возвращает `chan<- T`, функция-потребитель — `<-chan T`. [21]

## Запись в небуферизованный канал без читателя — deadlock

Базовая, но часто проверяемая аксиома: запись в небуферизованный (unbuffered) канал, когда нет горутины, готовой немедленно принять значение — блокирует отправителя навсегда (полноценный deadlock, если это единственная горутина и никто больше не запустит чтение) — небуферизованный канал требует **одновременной** готовности отправителя и получателя (рандеву), в отличие от буферизованного, который может временно «поглотить» отправку в свободный слот буфера. [19]

## `select` с несколькими готовыми каналами — недетерминированный выбор

Если в `select` сразу несколько `case`-веток одновременно готовы к выполнению (например несколько каналов одновременно имеют данные) — Go **случайно** выбирает одну из готовых веток (равномерно, без приоритета по порядку записи в коде) и выполняет её, после чего `select` завершается (не «выполняет все готовые», а ровно одну за вызов). Если ни одна ветка не готова — `select` без `case default` блокируется до готовности любой из них; с `default` — при отсутствии готовых веток сразу выполняется `default`, без блокировки. Практическое следствие — писать код так, чтобы не полагаться на порядок обработки при гонке нескольких готовых каналов. [19]

## Fan-in: слияние нескольких входных каналов в один выходной

Паттерн для объединения данных из N независимых входных каналов в единый выходной поток: для каждого входного канала запускается своя горутина, которая читает из него и пишет в общий (обычно буферизованный, чтобы читающие горутины не блокировали друг друга без необходимости) выходной канал. Закрытие выходного канала — через `defer close(out)` в отдельной координирующей горутине, причём безопасно закрыть только после того, как все читающие горутины точно закончили (аналогично паттерну worker pool — координация через `sync.WaitGroup`, либо, если исходных каналов заранее известное фиксированное число и они сами закрываются, можно обойтись без `WaitGroup`, синхронизируясь через сам факт закрытия всех входных каналов). Ключевая деталь дизайна такой функции (`mergeToChannels`) — правильная обработка уже закрытых входных каналов (не паниковать, не зависать, а просто переставать ждать данные с этого конкретного входа) и явных уточняющих вопросов интервьюеру про эти граничные случаи до того, как начать писать код — считается хорошей практикой на живом кодинге. [19]

## Широковещательный сигнал (broadcast) нескольким ждущим горутинам

Задача: разбудить все горутины, заблокированные на чтении из небуферизованного канала, не зная точного их числа. Правильный способ — `close(ch)`: чтение из закрытого канала никогда не блокирует и атомарно возвращает `(нулевое значение, false)` всем ожидающим одновременно — это встроенный в Go примитив broadcast. Правила: закрывать канал должен только отправитель, когда точно больше не будет отправок; повторное закрытие или запись в закрытый канал — паника. [10]

## Паттерн Worker Pool — детальный разбор

Фиксированный набор из N горутин-воркеров читает задачи из общего (обычно буферизованного) канала задач и пишет результаты в канал результатов; буферизованный канал задач сам по себе реализует backpressure (глубина очереди = размер буфера), число воркеров ограничивает уровень конкурентности. Практики: `sync.WaitGroup` — для отслеживания жизненного цикла воркеров; `context.Context` — для отмены всей группы; `recover()` внутри воркера — чтобы паника одной задачи не роняла весь пул; мониторинг живых горутин через `runtime.NumGoroutine()` (полезно для отладки утечек). Правильная последовательность graceful shutdown: `close(jobs)` → воркеры доделывают начатое и естественно завершаются → `wg.Wait()` → только после этого `close(results)`. [5, 10, 57] Частая ошибка именно на этом шаге — попытка закрыть канал результатов силами самих воркеров (кто первый закончил) вместо выделенной координирующей горутины: несколько воркеров, одновременно решивших, что они «последние», приводят либо к панике `send on closed channel` (если хоть один воркер попытается записать в уже закрытый другим канал), либо к преждевременному закрытию до того, как остальные воркеры дописали свои результаты — единственно надёжный паттерн - отдельная горутина, которая только ждёт `wg.Wait()` и лишь затем закрывает канал (`go func() { wg.Wait(); close(results) }()`), не участвуя в самой обработке задач. [57]

Дополнительная продакшн-деталь код-ревью такого пула на примере сервиса рассылки уведомлений: число воркеров и размер буфера канала задач должны быть конфигурируемыми параметрами, а не захардкоженными магическими числами (жёстко зашитые «3 воркера» — типичный, но неверный шаблон); при постановке задачи в очередь предпочтительна неблокирующая попытка (`select` с `default`) вместо безусловной блокирующей отправки в канал — если буфер (например ёмкостью 100) уже переполнен, а неблокирующая попытка не удалась, разумная реакция — эскалация во внешнюю очередь с более высокой пропускной способностью (Redis/Kafka), а не блокировка вызывающего кода до появления свободного места, и не молчаливая потеря задачи. [49]

## Параллельная обработка слайса чанками — типичные ошибки на живом кодинге

Задача: разбить слайс на N частей и обработать их параллельно через горутины с явным разделением работы (не через worker pool с очередью задач, а через прямое разбиение диапазона индексов). Частые ошибки кандидата: (1) классическая гонка с захватом переменной цикла в замыкании горутины — до Go 1.22 переменная цикла общая на все итерации, и без явной передачи параметром в горутину все горутины могут увидеть одно и то же (последнее) значение индекса/чанка (см. файл 05 про сам механизм и про изменение в Go 1.22); (2) забытая обработка остатка от деления при делении длины слайса на число воркеров нацело (например, 10 элементов на 3 воркера — последний чанк должен подхватить остаток, а не быть потерян или вызвать panic по границе). Правильный подход: явно вычислять границы чанков с учётом остатка (`chunkSize := n/workers; extra := n%workers` — последний чанк шире), передавать индекс/границы чанка как параметр горутины (`go func(start, end int) {...}(start, end)`), а не захватывать переменную цикла напрямую; синхронизировать через `sync.WaitGroup`; если результаты собираются через канал — закрывать канал в отдельной горутине именно после `wg.Wait()` (`go func() { wg.Wait(); close(resultsCh) }()`), чтобы не закрыть канал до того, как все воркеры закончили в него писать. [17]

## Поведение nil, открытого и закрытого канала — полная таблица

Частый вопрос-«аксиома», которую не все держат в голове полностью: чтение из nil-канала и запись в nil-канал **обе блокируются навсегда** (вечный deadlock, если это единственный путь горутины). Для сравнения полная картина по трём состояниям канала: nil-канал — и чтение, и запись блокируются навсегда; открытый канал — чтение/запись проходят (или блокируются на заполненности буфера/отсутствии данных, но не навечно, если есть встречная сторона); закрытый канал — чтение продолжает отдавать оставшиеся в буфере данные, а затем нулевое значение без блокировки, запись — паника. Это часто используется намеренно в `select`, чтобы «выключить» одну из веток (присвоить каналу nil, чтобы соответствующий `case` больше никогда не срабатывал) — типичное применение приёма — динамическое отключение ветки в цикле состояний конечного автомата (state machine), реализованном через `select`. Безопасное «вычерпывание» оставшихся данных из закрытого буферизованного канала — идиоматично через `for val := range ch` (естественно завершается сам, когда канал закрыт и пуст) либо явную двузначную форму чтения `val, ok := <-ch` (`ok == false` — канал закрыт и пуст). Сама паника при записи в закрытый канал — намеренный fail-fast механизм (предпочтительнее тихой потери данных). [15, 17, 24]

## `context.Context` — назначение и практика применения

Пакет `context` передаёт отмену, дедлайны/таймауты и данные, специфичные для запроса (например, токен авторизации), через дерево вызовов и горутин. `context.Background()` используется в подавляющем большинстве случаев (as ориентир — говорят про «80% случаев») как корень дерева контекстов; `WithTimeout`/`WithDeadline` — для автоматической отмены по времени; `WithValue` — для передачи данных по цепочке (использовать умеренно, не как замену обычных параметров функции). Дочерние контексты образуют дерево отмены: отмена родителя каскадно отменяет всех потомков. Правило без исключений — вызывать `cancel()` через `defer` сразу после создания отменяемого контекста, иначе горутины/таймеры, ожидающие его, утекают. [15]

## Механика каналов: внутреннее устройство и buffered vs unbuffered

Внутри канал — структура `hchan` с очередями ожидающих отправителей (`sendq`) и получателей (`recvq`). Небуферизованный канал — прямая передача данных между горутинами (рандеву, без промежуточного хранения), отправка и получение блокируют друг друга до готовности обеих сторон. Буферизованный канал — кольцевой буфер внутри `hchan`; отправитель не блокируется, пока буфер не заполнен, получатель — пока не опустеет. Практическое значение буферизации: «подушка» против backpressure ценой памяти; выбор размера буфера — дизайн-решение о том, где в пайплайне копится задержка. [5, 8, 10]

Более подробный список полей внутри `hchan` (по описанию с одного из собесов, стоит сверить с актуальным исходником рантайма перед тем как считать исчерпывающим): `qcount` (сколько элементов сейчас реально лежит в буфере), `dataqsiz` (заявленный размер буфера — то, что видно снаружи как `cap(ch)`), `buf` (указатель на сам кольцевой буфер), пара индексов `sendx`/`recvx` (позиции следующей записи/чтения в кольцевом буфере, продвигаются по модулю `dataqsiz` — по достижении конца массива оборачиваются на начало), очереди ожидающих `sendq`/`recvq` (списки `sudog`, см. выше про `goready()`), и собственный внутренний `lock` (мьютекс), защищающий все эти поля от гонок при конкурентном доступе к каналу из нескольких горутин одновременно. Небуферизованный канал в этом смысле — частный случай с `dataqsiz == 0`: данные передаются напрямую между стеками горутин-участников (rendezvous), а не через кольцевой буфер. [23, 24]

Важное отличие от `sync.Mutex` в вопросе честности: очереди ожидания канала (`sendq`/`recvq`) обслуживаются в порядке **FIFO** — то есть для каналов (в отличие от давно обсуждавшегося открытого вопроса о честности мьютекса, см. выше) фактическая честность порядка пробуждения ожидающих горутин задокументирована и предсказуема, а не зависит от normal/starvation режима. Списки ожидания также обеспечивают правильное управление временем жизни горутин с точки зрения GC — горутина, «припаркованная» в очереди ожидания канала, не считается мусором и не удерживает контекст неопределённо: сборщик отслеживает такие ссылки как часть графа достижимости обычным образом. [34]

## Паттерн «конвейер» (pipeline) из нескольких стадий-горутин, соединённых каналами

Ещё один именованный паттерн конкурентности, отдельный от worker pool и fan-in (см. выше): последовательность независимых стадий обработки, каждая — отдельная горутина (или пул горутин), читающая из входного канала предыдущей стадии и пишущая в выходной канал следующей (типичный пример — «валидация → дедупликация → проверка → фильтрация», где каждая стадия ничего не знает о соседних, кроме форматов входа/выхода). Преимущество перед одной большой функцией с последовательными циклами — каждая стадия работает конкурентно с соседними (стадия 2 обрабатывает элемент №5, пока стадия 1 уже готовит элемент №6), и стадии можно независимо тестировать/заменять/масштабировать числом горутин каждая по отдельности при необходимости (например у стадии с самой дорогой обработкой — больше воркеров, чем у остальных). [33]

## Graceful shutdown по сигналу ОС (SIGINT/SIGTERM) — эталонная последовательность

Полная последовательность плавного завершения долгоживущего конкурентного сервиса при получении сигнала завершения (`SIGINT`/`SIGTERM`, перехватываются через `signal.Notify`): (1) отменить корневой `context` — прерывает все операции, явно проверяющие `ctx.Done()`, вместо того чтобы ждать их естественного завершения; (2) закрыть канал приёма новых входных задач — сигнал «новых заданий больше не будет», не обрывая уже находящиеся в обработке; (3) дождаться завершения всех активных горутин через `sync.WaitGroup`, но **с таймаутом** (например через `select` между `wg.Wait()`, обёрнутым в горутину+канал, и `time.After(deadline)`) — иначе зависшая по любой причине горутина заблокирует завершение процесса навсегда; (4) если таймаут истёк, а часть горутин так и не завершилась — принудительное завершение процесса, залогировав, что graceful shutdown не уложился в отведённое время (лучше контролируемое принудительное завершение, чем бесконечное зависание). [33]

Идиоматичный современный каркас той же последовательности конкретно для HTTP-сервера (с Go 1.16+, `signal.NotifyContext` вместо ручной комбинации `signal.Notify`+канал):

```go
ctx, stop := signal.NotifyContext(context.Background(),
    syscall.SIGINT, syscall.SIGTERM)
defer stop()

srv := &http.Server{Addr: ":8080"}
go srv.ListenAndServe()

<-ctx.Done() // блокируется до получения сигнала

shutdownCtx, cancel := context.WithTimeout(context.Background(), 30*time.Second)
defer cancel()
srv.Shutdown(shutdownCtx) // ждёт завершения активных запросов, но не дольше таймаута
```

`signal.NotifyContext` оборачивает получение ОС-сигнала сразу в `context.Context` — не нужно вручную заводить канал и отдельную горутину-переходник; `http.Server.Shutdown(ctx)` — специально предназначенный метод graceful-остановки: перестаёт принимать новые соединения немедленно, но даёт активным запросам доехать до конца в пределах переданного контекста с таймаутом (в отличие от `srv.Close()`, обрывающего все соединения немедленно, без ожидания). [47]

## Сборщик мусора (GC) — устройство современной конкурентной модели

Новая крупная тема, не пересекающаяся напрямую с планировщиком горутин, но тесно с ним связанная рантаймово (обе системы конкурируют за CPU-время и синхронизируются друг с другом). До версии Go 1.5 сборка мусора была классическим stop-the-world Mark-and-Sweep — вся программа полностью останавливалась на время сборки, паузы могли достигать секунд на большой куче. С 1.5+ — конкурентный трёхцветный (tri-color) алгоритм маркировки, выполняющийся **параллельно** с работающей программой (мутатором), а не вместо неё:

- **Три фазы цикла:** Sweep termination (короткая STW-пауза — «дозавершение» уборки предыдущего цикла перед стартом нового), Mark (основная фаза — маркировка достижимых объектов, выполняется **конкурентно** с программой, самая долгая по времени фаза), Mark termination (вторая, тоже короткая STW-пауза — финализация маркировки, нужна для консистентности перед стартом Sweep). Итого — именно **две** короткие STW-паузы за цикл, а не одна сплошная остановка на весь цикл.
- **Трёхцветная маркировка:** объекты помечаются white (не посещён, кандидат на удаление), grey (посещён, но его ссылки ещё не обработаны — в очереди на обработку), black (посещён и все его ссылки обработаны — точно жив). Сборка идёт, пока очередь grey-объектов не опустеет — все оставшиеся white в конце фазы Mark считаются мусором.
- **Write barrier (барьер записи):** поскольку программа продолжает работать и менять указатели **во время** конкурентной маркировки, нужна защита от опасного сценария «чёрный объект получает указатель на белый объект напрямую, минуя серый» (тогда белый объект будет ошибочно посчитан мусором и удалён, хотя на него есть живая ссылка) — компилятор вставляет специальный код (барьер) на каждую операцию записи указателя во время активной сборки, поддерживающий инвариант корректности маркировки (гибрид Dijkstra/Yuasa барьеров в современных версиях).
- **Mutator assist («ассист» программы сборщику):** если сама программа аллоцирует память быстрее, чем сборщик успевает маркировать (риск того, что мусора накопится больше, чем ожидалось к концу цикла) — горутины, которые сейчас аллоцируют, временно и принудительно «одалживают» немного своего CPU-времени на помощь в маркировке, замедляя аллокацию ровно настолько, чтобы GC не отстал.
- **Pacing (управление частотой циклов):** GC не собирается по жёсткому расписанию — новый цикл стартует, когда куча выросла на `GOGC`% (по умолчанию 100%, то есть куча удвоилась) с момента окончания предыдущего цикла — компромисс между частотой пауз (чаще — короче каждая, но больше общий оверхед) и пиковым потреблением памяти (реже — экономнее по CPU, но требует больше памяти про запас).
- **Concurrent sweep:** после Mark termination собранная память не возвращается ОС/аллокатору вся разом, а высвобождается инкрементально, по мере того как программа запрашивает новые аллокации — ещё одна причина, почему нет отдельной длинной паузы на «очистку».
- **Ориентир по паузам:** современные версии рантайма Go нацелены на паузы порядка **<10 мс** (soft real-time target, не жёсткая гарантия) — предсказуемость задержки, по большому счёту, не зависящая от общего размера кучи (в отличие от классического stop-the-world, где пауза растёт вместе с кучей). [34]

**Уточнение ориентира по паузам (после источников 38/39/42):** на практике обе STW-паузы цикла заметно короче осторожной оценки «<10 мс» выше — реальный пример из продакшн-лога `gctrace=1` на куче 1–10 ГБ при `GOGC=100`: `gc 120 @2.1m: 0.032+0.41+0.028 ms clock` — первое и третье число (STW mark start и STW mark termination) — порядка **0.03 мс (~32 микросекунды)** каждое, среднее число (`0.41`) — длительность конкурентной фазы Mark, не блокирующей программу. Актуальный практический ориентир для каждой из двух STW-пауз — порядка **<100 микросекунд**, то есть на два порядка меньше, чем часто называемая «безопасная» цифра в 10 мс; последняя остаётся верной как запас прочности, но не отражает типичное поведение current-версий рантайма. [38, 39, 42]

**Расхождение <10 мс / <100 мкс закрыто — обе цифры реальны, просто относятся к разным эпохам рантайма Go, а не противоречат друг другу.** Сверено напрямую с историческим обсуждением разработчиков Go (объявление Austin Clements, октябрь 2016, вошедшее в Go 1.8, выпущенный в феврале 2017): именно тогда цель STW-пауз была официально сдвинута с прежнего ориентира порядка **~10 мс** на **«typical worst-case stop-the-world times less than 100 microseconds»** — дословно та же цифра, что независимо всплыла в продакшн-логах источников 38/39/42. То есть «<10 мс» — это не устаревший миф и не осторожная перестраховка «на всякий случай», а честная историческая цифра, актуальная для версий Go **до 1.8** (то есть до начала 2017 года); «<100 мкс» — целевой ориентир, действующий уже почти десятилетие, начиная с Go 1.8 и по сегодняшний день. Для собеседования это значит: называть современный ориентир правильно как «<100 мкс», но не будет ошибкой упомянуть и историю вопроса, если попросят объяснить, почему в интернете часто встречается устаревшая цифра в 10 мс. [независимо сверено с публичным обсуждением go-dev/golang-dev по GC-паузам Go 1.8, не источник из общей нумерации `_istochniki.md`]

**`GOGC` — точная формула и практика подбора:** таргетируемый размер кучи к следующему циклу — `Target = Live × (1 + GOGC/100)`, где `Live` — объём живых данных на момент окончания предыдущего цикла. При дефолтном `GOGC=100` куча вправе вырасти вдвое от live-данных (10 МБ живых данных → цикл стартует у отметки ~20 МБ). `GOGC=200` — рост в 3×, реже циклы, выше пиковая память; `GOGC=50` — рост в 1.5×, чаще циклы, ниже footprint. Практический диапазон для большинства нагрузок — **20–200** в зависимости от приоритета latency vs throughput; формула не учитывает абсолютный объём доступной памяти — растущий объём живых данных (например расширяющийся кэш) пропорционально тянет за собой и таргет кучи даже при неизменном `GOGC`, для абсолютного потолка нужен именно `GOMEMLIMIT` (Go 1.19+), а не подбор `GOGC`. [38, 39]

**Экстремальный случай `GOGC=1` — как ломается pacing:** демонстрация деградации при слишком агрессивной настройке — целевая куча превышает live-данные всего на 1% (`Target = Live × 1.01`), и при типичном темпе аллокации (например 50 МБ/с при 100 МБ живых данных) окно между текущим объёмом и таргетом схлопывается до ~20 мс — GC физически не успевает полноценно восстановиться между циклами и переходит в состояние постоянного «преследования» аллокаций: каждая отдельная пауза остаётся короткой, но совокупный расход CPU на маркировку резко растёт, а ассист-механизм принудительно и почти непрерывно превращает пользовательский код в маркировщика вместо эпизодической подстраховки. Практический вывод — `GOGC` ниже ~20 почти всегда контрпродуктивен; для жёсткого контроля памяти в проде правильный инструмент — `GOMEMLIMIT`, а не экстремально низкий `GOGC`. [38]

**«Целевые» ~25% CPU на фоновую маркировку (Goal CPU):** GC не резервирует фиксированную квоту ресурсов заранее — это именно таргет, а не жёсткое выделение: в steady state фоновые маркировщики (`gcBgMarkWorker`) стремятся занимать не больше **~25% (1/4)** времени одного логического процессора; при отсутствии аллокаций GC почти не потребляет CPU (кроме периодических проверок), при интенсивной аллокации — ассист-механизм добавляет работу поверх фоновых воркеров, если те не успевают, временно жертвуя пропускной способностью, чтобы не допустить неконтролируемого роста кучи. При заданном `GOMEMLIMIT` это правило переопределяется: если фактическое потребление памяти приближается к хард-лимиту, GC игнорирует таргет в 25% и может кратковременно занять почти всё доступное CPU, агрессивно пытаясь удержать кучу под лимитом — более предсказуемое поведение в memory-constrained окружениях (контейнеры с жёстким memory limit) ценой возможных всплесков CPU-нагрузки именно в момент приближения к лимиту. [38, 39]

**Пригодность Go для систем с жёсткими требованиями по latency (ориентир по p99):** p99 **< 1 мс** — Go обычно не подходит без экстремальной ручной оптимизации, разумнее C++/Rust с ручным управлением памятью; p99 **10–50 мс** — Go отлично справляется при базовой оптимизации (снижение аллокаций, тюнинг `GOGC`/`GOMEMLIMIT`); p99 **от 100 мс и выше** — стандартный, некритичный сценарий для Go без специальных ухищрений. Техники подготовки для нижней границы диапазона: агрессивное снижение аллокаций (value-типы вместо указателей там, где это не критично для семантики, `go build -gcflags="-m"` для проверки escape analysis, предвыделение слайсов известного размера через `make(..., 0, n)` вместо повторных `append` с реаллокациями), точечный тюнинг `GOGC`/`GOMEMLIMIT` под конкретную нагрузку (например `GOGC=70 GOMEMLIMIT=4G` для более частых, но предсказуемых циклов), ручной вызов `debug.GC()` в предсказуемый момент простоя приложения (например между батчами) вместо того, чтобы полагаться на автоматический pacing в самый неподходящий момент, и обязательная нагрузка на production-like данных с измерением именно STW-времени и доли CPU, съедаемой GC (таргет — STW < 100 мкс, GC CPU < 1–2%). [38, 39]

**Ключевые поля `runtime.MemStats` для мониторинга GC:** `PauseTotalNs` (суммарное время всех STW-пауз с момента старта процесса), `HeapAlloc` (текущий объём аллоцированной и ещё используемой памяти в куче), `NumGC` (счётчик количества выполненных циклов GC) — стандартный набор полей, снимаемых через `runtime.ReadMemStats(&stats)`, поверх которых обычно строятся собственные метрики Prometheus, если не хочется полагаться только на `GODEBUG=gctrace=1`. [46]

⚠ **Не проверено — предположительные изменения GC в Go 1.25, названные одним источником:** дальнейшее снижение STW-пауз с целью p99 <100 микросекунд, экспериментальные оптимизации конкурентного sweep, улучшенное освобождение памяти для очень больших куч (>100 ГБ), более глубокая интеграция с PGO (Profile-Guided Optimization). Это высказано интервьюером как ожидание/слух о будущей версии, а не как задокументированный факт релиза — перед тем как класть в конспект как факт, стоит сверить с реальными release notes конкретной версии Go на момент использования этого конспекта (нумерация и содержание будущих релизов на момент составления этого источника могли ещё измениться). [46]

**`sync.Pool` — практические ловушки, не только «GC может очистить»:** объекты в пуле физически привязаны к конкретному P (per-P locality) — горутина на одном P кладёт объект в `Put()`, а горутина на другом P при вызове `Get()` может его не найти и получить новый (не строго FIFO/LIFO глобально, распределение зависит от того, на каком P исполняется каждая горутина в момент вызова); GC при маркировке может полностью очистить содержимое пула, если объекты не были востребованы в последнем цикле — `Get()` в таком случае просто создаёт новый объект через `New`, без ошибки, но и без выигрыша в производительности; состояние объекта **не сбрасывается автоматически** — вызывающий код обязан сам вызывать `Reset()` (или аналог) сразу после `Get()`, прежде чем использовать объект, иначе можно получить объект с «грязными» остаточными данными от предыдущего использования. Практическое следствие — `sync.Pool` годится только для короткоживущих, легко переинициализируемых объектов на время одного запроса (буферы, временные структуры), а не как замена полноценному кэшу долгоживущих данных (для этого — `sync.Map`/Redis). Per-P locality как модель организации внутреннего хранилища пула — деталь, добавленная именно в Go 1.13 (до этого была более простая реализация); объекты пула действительно могут быть освобождены **на любом** цикле GC, а не только при явном давлении памяти — рассчитывать на переиспользование между двумя конкретными вызовами `Get()`/`Put()` в общем случае нельзя. [39, 43, 46]

## Механизм пробуждения заблокированной на отправке горутины

Более глубокий уровень вопроса про `hchan`/`sendq`/`recvq`: когда горутина-отправитель блокируется на неготовом к приёму канале, она не «крутится в цикле», а кладёт себя в очередь `sendq` в виде обёртки `sudog` (структура, привязывающая горутину к конкретной операции ожидания на канале) и физически паркуется — переходит в состояние `_Gwaiting`, поток освобождается для других горутин. Когда появляется читатель, он находит соответствующий `sudog` в `sendq`, напрямую копирует данные (при рандеву без промежуточного буфера) и вызывает рантайм-функцию `goready()` на этой горутине — она переводит горутину из `_Gwaiting` обратно в `_Grunnable` и кладёт в очередь на исполнение (сначала пытается локальную очередь P текущего потока). Тот же механизм симметрично работает и в обратную сторону (заблокированный читатель будит через `recvq`). [17]

## Блокирующий системный вызов и обнаружение его завершения планировщиком

Вопрос-продолжение про syscall handoff (см. модель GMP выше): после того как M «ушёл» в блокирующий системный вызов вместе со своей горутиной, а P передан другому M — кто и как узнаёт, что исходный блокирующий вызов наконец завершился? Два механизма параллельно: (1) `netpoller` — для сетевых операций рантайм использует неблокирующие сокеты под капотом и системные примитивы уровня ОС (`epoll` на Linux, `kqueue` на BSD/macOS, IOCP на Windows) — событие «данные готовы» приходит через них, без отдельного опроса; (2) `sysmon` — фоновый системный поток-монитор, не привязанный к обычной модели G/M/P, который просыпается примерно каждые **~10 мс** и, среди прочего, проверяет, не пора ли отобрать P у горутины, слишком долго сидящей в syscall. Как только соответствующий механизм фиксирует готовность — горутина переводится в `_Grunnable` и попадает в **глобальную очередь запуска** (GRQ), откуда её может забрать любой свободный P (не обязательно тот, что был у неё изначально). [17]

## Исчерпание потоков M — что происходит с P, когда все потоки заняты в блокирующих вызовах

Пограничный случай: что если абсолютно все M-потоки одновременно заняты в блокирующих системных вызовах (например, все воркеры одновременно уткнулись в медленный диск/CGo)? P, у которого физически не осталось живого M, переходит в состояние `_Pidle` — при этом его локальная очередь горутин (LRQ) никуда не девается, лежащие в ней горутины остаются в состоянии `_Grunnable` и ждут; другие P, у которых есть свободные M, могут work-stealing'ом забрать себе горутины из очереди простаивающего `_Pidle`-P (тот же механизм воровства, что и в обычной работе планировщика). Рантайм не создаёт M бесконечно — по умолчанию действует лимит в **10 000 потоков ОС** на процесс, настраиваемый через `runtime/debug.SetMaxThreads`; при достижении лимита рантайм паникует (это защита от неконтролируемого разрастания потоков при массовом одновременном блокирующем I/O без пула воркеров). [17]

## Сложность диспетчеризации горутин планировщиком — почему это ближе к O(1)

Отдельный вопрос, не пересекающийся напрямую с уже разобранной моделью GMP, а именно про алгоритмическую сложность самого выбора «какую горутину исполнить дальше»: локальное извлечение из LRQ конкретного P — по сути lock-free структура на основе кольцевого буфера, чтение и продвижение указателя головы — одна быстрая операция, O(1). Полная картина по сценариям: локальный диспетчинг — O(1); периодическая балансировка через work stealing — амортизированно редкая операция (не на каждый цикл диспетчеризации, а по правилу «раз в ~61 тик» или при опустевшей локальной очереди, см. выше), поэтому в среднем не портит амортизированную O(1)-картину; блокировка/пробуждение — вставка в локальную очередь O(1), переполнение в глобальную — редкая операция с синхронизацией. Архитектурно это достигается тем, что у планировщика Go нет единого сортируемого списка горутин с приоритетами (в отличие от классического POSIX-планировщика ОС, которому приходится поддерживать очереди приоритетов, affinity-ограничения, учёт квантов времени — отсюда его сложность порядка O(log N) и выше при большом числе потоков) — горутины существуют в нескольких раздельных состояниях (исполняется / в локальной очереди / в глобальной очереди / ожидает), и планировщик реагирует только на события (завершение, блокировка, таймер, syscall), без фонового цикла репереоценки приоритетов. Практическое следствие константной по сути диспетчеризации — рантайм способен эффективно обслуживать миллионы горутин, а создание горутины стоит порядка микросекунд. [38]

## Самодельный `WaitGroup` на каналах — три итерации решения и почему выигрывает координатор-горутина

Ещё одно учебное упражнение (в дополнение к самодельным мьютексу/RWMutex/атомарному счётчику на каналах выше) — реализовать аналог `sync.WaitGroup` без пакета `sync`, специально чтобы проверить понимание идиомы CSP («не общайся через разделяемую память, а разделяй память через общение»):

- **Вариант 1 — канал фиксированной ёмкости N как счётчик разрешений**: работает только когда число задач известно заранее (нельзя динамически `Add()`, как у настоящего `WaitGroup`), `Wait()` просто вычерпывает буфер целиком.
- **Вариант 2 — мьютекс на буферизованном канале ёмкостью 1 поверх обычного счётчика + отдельный канал-сигнал для `Wait()`**: ближе к желаемому API (динамический `Add(delta)`), но страдает классической TOCTOU-гонкой — между проверкой `count == 0` под локом и последующей блокировкой на сигнальном канале другая горутина может успеть вызвать `Add()`, и `Wait()` рискует упустить момент сигнала.
- **Вариант 3 — координатор-горутина, единолично владеющая счётчиком (рекомендуемый, в духе CSP)**: `Add()`/`Done()` не трогают счётчик напрямую, а отправляют дельту в командный канал; единственная горутина-координатор читает из этого канала строго последовательно (`for delta := range addCh`) и меняет счётчик — гонки по счётчику невозможны в принципе, потому что к нему обращается ровно одна горутина. Когда счётчик доходит до нуля, координатор закрывает сигнальный канал `waitCh` (широковещательно будя всех, кто сейчас в `Wait()`, — см. паттерн broadcast через `close()` выше) и тут же пересоздаёт новый `waitCh` для последующего цикла использования того же объекта:

```go
type ChannelWaitGroup struct {
    addCh  chan int
    waitCh chan struct{}
}

func NewChannelWaitGroup() *ChannelWaitGroup {
    wg := &ChannelWaitGroup{
        addCh:  make(chan int),
        waitCh: make(chan struct{}),
    }
    go wg.run()
    return wg
}

func (wg *ChannelWaitGroup) run() {
    count := 0
    for delta := range wg.addCh {
        count += delta
        if count == 0 {
            close(wg.waitCh)
            wg.waitCh = make(chan struct{})
        }
    }
}

func (wg *ChannelWaitGroup) Add(delta int) { wg.addCh <- delta }
func (wg *ChannelWaitGroup) Done()          { wg.Add(-1) }
func (wg *ChannelWaitGroup) Wait()          { <-wg.waitCh }
```

Ключевая мысль упражнения — единоличное владение изменяемым состоянием одной горутиной (вместо мьютекса вокруг разделяемого счётчика) автоматически устраняет саму возможность гонки данных: это и есть суть message-passing подхода CSP в противовес shared-memory-подходу с блокировками. [38]

## Уточнение к `errgroup`: `SetLimit()` для ограничения конкурентности группы

Дополнение к уже описанному `golang.org/x/sync/errgroup` (сбор первой ошибки + автоотмена через `context`, см. выше): в более новых версиях пакета доступен метод `SetLimit(n)`, ограничивающий число одновременно исполняющихся горутин внутри группы — вызов `g.Go(fn)` при уже достигнутом лимите блокируется, пока не освободится слот, что даёт встроенный аналог семафора/worker-pool прямо поверх `errgroup`, без отдельной ручной реализации ограничения конкурентности. [42]

## Паттерн «первый успешный ответ побеждает» (first-response-wins) для чтения с нескольких реплик

Задача распределённого чтения: разослать один и тот же запрос параллельно на несколько реплик (при синхронной репликации данные на всех репликах идентичны, так что это не нарушает консистентность) и вернуть результат первой успешно ответившей, отменив остальные ещё не завершившиеся запросы — снижает хвостовую задержку (не ждём самую медленную реплику).

- **Общая схема реализации:** по одной горутине на реплику, разделяемый общий `context` с таймаутом на всю операцию (`context.WithTimeout`), отдельные каналы для успешных результатов и для ошибок, семафор (buffered-channel или `x/sync/semaphore`) — ограничить число одновременно опрашиваемых реплик, если их много больше, чем стоит держать нагруженными одновременно.
- **Защита от лишней публикации результата** — после того как первый успешный ответ уже принят и обработан, остальные горутины, которые придут с ответом позже (до того как успеют среагировать на отмену `context`), не должны повторно пытаться что-то записать в уже обработанный результат: атомарный флаг через `atomic.CompareAndSwapInt32` (успешный `CAS` ровно у одной горутины гарантирует, что публикация результата произойдёт ровно один раз, даже при гонке нескольких «почти одновременных» успешных ответов).
- **Частичная недоступность реплик — не повод отменять весь запрос:** если часть реплик недоступна/отвечает с ошибкой, не нужно отменять ожидание оставшихся живых реплик из-за этого — грациозная деградация (graceful degradation): продолжать ждать хотя бы одного успешного ответа от оставшихся, а не считать частичный отказ фатальным для всего запроса.
- **`«не найдено»` — не повод для retry:** если ответ от реплики означает «такого ключа действительно нет» (доменная ошибка), а не транзиентный сбой сети/таймаут (инфраструктурная ошибка) — при синхронной репликации такой ответ означает отсутствие ключа глобально, ретраить его бессмысленно и вредно: массовый повторный опрос по заведомо несуществующим ключам создаёт паразитную, DoS-подобную нагрузку на систему. Разделение семантики требует **раздельных** каналов (или размеченных типов результата) для «успех», «доменная ошибка (не найдено)» и «инфраструктурная ошибка» — то же самое разделение нужно, чтобы отличить «все реплики согласованно ответили not-found» (легитимный ответ) от «все реплики недоступны» (авария), которые иначе выглядят одинаково («ничего не пришло»).
- **Backoff с полным джиттером против ретрай-шторма:** там, где ретрай всё же уместен (транзиентная ошибка) — экспоненциальный backoff со случайной задержкой в диапазоне `[0, delay]` (full jitter, а не просто экспоненциальный рост без случайности) — предотвращает синхронизированный «залп» повторных попыток от многих клиентов одновременно; задержка обязана учитывать оставшийся общий дедлайн `context`, а не расти неограниченно, потенциально превышая его.
- **Раздельные таймауты — общий и per-node:** таймаут на отдельный запрос к конкретной реплике должен быть **строже** (короче), чем общий таймаут всей операции — иначе одна зависшая реплика не даст вовремя переключиться (failover) на другую ещё в пределах общего бюджета времени; обязательно дожидаться завершения (или явной отмены) всех запущенных горутин перед выходом из функции, а не выходить сразу по первому успеху, оставляя часть горутин работать вхолостую без присмотра (утечка, см. уже описанный паттерн выше).
- **Различение таймаута всей операции и недоступности всего кластера:** через `select` с приоритетным разбором, что именно произошло — истечение общего дедлайна (`context.DeadlineExceeded`) отдельно от ситуации «все реплики по очереди ответили ошибкой» — разные диагностические категории для мониторинга и разной реакции (первое — вопрос к настройке таймаутов, второе — авария инфраструктуры). [50]

## Код-ревью потокобезопасного кэша — сборный чек-лист

Ещё один частый формат живого кодинга — дают реализацию простого in-memory кэша поверх map и просят найти проблемы (в дополнение уже разобранным примерам код-ревью в файлах 13/14):

- **`sync.Mutex` вместо `sync.RWMutex`** — если чтений заметно больше записей, обычный `Mutex` сериализует и параллельные чтения тоже, хотя они могли бы идти конкурентно (см. эвристику 10:1 выше).
- **Освобождение лока не через `defer`** — ручной `mu.Unlock()` в конце функции не сработает при панике или раннем `return` в середине тела; правильно — `defer mu.Unlock()` сразу после `Lock()`.
- **Проверка отсутствия ключа через сравнение с нулевым значением** (`if val == "" {...}`) вместо двузначной формы (`val, ok := store[key]`) — ложно принимает реально сохранённое пустое значение за отсутствие ключа.
- **Дорогая функция вычисления значения вызывается прямо под локом** — если вычисление отсутствующего значения (например поход в БД/внешний API) происходит, пока лок уже держится, все остальные обращения к кэшу (в том числе к другим ключам) блокируются на время этого похода; правильно — выносить дорогую операцию за пределы критической секции там, где это возможно.
- **Двойная проверка после получения write-лока (double-checked locking) в `GetOrCreate`**: между моментом, когда горутина поняла, что ключа нет (под `RLock`), и моментом, когда она получила `Lock()` для записи, другая горутина могла успеть создать то же самое значение — нужна повторная проверка наличия ключа уже под write-локом, прежде чем вычислять и класть значение, иначе конкурентные запросы могут задублировать дорогую работу («thundering herd», стадный эффект).
- **Продвинутая защита от thundering herd** — вместо ручного double-checked locking для этого конкретного сценария (много горутин одновременно промахиваются по одному и тому же отсутствующему ключу) идиоматичнее `golang.org/x/sync/singleflight` (см. также применение в кэшировании платных API-вызовов, файл 14) либо `sync.Once` на уровне отдельного ключа — оба гарантируют, что дорогая инициализация конкретного значения выполнится ровно один раз, даже если её одновременно запросили N горутин. [43]

## Код-ревью параллельного чтения файлов через `errgroup` — типичные ошибки с каналами

Задача: функция читает N файлов последовательно (например 5 файлов по 1 секунде каждый — итого 5 секунд минимум), нужно распараллелить с ранней отменой при первой ошибке. Идиоматичное решение — `errgroup.WithContext(ctx)`: каждая горутина, читающая свой файл, получает общий дочерний `context` через группу, явно проверяет его отмену в цикле чтения (чтобы не долистывать уже ненужный файл до конца), и первая же ошибка любой горутины автоматически отменяет контекст для всех остальных — итоговое время при успехе ограничено самым медленным файлом (~1 секунда), а не суммой всех, при ошибке — досрочное завершение почти сразу после первой неудачи, а не после того как все горутины успеют доработать вхолостую. Частые ошибки кандидата в такой реализации на живом кодинге: неверный расчёт ёмкости буферизованного канала для сбора ошибок (слишком маленький буфер при большем числе горутин, чем ёмкость канала, — часть горутин блокируется на отправке в уже заполненный канал ошибок, если никто вовремя его не вычерпывает, что превращается в deadlock); нарушение принципа «канал закрывает тот, кто пишет» (владелец канала — производитель, а не потребитель, см. также паттерн channel ownership выше); пропущенное распространение отмены контекста между горутинами (одна горутина видит отмену и завершается, но не транслирует её остальным, если общий `context` не был правильно прокинут каждой). [46]

## `context.WithValue` как антипаттерн — почему стоит использовать по минимуму

Помимо базового назначения (`Background`/`TODO` как корни дерева контекстов, `WithCancel`/`WithTimeout`/`WithDeadline` для отмены, `WithValue` для передачи данных по цепочке вызовов, отмена — через `<-ctx.Done()`), стоит явно проговаривать на собесе, почему `WithValue()` часто называют антипаттерном: (1) **неявность** — зависимость от конкретного значения в контексте не видна в сигнатуре функции, в отличие от обычного явного параметра, что снижает читаемость и затрудняет отслеживание, кто и что туда кладёт; (2) **отсутствие типобезопасности** — значение хранится и возвращается как `any`, приходится делать type assertion на извлечении, ошибка обнаруживается только в рантайме, а не компилятором; (3) как следствие — код, злоупотребляющий `WithValue()` для передачи данных, которые по сути являются обычными параметрами, деградирует в трудноотслеживаемую «спагетти»-структуру зависимостей. Практическая рекомендация — использовать `WithValue()` только для действительно кросс-сквозных, специфичных для запроса данных (request ID, токен авторизации для мидлваров), а не как общий канал передачи бизнес-данных в обход обычных параметров функции. [42] Отдельная обязательная деталь безопасного использования `WithValue()`, если уж он применяется — ключом должен быть значение собственного, **неэкспортируемого** именованного типа (например `type ctxKey string; const userIDKey ctxKey = "userID"`), а не голая строка или примитивный тип напрямую — иначе два независимых пакета, каждый использующий одну и ту же строку-литерал как ключ, рискуют случайно затереть значения друг друга в одном и том же контексте; собственный неэкспортируемый тип гарантирует, что ключ, объявленный в одном пакете, не совпадёт по типу с ключом другого пакета, даже при случайном совпадении текстового значения. [58]
