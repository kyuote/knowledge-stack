Базовый синтаксис

Коротко и по делу: как устроен файл на Go, переменные, типы, константы, операторы и видимость. Отдельно — что из этого чаще всего спрашивают на собеседовании.

1.1Анатомия файла

Любой файл начинается с объявления пакета, затем идут импорты, затем объявления. Точка входа программы — функция main в пакете main.

main.go
package main

import "fmt"

func main() {
    fmt.Println("Привет, Go!")
}
камень

Неиспользуемый импорт или неиспользуемая локальная переменная — это ошибка компиляции, а не предупреждение. Go нарочно не даёт мусору копиться в коде.

Подробнее про сборку файла medium

Пакет может состоять из нескольких файлов в одной директории — все они делят одно пространство имён, ничего не нужно импортировать друг у друга. Условие одно: у всех файлов одинаковый package.

Особая функция func init() запускается автоматически перед main, без явного вызова. В пакете таких функций может быть несколько, даже в разных файлах: сначала инициализируются все переменные уровня пакета, затем по порядку (файл за файлом) выполняются все init().

1.2Переменные

Три способа объявить переменную — с явным типом, с выводом типа и «короткое» объявление:

vars.go
var a int = 10     // явный тип
var b = 20         // тип выводится из значения — int
c := 30            // короткое объявление, только внутри функции

var (              // групповое объявление
    name    = "gopher"
    age int = 3
)
собес

Чем := отличается от var? := работает только внутри тела функции, требует хотя бы одну новую переменную слева и сам выводит тип. var работает и на уровне пакета, и позволяет объявить переменную без инициализации — тогда она получит zero value.

Подробнее: затенение переменных (shadowing) medium

:= внутри вложенного блока (if, for, просто { }) создаёт новую переменную, даже если снаружи уже есть переменная с таким же именем — внешняя на время блока просто «затеняется».

shadow.go
x := 1
if true {
    x := 2          // это НОВАЯ x, видна только внутри if
    fmt.Println(x)  // 2
}
fmt.Println(x)      // 1 — внешняя x не изменилась
Ещё глубже: почему это частый источник багов deep

Особенно коварно с ошибками — легко случайно затенить err из внешней области видимости:

shadowerr.go
var err error
if x, err := f(); x > 0 { // := создаёт новую err!
    _ = err
}
// внешняя err так и осталась nil, даже если f() вернула ошибку

Встроенный go vet это не ловит — нужен отдельный анализатор shadow (например, через golangci-lint).

У каждого типа есть значение по умолчанию — zero value. Необъявленных, «мусорных» переменных в Go не бывает:

runes.go
s := "Go, гофер!"
fmt.Println(len(s))          // 13 — длина в байтах, не в символах

for i, r := range s {
    fmt.Printf("%d:%c ", i, r) // range декодирует строку в rune'ы
}
собес

Зачем нужен zero value? Чтобы в языке в принципе не было неинициализированной памяти — любая переменная сразу в валидном состоянии, без UB как в C.

Byte vs rune? byte = uint8, один байт UTF-8. rune = int32, один символ Unicode. Индексация строки s[i] даёт байт, а range — руну.

камень

Строки в Go неизменяемы: s[0] = 'H' не скомпилируется. Чтобы менять — приводите к []byte или []rune и обратно.

Подробнее: усечение при конвертации medium

Явное приведение к меньшему типу не паникует — оно молча обрезает лишние биты:

truncate.go
var big int32 = 300
var small int8 = int8(big) // 300 не влезает в int8 (-128..127)
fmt.Println(small)          // 44 — молчаливое переполнение

Конвертация string ↔ []byte/[]rune — это всегда копирование памяти (O(n)), а не бесплатный reinterpret: строки в Go неизменяемы, слайсы — нет.

Подробнее: string изнутри — заголовок, графемы и zero value stringmedium

Внутри строка — не сами байты, а компактный заголовок (stringHeader) из двух слов: указатель на данные (Data) и длина в байтах (Len) — без поля ёмкости (Cap), в отличие от заголовка слайса. Именно поэтому len(s) всегда O(1) и всегда считает байты, а не «символы».

Байт (byte) — единица хранения UTF-8, руна (rune) — один code point Unicode, а то, что человек интуитивно называет «одним символом» — графема — может состоять из нескольких рун сразу (например «é», набранное как «e» + акцент, — это 2 руны, но 1 графема). Ни len(s), ни utf8.RuneCountInString графемы не считают — оба останавливаются на уровне байт/рун; для графемно-осознанного подсчёта нужны сторонние библиотеки (например rivo/uniseg).

Отдельная тонкость: zero value строки — всегда пустая строка "", а не nil, в отличие от слайса/map/канала. В этом смысле string ведёт себя как обычный value type (сравнима через ==, у неё нет «пустого/неинициализированного» состояния, отличного от "") — хотя физически внутри неё лежит указатель на данные.

Подробнее: почему float — плохой выбор для денег float32 / float64medium

float32/float64 следуют стандарту IEEE 754 — двоичному представлению, которое точно хранит далеко не все десятичные дроби (та же проблема, что и в большинстве других языков со стандартным float). Классический пример — сложение 0.1 миллион раз через float64 не даёт ровно 100000: мелкие ошибки округления накапливаются на масштабе.

money.go
var total float64
for i := 0; i < 1_000_000; i++ {
    total += 0.1
}
fmt.Println(total) // НЕ ровно 100000 — накопленная погрешность

// правильно — целые единицы валюты (копейки/центы)
var totalCents int64
for i := 0; i < 1_000_000; i++ {
    totalCents += 10 // 0.10 → 10 копеек
}

Практическое правило: для денег — либо целочисленный тип в минимальных неделимых единицах валюты (int64 в копейках/центах), либо тип NUMERIC/DECIMAL на уровне БД/специализированная decimal-библиотека, но не «голый» float32/float64. Дробный литерал без явного приведения (3.14) в Go по умолчанию имеет тип именно float64, а не float32 — это стоит держать в голове при работе со сторонними API, ожидающими float32.

Подробнее: правда ли, что rune — знаковый int32 специально ради -1 как признака ошибки? runemedium

⚠ Популярное, но неточное объяснение — встречается в разных обучающих материалах: якобы rune сделали знаковым (int32, а не uint32) специально для того, чтобы функции декодирования могли возвращать -1 как признак «невалидного символа». Это не так на практике: стандартная библиотека для этого использует не -1, а специальную руну utf8.RuneError (U+FFFD) — unicode/utf8.DecodeRuneInString возвращает (RuneError, 0) для пустой строки и (RuneError, 1) для невалидной кодировки, но никогда -1. Официальный блог-пост Go про строки лишь констатирует факт: «rune — это алиас для int32, чтобы в коде было явно видно, где значение представляет code point», не объясняя выбор знаковости.

Более скромное и проверяемое объяснение: одного code point Unicode достаточно 21 бита, поэтому естественным выбором стал 32-битный тип — а int32, а не uint32, просто следует общему соглашению Go по умолчанию использовать знаковые целые (как int для длин/индексов), а не потому что отрицательные руны специально задуманы как сигнал ошибки. byte (uint8), для сравнения, беззнаковый естественно — это просто единица хранения байта (0..255), а не Unicode-значение. (проверено в этой сессии: go.dev/blog/strings, pkg.go.dev/unicode/utf8)

1.4Константы и iota

Отдельного типа enum в Go нет — его эмулируют через const и счётчик iota, обнуляемый в каждом новом блоке:

weekday.go
type Weekday int

const (
    Sunday Weekday = iota // 0
    Monday                // 1
    Tuesday               // 2
    Wednesday             // 3
)
собес

Есть ли enum в Go? Нет ключевого слова — есть идиома «именованный тип + const + iota». Типобезопасность обеспечивает именно именованный тип (Weekday), а не сам iota.

Подробнее: iota с выражениями и битовые флаги medium

iota можно подставлять в произвольное выражение — классика: степени двойки для битовых флагов:

flags.go
const (
    Read  = 1 << iota // 1 << 0 = 1
    Write              // 1 << 1 = 2
    Exec               // 1 << 2 = 4
)
perms := Read | Write // 3 — комбинация флагов

Пропустить значение — подчёркивание вместо имени: const (a = iota; _; c) — c получит 2, хотя имени под 1 не было.

1.5Приведение типов

В Go нет неявных преобразований — даже между int и float64. Только явный вызов T(v):

convert.go
var i int = 42
var f float64 = float64(i) // явно
var u uint = uint(f)

// var f2 float64 = i      // ошибка компиляции:
                           // cannot use i (int) as float64
собес

Почему нет неявного приведения? Разработчики Go сознательно пожертвовали удобством ради явности: скрытая потеря точности или неожиданный оверфлоу — частый источник багов в C/C++/JS.

Подробнее: ловушка string(int) medium

string(n), где n — число, не переводит число в текстовую запись — Go воспринимает его как код Unicode-символа:

strconv_trap.go
s := string(65)       // "A" — код символа, НЕ "65"!
n := strconv.Itoa(65) // "65" — вот так правильно

Для чисел нужен пакет strconv: Itoa/Atoi — число в строку и обратно. С недавних версий go vet предупреждает про такое string(int), если явно не имелся в виду rune.

&^ — уникальный для Go оператор «AND NOT» (bit clear): a &^ b обнуляет в a те биты, где в b стоит 1.

++ и -- — это statement, а не выражение: x = i++ не скомпилируется, только i++ отдельной строкой.

Подробнее: приоритет операторов и переполнение medium

Целочисленное деление отбрасывает дробную часть, округляя к нулю: 7 / 2 == 3, -7 / 2 == -3. Остаток % берёт знак делимого.

Переполнение знаковых и беззнаковых целых не паникует — значение «оборачивается» по модулю (math.MaxInt8 + 1 == math.MinInt8). Единственное исключение среди целых — деление на 0: это паника в рантайме (runtime error: integer divide by zero), кроме случая, когда оба операнда — константы: тогда это ошибка компиляции, а не рантайм-паника.

У float64/float32 деление на 0 ведёт себя принципиально иначе — не паникует вообще: по IEEE 754 результат +Inf, -Inf или NaN (для 0.0/0.0). Частая ловушка на собеседовании — ответить «паника» и для float тоже, забыв про эту асимметрию между целыми и плавающей точкой. (источник: t.me/go_interview_lib)

1.7Экспорт и видимость

В Go нет private/public. Видимость идентификатора за пределами пакета решает регистр первой буквы:

shapes.go
package shapes

type Circle struct { // экспортируется — с заглавной
    Radius float64    // экспортируется
    color  string      // НЕ экспортируется — со строчной
}

func NewCircle(r float64) *Circle { … } // экспортируется
func (c *Circle) area() float64 { … }    // НЕ экспортируется

(c *Circle) перед именем функции — это receiver: он делает функцию методом, привязанным к типу Circle (грубо — как self/this в других языках, только явно указанный). Вызывается как c.area(). Подробно про методы — в главе 6, здесь важно только одно: видимость метода вне пакета решает та же заглавная буква — area строчная, значит метод приватный для пакета.

собес

Как в Go устроена инкапсуляция без private? На уровне пакета, а не класса: правило регистра действует для всех файлов пакета сразу и проверяется компилятором, а не соглашением.

Подробнее: видимость и encoding/json medium

Пакеты вроде encoding/json работают через рефлексию, а рефлексия не может ни прочитать, ни записать неэкспортируемое поле из другого пакета. Поэтому color string из примера выше просто молча пропускается при json.Marshal/Unmarshal — без ошибки, как будто поля не существует.

1.8Комментарии

Обычные — // и /* */. Комментарий прямо перед объявлением становится doc-комментарием и попадает в godoc:

doc.go
// Circle описывает круг с заданным радиусом.
// Используется пакетом geometry для расчёта площади.
type Circle struct {
    Radius float64
}
собес

Соглашение godoc: doc-комментарий начинается с имени сущности (Circle описывает…) — так его проще парсить и читать в сгенерированной документации.

Подробнее: спецкомментарии-директивы medium

Комментарий с префиксом //go: — это не документация, а инструкция для компилятора или тулчейна:

build.go
//go:build linux && amd64
// файл участвует в сборке только под linux/amd64

//go:generate stringer -type=Weekday
// запускается вручную командой go generate

Управляющие конструкции

if, switch, единственный цикл for во всех формах и defer — с местами, где Go делает не так, как остальные C-подобные языки.

2.1if / else

Без скобок вокруг условия, фигурные скобки — обязательны всегда, даже для одной строки:

ifelse.go
if x > 0 {
    fmt.Println("положительное")
} else if x < 0 {
    fmt.Println("отрицательное")
} else {
    fmt.Println("ноль")
}

// init-statement — переменная видна только внутри if/else
if v, err := parse(input); err != nil {
    log.Fatal(err)
} else {
    fmt.Println(v)
}
собес

Зачем в if можно писать init-statement? Чтобы область видимости временной переменной (обычно err) была ограничена телом if/else и не «утекала» в остальную функцию. Это самая частая идиома в Go-коде.

камень

Открывающая { обязана стоять на той же строке, что и if/for/func. Из-за автоматической подстановки ; перенос скобки на новую строку — ошибка компиляции.

Подробнее: почему в Go нет тернарного оператора medium

В C/JS/Java есть короткая форма cond ? a : b — в Go её нарочно нет. Причина та же, что и с отсутствием неявных преобразований типов: авторы языка сознательно жертвуют компактностью синтаксиса ради того, чтобы код читался однозначно, без плотно упакованных выражений с побочным эффектом внутри условия.

Идиоматичная замена — обычный if/else с присваиванием, либо (для действительно частого случая «одно из двух значений») — маленькая функция-хелпер. Библиотечных «псевдотернарников» через дженерики в стандартной библиотеке нет специально — это осознанное решение, а не забытая фича.

2.2switch

Три формы: обычный, «безусловный» (замена цепочки if/else if) и type switch:

switch.go
switch day {
case time.Saturday, time.Sunday:
    fmt.Println("выходной")
default:
    fmt.Println("будний день")
}

switch {                    // без выражения — читается как if/else if
case score >= 90:
    grade = "A"
case score >= 75:
    grade = "B"
default:
    grade = "C"
}

switch v := x.(type) {      // type switch — какой конкретный тип в интерфейсе
case int:
    fmt.Println("int:", v)
case string:
    fmt.Println("string:", v)
}
собес

Проваливается ли switch по умолчанию? Нет — в отличие от C/Java/JS каждый case завершается неявным break. Чтобы провалиться в следующий case, нужно явное слово fallthrough.

Что такое type switch? Способ узнать конкретный тип значения, лежащего в интерфейсе (any/interface{}), через x.(type).

Подробнее: несколько типов в одном case type switch medium

Если case в type switch перечисляет ровно один тип — переменная внутри ветки получает этот конкретный тип. Но если типов несколько через запятую, переменная остаётся исходного интерфейсного типа, а не какого-то из перечисленных:

typeswitch.go
switch v := x.(type) {
case int:
    fmt.Println(v * 2)      // v — именно int
case int32, int64:
    fmt.Println(v)          // v — всё ещё any, умножить нельзя без доп. assertion
}

Ещё одна деталь, часто ускользающая от новичков — fallthrough проваливается в тело следующего case безусловно, не проверяя его собственное условие; в type switch fallthrough вообще запрещён компилятором, потому что следующий case может ожидать другой тип.

2.3for — все формы

В Go один циклический keyword — for. Он же заменяет и while, и бесконечный цикл:

for.go
for i := 0; i < 5; i++ {    // классический, три части
    fmt.Println(i)
}

for cond {                   // замена while
    cond = step()
}

for {                         // бесконечный, выход через break
    if done() { break }
}

for i, v := range items {    // по индексу и значению
    fmt.Println(i, v)
}
собес

Сколько видов циклов в Go? Один keyword for, четыре формы записи — так проще читать чужой код: не нужно помнить разный синтаксис while/do-while/for, как в C++.

capture.go
for i, n := range nums {
    go func() { fmt.Println(i, n) }() // до Go 1.22 — i, n были ОДНИ на все итерации
}
камень

До Go 1.22 переменные цикла range были общими для всех итераций — замыкание в горутине выше почти всегда печатало одно и то же значение (обычно последнее). Начиная с Go 1.22 каждая итерация получает свою копию i/n, и код выше работает ожидаемо. Частый вопрос на собесе — знай оба поведения и версию, с которой это изменилось.

Подробнее: labeled break/continue и новые формы range (1.22+/1.23+) medium

Чтобы прервать или продолжить именно внешний цикл из вложенного, используют метку — обычную идентификатор-метку перед циклом, а не goto:

labels.go
outer:
for i := 0; i < 3; i++ {
    for j := 0; j < 3; j++ {
        if j == 1 {
            continue outer // переходит к следующей итерации ВНЕШНЕГО цикла
        }
        if i == 2 {
            break outer     // выходит из ОБОИХ циклов сразу
        }
    }
}

С Go 1.22 range научился принимать просто целое число — for i := range 5 { ... } заменяет классическое for i := 0; i < 5; i++ там, где нужен только счётчик. С Go 1.23 range дополнительно умеет принимать функцию-итератор специальной сигнатуры (func(yield func(V) bool) и её варианты, тип iter.Seq) — это позволяет писать собственные ленивые последовательности, по которым можно проходить обычным for range, без ручного построения промежуточного слайса.

2.4defer

defer откладывает вызов до выхода из окружающей функции — успешного или через panic. Несколько defer выполняются в обратном порядке — LIFO:

defer.go
func main() {
    defer fmt.Println("1")
    defer fmt.Println("2")
    defer fmt.Println("3")
    fmt.Println("main")
}
// вывод: main  3  2  1
собес

Когда вычисляются аргументы defer? Сразу в момент объявления defer, а не в момент фактического вызова:

eval.go
i := 0
defer fmt.Println("i =", i) // "i" читается ЗДЕСЬ → напечатает 0
i++
камень

defer внутри цикла копится до конца всей функции, а не до конца итерации — если в цикле на тысячи элементов открывать файлы и делать defer f.Close(), дескрипторы не освободятся, пока функция не завершится. Для таких циклов закрывайте ресурс явно или выносите итерацию в отдельную функцию.

Подробнее: recover() должен стоять строго на верхнем уровне defer-функции deep

recover() перехватывает панику, только если он вызван напрямую внутри той функции, которая была непосредственно передана в defer — а не в какой-либо вложенной функции, вызванной из неё:

recover_trap.go
defer func() {
    helper() // recover() внутри helper НЕ поймает панику
}()

func helper() {
    if r := recover(); r != nil { // не сработает — вызван не там
        fmt.Println("recovered:", r)
    }
}

Причина — recover() привязан к конкретному фрейму стека той функции, что зарегистрирована через defer; вызов из более глубоко вложенного фрейма уже не «видит» паникующий фрейм как непосредственно свой родительский. Правильно — вызывать recover() прямо в теле переданной в defer функции, без промежуточного вызова.

Именованные результаты (глава 3) в связке с этим дают идиоматичный способ подменить возвращаемое значение по итогам восстановления после паники — без него после recover() функция просто продолжит выполнение с зануленным результатом, не подавая наружу признак того, что вообще была паника:

recover_named.go
func safeCall() (err error) {
    defer func() {
        if r := recover(); r != nil {
            err = fmt.Errorf("паника: %v", r) // видно и снаружи функции
        }
    }()
    // ...
    return nil
}
Глава 03

Функции

Сигнатуры, множественный возврат вместо исключений, замыкания и то, почему в Go «передача по ссылке» — это иллюзия.

3.1Объявление

Соседние параметры одного типа можно не повторять:

func.go
func add(a, b int) int {
    return a + b
}

func greet(name string, times int) { // без возвращаемого значения
    for i := 0; i < times; i++ {
        fmt.Println("Привет,", name)
    }
}
Подробнее: функция — это тоже тип medium

Сигнатуру функции можно использовать как обычный тип — параметр, поле структуры, возвращаемое значение:

funcvalue.go
type Operation func(a, b int) int

func apply(op Operation, a, b int) int {
    return op(a, b)
}

apply(func(a, b int) int { return a + b }, 2, 3) // 5

Это то же самое свойство «функция — значение первого класса», которое дальше используется для замыканий (3.5) и для http.HandlerFunc в главе 10 — обычная функция подходящей сигнатуры сама становится значением нужного функционального типа без явного оборачивания в класс/интерфейс, как в языках без функций как значений.

3.2Множественный возврат

Самое частое применение — значение плюс ошибка вторым аргументом:

divide.go
func divide(a, b int) (int, error) {
    if b == 0 {
        return 0, errors.New("деление на ноль")
    }
    return a / b, nil
}

q, err := divide(10, 2)
if err != nil {
    log.Fatal(err)
}
собес

Почему в Go нет try/catch? Ошибка — обычное возвращаемое значение, а не отдельный механизм контроля потока. Множественный возврат (значение, error) делает это возможным без исключений. Подробно — в главе про обработку ошибок.

Подробнее: игнорировать значение можно, ошибку — не стоит medium

Любое из множественных возвращаемых значений можно явно отбросить через _:

discard.go
q, _ := divide(10, 2) // осознанно игнорируем ошибку

Компилятор это разрешает без единого предупреждения — Go не заставляет обработать ошибку синтаксически, в отличие от checked exceptions в Java. Именно поэтому игнорирование error — одна из самых частых находок статических линтеров (errcheck, входит в golangci-lint, глава 13): язык не мешает выстрелить себе в ногу, дисциплина обеспечивается инструментами поверх компилятора, а не самим компилятором.

3.3Именованные результаты

Результаты можно назвать заранее — тогда return без аргументов («naked return») вернёт их текущие значения:

split.go
func split(sum int) (x, y int) {
    x = sum * 4 / 9
    y = sum - x
    return // вернёт x и y
}
камень

Naked return удобен в маленьких функциях, но в длинных — вредит читаемости: не видно, что именно возвращается, без прокрутки к сигнатуре. В Effective Go и большинстве линтеров его советуют избегать за пределами коротких функций.

Подробнее: главная практическая польза именованных результатов — не naked return, а defer medium

Именованные результаты доступны и изменяемы внутри defer-функции уже после выполнения тела, но до фактического возврата управления вызывающей стороне — это и есть тот самый механизм, который в главе 2 позволяет recover() подменить возвращаемую ошибку по итогам восстановления после паники. Без именованного результата такой трюк невозможен — обычный (безымянный) результат уже «зафиксирован» на момент выполнения defer, и правка внутри отложенной функции на него не повлияет.

3.4Вариативные функции

Внутри функции nums — обычный []int, слайс можно распаковать при вызове через ...:

variadic.go
func sum(nums ...int) int {
    total := 0
    for _, n := range nums {
        total += n
    }
    return total
}

sum(1, 2, 3)          // 6
nums := []int{1, 2, 3}
sum(nums...)          // тот же результат — распаковка слайса
Подробнее: только последний параметр может быть вариативным medium

В сигнатуре функции вариативным может быть только самый последний параметр — func f(a int, nums ...int, b string) не скомпилируется. Вызов вариативной функции вообще без аргументов на этом месте — валиден, внутри функции слайс будет просто nil-слайсом с len == 0, а не паникой:

variadic_empty.go
sum() // 0 — nums внутри nil, но range по nil-слайсу просто не выполнится ни разу

Сам встроенный append(s, vs...) — вариативная функция, устроенная точно так же: ... при вызове распаковывает существующий слайс в отдельные аргументы, это симметрично объявлению функции с ...T в сигнатуре.

3.5Функции как значения и замыкания

Функция — значение первого класса: её можно вернуть из другой функции, и она «захватывает» переменные из внешней области видимости:

counter.go
func makeCounter() func() int {
    count := 0
    return func() int {
        count++
        return count
    }
}

c1 := makeCounter()
c2 := makeCounter()
c1() // 1
c1() // 2
c2() // 1 — свой, независимый счётчик
собес

Почему count не удаляется после return? Компилятор Go проводит escape-анализ: если на локальную переменную остаётся живая ссылка (здесь — из замыкания), она «убегает» на heap вместо стека и живёт, пока жива хотя бы одна ссылка на неё.

Подробнее: замыкание по ссылке на переменную, а не по значению на момент создания deep

Замыкание захватывает саму переменную (её адрес), а не снимок её значения на момент объявления функции — если после создания замыкания внешняя переменная меняется, замыкание увидит уже новое значение:

closure_ref.go
x := 1
f := func() { fmt.Println(x) }
x = 2
f() // печатает 2, а не 1 — захвачена переменная, а не её старое значение

Это ровно та же механика, что стоит за ловушкой захвата переменной цикла в горутине (глава 2): до Go 1.22 все итерации range делили одну и ту же переменную, поэтому все замыкания, созданные в разных итерациях, видели её финальное значение. Полезное практическое применение той же механики — счётчики/кэши на замыканиях (как makeCounter выше) и мемоизация: замыкание может держать состояние между вызовами, не выставляя его наружу как поле структуры.

3.6Всё передаётся по значению

В Go нет передачи по ссылке — только по значению. Даже когда «похоже», что передан оригинал:

byvalue.go
func double(n int) {
    n *= 2 // копия n — на оригинал не влияет
}

func appendOne(s []int) {
    s = append(s, 1) // может не повлиять на оригинальный слайс!
}
камень

Слайс — это маленький заголовок {ptr, len, cap}, который тоже копируется по значению. Пока хватает cap, append пишет в тот же массив — но как только вместимость кончается, функция получает новый массив, а заголовок вызывающего кода остаётся указывать на старый. Разбор с диаграммой — в главе про слайсы.

собес

Значит, указатели в Go не нужны? Нужны — если функция должна менять сам оригинал (а не то, на что он указывает), единственный способ — передать *T. Указателям посвящена отдельная глава.

Подробнее: что именно копируется для каждого составного типа medium

«Передача по значению» не значит «копируется всё, что физически есть в памяти» — для составных типов копируется ровно их заголовок:

ТипЧто копируется при передаче
[N]T (массив)весь массив целиком, все N элементов — дорого для больших N
[]T (слайс)только заголовок {ptr, len, cap} — 24 байта; базовый массив общий
map[K]Vтолько внутренний указатель на хеш-таблицу
structвсе поля целиком — включая заголовки вложенных слайсов/map (shallow copy)

Именно поэтому большую структуру с горячим путём вызовов часто передают через указатель — не чтобы «избежать копирования» в абстрактном смысле, а чтобы скопировать 8 байт адреса вместо, скажем, нескольких сотен байт полей.

Глава 04

Слайсы, массивы, map, struct

Composite-типы, на которых держится весь Go-код. Главное здесь — как устроен слайс внутри: это объясняет половину багов новичков.

4.1Массивы

Размер — часть типа, поэтому массив используют редко: почти везде вместо него берут слайс.

array.go
var a [3]int              // [0 0 0]
b := [3]int{1, 2, 3}
c := [...]int{1, 2, 3, 4}  // компилятор сам посчитает длину → [4]int

fmt.Println(a == [3]int{0, 0, 0}) // true — массивы сравнимы и копируются целиком
собес

[3]int и [4]int — разные типы, один в другой не присвоить и не передать в функцию, ожидающую другой размер. Массив копируется по значению целиком — это и есть та самая причина, почему на практике почти всегда берут слайс.

Подробнее: массив как ключ map, и почему размер обязан быть константой medium

Массивы (в отличие от слайсов) сравнимы и хешируемы — их можно использовать как ключи map, если оба массива одного размера (размер — часть типа, разные размеры несовместимы для этой цели тоже):

arraykey.go
type Point [2]int
seen := map[Point]bool{}
seen[Point{1, 2}] = true // валидно — массив сравним и хешируем

Размер массива обязан быть константой времени компиляции (числовой литерал, const или выражение на основе iota) — переменная времени исполнения не годится, потому что компилятору нужно заранее знать точный размер типа для расчёта размера кадра стека. Именно поэтому [8]byte и [16]byte — полностью разные, несовместимые типы, хотя оба хранят просто байты.

4.2Слайсы

Слайс — это не массив, а маленький заголовок из трёх полей: указатель на массив, длина и вместимость.

slice.go
s := make([]int, 3, 4)   // len=3, cap=4
s = append(s, 4)          // cap хватает → тот же массив, len=4

t := []int{1, 2, 3}       // len=3, cap=3
t = append(t, 4, 5)       // cap не хватило → НОВЫЙ массив, ptr сменился
камень

Срез большого слайса держит в памяти весь исходный массив, пока жив хотя бы один под-срез:

leak.go
big := make([]byte, 1<<20) // 1 МБ
small := big[:10]           // держит весь big в памяти, пока жив small

safe := make([]byte, 10)
copy(safe, big[:10])        // независимая копия — big можно освобождать
собес

len vs cap? len — сколько элементов реально записано, cap — сколько влезает в текущий массив без реаллокации. len(s) ≤ cap(s) всегда.

Подробнее: точная формула роста cap и защита three-index slicing deep

Стратегия роста ёмкости, сверенная напрямую с исходником runtime/slice.go (функция nextslicecap): порог — ровно 256 элементов. При cap < 256 — удвоение (newcap = 2×oldcap). При cap ≥ 256 — рост по формуле newcap += (newcap + 3×256) >> 2, что стремится к ×1.25. Сам исходник поясняет это в комментарии: «переход от роста ×2 для маленьких слайсов к росту ×1.25 для больших — специально сделан плавным».

Опасный сосед этой темы — срез, полученный из другого слайса, при append может писать в тот же базовый массив, если в оставшуюся ёмкость помещается:

shareoverwrite.go
a := make([]int, 3, 5)     // len 3, cap 5
b := a[:2]                   // делит память с a
b = append(b, 99)            // затирает a[2], потому что cap ещё не исчерпан!

// защита — three-index slicing: принудительно режет cap нового среза
c := a[:2:2]                 // cap(c) == 2 → append(c, …) точно реаллоцирует

Полная форма s[low:high:max] задаёт третий индекс — предел ёмкости нового среза (cap = max - low), гарантируя, что append к нему всегда получит новый массив вместо тихой записи в чужие данные.

Подробнее: почему append внутри функции с параметром []int «не работает» medium

Заголовок слайса (указатель, len, cap) передаётся в функцию по значению — как копия. Это создаёт два разных класса изменений с разной видимостью снаружи:

valueptr.go
func mutateElem(s []int)  { s[0] = 99 }         // видно снаружи: тот же массив
func growSlice(s []int)   { s = append(s, 1) }   // НЕ видно: append(...) вернул
                                                  // новый заголовок, но это лишь
                                                  // локальная копия переменной s
func growViaPtr(s *[]int) { *s = append(*s, 1) } // видно: пишем через указатель
                                                  // в заголовок caller'а напрямую

Изменение элемента слайса всегда видно вызывающему коду — оба заголовка (оригинал и копия-параметр) указывают на один и тот же массив. А вот переприсваивание самой переменной s внутри функции (в том числе через append, которому не хватило вместимости, — тогда меняются сразу все три поля заголовка, включая указатель) правит только локальную копию заголовка и снаружи не видно никак. Чтобы функция могла надёжно расширить чужой слайс, ей нужен указатель на сам слайс (*[]int), а не сам слайс — именно поэтому у стандартных функций вроде json.Unmarshal в сигнатуре указатель. (источник: habr.com/ru/companies/ru_mts/articles/909158/)

4.3map

map.go
m := make(map[string]int)
m["a"] = 1

v, ok := m["b"] // comma-ok — есть ли вообще такой ключ
delete(m, "a")

var nilMap map[string]int
_ = nilMap["x"]   // 0 — читать из nil map можно
nilMap["y"] = 1    // panic: assignment to entry in nil map
камень

nil-map ведёт себя как пустая при чтении, но паникует при записи. Перед первой записью обязательно make(map[K]V) — либо в объявлении, либо в конструкторе.

собес

Гарантирован ли порядок for k, v := range m? Нет — рантайм Go нарочно рандомизирует порядок обхода map при каждом запуске, чтобы код не смог случайно на него положиться.

Подробнее: как устроена map внутри — от бакетов к Swiss Tables в Go 1.24 deep

До Go 1.24 — классические бакеты вместимостью 8 элементов каждый, с overflow-бакетом при переполнении. Порог load factor для роста — около 6.5 элементов в среднем на бакет по всей таблице (не 8 в одном бакете). Внутри бакета элемент ищется через сравнение tophash — старших 8 бит хеша, хранящихся отдельно от самого ключа для быстрого предварительного отсева без сравнения всего ключа целиком.

Начиная с Go 1.24 (официальные release notes) реализация map заменена на новую, основанную на Swiss Tables (техника open addressing, изначально из библиотеки Abseil для C++) — включено по умолчанию, откат на старую реализацию — сборочный флаг GOEXPERIMENT=noswissmap. Для собеса важно не путать это с тем, что «старую реализацию совсем убрали» — она физически осталась в дереве исходников как fallback.

Механика поиска в Swiss Tables: хеш ключа делится на две части — старшие биты (H1) выбирают группу слотов, младшие 7 бит (H2) кладутся в компактный «control byte» этого слота (отдельно от самого ключа/значения, как и tophash в старой реализации). Поиск сравнивает H2 сразу против целой группы control-байтов одной SIMD-подобной операцией (несколько слотов проверяются параллельно, а не по одному последовательным циклом) — это и даёт основной выигрыш в скорости по сравнению с бакетной реализацией. При коллизии (H2 совпал, но ключ реально другой, либо слот занят) поиск переходит к следующей группе по последовательности, гарантированно проходящей все группы таблицы ровно по одному разу — triangular number probing. (источник: t.me/go_interview_lib)

Почему &m[key] — ошибка компиляции: при рехешировании бакеты/слоты перевыделяются и элементы физически перемещаются в памяти, сохранённый указатель стал бы висячим. Обходные пути — читать-изменять-записывать значение целиком, либо хранить в map указатели (map[K]*V). Идиоматичная замена множества (set) — map[T]struct{}: пустая структура не занимает памяти, в отличие от map[T]bool, где пришлось бы хранить лишний булев флаг.

4.4struct

struct.go
type Point struct {
    X, Y int
}

type Circle struct {
    Point           // embedding — композиция, не наследование
    Radius float64
}

c := Circle{Point{1, 2}, 5}
fmt.Println(c.X)     // 1 — поле встроенного типа "продвинуто" наружу

type User struct {
    Name string `json:"name"`
    Age  int    `json:"age,omitempty"`
}
собес

Есть ли наследование в Go? Нет — только композиция через embedding. Поля и методы встроенного типа «продвигаются» наружу для удобного доступа, но это не полиморфизм: Circle нельзя передать туда, где ожидают именно Point, без явного c.Point.

камень

Теги (json:"name") — просто строка-метаданные, компилятор их не проверяет. Опечатка в теге не даст ошибки — encoding/json через reflect молча не найдёт поле и пропустит его.

Структуры сравнимы через ==, только если сравнимы все их поля — структура со слайсом, map или func внутри перестаёт быть сравнимой.

Подробнее: padding и порядок полей влияют на реальный размер структуры deep

Поля располагаются в памяти строго в порядке объявления — но компилятор может вставлять байты-«прокладки» (padding) между ними ради выравнивания (alignment): каждый тип должен начинаться по адресу, кратному своему размеру (например int64/указатель — по адресу, кратному 8 на 64-битной платформе).

padding.go
type Bad struct {
    A bool    // 1 байт + 7 байт padding
    B int64   // 8 байт
    C bool    // 1 байт + 7 байт padding
}
// unsafe.Sizeof(Bad{}) == 24

type Good struct {
    B int64   // 8 байт
    A bool    // 1 байт
    C bool    // 1 байт + 6 байт padding
}
// unsafe.Sizeof(Good{}) == 16 — тот же набор полей, другой порядок

Чередование мелких полей (bool, int8) с крупными (int64) заставляет компилятор вставлять padding после каждого мелкого поля. Практическая оптимизация — сортировать поля от крупных к мелким; это не только уменьшает размер структуры, но и помогает ей компактнее умещаться в кэш-линию процессора при обходе больших слайсов таких структур. Точный размер — unsafe.Sizeof().

Обратная сторона той же кэш-линии (обычно 64 байта) — cache thrashing (false sharing, «ложное разделение»): если несколько горутин на разных ядрах CPU часто пишут в разные поля, которые физически попали в одну кэш-линию, каждая запись инвалидирует копию всей линии в кэше других ядер — переменные логически независимы, но начинают «состязаться» за кэш, и линия непрерывно гоняется между ядрами, резко деградируя производительность конкурентного кода. Типичное решение — явный padding между часто изменяемыми конкурентно полями (например, полями-счётчиками разных горутин в структуре), чтобы развести их по разным кэш-линиям — здесь padding уже не враг (как в примере Bad выше), а осознанный инструмент. (источник: t.me/go_interview_lib)

Подробнее: чей метод побеждает при переопределении в embedding medium

Если дочерняя структура объявляет метод с тем же именем, что и у встроенного (embedded) типа, — побеждает метод самой дочерней структуры. Продвижение (promotion) работает только «снизу вверх»: свой метод на глубине 0 всегда перекрывает одноимённый метод встроенного поля на глубине 1, а не наоборот — это обычное разрешение по кратчайшей глубине, а не какая-то отдельная механика переопределения, как в языках с виртуальными методами.

override.go
type Parent struct{}
func (Parent) Print() string { return "parent" }

type Child struct{ Parent } // embedding
func (Child) Print() string { return "child" } // тот же метод, свой уровень

c := Child{}
c.Print()        // "child" — свой метод побеждает
c.Parent.Print() // "parent" — исходный всё ещё доступен через явное поле

Важный нюанс: это не полиморфизм в духе override/virtual — если код держит переменную статического типа Parent (не Child), вызов Print() на ней всегда останется методом Parent, даже если фактически внутри лежит embedded-часть от Child. Диспетчеризация по статическому типу переменной, а не по «динамическому классу», как в ООП с наследованием. (источник: habr.com/ru/articles/654569/)

Глава 05

Указатели

Единственный законный способ изменить оригинал, если Go всё передаёт по значению — и заодно самая частая паника в проде.

5.1& и *

& берёт адрес переменной, * — разыменовывает указатель:

pointer.go
x := 10
p := &x    // p — *int, адрес x
*p = 20     // разыменование — меняем x через указатель
fmt.Println(x) // 20

Это и есть способ обойти «всё передаётся по значению» из главы 3 — указатель тоже копируется, но копия указывает на тот же адрес:

double.go
func double(n int)  { n *= 2 }   // копия — x не изменится
func doublePtr(p *int) { *p *= 2 } // указывает на x — x изменится

x := 10
double(x)          // x всё ещё 10
doublePtr(&x)      // x стало 20
Подробнее: копирование структуры — не то же самое, что копирование её данных deep

Присвоение структуры (без указателя) копирует всю структуру целиком — но если внутри есть поле-слайс или поле-map, копируется только их заголовок (shallow copy): обе копии продолжают ссылаться на одни и те же исходные данные:

shallow.go
type Order struct {
    Items []string
}

a := Order{Items: []string{"хлеб"}}
b := a               // копия структуры, но Items — тот же заголовок
b.Items[0] = "молоко"
fmt.Println(a.Items[0]) // "молоко" — a тоже изменилась!

append, если требует реаллокации, разрывает эту связь — с этого момента копии расходятся. Если нужны по-настоящему независимые копии — либо хранить указатели ([]*T, map[K]*V), либо делать глубокое копирование вручную.

5.2new() vs &T{}

new.go
p1 := new(int)       // *int, указывает на zero value — 0
p2 := &Point{1, 2}    // *Point, сразу с нужными полями — так пишут почти всегда
собес

new(T) просто выделяет память под zero value T и возвращает *T. &T{...} делает то же самое, но с инициализацией полей на месте — поэтому на практике new почти не встречается вне учебников.

Для полей структуры компилятор сам разыменовывает — p.X вместо (*p).X:

autoderef.go
p := &Point{1, 2}
p.X = 10   // сахар для (*p).X = 10
Подробнее: new() для слайса/map/канала обычно бесполезен medium

new(T) работает для любого типа, но для слайса/map/канала он даёт указатель на zero value этого типа, то есть на nil — использовать сразу нельзя, нужна отдельная инициализация:

new_nil.go
p := new([]int) // *[]int, указывает на nil-слайс
(*p)[0] = 1      // panic: index out of range — слайс всё ещё пуст

s := make([]int, 0, 10) // так — сразу с выделенным буфером

Поэтому make, а не new — стандартный способ создать эти три типа. Отдельная деталь: то, окажется ли значение на стеке или в куче, решает escape analysis (разбор ниже), а не то, через new или make оно создано.

5.3Указатель на локальную переменную

В отличие от C, возвращать адрес локальной переменной в Go совершенно безопасно:

newpoint.go
func newPoint(x, y int) *Point {
    p := Point{x, y}
    return &p // безопасно! компилятор перенесёт p на heap
}
собес

А как же dangling pointer, как в C? Невозможен — сработает тот же escape-анализ, что и с замыканиями в главе 3: раз на p остаётся живая ссылка после возврата, компилятор размещает её на heap вместо стека.

Подробнее: взятие адреса не гарантирует уход на heap medium

Частое заблуждение — считать, что раз у переменной взяли &, она автоматически окажется в куче. На самом деле компилятор анализирует, «убегает» ли переменная из функции (возвращается, сохраняется глобально, передаётся в горутину/канал) — если нет, она вполне может остаться на стеке, даже если её адрес был взят внутри функции:

noescape.go
func sum(a, b int) int {
    p := &a  // адрес взят, но p никуда не "убегает" из функции
    return *p + b // компилятор вполне может оставить a на стеке
}

Посмотреть, что решил компилятор для конкретной функции — go build -gcflags="-m": он печатает решения escape-анализа построчно (moved to heap / does not escape). Полезно при профилировании — лишние аллокации на горячем пути часто оказываются неожиданным «убеганием» переменной туда, где её не ждали.

5.4nil-указатель

nilptr.go
var p *Point
p.X = 1 // panic: runtime error: invalid memory address or nil pointer dereference
камень

Разыменование nil-указателя — одна из самых частых паник в проде, особенно если указатель пришёл откуда-то извне (не найденная запись, несработавший поиск). Проверка if p == nil перед использованием — не паранойя, а норма.

собес

Есть ли в Go арифметика указателей? Нет (кроме экзотического unsafe.Pointer). Указатель либо валиден, либо nil — это упрощает сборщик мусора и делает памятную модель Go безопаснее, чем в C.

Подробнее: unsafe.Pointer и почему указатель всегда весит одинаково deep

Указатель — это всегда просто адрес: 4 байта на 32-битной платформе, 8 байт на 64-битной, независимо от того, указывает он на int8 или на мегабайтную структуру — сам указатель не «весит» больше от размера цели.

unsafe.Pointer — способ обойти систему типов и явно приводить указатели между несовместимыми типами; точечно используется во внутренностях стандартной библиотеки (например в strings.Builder/конвертации string↔[]byte без копирования). В обычном прикладном коде это считается кодом-запахом — почти всегда есть типобезопасная альтернатива, а любая ошибка в ручной арифметике с unsafe.Pointer — потенциальный SIGSEGV, который компилятор уже не может предотвратить.

Глава 06

Методы и интерфейсы

Самая собеседовательная глава: receiver'ы, method sets и ловушка nil-интерфейса, на которой спотыкаются даже опытные разработчики.

6.1Value vs pointer receiver

counter.go
type Counter struct{ n int }

func (c Counter) Value() int { return c.n } // value receiver — работает с копией
func (c *Counter) Inc()      { c.n++ }       // pointer receiver — меняет оригинал

c := Counter{}
c.Inc()                // компилятор сам подставляет (&c).Inc()
fmt.Println(c.Value()) // 1
собес

Когда брать pointer receiver? Когда метод должен менять получателя; когда структура большая и копировать её дорого; или просто для консистентности — если хоть один метод типа меняет состояние через *T, остальные методы обычно тоже делают *T, чтобы не путать вызывающих.

камень

Pointer-метод нельзя вызвать на неадресуемом значении: Counter{}.Inc() — ошибка компиляции, потому что у временного значения Counter{} нет адреса, который можно взять. Это первый намёк на method sets — разберём ниже.

Подробнее: автоматическое разыменование работает только у адресуемых значений medium

Go неявно подставляет & при вызове pointer-receiver метода — но только у адресуемых значений (переменных). Временные значения (литералы структур, результат вызова функции) неадресуемы:

addressable.go
Counter{}.Inc()  // ошибка: нельзя взять адрес литерала

c := Counter{}
c.Inc()          // ок: компилятор неявно делает (&c).Inc()

Отсюда практическое правило именования: если метод типа хоть раз меняет получателя через *T, остальные методы обычно тоже делают *T — не столько по техническим причинам, сколько ради консистентности API и предсказуемости для вызывающего кода.

6.2Method sets

Method set типа T включает только методы с value receiver. Method set *T включает и value-, и pointer-receiver методы. Отсюда — самая частая ошибка новичков с интерфейсами:

speaker.go
type Speaker interface{ Speak() string }

type Dog struct{}
func (d *Dog) Speak() string { return "Гав" } // pointer receiver

var s Speaker = Dog{}   // ошибка компиляции:
                        // Dog does not implement Speaker
var s Speaker = &Dog{}  // OK
Подробнее: точное правило одной фразой medium

Если у типа T все методы объявлены с value receiver — интерфейсу удовлетворяют и T, и *T. Если хотя бы один метод объявлен с pointer receiver — интерфейсу удовлетворяет только *T. Частая ошибка на практике — не столько путаница в теории (её обычно объясняют верно), сколько забывчивость: присваивая интерфейсной переменной, легко забыть явно передать &structVar, а не голую переменную, если среди методов есть хоть один pointer receiver.

6.3Неявная реализация

Интерфейс в Go описывает поведение, а не иерархию типов — слово implements не пишут никогда:

writer.go
type Writer interface {
    Write(p []byte) (int, error)
}

type File struct{ /* … */ }
func (f *File) Write(p []byte) (int, error) { return len(p), nil }

var w Writer = &File{} // *File реализует Writer автоматически
собес

Структурная типизация (structural typing). Компилятор просто проверяет, есть ли у типа нужные методы с нужными сигнатурами — откуда тип и зачем, не важно. Поэтому в Go интерфейсы маленькие и определяются на стороне потребителя (io.Reader, io.Writer — по одному методу).

Подробнее: почему интерфейс объявляют рядом с потребителем, а не с реализацией medium

Идиоматичное правило размещения (в противовес практике многих других языков, где интерфейс объявляют рядом с реализацией): интерфейс должен жить в пакете, который его использует, а не в пакете, который его реализует. Реализующий тип вообще не обязан знать о существовании интерфейса — благодаря неявному удовлетворению это просто работает.

Практическая польза — пакет-потребитель объявляет ровно тот минимальный интерфейс, который ему реально нужен (часто на 1 метод меньше, чем «полный» интерфейс поставщика) — это упрощает мокирование в тестах (глава 11) и снижает связанность между пакетами: поставщик может добавлять новые методы своему типу, не затрагивая уже написанные интерфейсы потребителей.

6.4any и type assertion

assert.go
var x any = 42

n, ok := x.(int) // comma-ok — безопасное приведение
if ok {
    fmt.Println(n * 2)
}

n2 := x.(string) // без ok: паника, если x не string

Если типов несколько — вместо цепочки assertion'ов используют switch v := x.(type) из главы 2.

Подробнее: сравнение любых any и сужение после assertion к другому интерфейсу deep

Два значения any сравнимы через ==, только если сравним их динамический тип. Если хотя бы одно хранит несравнимый тип (слайс, map, функцию) — сравнение не просто вернёт false, а паникует в рантайме:

anycompare.go
var a any = []int{1, 2}
var b any = []int{1, 2}
fmt.Println(a == b) // panic: comparing uncomparable type []int

Компилятор не может отследить это статически для any — конкретный динамический тип известен только в рантайме. Альтернатива для слайсов — slices.Equal() (Go 1.21+) или более универсальный, но медленный reflect.DeepEqual().

Отдельный, часто упускаемый нюанс type assertion — если приводить не к конкретному типу, а к другому интерфейсу, после успешной assertion доступны только методы целевого интерфейса, даже если реальный динамический тип реализует значительно больше методов:

narrowassert.go
type AB interface { A; B }
type BC interface { B; C }

var ab AB = T{}   // T реализует A, B и C
bc := ab.(BC)      // успешно — T реализует всё, что требует BC
bc.MethodA()       // ОШИБКА КОМПИЛЯЦИИ: интерфейс BC не включает A

Assertion срабатывает, потому что рантайм проверяет соответствие по динамическому типу — но статический тип переменной bc после присвоения именно BC, и компилятор разрешает вызывать только то, что объявлено в этом статическом типе.

6.5Ловушка nil-интерфейса

Интерфейс внутри — это пара (тип, значение). Он равен nil, только если обе части пустые:

niltrap.go
type MyError struct{ msg string }
func (e *MyError) Error() string { return e.msg }

func doSomething() error {
    var p *MyError = nil
    return p // интерфейс НЕ nil!
}

err := doSomething()
fmt.Println(err == nil) // false — хотя p был nil
собес

Как правильно? Возвращать nil напрямую как error, а не через типизированный nil-указатель: if p == nil { return nil }; return p. Это один из самых частых вопросов на Go-собеседованиях — про него часто спрашивают именно словами «почему err != nil, хотя функция явно вернула nil?».

Подробнее: почему пустой и непустой интерфейс устроены по-разному внутри deep

Непустой интерфейс (с хотя бы одним методом, вроде error) хранится как пара (itab, data): указатель на itab — таблицу методов конкретного типа — и указатель на сами данные. Именно ненулевой itab и создаёт ловушку выше: типизированный nil-указатель даёт заполненный itab при пустых данных, и пара в целом уже не nil.

Пустой интерфейс (any/interface{}, без методов вообще) устроен иначе: диспетчеризировать нечего, поэтому вместо itab его представление — пара «указатель на дескриптор типа, указатель на данные» напрямую, без промежуточной таблицы методов. Оба представления двухсловные (два указателя), но смысл первого слова разный — присвоение конкретного значения пустому интерфейсу немного дешевле именно из-за отсутствия косвенного обращения через itab, хотя стоимость самого копирования данных это не меняет.

Глава 07

Обработка ошибок

Ошибка — обычное значение, а не исключение. Здесь — идиома error, оборачивание, errors.Is/As и когда всё-таки нужна паника.

7.1Интерфейс error

error — это интерфейс с одним методом. Любой тип с таким методом — уже ошибка:

error.go
type error interface {
    Error() string
}

err := errors.New("что-то пошло не так")
err2 := fmt.Errorf("не удалось открыть файл %q: %w", name, err)
Подробнее: panic — для программистских ошибок, error — для ожидаемых сбоев medium

Интерфейс error минимален — единственный обязательный метод Error() string, и nil тоже ему удовлетворяет (отсюда и ловушка typed-nil из главы 6). Смысловое разграничение с panic: panic — для нарушения инвариантов программы, программистских ошибок, которые в принципе не должны происходить; error — для ожидаемых, штатных сбоев (не найден файл, не прошла валидация, недоступна сеть). Не стоит использовать panic как замену обычной обработке ошибок в бизнес-коде — это разбирается подробнее ниже, в 7.5.

7.2Оборачивание — %w

%w в fmt.Errorf сохраняет ссылку на исходную ошибку — в отличие от %v, который просто печатает текст и рвёт цепочку:

wrap.go
func readConfig() error {
    _, err := os.Open("config.yaml")
    if err != nil {
        return fmt.Errorf("readConfig: %w", err) // оборачивает, не теряя оригинал
    }
    return nil
}
Подробнее: несколько %w сразу и errors.Join medium

С Go 1.20 fmt.Errorf допускает несколько %w в одном вызове — получившаяся ошибка оборачивает сразу несколько причин, и errors.Is/errors.As проверяют все ветки:

multiwrap.go
err := fmt.Errorf("два сбоя сразу: %w и %w", err1, err2)

// более прямой способ объединить набор независимых ошибок —
// например все ошибки валидации формы разом:
joined := errors.Join(err1, err2, err3)
fmt.Println(joined) // печатает все три ошибки, по одной на строку

errors.Join (тоже с Go 1.20) — стандартный способ собрать несколько независимых ошибок в одну без ручной конкатенации строк; nil-элементы внутри отбрасываются автоматически.

7.3errors.Is и errors.As

isas.go
var ErrNotFound = errors.New("не найдено")

func find(id int) error {
    return fmt.Errorf("find(%d): %w", id, ErrNotFound)
}

err := find(5)
if errors.Is(err, ErrNotFound) { // проходит сквозь все обёртки
    fmt.Println("не нашли запись")
}

var myErr *MyError
if errors.As(err, &myErr) { // достаёт конкретный тип из цепочки
    fmt.Println(myErr.Code)
}
Подробнее: на чём именно держится цепочка — метод Unwrap() medium

fmt.Errorf с %w под капотом создаёт значение, реализующее необязательный метод Unwrap() error — именно по нему errors.Is/errors.As проходят цепочку дальше. Собственный тип ошибки может реализовать Unwrap() вручную, чтобы участвовать в этой же цепочке:

unwrap.go
type ValidationError struct {
    Field string
    Err   error
}

func (e *ValidationError) Error() string { return e.Field + ": " + e.Err.Error() }
func (e *ValidationError) Unwrap() error { return e.Err } // включает в общую цепочку

errors.Is(err, target) — по сути «==, но по всей цепочке» — годится для сравнения с sentinel-ошибками (var ErrNotFound = errors.New(...)). errors.As(err, &target) — «type assertion, но по всей цепочке» — находит в цепочке ошибку конкретного типа и извлекает её в target, давая доступ к дополнительным полям вроде Field выше.

7.4Кастомные ошибки

customerr.go
type MyError struct {
    Code int
    Msg  string
}

func (e *MyError) Error() string {
    return fmt.Sprintf("[%d] %s", e.Code, e.Msg)
}
камень

Sentinel-ошибки (var ErrX = errors.New(...)) нельзя надёжно сравнивать через ==, если по пути их могли обернуть — используйте errors.Is. Для ошибок с данными (код, поля) — свой тип и errors.As.

Подробнее: продакшн-паттерн — код ошибки вместо текста deep

На высоконагруженных сервисах текст ошибки в кастомном типе — хрупкая база для контракта: тесты, сравнивающие строки текста, ломаются при любой правке формулировки, а клиент, разбирающий текст, лишён стабильного API. Продакшн-паттерн — доменные типы ошибок с явным кодом, а не только текстом:

domainerr.go
type Code string

const (
    ErrNotFound        Code = "NOT_FOUND"
    ErrInvalidArgument Code = "INVALID_ARGUMENT"
)

type DomainError struct {
    Code    Code
    Message string
    TraceID string // сквозная трассируемость по логам
}

func (e *DomainError) Error() string { return string(e.Code) + ": " + e.Message }

В JSON-ответе клиенту передаётся именно код ошибки — локализация текста для конечного пользователя остаётся на стороне клиента, а не зашита в сообщение с бэкенда. Отдельное централизованное middleware отвечает за маппинг доменного кода в конкретный HTTP-статус в одном месте, а не разбросанной по каждому хендлеру логикой.

7.5panic / recover

recover работает только внутри defer:

recover.go
func safeDivide(a, b int) (result int, err error) {
    defer func() {
        if r := recover(); r != nil {
            err = fmt.Errorf("восстановились после паники: %v", r)
        }
    }()
    return a / b, nil // паника при b == 0: integer divide by zero
}
собес

Когда использовать panic вместо error? Почти никогда для обычной бизнес-логики. panic — для по-настоящему невосстановимых ситуаций: нарушен инвариант программы, баг, а не ожидаемая ошибка вроде «файл не найден». Библиотеки не должны паниковать наружу — на границе пакета панику принято ловить recover и превращать в обычный error.

Подробнее: recover работает только в той горутине, где случилась паника deep

Критичный нюанс для конкурентного кода: необработанная паника в любой горутине убивает весь процесс целиком, а не только эту горутину — recover() в main никак не спасёт от паники, случившейся в другой горутине. Каждой горутине, где в принципе может случиться паника (особенно воркерам в пуле), нужен свой собственный defer+recover:

workerrecover.go
func worker(jobs <-chan Job) {
    for j := range jobs {
        func() {
            defer func() {
                if r := recover(); r != nil {
                    log.Println("worker паникнул на задании:", r)
                }
            }()
            process(j) // паника здесь не уронит остальных воркеров
        }()
    }
}

Рекомендуемая практика — ставить recover на верхнем уровне логической единицы работы (middleware HTTP-сервера, обёртка над обработчиком воркера), а не разбрасывать по всему коду. recover() возвращает значение типа any — чтобы понять, что именно запаниковало, требуется type assertion к этому значению.

Глава 08

Конкурентность

Визитная карточка Go: горутины, каналы, select, sync — и где именно прячутся гонки данных.

8.1Горутины

goroutine.go
go func() {
    fmt.Println("работает в фоне")
}()
собес

Горутина — это поток ОС? Нет. Это лёгкая «зелёная» нить: рантайм Go сам мультиплексирует множество горутин на меньшее число настоящих потоков ОС (планировщик M:N). Стартовый стек горутины — около 2 КБ и растёт по мере надобности, тогда как поток ОС обычно резервирует мегабайты. Поэтому горутин легко запустить тысячи и десятки тысяч.

камень

Когда main() завершается, все горутины обрываются без предупреждения — даже недописанные:

gotcha.go
func main() {
    go fmt.Println("привет") // main может завершиться раньше — и это не напечатается
}
Подробнее: модель планировщика GMP и до какого предела растёт стек deep

Планировщик Go — модель GMP: G (горутина), M (поток ОС), P (логический процессор, число = GOMAXPROCS, по умолчанию — число ядер). У каждого P — своя локальная очередь горутин; когда она опустеет, P ворует горутины из чужой очереди (work stealing), забирая обычно половину, чтобы не создавать лишней конкуренции за одну очередь.

Стартовый стек горутины — 2 КБ, растёт динамически до ~1 ГБ по умолчанию — упереться в этот лимит почти всегда признак неограниченной рекурсии, а не легитимной глубокой нагрузки. Именно за счёт лёгкого старта на типичном железе можно держать миллионы горутин одновременно, хотя практический ориентир для одного инстанса — не превышать 500 тыс.–1 млн, с запасом по памяти и с использованием worker pool (8.7) для контроля нагрузки, а не бесконтрольного спавна.

С Go 1.14 планировщик умеет асинхронно вытеснять горутину, которая слишком долго не отдаёт управление добровольно (сигнал SIGURG) — до этого «тяжёлый» вычислительный цикл без операций ввода-вывода мог надолго занять поток целиком.

Три штатных способа остановить горутину (в отличие от потока ОС, у горутины нет метода вроде Kill() — остановить можно только «изнутри», кооперативно):

  1. завершение main() — обрывает вообще все горутины программы разом, без каких-либо гарантий завершённости;
  2. закрытие канала, который слушают горутины — close(ch) будит разом всех, кто ждёт на нём, стандартный «широковещательный» сигнал;

Управление ресурсами планировщика — не только GOMAXPROCS как переменная окружения: идиоматичный явный вызов runtime.GOMAXPROCS(runtime.NumCPU()) фиксирует число P равным числу логических ядер (это и есть значение по умолчанию, явный вызов нужен, только если до этого кто-то его переопределил). runtime.Gosched() — добровольно уступить текущий поток, поставив свою горутину в конец очереди на выполнение, не блокируясь при этом ни на чём; в проде почти не нужен благодаря вытесняющему планировщику с Go 1.14, но всплывает в вопросах про кооперативную многозадачность. (источник: habr.com/ru/articles/670974/)

8.2Каналы

channel.go
ch := make(chan int)      // небуферизованный
bch := make(chan int, 3)  // буферизованный на 3

ch <- 5      // отправка
v := <-ch    // получение
close(ch)    // сигнал "больше данных не будет"

v, ok := <-ch // ok == false — канал закрыт и пуст
камень

Отправка в закрытый канал — паника (send on closed channel). Повторное close — тоже паника. А вот читать из закрытого канала можно всегда — вернётся zero value и ok == false.

Подробнее: nil-канал не паникует — он блокируется навсегда deep

Полная таблица поведения по трём состояниям канала — частый вопрос-«аксиома», который путают: nil-канал — и чтение, и запись блокируются навсегда (вечный deadlock, если это единственный путь горутины), не паника; открытый канал — обычная семантика рандеву/буфера; закрытый канал — чтение продолжает отдавать оставшиеся данные, затем zero value без блокировки, запись — паника.

Подробнее: почему chan struct{}, а не chan bool, для канала-сигнала medium

Когда через канал не передаётся полезных данных, а важен только сам факт получения значения или закрытия («стоп», «готово», «разбудить») — идиоматичный тип канала: chan struct{}, а не chan bool. Причина не только стилистическая: struct{} — тип нулевого размера, не занимает памяти вообще, тогда как bool физически занимает байт и создаёт ложное впечатление, что переданное значение (true/false) само по себе что-то значит. chan struct{} явно говорит читателю кода: этот канал — только для синхронизации.

Тот же тип struct{} — идиоматичная реализация множества (set) как map[T]struct{} вместо map[T]bool ровно по той же причине нулевого размера значения. (источник: t.me/go_interview_lib)

8.3select

select.go
select {
case v := <-ch1:
    fmt.Println("из ch1:", v)
case v := <-ch2:
    fmt.Println("из ch2:", v)
case <-time.After(time.Second):
    fmt.Println("таймаут")
default:
    fmt.Println("ни один канал не готов")
}
собес

Что если готовы сразу два case? select выберет один из готовых случайно — намеренно, чтобы код не мог незаметно положиться на порядок case'ов как на приоритет.

Подробнее: time.After в цикле — незаметная утечка памяти deep

Частая ошибка на собеседовании и в проде: time.After(d) создаёт новый таймер (и канал под него) при каждом вызове. Если вызвать её внутри select, который крутится в цикле, — на каждой итерации создаётся новый таймер, а старые продолжают жить в памяти до срабатывания (таймер не собирается GC, пока не истечёт). При частых итерациях это ощутимая утечка.

select_leak.go
// плохо: новый таймер на каждой итерации цикла
for {
    select {
    case v := <-ch:
        process(v)
    case <-time.After(5 * time.Second):
        return
    }
}

// хорошо: один таймер, переиспользуется через Reset
t := time.NewTimer(5 * time.Second)
defer t.Stop()
for {
    if !t.Stop() {
        <-t.C
    }
    t.Reset(5 * time.Second)
    select {
    case v := <-ch:
        process(v)
    case <-t.C:
        return
    }
}

Ещё один нюанс: nil-канал в select никогда не готов — этим пользуются, чтобы динамически «выключать» case, присвоив переменной канала nil (см. 8.2), вместо того чтобы городить дополнительный bool-флаг и ветвление.

Подробнее: основы context.Context — Background/TODO и три способа отмены medium

context.Background() и context.TODO() возвращают технически идентичный пустой контекст — разница чисто смысловая, для читаемости кода. Background() — канонический корень дерева контекстов, с которого стартуют в точке входа программы (main, обработчик верхнего уровня). TODO() — временная заглушка для мест, где ещё не решено, какой контекст должен быть на самом деле, либо родительский контекст пока объективно неоткуда взять — сигнал «здесь чего-то не хватает», а не альтернативный «корень».

Три конструктора производного отменяемого контекста, у каждого из которых обязательно нужно вызвать возвращаемую функцию отмены (обычно через defer cancel()), даже если дедлайн/таймаут уже успел сработать сам — иначе связанные с контекстом ресурсы (например горутина внутри самого пакета context, отслеживающая дедлайн) не освобождаются сразу:

КонструкторКогда сработает отмена
WithCancel(parent)только вручную — когда вызывающий сам решит и позовёт cancel()
WithDeadline(parent, t)автоматически в конкретный момент времени t
WithTimeout(parent, d)автоматически через интервал d от текущего момента (по сути обёртка над WithDeadline)
ctxselect.go

Канал ctx.Done() закрывается ровно один раз при отмене (см. широковещательную семантику close из 8.2) — поэтому его можно безопасно слушать сразу в нескольких горутинах и в select вперемешку с другими каналами; ctx.Err() после закрытия возвращает конкретную причину — context.Canceled (позвали cancel()) либо context.DeadlineExceeded (истёк срок). Подробнее: errgroup — WaitGroup + ошибки + отмена контекста medium

Голый sync.WaitGroup не умеет собирать ошибки из горутин и не умеет остановить остальные при первой ошибке — обе задачи приходится решать вручную (общий error под мьютексом, канал ошибок). Пакет golang.org/x/sync/errgroup закрывает именно этот пробел: g, ctx := errgroup.WithContext(ctx) создаёт группу, привязанную к контексту — как только любая горутина вернёт ненулевую ошибку, этот ctx отменяется, и остальные горутины (если написаны с оглядкой на ctx.Done()) могут завершиться раньше срока; g.Wait() возвращает первую полученную ошибку.

errgroup.go
g, ctx := errgroup.WithContext(context.Background())
g.SetLimit(10) // не более 10 горутин одновременно

for _, url := range urls {
    url := url
    g.Go(func() error {
        return fetch(ctx, url)
    })
}
if err := g.Wait(); err != nil {
    log.Fatal(err)
}

SetLimit(n) дополнительно превращает группу в готовый пул с ограничением параллелизма — не нужно вручную городить буферизованный канал-семафор.

Подробнее: как счётчик и число ожидающих упакованы в одно 64-битное слово deep

Внутреннее состояние WaitGroup — не два отдельных поля-счётчика, а одно упакованное uint64: старшие 32 бита — счётчик незавершённых задач (то, что меняют Add/Done), младшие 32 бита — число горутин, заблокированных в Wait(). Упаковка в одно слово — не экономия памяти, а способ менять оба значения одной атомарной инструкцией CPU (atomic.Add/CAS) без отдельного мьютекса: если бы это были два независимых int32, между их обновлениями возможна была бы гонка.

Отсюда и историческое требование выравнивания WaitGroup на границу 8 байт на 32-битных платформах — атомарная операция над 64-битным словом невозможна, если оно не выровнено, а несоблюдение этого требования на старых версиях Go могло приводить к панике именно на 32-битных архитектурах. Подробнее: normal- и starvation-режим мьютекса deep

С Go 1.9 sync.Mutex внутри (internal/sync/mutex.go) — не просто один бит блокировки, а конечный автомат с двумя режимами. В normal mode горутина, не сумевшая захватить мьютекс сразу, несколько раз активно крутится в спин-цикле (busy-wait) в надежде, что владелец вот-вот освободит блокировку — это дёшево на многоядерных машинах, если критическая секция короткая, и только после нескольких неудачных попыток горутина паркуется в очереди ожидания. Из-за этого разбуженная горутина конкурирует за захват наравне с новоприбывшими и может проигрывать им много раз подряд — это несправедливо, но быстро в среднем.

Если конкретная горутина ждёт в очереди дольше порога starvationThresholdNs = 1мс, мьютекс переключается в starvation mode: захват передаётся строго первой горутине из очереди FIFO, новоприбывшие вообще не пытаются захватить мьютекс сразу, а встают в конец очереди — спин-цикл в этом режиме отключается. Это гарантирует прогресс долго ждавшим ценой пиковой пропускной способности. Как только очередь опустевает или последняя разбуженная горутина ждала меньше 1мс, мьютекс возвращается в normal mode.

RWMutex добавляет к этому разделение read/write-блокировок: несколько читателей могут держать RLock() одновременно, но писатель, ожидающий Lock(), блокирует новых читателей от захвата (чтобы не голодал бесконечно) — типичное практическое правило: RWMutex оправдан, когда чтений на порядок больше записей (грубая эвристика — 10:1 и выше), иначе накладные расходы на его более сложную логику не окупаются по сравнению с обычным Mutex.

Подробнее: sync.Once и sync.Cond — соседи Mutex, о которых часто забывают medium

sync.Once гарантирует, что переданная в Do(f) функция выполнится ровно один раз за весь жизненный цикл программы, даже если Do вызывают конкурентно из множества горутин одновременно — остальные вызовы просто дождутся завершения первого и вернутся, ничего не выполнив повторно. Типичное применение — ленивая потокобезопасная инициализация синглтона или общего подключения без ручной возни с мьютексом и флагом «уже инициализировано».

once.go
var once sync.Once
var conn *Connection

func getConn() *Connection {
    once.Do(func() { conn = connect() }) // выполнится только у первого вызвавшего
    return conn
}

sync.Cond — условная переменная поверх блокировки (обычно *sync.Mutex), нужна, когда горутине важно не просто дождаться освобождения лока, а дождаться конкретного условия. Методы: Wait() — атомарно освобождает лок и паркует горутину, при пробуждении сама же снова захватывает лок перед возвратом; Signal() — будит ровно одну ожидающую горутину; Broadcast() — будит все разом. Классическое правило использования — проверять условие в цикле for, а не в if: между пробуждением и повторным захватом лока условие могла успеть изменить другая горутина (или сработало «паразитное» пробуждение), поэтому после Wait() нужно перепроверять условие заново, а не считать пробуждение доказательством его истинности. (источник: habr.com/ru/articles/658623/)

Подробнее: дедлок, livelock, голодание — не путать medium

Три разных отказа конкурентной программы, которые часто путают на собеседовании:

ТерминСуть
Дедлок (deadlock)все участники заблокированы навсегда, взаимно ожидая друг друга — прогресса нет вообще; рантайм Go умеет обнаружить дедлок всех горутин сразу (тогда паникует с "all goroutines are asleep — deadlock!"), но не частичный дедлок подмножества горутин
Livelockгорутины не заблокированы, активно выполняются и реагируют друг на друга, но система в целом не продвигается — классический пример: два человека в коридоре синхронно уступают дорогу друг другу и одновременно шагают в одну сторону
Голодание (starvation)какая-то горутина в принципе может продвинуться, но ей систематически не даёт этого сделать более «агрессивный» сосед (см. normal-mode мьютекса в 8.5, где именно от этого защищает starvation mode)

Классические четыре условия Коффмана (Coffman conditions), при одновременном выполнении которых возможен дедлок: взаимное исключение (ресурс нельзя разделить), удержание-и-ожидание (процесс держит один ресурс и ждёт другой), отсутствие принудительного отбора ресурса, и циклическое ожидание (A ждёт B, B ждёт A). Убрать хотя бы одно условие — например, всегда захватывать несколько мьютексов в фиксированном глобальном порядке, убирая циклическое ожидание — стандартный способ гарантированно избежать дедлока при работе с несколькими блокировками.

Детектор гонок (-race) работает по алгоритму vector clocks поверх реальных запусков и замедляет выполнение примерно в 5–10 раз и увеличивает потребление памяти в разы — поэтому его держат во включённом виде в CI на тестах, но не в проде.

Подробнее: lock-free vs wait-free — чем CAS-цикл отличается от более строгой гарантии deep

sync/atomic позволяет писать алгоритмы вообще без блокировок — типичный паттерн: прочитать текущее значение, вычислить новое, попытаться атомарно подменить через CompareAndSwap, при неудаче (кто-то успел изменить значение первым) — повторить цикл заново.

cas_loop.go
for {
    old := atomic.LoadInt64(&x)
    n := f(old) // например, old*2 или max(old, candidate)
    if atomic.CompareAndSwapInt64(&x, old, n) {
        break
    }
    // проиграли гонку — old устарел, повторяем с начала
}

Это lock-free, но не wait-free — важное различие в строгости гарантии прогресса. Lock-free гарантирует лишь, что хотя бы одна горутина из всех конкурирующих продвинется вперёд за конечное время (система в целом не зависает) — но конкретная отдельная горутина в теории может проигрывать CAS сколь угодно много раз подряд при очень высокой конкуренции («живое голодание» одного участника при общем прогрессе системы). Wait-free — более сильная гарантия: каждая горутина завершает операцию за ограниченное число шагов независимо от того, что делают остальные — на практике такие структуры данных сложнее в реализации и применяются реже, чем lock-free с CAS-ретраем.

(источник: t.me/go_interview_lib)

8.7Мини-паттерн: worker pool

Несколько воркеров разбирают одну очередь заданий и пишут результат в общий канал:

pool.go
func worker(id int, jobs <-chan int, results chan<- int) {
    for j := range jobs { // выходит из цикла, когда jobs закрыт и пуст
        results <- j * 2
    }
}

func main() {
    jobs := make(chan int, 5)
    results := make(chan int, 5)

    for w := 1; w <= 3; w++ {
        go worker(w, jobs, results)
    }
    for j := 1; j <= 5; j++ {
        jobs <- j
    }
    close(jobs) // сигнал воркерам — заданий больше не будет

    for i := 0; i < 5; i++ {
        fmt.Println(<-results)
    }
}
собес

Что означают <-chan int и chan<- int? Направленные типы каналов: jobs в сигнатуре worker — только для чтения, results — только для записи. Компилятор не даст перепутать направление — это защита от ошибок на уровне типов, а не просто соглашение.

Подробнее: кто закрывает канал результатов и как остановиться по контексту deep

Пример выше жёстко знает, что результатов будет ровно 5, поэтому читает результаты фиксированное число раз без закрытия results. В реальном пуле воркеров так не получится — читателю нужно знать, когда результаты закончились, а закрывать канал из нескольких воркеров одновременно нельзя (повторное закрытие — паника). Стандартное решение — отдельная «координирующая» горутина, которая через sync.WaitGroup дожидается завершения всех воркеров и только затем закрывает канал результатов:

pool_shutdown.go
var wg sync.WaitGroup
for w := 1; w <= 3; w++ {
    wg.Add(1)
    go func() {
        defer wg.Done()
        for j := range jobs {
            select {
            case results <- process(j):
            case <-ctx.Done():
                return // корректная остановка по отмене контекста
            }
        }
    }()
}
go func() {
    wg.Wait()
    close(results) // закрывает ровно ОДНА горутина, когда все воркеры точно завершились
}()
for r := range results { // читаем, пока канал не закроется
    fmt.Println(r)
}

Второй нюанс — грациозная остановка: воркер, слепо читающий из jobs в бесконечном for range, не отреагирует на отмену контекста, пока не придёт следующее задание или канал не закроется. Чтобы пул можно было остановить по таймауту/сигналу немедленно, каждую отправку/приём внутри воркера оборачивают в select с case <-ctx.Done(): return, как показано выше.

Подробнее: сколько воркеров заводить — CPU-bound и I/O-bound требуют разного ответа medium

Универсального числа воркеров не существует — правильный размер пула прямо зависит от того, чем именно занята задача внутри воркера:

Для CPU-bound задач (чистые вычисления, без ожидания сети/диска) оптимум обычно близок к runtime.NumCPU() (то есть к GOMAXPROCS) — больше воркеров, чем логических ядер, лишь увеличивает переключение контекста между горутинами, не давая реального прироста параллелизма, поскольку одновременно исполняться может ровно столько горутин, сколько есть P.

Для I/O-bound задач (сеть, диск, ожидание ответа БД) воркеров осмысленно заводить в разы или на порядки больше числа ядер — большую часть времени такая горутина не потребляет CPU вообще, а простаивает в ожидании ответа, дешёво занимая лишь несколько КБ стека. Здесь ограничивающий фактор — не число ядер, а внешние лимиты: число одновременных соединений, которое выдержит удалённый сервис/пул соединений БД, и под них подбирается размер пула (часто эмпирически, через нагрузочное тестирование), а не под NumCPU(). Generics

В Go с версии 1.18. Параметризация по типу вместо копипаста функций под каждый тип или небезопасного any.

9.1Зачем нужны

До 1.18 — либо дублировать функцию под каждый тип, либо писать через any с приведением типов внутри (теряя проверку на этапе компиляции):

before.go
func SumInts(nums []int) int {
    var s int
    for _, n := range nums { s += n }
    return s
}

func SumFloats(nums []float64) float64 {
    var s float64
    for _, n := range nums { s += n }
    return s
}
Подробнее: почему просто any — не замена дженерикам medium

Вариант с any (func Sum(nums []any) any) решает проблему дублирования кода, но создаёт две новые: во-первых, приведение типов происходит в рантайме — ошибку в приведении (n.(int) к неверному типу) компилятор не поймает, программа упадёт по панике только во время выполнения; во-вторых, это ощутимо медленнее — доступ к значению внутри any почти всегда требует отдельного выделения памяти в куче (boxing) и косвенного обращения через интерфейсный дескриптор, тогда как дженерик-версия для конкретного T компилируется в код, работающий с типом напрямую, без боксинга и без приведений в рантайме.

Итого: дженерики — это про безопасность типов на этапе компиляции и производительность, а не только про экономию строк кода.

9.2Обобщённые функции

T в квадратных скобках — параметр типа, ограничение после него — какие типы допустимы:

generic.go
func Sum[T int | float64](nums []T) T {
    var s T
    for _, n := range nums {
        s += n
    }
    return s
}

Sum([]int{1, 2, 3})       // T выводится как int
Sum([]float64{1.5, 2.5})  // T выводится как float64
Подробнее: мономорфизация vs дженерики через стирание типов deep

Компилятор Go использует гибридный подход, а не чистую мономорфизацию (как C++ шаблоны, где под каждый конкретный тип генерируется полностью отдельная копия машинного кода) и не чистое стирание типов с боксингом (как дженерики в Java до project Valhalla). Компилятор группирует типы по одинаковой «форме» (shape) — например, все указательные типы (*T для любого T) обычно разделяют одну реализацию, потому что указатель всегда занимает одинаковое количество байт и имеет одинаковое представление в памяти, а вот int и float64 получают отдельные инстанциации, так как хранятся и обрабатываются по-разному (GC-информация, размер, арифметика).

Практический вывод: дженерик-код с числовыми типами почти не уступает по скорости написанному вручную под конкретный тип, но злоупотребление дженериками с большим числом разных инстанциаций может ощутимо увеличить размер скомпилированного бинарника (каждая уникальная «форма» — это отдельный сгенерированный код).

Ограничение — обычный интерфейс, объединение типов через |, либо встроенное comparable:

constraints.go

    int | int64 | float64 // union constraint
}

func Sum[T Number](nums []T) T { /* … */ }

func Equal[T comparable](a, b T) bool {
    return a == b // comparable разрешает == и !=

Подробнее: миф «встроенные min/max работают только для float» medium

Эта формулировка до сих пор кочует по некоторым разборам вопросов для собеседований как актуальный факт — но начиная с Go 1.21 она устарела.

Так что правильный на сегодня ответ на собеседовании — «нужно писать свою реализацию для int» был верен до версии 1.21 (2023) и устарел с её выходом; актуальный факт — билтины min/max универсальны по любому упорядочиваемому типу. (миф — habr.com / folko.gitbook.io; уточнено по официальным release notes tip.golang.org/doc/go1.21)

9.4Обобщённые типы

stack.go
type Stack[T any] struct {
    items []T
}

func (s *Stack[T]) Push(v T) {
    s.items = append(s.items, v)
}

func (s *Stack[T]) Pop() (T, bool) {
    var zero T
    if len(s.items) == 0 {
        return zero, false
    }
    v := s.items[len(s.items)-1]
    s.items = s.items[:len(s.items)-1]
    return v, true
}

var s Stack[int]
s.Push(1)
s.Push(2)
v, ok := s.Pop() // 2, true
собес

Зачем var zero T? Внутри обобщённого кода нельзя написать литерал вроде 0 или "" — компилятор не знает конкретный тип T заранее. var zero T — стандартный способ получить zero value любого T.

камень

У метода нельзя завести собственный, независимый параметр типа — только тот, что уже объявлен у получателя ((s *Stack[T])). Если нужен ещё один параметр типа — это должна быть отдельная функция, а не метод.

Подробнее: несколько параметров типа и вывод типов medium

Параметров типа может быть несколько — например, обобщённая мапа с произвольными ключом и значением: type Pair[K comparable, V any] struct { Key K; Value V }. Компилятор старается вывести все параметры типа из аргументов вызова автоматически (как в примере Sum([]int{...}) выше), но если тип нельзя однозначно вывести — например, при вызове функции без аргументов, использующих T, — параметр указывают явно: New[int]().

На практике обобщённые типы данных (стеки, очереди, связные списки, деревья, кэши с обобщённым значением) — самое частое применение дженериков в реальном коде, наравне с обобщёнными хелперами вроде Map/Filter/Reduce над срезами.

Подробнее: почему Builder быстрее, и разница строка/[]byte/[]rune deep

strings.Builder внутри — просто растущий []byte (с той же логикой роста, что и у слайсов, глава 4), плюс защита от копирования через встроенный noCopy-детектор (паника при go vet, если Builder скопировали по значению после первой записи). Ещё один частый вопрос на собеседовании — разница между []byte(s) и []rune(s): строка в Go — это последовательность байт в UTF-8, а не рун. []byte(s) просто копирует сырые байты (длина совпадает с len(s)); []rune(s) декодирует UTF-8 и даёт по одному элементу на кодовую точку Unicode — для строки с кириллицей или эмодзи len([]rune(s)) обычно меньше, чем len(s), потому что не-ASCII символы занимают 2–4 байта, но всего одну руну. Индексирование строки s[i] всегда возвращает байт, а не символ — для посимвольного (по рунам) прохода нужен for i, r := range s или явное приведение к []rune.

Подробнее: time.Time vs time.Duration, и почему нельзя сравнивать время через == medium

time.Duration — это просто int64-наносекунды с собственным типом и методом String() (отсюда красивый вывод вроде 1h30m0s), а time.Time — структура, хранящая момент времени с точностью до наносекунды плюс информацию о часовом поясе (*time.Location) и, для времён, полученных через time.Now(), ещё monotonic-компонент — отдельный «счётчик тиков» ядра, не привязанный к настенным часам.

Именно из-за monotonic-компонента t1 == t2 для двух значений time.Time — плохая идея: у двух логически одинаковых моментов может отличаться представление часового пояса или отсутствовать monotonic-часть (например, после Round/десериализации), и == сравнит все поля структуры буквально. Правильный способ сравнения — метод t1.Equal(t2), который сравнивает именно момент времени, игнорируя представление зоны; для упорядочивания — t1.Before(t2) / t1.After(t2).

os.Exit(code) завершает процесс немедленно — в отличие от обычного выхода из main(), он не выполняет отложенные defer ни в текущей, ни в других горутинах: если в коде есть defer file.Close() или defer wg.Wait(), они просто не сработают при вызове os.Exit.     return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        start := time.Now()
        next.ServeHTTP(w, r)
        log.Printf("%s %s — %v", r.Method, r.URL.Path, time.Since(start))

}

11.1Базовый тест

func TestAdd(t *testing.T) {

собес

t.Errorf vs t.Fatalf? Errorf помечает тест проваленным и продолжает выполнение (можно собрать несколько ошибок за один прогон), Fatalf сразу останавливает текущий тест — используйте его, когда без прерванного шага (например, без успешного открытия файла) продолжать бессмысленно.

Подробнее: почему Fatalf нельзя вызывать не из горутины теста deep

t.Fatalf (и t.FailNow, на котором он основан) внутри вызывает runtime.Goexit() — специальную функцию, которая завершает текущую горутину, предварительно прогнав все её defer, но не завершая всю программу. Именно поэтому Fatalf нельзя вызывать из горутины, запущенной внутри теста (например, воркера), а не из горутины самого теста — Goexit просто «убьёт» ту горутину, где был вызван, но не остановит и не провалит тест из горутины, где он в реальности исполняется; в лучшем случае это приведёт к зависшему тесту или гонке на завершении, а не к ожидаемой ошибке.

Практическое правило: t.Fatal/t.FailNow вызываются только из той же горутины, в которой выполняется тело TestXxx (или его подтеста, запущенного через t.Run). Если ошибку нужно сообщить из воркер-горутины — используют канал с результатом или t.Errorf после wg.Wait() в основной горутине теста.

11.2Table-driven tests

Де-факто стандарт в Go: один кейс — одна строка таблицы, t.Run даёт каждому кейсу свой независимый подтест:

table_test.go
func TestAdd(t *testing.T) {
    tests := []struct {
        name string
        a, b int
        want int
    }{
        {"положительные", 2, 3, 5},
        {"с нулём", 0, 5, 5},
        {"отрицательные", -1, -1, -2},
    }

    for _, tt := range tests {
        t.Run(tt.name, func(t *testing.T) {
            got := Add(tt.a, tt.b)
            if got != tt.want {
                t.Errorf("Add(%d, %d) = %d, хотим %d", tt.a, tt.b, got, tt.want)
            }
        })
    }
}
собес

Зачем именно так? Новый кейс — это одна строка в срезе, а не новая функция. t.Run(tt.name, …) даёт каждому кейсу отдельное имя в выводе — сразу видно, какой конкретно провалился, и можно перезапустить только его через -run.

камень

Тот же подвох, что и с range в горутинах (глава 2): до Go 1.22 переменную цикла tt нужно было перехватывать явно (tt := tt) внутри тела, иначе при запуске подтестов параллельно (t.Parallel()) все они видели последнее значение tt. С 1.22 каждая итерация получает свою копию.

Подробнее: t.Parallel() и golden-файлы medium

Вызов t.Parallel() первой строкой внутри тела подтеста сигнализирует go test, что этот подтест можно выполнять параллельно с другими такими же подтестами — сам родительский тест при этом приостанавливается до тех пор, пока не будут запущены все его подтесты, после чего они реально исполняются одновременно (ограничено флагом -parallel, по умолчанию равным GOMAXPROCS). Это ускоряет большие table-driven наборы, но требует, чтобы кейсы были независимы друг от друга и не делили изменяемое состояние без синхронизации.

Для тестов со сложным ожидаемым выводом (сгенерированный код, большой JSON/HTML-ответ) вместо литералов в самом тесте часто используют golden-файлы — эталонный вывод сохраняют в отдельный файл (testdata/case.golden) и сравнивают фактический результат с его содержимым; флаг вида -update (соглашение, не встроено в testing) позволяет перегенерировать golden-файлы одной командой при осознанном изменении ожидаемого поведения.

Флаг -benchmem добавляет в вывод бенчмарка число аллокаций на операцию (allocs/op) и байт на операцию (B/op) — часто именно эти две цифры интереснее сырого времени, потому что аллокации напрямую нагружают GC. Опасность, о которой часто спрашивают: компилятор умеет заметить, что результат вызова внутри цикла бенчмарка нигде не используется, и убрать сам вызов через dead code elimination — тогда бенчмарк «измеряет» пустой цикл и врёт о производительности. Выбор между ручным fake и сгенерированным mock — это компромисс между простотой/читаемостью и точностью контроля над поведением зависимости в тесте.

HTTP-сервер

Мини-проект, который собирает вместе структуры, методы, мьютексы, JSON и net/http из прошлых глав — простой REST API для списка задач.

12.1Модель и хранилище

In-memory хранилище на map, защищённое мьютексом (глава 8) — вместо настоящей БД, но с тем же принципом:

store.go
type Task struct {
    ID   int    `json:"id"`
    Text string `json:"text"`
    Done bool   `json:"done"`
}

type Store struct {
    mu     sync.Mutex
    tasks  map[int]Task
    nextID int
}

func NewStore() *Store {
    return &Store{tasks: make(map[int]Task), nextID: 1}
}

func (s *Store) Add(text string) Task {
    s.mu.Lock()
    defer s.mu.Unlock()
    t := Task{ID: s.nextID, Text: text}
    s.tasks[t.ID] = t
    s.nextID++
    return t
}

func (s *Store) All() []Task {
    s.mu.Lock()
    defer s.mu.Unlock()
    out := make([]Task, 0, len(s.tasks))
    for _, t := range s.tasks {
        out = append(out, t)
    }
    return out
}

func (s *Store) Get(id int) (Task, bool) {
    s.mu.Lock()
    defer s.mu.Unlock()
    t, ok := s.tasks[id]
    return t, ok
}
Подробнее: почему All() возвращает копии, а не ссылку на карту medium

All() собирает срез из значений карты внутри критической секции и возвращает уже готовый срез — это принципиально: если бы метод возвращал саму карту s.tasks по ссылке, вызывающий код мог бы читать и писать её уже вне мьютекса, что превратило бы весь механизм защиты в фикцию (см. главу 8 про гонки данных). Возврат копии данных, а не доступа к внутреннему состоянию — стандартный способ безопасно «выпустить» защищённые мьютексом данные наружу.

Этот же Store — простая иллюстрация паттерна repository: обработчики HTTP ничего не знают о том, что данные лежат в map в памяти, а не в PostgreSQL — они видят только методы Add/All/Get. Замена map на реальную БД в проде не потребует менять код обработчиков вообще, если интерфейс хранилища выделить отдельно (см. 11.4, тестируемость через интерфейсы).

12.2Обработчики

handlers.go
type API struct{ store *Store }

func (a *API) listTasks(w http.ResponseWriter, r *http.Request) {
    w.Header().Set("Content-Type", "application/json")
    json.NewEncoder(w).Encode(a.store.All())
}

func (a *API) createTask(w http.ResponseWriter, r *http.Request) {
    var in struct{ Text string `json:"text"` }
    if err := json.NewDecoder(r.Body).Decode(&in); err != nil {
        http.Error(w, "некорректный JSON", http.StatusBadRequest)
        return
    }
    task := a.store.Add(in.Text)
    w.WriteHeader(http.StatusCreated)
    json.NewEncoder(w).Encode(task)
}

func (a *API) getTask(w http.ResponseWriter, r *http.Request) {
    id, err := strconv.Atoi(r.PathValue("id"))
    if err != nil {
        http.Error(w, "некорректный id", http.StatusBadRequest)
        return
    }
    task, ok := a.store.Get(id)
    if !ok {
        http.Error(w, "не найдено", http.StatusNotFound)
        return
    }
    json.NewEncoder(w).Encode(task)
}
Подробнее: почему Content-Type нужно ставить до WriteHeader deep

Первый вызов w.Write(...) (или неявный первый вызов внутри json.NewEncoder(w).Encode(...)) неявно посылает статус-код 200 OK, если WriteHeader ещё не был вызван явно, — и в этот момент фиксируются все заголовки, выставленные к тому моменту. Установка заголовка (w.Header().Set(...)) после первой записи в тело ответа ни на что не повлияет — заголовки уже отправлены клиенту. Поэтому в listTasks заголовок ставится первой строкой, а в createTask порядок ещё строже: WriteHeader(http.StatusCreated) вызывается явно и до Encode, иначе тело ответа отправило бы неявные 200 вместо нужного 201.

Ещё один частый промах в таком коде: ошибка от json.NewEncoder(w).Encode(...) в конце обработчика почти никогда не проверяется — на практике к этому моменту заголовки уже отправлены, и сделать полноценный http.Error уже нельзя, поэтому обычно её как минимум логируют, а не молча игнорируют.

Подробнее: http.Handler vs http.HandlerFunc, и чем плох nil вторым аргументом в ListenAndServe medium

http.Handler — интерфейс с единственным методом ServeHTTP(w http.ResponseWriter, r *http.Request). Методы a.listTasks/a.createTask выше — обычные функции с такой сигнатурой, а не значения, реализующие интерфейс напрямую; связывает их с интерфейсом тип-обёртка http.HandlerFunc — она сама реализует ServeHTTP, просто вызывая себя как функцию. Именно поэтому mux.HandleFunc(...) (принимающий обычную функцию) и mux.Handle(...) (принимающий готовый Handler) — по сути один и тот же механизм с разным уровнем адаптации.

Отдельная ловушка — вызов http.ListenAndServe(addr, nil) с nil вместо явного мультиплексора: тогда используется http.DefaultServeMux — единый глобальный экземпляр роутера пакета net/http, в который пишет любой импортированный в процесс пакет, вызвавший пакетные функции http.HandleFunc/http.Handle (в том числе сторонние зависимости, регистрирующие туда отладочные хендлеры). В отличие от кода выше, явно создающего свой mux := http.NewServeMux(), использование DefaultServeMux в проде считается плохой практикой — риск незаметного конфликта путей между независимыми частями кода и невозможность держать несколько независимых серверов в одном процессе. (источник: t.me/go_interview_lib)

Свежая деталь: запись метода прямо в паттерне ("GET /tasks") и path-параметры вроде {id} с r.PathValue("id") — это возможности http.ServeMux, добавленные в Go 1.22. До этого стандартный роутер не различал методы и параметры пути — ради этого тянули сторонние библиотеки (chi, gorilla/mux).

Подробнее: почему до 1.22 тянули chi/gorilla, и приоритет более конкретного паттерна medium

До Go 1.22 http.ServeMux умел маршрутизировать только по точному совпадению пути или по префиксу, заканчивающемуся на / (например, "/tasks/" ловил всё, что начинается с этого префикса), и совсем не различал HTTP-методы — GET /tasks и POST /tasks обрабатывались бы одним и тем же паттерном "/tasks", а различать методы и вытаскивать path-параметры ({id}) приходилось руками внутри обработчика (r.Method == "GET", ручной парсинг r.URL.Path) или сторонними роутерами вроде gorilla/mux и chi, которые умели это из коробки. С 1.22 методы и {param} вошли в сам стандартный http.ServeMux, и многим проектам сторонний роутер стал не нужен вообще.

Когда несколько зарегистрированных паттернов могут совпасть с одним и тем же запросом, побеждает более конкретный — например, "GET /tasks/{id}" выигрывает у "GET /tasks/" для запроса GET /tasks/7, даже если оба зарегистрированы. Специальный синтаксис {id...} (с многоточием) ловит «хвост» пути произвольной длины — аналог wildcard-сегмента в сторонних роутерах.

Подробнее: graceful shutdown целиком deep

Grace­ful shutdown — это остановка сервера, при которой уже принятые запросы успевают доработать, а новые соединения перестают приниматься сразу после сигнала завершения. http.Server.Shutdown(ctx) делает именно это: закрывает слушающий сокет (новые соединения больше не принимаются), но ждёт завершения уже идущих обработчиков, пока не истечёт дедлайн переданного context.Context — если дедлайн истекает раньше, чем все обработчики закончили, Shutdown возвращает ошибку контекста, а незавершённые соединения обрываются принудительно.

graceful.go
srv := &http.Server{Addr: ":8080", Handler: mux}

go func() {
    if err := srv.ListenAndServe(); err != nil && err != http.ErrServerClosed {
        log.Fatalf("ListenAndServe: %v", err)
    }
}()

stop := make(chan os.Signal, 1)
signal.Notify(stop, syscall.SIGINT, syscall.SIGTERM)
<-stop // блокируемся, пока не придёт сигнал

ctx, cancel := context.WithTimeout(context.Background(), 10*time.Second)
defer cancel()
if err := srv.Shutdown(ctx); err != nil {
    log.Printf("принудительное завершение: %v", err)
}

Важная деталь: сам ListenAndServe() нужно запускать в отдельной горутине именно потому, что он блокирует вызывающую горутину до остановки сервера — если запустить его в основной горутине, код после него (ожидание сигнала, вызов Shutdown) никогда не выполнится. После успешного Shutdown, ListenAndServe в фоновой горутине вернёт специальную, ожидаемую ошибку http.ErrServerClosed — её явно исключают из «настоящих» ошибок, иначе штатная остановка сервера выглядела бы как сбой.

Код выше — «ручной» вариант через signal.Notify и отдельный канал. Более современная альтернатива — signal.NotifyContext (с Go 1.16): ctx, stop := signal.NotifyContext(context.Background(), os.Interrupt, syscall.SIGTERM) сразу возвращает обычный context.Context, который отменяется при получении сигнала, — тогда весь остальной код (в том числе части, уже написанные с оглядкой на ctx.Done(), например через errgroup) реагирует на завершение единым образом, без отдельного канала сигналов и ручного select. Обязателен defer stop() сразу после получения — он освобождает регистрацию обработчика сигнала в рантайме; без него регистрация продолжает висеть до конца процесса. (источник: t.me/go_interview_lib)

Подробнее: SQL-инъекция и XSS — минимально необходимая защита medium

«Более строгая валидация входных данных», упомянутая выше, на практике в первую очередь означает защиту от двух классических атак.

От SQL-инъекции защищают исключительно параметризованные запросы — плейсхолдеры ($1 в PostgreSQL, ? в MySQL/SQLite), где значения передаются драйверу отдельно от текста запроса, а не подставляются в строку конкатенацией или через fmt.Sprintf. Драйвер и СУБД в этом случае гарантированно интерпретируют переданное значение как данные, а не как часть SQL-синтаксиса, какие бы кавычки или ключевые слова оно ни содержало.

От XSS (внедрения чужого JS/HTML через пользовательский ввод, впоследствии отображаемый другим пользователям) защищает контекстно-зависимое экранирование при рендеринге. Стандартный пакет html/template делает это автоматически — экранирует значение по-разному в зависимости от того, куда именно оно подставляется в шаблоне (тело HTML-тега, атрибут, URL, встроенный <script>). Пакет text/template с виду тождественен по API, но не экранирует ничего вообще — использовать его для генерации HTML-страниц из непроверенных пользовательских данных небезопасно, это только для обычного текстового вывода. (источник: t.me/go_interview_lib)

Подробнее: инициализмы, и почему не GetName() medium

Официальный гайд Go по именованию требует единый регистр для инициализмов целиком: URL, ID, HTTP, API — а не Url, Id. Отсюда userID, ServeHTTP, parseURL — и характерная проблема при переходе с других языков, где принято Id/Url. golangci-lint и staticcheck отдельно проверяют это правило (линтер ST1003/revive).

Отказ от префикса Get для геттеров — тоже не случайность, а официальная рекомендация: если метод Name() просто возвращает поле без побочных эффектов, приставка Get ничего не добавляет к пониманию кода и только удлиняет каждый вызов. Исключение — когда операция реально что-то «получает» с side-эффектом (сходить в сеть, за файл), там `Get`-подобное имя уместно, потому что сигнализирует, что вызов не бесплатный.

13.2Accept interfaces, return structs

accept.go
// хорошо: принимает узкий интерфейс — подойдёт любой источник данных
func Copy(dst io.Writer, src io.Reader) (int64, error)

// хуже: требует конкретный тип, хотя нужен только один метод
func Save(f *os.File, data []byte) error

Принимая интерфейс, функция работает с чем угодно, реализующим нужное поведение — включая фейки в тестах (глава 11). Возвращая конкретный тип, а не интерфейс, вы даёте вызывающему доступ ко всем его методам, а не только к урезанному подмножеству.

Подробнее: почему возврат интерфейса «на будущее» обычно вредит medium

Соблазн вернуть интерфейс из конструктора («а вдруг понадобится другая реализация») на практике почти всегда лишний: вызывающий код теряет доступ к конкретным методам и полям возвращаемого типа, которых нет в интерфейсе, а сам интерфейс приходится расширять при каждом новом методе — то есть интерфейс, объявленный «на стороне поставщика», в итоге пытается предугадать все нужды потребителей и либо разрастается, либо режет функциональность. Согласуется с идиомой из главы 6 («interface declared on consumer side»): именно потребитель кода должен объявить у себя узкий интерфейс под свои нужды, а не поставщик — заранее «широкий» интерфейс от поставщика.

Практическое правило: возвращать интерфейс из функции стоит только тогда, когда действительно нужно скрыть за одной сигнатурой несколько взаимозаменяемых реализаций уже сейчас (фабрика, возвращающая разные бэкенды по конфигу) — а не «про запас».

Подробнее: SOLID применительно к Go — без классов, но не без принципов medium

В Go нет классов и наследования, но все пять принципов SOLID переносятся на структуры/интерфейсы почти без искажений:

ПринципКак выглядит в Go
S — Single Responsibilityпакет или тип решает одну узкую задачу и решает её хорошо — в духе Unix-философии, а не «богатого» типа на всё сразу
O — Open/Closedкод открыт расширению через добавление новой реализации интерфейса и закрыт для модификации уже написанных и протестированных реализаций
L — Liskov Substitutionбез иерархии классов принцип превращается в требование к контракту интерфейса: реализация не должна вести себя так, что нарушает ожидания вызывающего кода (не паниковать там, где интерфейс это не предполагает, не менять смысл метода)
I — Interface Segregationровно идиома этой главы (13.2, выше) — маленькие интерфейсы на стороне потребителя лучше одного большого «на все случаи»
D — Dependency Inversionзависеть от интерфейсов, а не от конкретных реализаций; зависимости явно передаются через конструктор (constructor injection), а не создаются внутри самого типа

На практике I и D в Go получаются «бесплатно» из-за самой структурной типизации и идиомы «интерфейс объявляется у потребителя» (глава 6.3) — именно поэтому Go-код часто выглядит SOLID-совместимым, даже когда никто сознательно не следовал этой аббревиатуре. (источник: habr.com/ru/articles/658623/)

Подробнее: gofmt работает по AST, а не по текстовым правилам deep

Подробнее: internal/, layout проекта и циклические импорты deep

Каталог с зарезервированным именем internal/ — единственный механизм видимости пакетов на уровне модуля, встроенный прямо в тулчейн: пакет myapp/internal/db можно импортировать только из кода, лежащего внутри myapp (точнее — внутри дерева, корень которого — родитель internal); попытка импортировать его из другого модуля — ошибка компиляции, а не просто соглашение об именовании. Циклический импорт (пакет A импортирует B, а B — A) — ошибка компиляции, а не предупреждение; типичное лечение — выделить общий код, от которого зависят оба, в третий пакет, либо объединить A и B в один пакет, если они настолько тесно связаны, что тянут друг на друга.

14.1Индексы БД и диагностика медленных запросов

Индекс — вспомогательная структура, ускоряющая поиск ценой дополнительной памяти и замедления записи (индекс тоже обновляется при каждом INSERT/UPDATE/DELETE):

Тип индексаКогда применим
B-tree (B+tree)индекс по умолчанию, O(log n), поддерживает диапазоны и сортировку — универсальный выбор для большинства колонок
HashO(1) в среднем, но только точное совпадение — не поддерживает диапазоны
GiST / R-treeпространственные/геометрические данные — «что рядом» (GIS)
GINполнотекстовый поиск, массивы, JSONB — инвертированный индекс
BRINочень большие таблицы с физической корреляцией значения и порядка на диске (типично — временные ряды); на порядки компактнее B-tree
Bitmapнизкая кардинальность (пол/статус); плохо ведёт себя под конкурентной записью — область OLAP

Отдельно — покрывающий индекс (CREATE INDEX ... (col) INCLUDE (a, b)) даёт index-only scan без обращения к таблице, а частичный индекс (WHERE в самом индексе) строится только по нужному подмножеству строк.

explain.sql
EXPLAIN ANALYZE
SELECT * FROM orders WHERE user_id = 42;
-- Seq Scan (сканирование всей таблицы) на большой таблице — тревожный знак
-- Index Scan / Index Only Scan — индекс используется
-- сильное расхождение оценки и факта — устаревшая статистика, нужен ANALYZE

Индекс есть, а не используется — почему? Частая причина — не-SARGable условие: функция над колонкой в условии (WHERE UPPER(email) = 'X') мешает использовать обычный индекс по этой колонке без отдельного функционального индекса; вторая частая причина — несовпадение типов данных в сравнении.

Подробнее: воронка диагностики медленной БД — от дешёвого к дорогому deep

Показательный порядок ответа на собесе «прод тормозит на БД, с чего начать» — не хаотичный список техник, а последовательность от дешёвых точечных решений к дорогим архитектурным: (1) проверить индексы через EXPLAIN/EXPLAIN ANALYZE; (2) оптимизировать сами запросы (не SELECT *, устранить N+1); (3) тюнинг параметров СУБД (shared_buffers, work_mem); (4) HDD→SSD, если узкое место — диск; (5) партиционирование по дате/диапазону; (6) репликация (read-реплики); (7) шардирование; (8) кэширование (Redis/Memcached) перед БД; (9) денормализация схемы; (10) специализированное хранилище под конкретный паттерн доступа (колоночное — для аналитики, time-series — для метрик). Переход сразу к шардированию до того, как исчерпаны более дешёвые шаги — типичная поспешность, которую интервьюеры отдельно отмечают.

Расширенный вызов EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON) дополнительно показывает статистику буферного кэша (сколько страниц прочитано из shared_buffers против диска) и отдаёт план в JSON для автоматического парсинга. Поскольку EXPLAIN ANALYZE реально выполняет запрос — для INSERT/UPDATE/DELETE это значит реальное изменение данных; безопасный способ снять план без побочных эффектов — обернуть в BEGIN; EXPLAIN ANALYZE ...; ROLLBACK;.

14.2Транзакции и уровни изоляции (ACID)

Транзакция — атомарная единица работы: либо целиком COMMIT, либо целиком ROLLBACK. ACID: Atomicity, Consistency, Isolation, Durability.

Уровень изоляцииЧто допускает
Read Uncommittedвидны незакоммиченные данные («грязное чтение») — в PostgreSQL синтаксически принимается, но реально работает как Read Committed
Read Committed (дефолт в PostgreSQL)видны только закоммиченные данные, но повторное чтение той же строки может дать другой результат

Классический пример — денежный перевод. Списание с одного счёта и зачисление на другой должны либо оба применяться, либо ни один. Практический совет: defer tx.Rollback() сразу после открытия транзакции — надёжнее против забытых веток отката, чем расставлять его вручную по каждой ошибке.

Подробнее: MVCC на уровне строки — xmin/xmax deep

Каждая физическая версия строки в PostgreSQL несёт служебные поля xmin (ID транзакции, создавшей эту версию) и xmax (ID транзакции, пометившей версию устаревшей, если применимо). Читающая транзакция видит только те версии, чей xmin завершился раньше начала её собственного снэпшота, и чей xmax либо не установлен, либо принадлежит ещё не завершившейся транзакции. Именно за счёт этого читатели работают с согласованным снэпшотом, вообще не блокируя писателей (и наоборот) — а старые версии с уже неактуальным xmax остаются на диске до прохода VACUUM (те самые dead tuples).

И Repeatable Read, и Serializable в PostgreSQL реализованы через единый механизм SSI (Serializable Snapshot Isolation) — Serializable дополнительно отслеживает предикатные блокировки поверх снэпшота, чтобы ловить и фантомные аномалии. Практический ориентир: Read Committed достаточен для типичной OLTP-нагрузки, более высокие уровни — там, где цена ошибки высока (финансы/биллинг), с обязательным retry при ошибке сериализации (код 40001) на прикладном уровне.

14.3Блокировки: pessimistic vs optimistic

locking.sql
-- пессимистичная: блокирует строку сразу, на всё время транзакции
SELECT balance FROM accounts WHERE id = $1 FOR UPDATE;

-- оптимистичная: конфликт обнаруживается только в момент записи
UPDATE accounts
SET balance = $1, version = version + 1
WHERE id = $2 AND version = $3;
камень

Если оптимистичный UPDATE вернул RowsAffected() == 0 — значит кто-то другой уже обновил эту строку между чтением и записью; приложение обязано перечитать актуальное состояние и повторить попытку, а не считать это обычной ошибкой.

Подробнее: почему для баланса счёта не всегда нужен Serializable deep

Контраргумент для конкретно банковского сценария «списать деньги со счёта» — не всегда правильный ответ «бери уровень построже». Для точечного изменения баланса одного известного счёта часто предпочтительнее именно Read Committed (дефолт) в сочетании с явной блокировкой конкретной строки через SELECT balance FROM accounts WHERE id = $1 FOR UPDATE перед проверкой достаточности средств — блокировка ложится точно на нужную строку, конкурентные транзакции над другими счетами продолжают работать без взаимных помех, и не возникает ошибок сериализации, которые пришлось бы ретраить целиком на уровне приложения при более строгом уровне изоляции.

Дополнительная защитная мера на уровне самой схемы — ограничение CHECK (balance >= 0) прямо на колонке баланса: отдельный барьер против ухода в минус, не зависящий от прикладной логики, даже при ошибке в коде приложения. Пессимистичная блокировка при захвате нескольких строк разными транзакциями рискует дедлоком — стандартное лечение то же, что и для мьютексов (глава 8): фиксированный глобальный порядок захвата.

Подробнее: cache stampede и защита через SET NX / singleflight deep

При истечении TTL популярного ключа множество параллельных запросов одновременно промахиваются мимо кэша и все синхронно бьют в БД («эффект грозовой тучи», thundering herd). Два рабочих способа защиты: на уровне процесса — golang.org/x/sync/singleflight схлопывает несколько одновременных запросов одного и того же ключа в один реальный поход за данными; на уровне распределённого кэша — атомарная установка ключа-«замка» SET key value NX (только если ключа ещё нет), дающая ровно одному инстансу право пойти в БД, пока остальные ждут или отдают чуть устаревшее значение.

singleflight.go
var g singleflight.Group

func GetUserData(ctx context.Context, id string) (Result, error) {
    v, err, _ := g.Do(id, func() (interface{}, error) {
        return doFetch(ctx, id) // реально выполнится только один раз на все параллельные вызовы с этим id
    })
    return v.(Result), err
}

Многоуровневое кэширование — L1 (in-memory, sync.Map или ristretto/bigcache) для самых горячих данных с TTL и лимитом объёма, L2 (Redis/Memcached) — общий на все инстансы сервиса, чтобы реплики не дублировали одни и те же дорогие запросы. Негативное кэширование (кратковременно кэшировать и сами ошибки вроде 404) экономит повторные обращения за заведомо несуществующим ресурсом.

Подробнее: Dead Letter Queue и надёжность продюсера deep

Наивное «залогировать ошибку и продвинуть offset дальше» означает молчаливую потерю сообщения. Паттерн Dead Letter Queue: проблемное сообщение публикуется в отдельный топик-DLQ с сохранением исходного контекста (топик/партиция/offset оригинала, текст ошибки, счётчик попыток), а не отбрасывается. Важное разграничение перед retry: фатальная ошибка (неразбираемый формат — повторная попытка не поможет, сразу в DLQ) против временной (сетевой таймаут — ограниченное число ретраев с растущей задержкой, прежде чем уйти в DLQ). Offset коммитится только после успешной обработки или осознанной отправки в DLQ.

Настройки надёжности продюсера: min.insync.replicas — минимальное число реплик-подтверждений записи перед тем, как она считается зафиксированной; enable.idempotence=true — присваивает сообщениям порядковые номера и защищает от дублей при внутренних ретраях самого продюсера после сетевого сбоя (это защита именно от дублей на уровне транспорта, а не замена идемпотентности потребителя). Kafka-транзакции дают атомарную запись сразу в несколько партиций/топиков одним махом.

14.6Transactional Outbox и идемпотентность

Проблема двойной записи (dual write): нельзя атомарно и записать в БД, и опубликовать в Kafka одной операцией — при сбое между двумя шагами возможна либо потеря события, либо публикация без соответствующего изменения в БД.

outbox.sql
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
INSERT INTO outbox (aggregate_id, event_type, payload, status)
VALUES (1, 'BalanceChanged', '{"delta": -100}', 'pending');
COMMIT;
-- отдельный фоновый процесс вычитывает outbox и публикует в Kafka:
SELECT * FROM outbox WHERE status = 'pending'
  ORDER BY created_at FOR UPDATE SKIP LOCKED LIMIT 100;
собес

Идемпотентный ключ: клиент сам генерирует UUID конкретной попытки операции и передаёт с каждым запросом, включая повторные. Сервер при первом получении ключа выполняет операцию и сохраняет результат вместе с ключом; при повторном — сразу возвращает сохранённый результат. В PostgreSQL — атомарно через INSERT ... ON CONFLICT (idempotency_key) DO NOTHING.

Подробнее: FOR UPDATE SKIP LOCKED и альтернатива через CDC deep

FOR UPDATE SKIP LOCKED — ключевой приём для горизонтального масштабирования нескольких инстансов relay-процесса без дублирования работы: каждый инстанс блокирует и забирает свою порцию строк, не мешая другим, вместо конкуренции за одни и те же строки. Тот же приём применим к любой задаче «несколько инстансов безопасно разбирают общий пул задач без гонки» — предпочтительнее хрупких схем разбиения по offset/диапазону между инстансами, поскольку не требует заранее фиксировать, какой инстанс какой диапазон обрабатывает.

Полноценный exactly-once для outbox достижим либо через транзакционный API самой Kafka, либо через переход на CDC (Change Data Capture, например Debezium) — при CDC отдельная outbox-таблица и polling вообще не нужны: инструмент читает журнал транзакций самой БД (WAL в PostgreSQL) напрямую и публикует события из него, снимая накладные расходы на ручной polling.

idempotent_handler.go
existing, err := s.repo.GetByHash(ctx, tx.Hash)
if err != nil && !errors.Is(err, sql.ErrNoRows) {
    return fmt.Errorf("get tx: %w", err)
}
if existing != nil {
    return nil // уже обработано — идемпотентный no-op
}

Здесь ключом идемпотентности выступает хэш самой транзакции (естественно уникальный для данных), а не отдельно сгенерированный UUID попытки — уместно, когда доменная сущность уже несёт достаточно уникальности сама по себе.

Рантайм Go по умолчанию видит все ядра хост-машины и выставляет GOMAXPROCS под них, даже если контейнеру по cgroup-лимиту выделена лишь часть CPU — рантайм создаёт больше системных потоков, чем реально может исполняться под квотой, что даёт CPU throttling. Решение — _ "go.uber.org/automaxprocs": автоматически считывает реальный cgroup-лимит и выставляет GOMAXPROCS под него при старте.

Подробнее: как выглядит throttling на метриках, и OOM Killer deep

Throttling по cgroup CFS-квоте не линейно замедляет, а даёт скачкообразные задержки сразу по всем горутинам процесса — весь процесс «замирает» до начала следующего периода квоты. Конкретные метрики диагностики: container_cpu_cfs_throttled_periods_total (сколько периодов планирования контейнер был принудительно приторможен) и container_cpu_cfs_throttled_seconds_total (суммарное время в throttled-состоянии) — рост этих метрик при внешне невысокой средней загрузке CPU однозначно указывает на троттлинг, а не на общую нехватку ресурсов. Практический ориентир — резервировать 10–20% CPU-бюджета сверх заявленного GOMAXPROCS, а не выставлять лимиты впритык.

Отдельная подсистема — OOM Killer: когда физическая память (с учётом cgroup-лимита) исчерпана, ядро Linux завершает процесс-жертву (SIGKILL) по показателю oom_score; в Kubernetes это видно как OOMKilled в статусе контейнера. Throttling и OOM Killer работают на разных уровнях (планировщик CPU vs подсистема памяти ядра) и требуют разных метрик для диагностики: throttling не убивает процесс, лишь замедляет, OOM Killer убивает безвозвратно.

RED vs USE? RED (Rate/Errors/Duration) — методология для сервисов-запросчиков; USE (Utilization/Saturation/Errors) — для ресурсов (диск, CPU, память). Prometheus работает по pull-модели — сам с заданным интервалом опрашивает /metrics-эндпоинт каждого инстанса.

Подробнее: Histogram vs Summary, и опасность высокой кардинальности лейблов deep

Для измерения задержки операции предпочтительнее Histogram, а не Summary: Histogram считает попадания в заранее заданные бакеты и позволяет агрегировать перцентили постфактум на стороне сервера запросов — можно пересчитать p95/p99 по любому окну и просуммировать данные с разных инстансов. Summary считает квантили уже на стороне клиента метрики в момент наблюдения — они не агрегируются корректно между несколькими инстансами (нельзя просто усреднить уже посчитанные на разных инстансах перцентили). Поэтому для метрик, которые нужно агрегировать по всему флоту — Histogram почти всегда предпочтительнее.

Высокая кардинальность меток (labels) — если добавить, например, user_id как label — практический риск: каждое уникальное сочетание значений labels создаёт отдельный временной ряд, и их бесконтрольный рост может исчерпать память самого Prometheus. Для распределённого трейсинга — стандарт W3C Trace Context (заголовок traceparent), сквозной correlation ID через весь путь запроса связывает конкретную строку лога с конкретным трейсом. Стратегии сэмплирования: head-based (решение принимается сразу на входе, дёшево) vs tail-based (откладывается до завершения трейса — можно осознанно оставлять именно медленные/ошибочные трейсы, но дороже по инфраструктуре).

Монолит: проще стартовать, лучше производительность (вызовы в процессе), полноценные ACID-транзакции. Микросервисы: автономность команд, гранулярное масштабирование, изоляция отказов — ценой сетевой сложности.

Stateless-сервис не хранит критичное для бизнес-логики состояние пользователя в памяти между запросами — благодаря этому его можно свободно масштабировать горизонтально и перезапускать без координированной миграции состояния (большинство прикладных backend-сервисов и должны проектироваться именно так, вынося состояние во внешнее хранилище — БД, Redis, брокер). Stateful-компоненты (сами БД, брокеры, хранилища сессий) — исключение: они обязаны хранить состояние по определению и требуют репликации и согласованной обработки отказов (кворумы, лидер-выборы).

Принципы осознанной декомпозиции монолита (в противовес дроблению «потому что модно»): доменные границы по DDD (bounded context — сервис отвечает ровно за одну связную предметную область), высокая связность внутри сервиса при слабой связанности между сервисами, независимость деплоя каждого сервиса, изоляция данных (каждый сервис владеет своей БД), разные профили масштабирования и нагрузки как повод для отдельного сервиса, изоляция отказов (сбой в одном домене не должен ронять соседние), стабильные версионированные интерфейсы между сервисами.

И CQRS, и Event Sourcing, и Saga добавляют архитектурную сложность — оправданы не по умолчанию, а именно там, где эта сложность окупается требованиями предметной области (типично — финансовые/учётные домены, где важен полный аудиторский след движений).

когда метод мутирует получателя, или тип большой/несравниваемый; если у типа есть хоть один pointer-метод, остальные обычно тоже делают pointer — иначе метод-сет неполный.
Буферизованный vs небуферизованный канал?
небуферизованный блокирует отправителя до встречного получателя; буферизованный блокирует, только когда буфер полон (отправка) или пуст (приём).
select с несколькими готовыми case?
выбор случайный, справедливость по конкретному case не гарантирована.
Как найти гонки?
go test -race / go run -race — детектор данных-рейсов во время выполнения.
Как правильно обернуть ошибку?
fmt.Errorf("контекст: %w", err), разворачивать — через errors.Is/errors.As, никогда не ==.
Что произойдёт при записи в nil map?
паника в рантайме; чтение из nil map безопасно и возвращает нулевое значение.
