Что такое «сериализация»?

Сериализация (Serialization) — процесс преобразования структуры данных в линейную последовательность байтов для дальнейшей передачи или сохранения. Сериализованные объекты можно затем восстановить (десериализовать).

В Java существует два стандартных способа сериализации: стандартная сериализация через интерфейс java.io.Serializable и «расширенная» сериализация — java.io.Externalizable.

Сериализация позволяет в определённых пределах изменять класс. Автоматически поддерживаются:

  • добавление в класс новых полей;
  • изменение полей из статических в нестатические;
  • изменение полей из транзитных в нетранзитные.
Опишите процесс сериализации/десериализации с использованием Serializable.

При использовании Serializable алгоритм сериализации с помощью рефлексии (Reflection API) выполняет:

  • запись в поток метаданных о классе (имя, SerialVersionUID, идентификаторы полей);
  • рекурсивную запись описания суперклассов до java.lang.Object (не включительно);
  • запись примитивных значений полей, начиная с самого верхнего суперкласса;
  • рекурсивную запись объектов, являющихся полями.

Ранее сериализованные объекты повторно не сериализуются — это позволяет корректно работать с циклическими ссылками.

При десериализации под объект выделяется память и поля заполняются из потока. Конструктор объекта не вызывается, однако вызывается конструктор без параметров родительского несериализуемого класса.

Как изменить стандартное поведение сериализации/десериализации?
  • Реализовать интерфейс java.io.Externalizable — логика описывается в методах writeExternal() и readExternal(). При десериализации вызывается конструктор без параметров, затем readExternal.
  • Если у сериализуемого объекта реализован один из следующих методов, механизм сериализации использует его вместо метода по умолчанию:
    • writeObject() — запись объекта в поток;
    • readObject() — чтение объекта из потока;
    • writeReplace() — замена себя другим экземпляром перед записью;
    • readResolve() — замена другого объекта на себя после чтения.
Как исключить поля из сериализации?

Для исключения полей из сериализации используется ключевое слово transient.

Что обозначает ключевое слово transient?

Поля, помеченные модификатором transient, не сериализуются.

Обычно в таких полях хранится промежуточное состояние объекта, которое проще вычислить заново, или ссылка на объект, который не требует или не может быть сериализован.

Какое влияние оказывают на сериализуемость модификаторы полей static и final?

Поля с модификатором static при стандартной сериализации не сериализуются — после десериализации значение поля не меняется. При использовании Externalizable сериализовать статическое поле можно, но не рекомендуется.

Поля с модификатором final сериализуются как обычные. Исключение — Externalizable: final поля должны быть инициализированы в конструкторе, и после этого в readExternal() изменить их значение невозможно. Для объектов с final полями используйте только стандартную сериализацию.

Как не допустить сериализацию?

Переопределить private методы для создания исключительной ситуации NotSerializableException:

private void writeObject(ObjectOutputStream out) throws IOException {
    throw new NotSerializableException();
}

private void readObject(ObjectInputStream in) throws IOException {
    throw new NotSerializableException();
}

Любая попытка записать или прочитать этот объект приведёт к исключению.

Как создать собственный протокол сериализации?

Реализовать интерфейс Externalizable, который содержит два метода:

public void writeExternal(ObjectOutput out) throws IOException;
public void readExternal(ObjectInput in) throws IOException, ClassNotFoundException;
Какая роль поля serialVersionUID в сериализации?

serialVersionUID используется для указания версии сериализованных данных.

Если не объявить явно, JVM сгенерирует его автоматически на основе метаданных класса (поля, модификаторы, интерфейсы и пр.). При изменении класса значение может измениться — при десериализации будет выброшено InvalidClassException.

Рекомендуется объявлять явно:

private static final long serialVersionUID = 20161013L;
Когда стоит изменять значение поля serialVersionUID?

При внесении в класс несовместимых изменений — например, при удалении какого-либо атрибута.

В чем проблема сериализации Singleton?

После десериализации получается другой объект — сериализация создаёт Singleton повторно, что недопустимо. Два способа избежать:

  • явный запрет сериализации (через NotSerializableException);
  • определение метода readResolve(), который возвращает существующий экземпляр вместо десериализованного.
Какие существуют способы контроля за значениями десериализованного объекта?

Реализовать интерфейс ObjectInputValidation с переопределением метода validateObject():

public class Person implements java.io.Serializable,
                               java.io.ObjectInputValidation {
    ...
    @Override
    public void validateObject() throws InvalidObjectException {
        if ((age < 39) || (age > 60))
            throw new InvalidObjectException("Invalid age");
    }
}

Также существуют способы подписывания и шифрования:

  • описать логику в writeObject() и readObject();
  • использовать javax.crypto.SealedObject для шифрования или java.security.SignedObject для подписи.
