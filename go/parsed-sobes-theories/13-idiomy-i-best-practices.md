## Чек-лист «продакшн-готовности» — 7 категорий

Типичные пробелы при переходе от «просто работающего» кода к продакшн-готовому (по разбору интервью с Head of Backend): (1) управление жизненным циклом CGo-объектов (актуально при обёртках над C-библиотеками); (2) ограничение уровня конкурентности (сколько горутин/воркеров разрешено одновременно — защита от перегрузки); (3) обработка таймаутов и контекста (`context.Context` с дедлайном на каждую операцию); (4) очистка временных файлов (гарантированная, даже при ошибке); (5) мониторинг и метрики (не просто логи, а метрики для алертинга); (6) стратегии повторных попыток при ошибках (retry с backoff — экспоненциально растущая задержка между попытками специально защищает от «лавинного эффекта», когда все клиенты разом синхронно ретраят после временного сбоя и своим валом усугубляют перегрузку сервиса, а не наивный цикл без задержки) [33]; (7) паттерн circuit breaker (защита от каскадных отказов при недоступности зависимости). Готовый каркас для чек-листа «продакшн-готовности» — хорошо ляжет в конспект отдельным пунктом от чисто языковых ошибок (shadowing, nil-map и т.п.). [5]

Ещё пара практических пунктов из этого же разряда, встреченных на живом кодинге: отсутствие хуков профилирования (`net/http/pprof` — стандартный способ на живую снять профиль CPU/памяти прямо с работающего сервиса) и явную обработку отмены через `context` в каналах/горутинах воркеров, а не только «плановое» завершение. [16]

Размер скомпилированного бинарника Go — заметно больше эквивалентного C++ (обычно несколько мегабайт даже для тривиальной программы), потому что в бинарник статически встроен весь рантайм (планировщик, сборщик мусора, поддержка рефлексии) — в противовес C++ с динамической линковкой, дающей меньший файл, но требующей совместимых системных библиотек на целевой машине при запуске. Практическое уменьшение размера — флаги линковщика `go build -ldflags="-s -w"`: `-s` убирает таблицу символов, `-w` убирает отладочную информацию DWARF — компромисс в обмен на потерю читаемых имён символов/полноценной отладки через `delve` на итоговом бинарнике, обычно приемлемый именно для прод-сборки (в отличие от сборки для локальной отладки). [60]

Отдельный, менее известный инструмент профилирования из той же стандартной поставки — `go trace` (пакет `runtime/trace`): в отличие от `pprof` (агрегированная статистика — сколько времени/памяти суммарно ушло куда) `trace` строит подробную временную шкалу конкретного запуска — активность каждого OS-потока и логического процессора (P), моменты блокировки/пробуждения горутин, фазы сборщика мусора, сетевые/синхронизационные блокировки — то есть годится именно для разбора конкретной аномалии («почему вот эта горутина зависла именно тут»), а не для агрегированного «где горячо». Запуск — программно (`trace.Start(f)`/`trace.Stop()` в коде), через флаг тестов (`go test -trace=file.out`) либо на живом сервисе с уже подключённым `net/http/pprof` — эндпоинт `curl http://localhost:6060/debug/pprof/trace?seconds=5` снимает трейс за N секунд без перезапуска процесса; просмотр — стандартный `go tool trace file.out`, открывающий интерактивный веб-интерфейс с временной шкалой. [43]

Соглашение по организации импортов (мелкая, но регулярно проверяемая деталь стиля): порядок групп — стандартная библиотека → сторонние (`third-party`) пакеты → внутренние пакеты организации/монорепозитория → пакеты самого проекта, с пустой строкой между группами; поддерживается автоматически инструментами `goimports` (расширенная версия `gofmt`, дополнительно расставляющая/удаляющая импорты) и `gofmt -s` (упрощающая избыточные конструкции), встроенными в CI через `golangci-lint` с линтерами `gci`/`goimports` — то же самое семейство инструментов, что уже упоминалось для CI-пайплайна выше, конкретно для формата импортов. [49]

Практика организации самого процесса код-ревью на уровне команды (не про конкретный найденный баг, а про то, как вообще устроен процесс, чтобы баги такого рода ловились до продакшна): автоматизация базовых проверок линтерами до того, как ревьюер вообще открывает PR (`golangci-lint run --enable-all`, `go vet ./...`, `gofmt -d .` — прогоняются в CI, ревьюер не тратит время на то, что можно проверить автоматически), явный лимит размера одного PR (порядка 400–500 строк diff) — крупные PR резко снижают качество ревью просто из-за объёма, который физически невозможно удержать в голове целиком, ролевое согласование (PR в область компетенции конкретного домена обязательно смотрит человек, реально в этой области разбирающийся, а не любой свободный ревьюер), явные и конкретные комментарии вместо общих замечаний, обязательный `go test -race` в CI именно для кода с конкурентностью (статический линтер такие баги обычно не ловит). [47]

## Обобщённые выводы по итогам 100+ пройденных технических собеседований

Материал, обобщающий сотню-другую реальных Go-собесов, а не разбор одного конкретного — компактно дополняет уже накопленные наблюдения о формате и частых ошибках. Тематический охват типичного Go-собеса подтверждает уже выстроенную структуру этого конспекта: язык (внутреннее устройство слайсов/map/структур, GC, escape analysis), конкурентность как самая насыщенная область (горутины/каналы/select/context/примитивы синхронизации, паттерны worker pool/fan-out-fan-in/rate limiter/graceful shutdown, модель GMP), классические алгоритмы и структуры данных (связные списки/деревья/хеш-таблицы/графы, Big O), БД (индексы/нормализация/уровни изоляции/фантомные чтения/MVCC, для NoSQL — CAP-теорема/eventual consistency, для Redis — структуры данных/TTL/стратегии кэширования), распределённые системы (gRPC/REST для синхронного, Kafka/RabbitMQ для асинхронного взаимодействия, паттерны circuit breaker/retry/bulkhead/saga), инфраструктура (Docker/Kubernetes/CI-CD/базовые облачные примитивы — см. файл 14). Практический совет по алгоритмической подготовке — порядка 100–150 решённых задач с упором именно на распознавание паттернов (two pointers, sliding window, BFS/DFS, динамическое программирование, бинарный поиск), а не на механическое заучивание конкретных решений — такой подход эффективнее прямого перебора большого числа задач без систематизации. [35]

Часто повторяющиеся ошибки кандидатов по итогам сотни с лишним собесов: не уточнять требования/ограничения задачи перед тем как сразу писать код; писать технически рабочий, но неидиоматичный Go-код (без нормальной обработки ошибок, без `context` там, где он уместен); забывать про очистку ресурсов и управление соединениями; занижать или неверно формулировать зарплатные ожидания настолько, что это само по себе подрывает доверие к остальным ответам кандидата; чрезмерная опора на чистое решение LeetCode-задач без понимания стоящих за ними паттернов; слабая коммуникация именно **компромиссов** архитектурных решений (не просто «я сделал так», а «я выбрал так, потому что взамен на X получаем Y — вот почему это оправдано здесь»). Реалистичный ориентир по конверсии: около 15–20% успешных исходов на количество пройденных собесов в целом по больше чем сотне попыток — то есть в среднем порядка 10 собесов на 1 оффер, и это нормальный, а не провальный результат, если рассматривать поиск работы как воронку с параллельными потоками, а не последовательность попыток «в лоб». [35]

## Код-ревью функции топ-N по рейтингу (`TopProducts`) — ещё один сборный чек-лист

Ещё одно показательное упражнение с код-ревью (в дополнение к разбору `processPayment`, см. файл 14) — функция «вернуть топ-3 товара по рейтингу»:

- **Отсутствие проверки границ** (критично) — прямой доступ по индексам `[0]`, `[1]`, `[2]` без проверки длины входного слайса паникует на пустом/коротком слайсе; нужна явная проверка длины и/или `k := min(3, len(slice))`.
- **Мутация входных данных на месте** (опасно) — `sort.Slice` сортирует переданный слайс **in-place**; если вызывающая сторона не ожидает, что её данные переупорядочат, нужно явно скопировать слайс перед сортировкой (`sorted := make([]T, len(in)); copy(sorted, in)`), а не сортировать оригинал.
- **Нестабильная сортировка при равных значениях** (смысловая проблема) — `sort.Slice` не гарантирует стабильность: при равном рейтинге порядок между такими элементами недетерминирован от запуска к запуску; если это важно для воспроизводимости (например для UI/тестов), нужен явный tie-breaker во втором условии компаратора (например по ID) либо `sort.SliceStable`.
- **Неоптимальный алгоритм для топ-K** — полная сортировка всего слайса — O(N log N), избыточно ради того, чтобы получить только первые K элементов; для топ-K эффективнее QuickSelect (в среднем O(N)) или min-куча размера K через `container/heap` (O(N log K)) — стоит явно проговорить этот компромисс на собесе, даже если для маленького фиксированного K (вроде «топ-3») разница на практике незначима.
- **Прямое сравнение чисел с плавающей точкой через `>`** — для `float32`/`float64`-рейтингов прямое сравнение операцией `>` в принципе корректно для строгого неравенства (в отличие от `==`), но стоит явно отметить на собесе, что вообще сравнивать float напрямую — тема, требующая аккуратности (см. файл 14 про деньги как float — тот же класс проблем, только не для точного равенства, а для устойчивости результата при близких значениях). [26]

## Формат алгоритмической «разминки» на собесе — на что реально смотрят

Помимо чисто языковых вопросов, часть собесов включает лёгкую алгоритмическую задачу общего CS-профиля (без привязки к специфике Go) — типичный пример с одного из разборов: пройтись по массиву флагов и посчитать какую-то геометрическую/числовую характеристику за один проход (O(n) по времени). Показательная деталь, которую интервьюеры целенаправленно проверяют — не сам ли алгоритм (кандидаты обычно предлагают корректный подход с первой попытки), а полнота обработки **граничных случаев** после основного цикла (типичная недоработка — забыть посчитать «хвост» после последнего значимого элемента, если он не встречается до конца массива); фидбек с одного из разборов прямо формулирует это как «проверка после цикла не опциональна, а обязательна». Практический вывод для подготовки — при разборе почти любой O(n)-задачи в духе «пройти и посчитать» явно проговаривать и проверять, что происходит после выхода из основного цикла, а не считать решение законченным сразу после написания тела цикла. [20]

## Критерии различия «сильного» и «слабого» мидл-разработчика на Go

Компактный, часто озвучиваемый на собесах ориентир для самооценки уровня (а не формальная градация из HR-грейдов): более сильный мидл отличается от более слабого не столько знанием синтаксиса языка, сколько (1) пониманием внутреннего устройства базовых структур (реализация каналов, бакеты map, механика GC mark-and-sweep) вместо использования их «как чёрного ящика»; (2) способностью писать корректный конкурентный код самостоятельно, без постоянного внешнего контроля со стороны более старших коллег на код-ревью; (3) осознанным управлением моделью памяти — снижение давления на аллокатор/GC там, где это действительно важно для перформанса, а не бездумная оптимизация всего подряд; (4) зрелой обработкой ошибок и модульностью кода (не «раскидать try/catch-подобные конструкции», а осмысленно оборачивать/классифицировать ошибки — см. файл 07); (5) правильным управлением ресурсами через `context` (таймауты, отмена, распространение дедлайна по цепочке вызовов), а не ручным управлением жизненным циклом горутин без единого механизма отмены. [64]

## Переход процесса разработки со Scrum на Kanban после релиза MVP

Практическое наблюдение про эволюцию процесса управления задачами внутри одной и той же команды: на активной фазе разработки MVP-функциональности (когда объём и приоритеты задач относительно предсказуемы на короткий горизонт) команда работала по классическому Scrum со спринтами; после релиза в прод, когда поток задач стал состоять из смеси мелких доработок, инцидентов и внеплановых запросов с непредсказуемым приоритетом, команда перешла на Kanban — непрерывный поток задач без жёсткой нарезки на спринты, что лучше отражает реальный характер пост-релизной работы (задачи разного размера и срочности прилетают асинхронно, а не пачкой в начале двухнедельного цикла). Общий практический вывод — выбор между Scrum и Kanban не догматичен и может осознанно меняться по ходу жизненного цикла одного и того же проекта в зависимости от характера потока задач, а не фиксироваться раз и навсегда на старте. [65]

## Императивный vs декларативный подход — общее CS-понятие, регулярно всплывающее на Go-собесах

Разграничение, которое часто спрашивают не как языко-специфичный, а как общий концептуальный вопрос: императивный подход описывает **как** именно достичь результата — явная последовательность шагов/инструкций, изменяющих состояние (сам код на Go/Python — императивный по своей природе: `for`-цикл, явное присваивание переменных, пошаговая мутация состояния). Декларативный подход описывает **что** нужно получить в итоге, оставляя решение о конкретных шагах исполнителю/движку (SQL — эталонный пример: `SELECT` описывает желаемый результат, а не алгоритм его получения, конкретный план выполнения строит оптимизатор запросов; Docker/Kubernetes-манифесты и Terraform — тоже декларативны: описывают желаемое конечное состояние инфраструктуры, а не пошаговый сценарий его достижения, конкретные шаги для перехода от текущего состояния к желаемому вычисляет сам инструмент). Важный нюанс, который стоит проговорить на собесе сверх базового определения — сам Go как императивный язык вполне может использоваться для построения декларативных абстракций поверх себя (билдер-паттерны, DSL на функциональных опциях, декларативно описывающие желаемую конфигурацию объекта, при том что реализация билдера внутри — обычный императивный код). [70]
