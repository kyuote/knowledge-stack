## `var` vs `:=`

`:=` работает только внутри тела функции; на уровне пакета обязателен `var`. `:=` допускает переприсваивание в том же блоке, если хотя бы одна переменная слева — новая; у `var` — свои правила области видимости (можно объявить без инициализации, получив zero value). [12]

Частая ошибочная линия объяснения, почему переменная, объявленная во вложенном блоке (`{ ... }`, тело `if`/`for`/произвольный блок), недоступна снаружи этого блока — попытка объяснить это через сборщик мусора («переменная вышла из блока — значит, GC её уже забрал/её память не гарантирована» и подобные формулировки). Это неверная причинно-следственная связь: недоступность переменной за пределами блока — чисто **лексическая область видимости** (lexical scoping), решаемая компилятором статически на этапе компиляции по правилам вложенности блоков `{}`, и никак не связана с работой GC во время исполнения программы — переменная может быть жива в памяти сколь угодно долго после выхода из блока (например если на неё осталась ссылка через замыкание), просто обратиться к ней по имени из внешнего кода уже нельзя — компилятор не найдёт такое имя в таблице символов внешней области видимости. Каждый `{}` создаёт новую вложенную область видимости; регистр первой буквы имени (заглавная/строчная) определяет видимость на уровне **пакета** (экспортируется наружу или нет), но никак не отменяет и не расширяет обычную блочную вложенность области видимости внутри функции. [67]

## Базовые типы — что часто забывают

Частый пробел в ответах кандидатов: перечисляют целые (`int8`–`int64`, `uint*`), `bool`, `string`, составные типы (слайсы/map/каналы/структуры/интерфейсы) — но забывают `float32`/`float64` и `complex64`/`complex128`. Более полный ответ также упоминает: дженерики (с Go 1.18+), именованные типы (type aliases) для создания собственных типов поверх базовых, `interface{}`/`any` для полиморфизма. [1, 7, 15]

## Спор про внутреннюю структуру строки — разрешён в пользу кандидата

На одном из собесов интервьюер утверждал, что строка внутри содержит указатель на слайс байт; кандидат не согласился и оказался прав (подтверждается исходным кодом рантайма Go): структура строки (`stringStruct`) содержит только `Data` (`uintptr`) и `Len` (`int`) — без поля `Cap`, то есть без структуры слайса внутри. Из этого напрямую следует то, что уже отмечено выше: строки неизменяемы, слайсы — нет, и они не разделяют одну внутреннюю структуру, хотя по набору полей (указатель+длина) выглядят похоже. Хороший пример того, что даже интервьюер может ошибаться — при разногласии полезно опираться на исходники стандартной библиотеки, а не только на память. [15]

## Псевдоним типа (`type X = Y`) — в отличие от определения нового типа (`type X Y`)

Важно не путать с уже описанной ниже номинативной типизацией — это два разных механизма `type`-объявления с противоположным эффектом на совместимость типов. Определение нового типа (`type UserID int`, без знака `=`) создаёт **новый, отдельный** именованный тип — номинативно несовместимый с базовым `int` и с любым другим типом, определённым поверх того же базового типа (см. ниже), даже при идентичном представлении в памяти. Псевдоним типа (`type Alias = Type`, со знаком `=`) — это не новый тип, а буквально **другое имя того же самого типа**: `Alias` и `Type` после такого объявления полностью взаимозаменяемы всюду, включая передачу в функции, ожидающие один или другой, без какого-либо явного приведения — компилятор не видит между ними разницы вообще. Практическое применение алиасов — обратная совместимость при постепенном переносе типа в другой пакет (старое имя остаётся рабочим алиасом на новое расположение, не ломая уже написанный код зависимых пакетов) и сокращение длинных сгенерированных/параметризованных типов (например алиас на конкретную специализацию generic-типа) для более читаемых сигнатур. [42(предвосхищено), 51]

## Дженерики (Go 1.18+) — параметризация типов и ограничения

До generics единственным способом писать код, работающий с разными типами, было использование `interface{}`/`any` — ценой полной потери типобезопасности на этапе компиляции (тип восстанавливается только через приведение/type assertion в рантайме, ошибка несовпадения типов всплывает не раньше выполнения). Дженерики решают это на уровне компилятора: функция или тип параметризуется одним или несколькими типовыми параметрами в квадратных скобках, с необязательным, но обычно желательным ограничением (constraint) — интерфейсом, описывающим, какие операции разрешены над этим типовым параметром:

```go
func Max[T constraints.Ordered](a, b T) T {
    if a > b {
        return a
    }
    return b
}
```

`constraints.Ordered` (пакет `golang.org/x/exp/constraints`, часть идей позже вошла в стандартный `cmp`) — готовое ограничение «любой тип, поддерживающий операторы сравнения `<`/`>`» (числовые типы и строки); собственные ограничения можно определять как обычные интерфейсы, в том числе через объединение типов с `~` (например `~int | ~float64` — «любой тип, чей базовый тип — `int` или `float64`», включая именованные типы поверх них, а не только сами `int`/`float64` буквально). Выигрыш по сравнению с `any` — ошибки несовпадения типов ловятся на этапе компиляции, а не в рантайме, и не нужен type assertion внутри тела функции для доступа к типизированным операциям (сравнение, арифметика) — компилятор уже знает конкретный тип на месте вызова. [48]

## Именованные типы — номинативная типизация, а не структурная

Частая ловушка: если два именованных типа определены поверх одного и того же базового типа (например `type UserID int` и `type ProductID int`), это всё равно **разные типы** с точки зрения компилятора — присвоение значения одного в переменную другого напрямую не скомпилируется, даже при полном совпадении базового типа. Go использует номинативную (по имени) систему типов для явно объявленных типов, а не структурную (по форме/составу) — совпадение представления в памяти ничего не значит для совместимости типов. Нужно явное приведение: `TargetType(value)`. Частая ошибка кандидатов — предполагать, что раз "внутри одно и то же", присваивание сработает само. [19]

## Размер `int` и путаница бит/байт

Частая ошибка — путать биты и байты: число в имени типа — это биты, не байты (`int32` = 4 байта, не 32). `int` платформозависим: 4 байта на 32-битных системах, 8 байт на 64-битных (в современных окружениях почти всегда 8). Использовать `int32`/`int64` явно, когда нужен гарантированный фиксированный размер (бинарные протоколы, сериализация); голый `int` — идиоматичен для счётчиков и индексов. [7, 12]

## Представление чисел в памяти: two's complement

Отрицательные числа представлены в дополнительном коде: старший (most significant) бит определяет знак (0 — положительное, 1 — отрицательное); поэтому диапазон `int8` асимметричен — −128..127, а не −128..128. `uint` использует все биты под величину, без бита знака. Конкретный пример переполнения без паники (арифметика по модулю 2^N «заворачивает» через границу диапазона незаметно для рантайма): `int8(127) + int8(1)` даёт `-128`, а не ошибку и не панику — платформозависимость размера касается именно голого `int` (см. выше), а не `int8`/`int16`/`int32`/`int64` с явно зафиксированным размером. [7, 36]

## Zero values — единое правило для всех типов

Любая переменная при объявлении получает zero value, а не «мусор» в памяти: `0`/`0.0` для чисел, `false` для bool, `""` для строк, `nil` для указателей/слайсов/map/каналов/функций/интерфейсов. Важный нюанс: nil-слайс и явно созданный пустой слайс (`[]int{}`) — оба с `len==0`, но это разные значения (см. подробности и код в файле 04 «Слайсы/массивы/map/struct»). [3(доп.), 12]

## Явное приведение типов и переполнение при конвертации

В Go нет неявных преобразований между числовыми типами — даже если `int` и `int32` физически совпадают по размеру на конкретной платформе, это разные типы, нужен явный `int32(a)`. Конвертация не паникует и не выдаёт ошибку при выходе значения за пределы диапазона целевого типа — она молча усекает биты. Пример: `int32(math.Pow(2, 31))` — результат `2147483648.0` превышает `math.MaxInt32` (`2147483647`), биты усекаются и переинтерпретируются как знаковое число — получается `-2147483648` (переполнение "заворачивает" через ноль). Дробная часть float при конвертации в целое всегда отбрасывается (не округляется). В продакшн-коде диапазон стоит валидировать до конвертации, а не полагаться на поведение по умолчанию. [12]

```go
var overflow int32 = int32(math.Pow(2, 31))
fmt.Println(overflow) // -2147483648 (переполнение)
```

## Строка: внутреннее устройство

Строка — неизменяемая структура `stringHeader`/`StringHeader` с двумя полями: указатель на байтовый массив и длина в байтах (без поля ёмкости — в этом отличие заголовка строки от заголовка слайса). Заголок занимает 16 байт на 64-битной платформе — именно он копируется при передаче строки по значению, а не сами данные, поэтому передача строки почти бесплатна. Иммутабельность даёт: безопасность при конкурентном чтении без синхронизации, эффективное разделение памяти между копиями, стабильный хеш для использования строк как ключей map. Базовый байтовый массив литералов может лежать в read-only памяти (секция `.rodata`) — попытка обойти неизменяемость через `unsafe` и записать туда напрямую может привести к `SIGSEGV` в рантайме, а не просто к логической ошибке. [3, 11]

## Нет типа `char`; байты, руны, графемы — три разных уровня

В Go нет типа `char` — вместо него `rune` (alias `int32`), представляющий один Unicode code point (0..1 114 111). Важно различать три уровня: `byte` (`uint8`, единица хранения UTF-8), `rune` (один code point), и **графема** (то, что пользователь воспринимает как «один символ» — может состоять из нескольких code point'ов: комбинирующие диакритики, эмодзи с ZWJ-последовательностями). Практические байтовые размеры: кириллица — 2 байта/руна, иероглифы (CJK) — 3 байта/руна, большинство эмодзи — 4 байта/руна; составной символ вроде эмодзи «семьи» с ZWJ может состоять из 11 рун, но восприниматься как одна графема; «é» как e+акцент — 2 руны, 1 графема; парный региональный индикатор (флаг страны) — 2 руны, 1 графема. Для графемно-осознанного подсчёта (например для лимитов в UI/БД) нужны сторонние библиотеки — руны для этого не годятся (например `github.com/rivo/uniseg`). [1, 7, 11]

## `len(s)`, индексация и подсчёт символов

`len(s)` возвращает число **байт**, не символов и не графем (например `len("привет")` = 12, а не 6 — по 2 байта на кириллическую букву). `s[i]` возвращает i-й **байт** (тип `byte`/`uint8`), не i-й символ — `s[0] == 'П'` не скомпилируется вовсе (несовпадение типов `byte` и `rune`). Для подсчёта именно рун — `utf8.RuneCountInString(s)`: O(n) по времени и **без аллокаций**; в противовес `len([]rune(s))`, который тоже O(n), но аллоцирует целый новый слайс `[]int32` (накладные расходы на GC) — конвертировать в `[]rune` стоит, только если реально нужен произвольный доступ по индексу руны, а не просто подсчёт. [1, 3, 7, 11, 23]

## Срезание строки и `for range` — байтовые границы, не рунные

Срез `s[i:j]` режет по байтовым смещениям, а не по границам символов — `s[0:3]` на кириллической строке может разрезать руну пополам и дать невалидный UTF-8; резать безопасно только по индексам, полученным из `for range` или `utf8.DecodeRuneInString`. `for i, r := range s` сам декодирует UTF-8 на лету: `i` — это байтовое смещение начала каждой руны (для кириллицы — 0,2,4,6…; для CJK — 0,3,6…), `r` — сама руна. Цикл никогда не паникует на невалидном UTF-8 — заменяет плохую последовательность на `RuneError` (U+FFFD) и пропускает 1 байт. [7, 11]

## Изменение строки и конвертация `string` ↔ `[]byte`

Прямое изменение символа (`s[0] = 'H'`) — ошибка компиляции: строки неадресуемы для записи, `s[i]` возвращает **значение** байта, а не адресуемую ячейку. Обходной путь — привести к `[]byte`, изменить, привести обратно к `string`; для юникод-осознанного изменения нужен именно `[]rune` (иначе можно разрезать многобайтовый символ), не `[]byte`. Оба направления конвертации (`string`→`[]byte` и обратно) **всегда** аллоцируют новую память и копируют данные — распространённое заблуждение, что `[]byte(s)` "делит" память с исходной строкой, неверно: изменение среза не затрагивает оригинальную строку именно потому, что данные скопированы. Единственный гарантированно бесплатный (zero-copy) путь — `strings.Builder.String()`, который использует `unsafe` внутри, сохраняя безопасность через контракт API (не давая изменить то, что отдаёт). [3, 11, 19]

## Эффективная конкатенация строк

Конкатенация в цикле через `+`/`+=` — O(n²): каждая операция создаёт новую строку и копирует все предыдущие данные заново. Правильный инструмент — `strings.Builder`, который растит внутренний буфер экспоненциально (стратегия ×2), давая амортизированную O(1) на запись; финальный `String()` — тоже zero-copy через `unsafe`. C Go 1.20+ у `strings.Builder` есть защита от копирования — попытка скопировать уже использованный `Builder` вызывает панику в рантайме. [3, 11, 23]

```go
var b strings.Builder
for _, part := range parts {
    b.WriteString(part)
}
return b.String()
```
