## HTTP/1.1 vs HTTP/2 — ключевые архитектурные отличия

HTTP/1.1 — текстовый протокол; при N параллельных запросах к одному хосту браузер/клиент вынужден открывать несколько (типично 6–8) отдельных TCP-соединений, потому что одно соединение без мультиплексирования сериализует запросы (head-of-line blocking на уровне приложения). HTTP/2 вводит: бинарный фрейминг (данные режутся на бинарные фреймы, а не текстовые строки — быстрее парсить); мультиплексирование нескольких логических потоков-запросов в **одном** TCP-соединении без взаимной блокировки на уровне HTTP (см. также раздел про gRPC ниже — это тот же транспортный механизм); сжатие заголовков HPACK (типичное сокращение объёма заголовков — порядка **85%**, особенно заметно при большом числе однотипных запросов с почти одинаковыми заголовками между собой); приоритизацию потоков и явные зависимости между ними (клиент может подсказать серверу, какие ответы важнее отдать раньше); Server Push (сервер может проактивно отправить ресурс, который клиент ещё не запросил, но точно запросит — на практике использовался ограниченно и во многом вытеснен другими техниками). В Go — HTTP/2 включается автоматически при `ListenAndServeTLS` (для обычного TLS-трафика); для HTTP/2 без шифрования (h2c, используется в основном для внутреннего служебного трафика) нужен отдельный явный обработчик. [36]

## HTTP-запрос/ответ — базовая структура

Запрос: строка запроса в формате `МЕТОД ПУТЬ HTTP/ВЕРСИЯ`, заголовки (`Host`, `Content-Type`, `Authorization` и т.п.), тело (у `GET` тело технически возможно протоколом, но по соглашению обычно не используется — семантически `GET` не должен иметь тела). Ответ: код статуса (категории `1xx` информационные, `2xx` успех, `3xx` редирект, `4xx` ошибка клиента, `5xx` ошибка сервера), заголовки, тело. Передача тела — либо через явный `Content-Length` (заранее известный размер), либо `Transfer-Encoding: chunked` (тело передаётся частями без знания итогового размера заранее — полезно для потоковой генерации ответа). [30]

## HTTP-клиент: явная конфигурация вместо `http.DefaultClient`, middleware через `RoundTripper`

Общая рекомендация — не использовать глобальный `http.DefaultClient`/`http.Get()` в продакшн-коде: явное создание своего `http.Client` с настроенным `Transport` (переиспользуемый пул соединений, `MaxIdleConns`/`IdleConnTimeout`) и `Timeout` — управляемее и тестируемее. Идиоматичный способ добавить сквозную функциональность (логирование запросов, метрики, ретраи) без изменения кода каждого вызова — обернуть транспорт кастомной реализацией интерфейса `http.RoundTripper` (единственный метод `RoundTrip(*http.Request) (*http.Response, error)`), который подставляется в `http.Client.Transport` — аналог middleware/декоратора для HTTP-клиента, симметрично серверным middleware-обёрткам над `http.Handler`. Стандартный порядок вызовов: `http.NewRequestWithContext(ctx, method, url, body)` → `client.Do(req)` → обязательный `defer resp.Body.Close()` сразу после проверки ошибки (утечка соединения, если тело ответа не закрыто, даже если оно не читается). Критичный нюанс, часто приводящий к панике на практике: при ошибке на уровне транспорта (не удалось установить соединение, DNS не резолвится, TLS handshake не прошёл и т.п.) `client.Do()` возвращает `(nil, err)` — сам `resp` **гарантированно nil** в этом случае; вызов `resp.Body.Close()` или любое другое обращение к полям `resp` без предварительной проверки `err != nil` (или явной `resp == nil`) — паника на nil-указателе. Правильный порядок — сначала проверить ошибку и выйти при `err != nil`, и только потом обращаться к `resp` и планировать `defer resp.Body.Close()`. Дополнительно стоит явно решить для конкретного случая, что считать «успехом» ответа — не только код `200`, но зачастую и весь диапазон `2xx` (`201`, `202`, `204` и т.п.), и явно решить, нужно ли автоматически следовать редиректам (`http.Client.CheckRedirect`) или отключить это поведение для точного контроля. [32, 33]

## HTTP-клиент: почему одного `Timeout` недостаточно

Частая ошибка — использовать `http.DefaultClient` (вообще без таймаута — риск зависнуть навсегда на недоступном сервере) или ограничиться единственным полем `http.Client{Timeout: 10*time.Second}`. Проблема одного общего таймаута — он покрывает **весь** цикл запроса разом (DNS+TCP-подключение → TLS-handshake → заголовки ответа → тело ответа), и не различает, на каком именно этапе застряло — например при медленной построчной отдаче тела ответа (техника атаки/деградации в духе Slowloris) общий таймаут срабатывает так же, как и при обычной медленной сети, без возможности точечно среагировать раньше именно на конкретную фазу. Более точная настройка — через `http.Transport` с раздельными таймаутами по фазам: `DialContext` с `net.Dialer{Timeout: ...}` (TCP-подключение), `TLSHandshakeTimeout` (отдельно фаза TLS), `ResponseHeaderTimeout` (специально ловит зависание сервера именно на присылке заголовков ответа), плюс `MaxIdleConns`/`MaxIdleConnsPerHost`/`IdleConnTimeout` для управления пулом переиспользуемых keep-alive соединений (`MaxIdleConnsPerHost` в частности защищает от исчерпания файловых дескрипторов при большом числе запросов к одному хосту). Поверх всего этого — общий `context` с дедлайном на весь вызов (`context.WithTimeout` + `http.NewRequestWithContext`) как верхнеуровневая защита. Дополнительно — `io.LimitReader(resp.Body, maxBytes)` перед чтением тела ответа ограничивает максимальный размер вычитываемых данных, защищая от намеренно огромного или аномального ответа сервера, исчерпывающего память клиента. [26]

Смежная проблема — неограниченный веер параллельных запросов (например «сходить по 10 000 URL одновременно») рискует исчерпать файловые дескрипторы, память (стек на каждую горутину), упереться в лимиты соединений ОС/удалённого сервера и создать давление на планировщик. Митигации: ограничение уровня конкурентности (worker pool или семафор — см. выше), настройка `http.Transport.MaxConnsPerHost`/`MaxIdleConnsPerHost` (жёсткий потолок соединений на хост, а не только «мягкие» idle-таймауты), обязательные таймауты через `context` на каждый отдельный запрос (иначе зависшие запросы копят утёкшие горутины), rate limiting (например `golang.org/x/time/rate`) и осознанная плавная деградация при перегрузке вместо попытки обслужить всё сразу. [31]

Конкретный пример продакшн-конфигурации `http.Transport` для сценария массовых параллельных запросов (порядки величин, не универсальные константы — подбираются под конкретную нагрузку): `MaxIdleConns: 1000`, `MaxIdleConnsPerHost: 1000`, `MaxConnsPerHost: 1000`, `IdleConnTimeout: 90 * time.Second`, плюс обязательный таймаут на весь запрос в диапазоне 10–30 секунд. Также стоит явно разграничивать сетевой I/O (по своей природе не блокирует поток ОС благодаря netpoller, см. выше) и файловый I/O (на большинстве платформ фактически блокирующий на уровне ОС) при планировании числа одновременных воркеров — конкурентность полезна щедро для первого и куда осторожнее для второго. [37]

## Retry-логика клиента должна различать HTTP-коды, а не ретраить вслепую

Частая недоработка в реализации retry-логики поверх HTTP-клиента — обрабатывать любую неудачу одинаково (просто повторить через фиксированную паузу), не различая семантику конкретного кода ответа. Правильная классификация: `429 Too Many Requests` — сигнал именно rate-limiting, а не транзиентной сетевой ошибки, и сервер часто явно сообщает, сколько ждать, через заголовок `Retry-After` (в секундах или как HTTP-дата) — клиенту стоит распарсить и уважать именно это значение вместо собственного фиксированного расписания ретраев; `5xx` — обычно транзиентная серверная проблема, ретраить с экспоненциальным backoff и джиттером имеет смысл; `4xx` кроме `429` (например `400`/`404`) — как правило, ошибка самого запроса, повторять его без изменений бессмысленно и только тратит квоту ретраев. Дополнительные продакшн-практики поверх этого — dead-letter queue для сообщений/запросов, исчерпавших лимит попыток (не терять их молча, а откладывать для последующего ручного или отложенного разбора), и структурированное логирование каждой попытки ретрая отдельно (а не только финальной ошибки) — иначе при разборе инцидента невозможно понять, сколько раз и с какими промежуточными ошибками реально повторялся запрос. [47]

## Продакшн-чек-лист безопасности HTTP-хендлера — код-ревью сервиса уведомлений

Показательный код-ревью HTTP-хендлера, принимающего задачу на отправку уведомления (email/SMS) — набор проблем, которые интервьюер (Head of Development в FinTech) оценил как критичные для продакшена, несмотря на в целом корректную бизнес-логику:

- **Неверный HTTP-метод** — использование `GET` для операции, реально мутирующей состояние (постановка уведомления в очередь): `GET` по контракту протокола идемпотентен, кэшируем и ограничен по длине URL (RFC 7231) — прокси/краулеры могут непреднамеренно повторно вызвать такой запрос, продублировав отправку; мутирующие операции — только `POST`/`PUT`/`PATCH`/`DELETE`.
- **Отсутствие валидации входных данных** — принимаемые значения (например тип канала доставки) должны сверяться с явным белым списком допустимых констант, а не приниматься как есть; `http.MaxBytesReader` — ограничение максимального размера тела запроса перед чтением, защита от намеренно огромного тела; для полей, попадающих затем в SMTP-заголовки (email) — риск email header injection через управляющие последовательности `\r\n` в пользовательском вводе, если поля не экранируются перед подстановкой в заголовки письма.
- **Секреты в переменных окружения** — распространённая, но небезопасная практика: переменные окружения процесса могут утечь через логи или через `/proc/self/environ` при определённых уязвимостях; продакшн-стандарт — динамически выдаваемые учётные данные (например через IAM-роль в Kubernetes) или менеджер секретов (Vault/AWS Secrets Manager) с автоматической ротацией, а не статичный токен в конфиге/окружении.
- **Отсутствие аутентификации между внутренними сервисами** — подход «Zero Trust»: даже вызовы между сервисами внутри доверенного периметра сети должны быть аутентифицированы (mTLS, ограниченные по правам токены) — доверие по факту нахождения во внутренней сети само по себе не гарантия.
- **Утечка данных через текст ошибки** — полный stack trace или детали внутренней ошибки (включая, например, пароль от БД в строке подключения) в ответе клиенту наружу — недопустимо; наружу — обобщённый код ответа (`500` без деталей), подробности — только во внутренний лог; типовой паттерн — единый middleware с `defer recover()`, перехватывающий панику и превращающий её в generic-ответ.
- **Неверные HTTP-коды ответа** — например `200` при ошибке валидации данных или `500` при том, что на самом деле является ошибкой клиента (данные неверны) — нарушает контракт статус-кодов, затрудняет автоматическую обработку ответа клиентом.
- **Отсутствие rate limiting** — без ограничения частоты запросов сервис уязвим к тривиальному DoS через переполнение внутренней очереди задач и исчерпание памяти; требуется явный rate limiter и/или circuit breaker перед точкой входа, с ответом `429 Too Many Requests` при превышении лимита (см. также обработку `Retry-After` на стороне клиента выше). [49]

## Аутентификация: access/refresh токены (JWT) и их безопасное хранение

Практическая схема из живого собеса — короткоживущий access-токен (обычно JWT, 15–60 минут) для авторизации каждого запроса, плюс долгоживущий refresh-токен (7+ дней) для получения нового access-токена без повторного логина — компромисс между безопасностью (короткий TTL ограничивает окно эксплуатации скомпрометированного токена) и удобством (не логиниться каждый час). Важный нюанс уровня продакшна — **refresh-токен НЕ обязан быть JWT**: практичнее делать его непрозрачной случайной строкой (криптографическая случайность), привязанной к записи в БД (сессия) — это даёт возможность его отозвать (чего нельзя сделать с классическим stateless JWT без дополнительного стораджа отозванных токенов). Хранение на клиенте: access-токен — в памяти приложения/заголовке `Authorization: Bearer` (уязвим к XSS, но по-другому его не передать серверу через API); refresh-токен — в cookie с флагами `HttpOnly` (недоступен из JS, защита от XSS), `Secure` (только по HTTPS), `SameSite=Strict` (защита от части CSRF-сценариев — для мутирующих запросов дополнительно нужен явный CSRF-токен). Ротация и защита от кражи: при каждом использовании refresh-токена выдаются новые access+refresh, старый refresh инвалидируется в БД; если **уже инвалидированный** refresh-токен пришёл повторно — это сигнал кражи токена (кто-то использовал старую скомпрометированную копию) — в ответ разумно отозвать вообще все активные сессии пользователя. Дополнительные продвинутые техники: token binding (хешировать refresh-токен вместе с User-Agent/IP клиента — резкое несовпадение сигнализирует использование с другого устройства), «тихое» обновление access-токена клиентом заранее (за несколько минут до истечения, прозрачно для пользователя), и блэклист по `jti` (уникальному ID конкретного JWT) в Redis для точечного отзыва ещё не истёкших access-токенов при инциденте безопасности. [26]

## Уязвимости при самодельной проверке JWT — код-ревью реализации

Показательный код-ревью функции валидации JWT, вскрывший целый набор критичных проблем, типичных именно для самодельной (а не через проверенную библиотеку) реализации:

- **`base64` — не шифрование** — payload JWT просто закодирован (не зашифрован), не даёт ни конфиденциальности, ни целостности сам по себе; целостность обеспечивается исключительно подписью, а не самим форматом.
- **Атака подмены алгоритма (algorithm substitution / alg confusion)** — если валидатор слепо доверяет полю `alg` из самого токена, атакующий может подменить заявленный алгоритм на симметричный (например `HS256`) и подписать поддельный токен, используя **публичный** ключ сервера (который часто доступен открыто) в качестве секрета для HMAC — сервер, доверяющий полю `alg` из токена, успешно проверит такую поддельную подпись. Защита — валидатор обязан **жёстко зафиксировать** ожидаемый алгоритм на своей стороне и игнорировать значение `alg` из самого токена, а не брать его оттуда.
- **Отсутствие структурной проверки** — токен должен состоять ровно из 3 частей (header.payload.signature) до попытки разбора; непроверенное приведение типов при разборе claims (`map[string]interface{}` без проверок на существование/тип поля) — источник паники на некорректном вводе.
- **Пропущенная проверка стандартных claims** — `exp` (срок действия), `nbf` (not before — токен ещё не должен действовать), `aud` (audience — токен предназначен именно этому получателю) — валидны не только структурно, но и семантически.
- **Небезопасное сравнение подписи по времени (timing attack)** — побайтовое сравнение через обычный `==`/`bytes.Equal` может на некоторых платформах давать заметную по времени исполнения разницу в зависимости от того, на каком байте произошло несовпадение, теоретически позволяя атакующему восстановить корректную подпись по времени ответа; правильно — сравнение константного времени через `hmac.Equal()` (или аналог), не короткозамыкающееся на первом несовпадении.

Практическая рекомендация в противовес самодельной реализации — использовать проверенную библиотеку (`golang-jwt/jwt`) с типизированными структурами Claims вместо ручного разбора, короткое время жизни токена (минуты/часы) в сочетании с паттерном refresh-токена (см. выше), и ротацию ключей подписи через JWKS (JSON Web Key Set) — набор актуальных публичных ключей, публикуемый по стандартному эндпоинту, позволяющий проверяющей стороне подхватывать новый ключ без полной синхронной пересборки/редеплоя всех сервисов-потребителей токена. [53]

## gRPC: сильные и слабые стороны против REST

gRPC использует бинарный протокол (protobuf) — компактнее и быстрее сериализация/десериализация, чем JSON; встроенная кодогенерация клиента/сервера из `.proto`-схемы; поверх HTTP/2 — мультиплексирование запросов в одном соединении и 4 паттерна стриминга (unary, server-streaming, client-streaming, bidirectional). Строгий типизированный контракт (schema-first) снижает рассинхрон клиента и сервера по сравнению с вольным JSON. Минусы: ограниченная поддержка в браузерах (нужен grpc-web/прокси), сложнее отлаживать (бинарный трафик не читается глазами как JSON), более узкая экосистема инструментов, сложнее версионирование контрактов при breaking changes. Практическое правило из интервью: gRPC — для внутреннего взаимодействия сервисов друг с другом; REST — для внешних API и там, где важна доступность для разработчиков, незнакомых с gRPC. [15]

Дополнительные конкретные детали: сериализация protobuf сжимает данные примерно в **3–10 раз** плотнее, чем эквивалентный JSON, за счёт бинарного формата с variable-length целыми числами и нумерацией полей вместо текстовых имён ключей. HTTP/2 даёт gRPC бинарный фрейминг (данные режутся на бинарные фреймы, а не текстовые строки как в HTTP/1.1) и мультиплексирование потоков — несколько логических запросов идут в одном TCP-соединении без взаимной блокировки на уровне HTTP (head-of-line blocking одного запроса не тормозит остальные потоки того же соединения), с управлением потоком через `WINDOW_UPDATE`-фреймы (получатель явно сообщает, сколько данных готов принять, защита от переполнения буфера). Встроенные возможности из коробки: TLS, сжатие тела сообщения, отмена вызова и распространение дедлайна (deadline) по всей цепочке вызовов между сервисами. Важная оговорка — мультиплексирование HTTP/2 решает head-of-line blocking только на уровне HTTP-потоков, но не устраняет head-of-line blocking на уровне самого TCP (одна потерянная сетевая посылка всё ещё блокирует все потоки соединения, пока не переотправится) — эта проблема решена только в HTTP/3 поверх QUIC (транспорт на UDP). [22]

## gRPC: практический workflow кодогенерации, server reflection, инструменты тестирования

Полный практический цикл работы с `.proto`-схемой: (1) описание контрактов в `.proto`-файле (сервисы, сообщения, типы RPC — unary/streaming); (2) кодогенерация через `protoc --go_out=. --go-grpc_out=.` (генерирует структуры сообщений и интерфейсы клиента/сервера из схемы); (3) реализация серверного интерфейса конкретным типом; (4) регистрация реализации на gRPC-сервере (`RegisterUserServiceServer(grpcServer, impl)`); (5) на стороне клиента — генерируемый типобезопасный клиент формирует запросы уже готовыми сгенерированными структурами. Всё взаимодействие идёт как бинарный Protobuf поверх HTTP/2 — вручную сериализацией заниматься не нужно. [66]

**Server reflection** — механизм динамического обнаружения сервисов gRPC-сервером без необходимости иметь `.proto`-файлы заранее на стороне клиента: сервер во время выполнения сообщает список доступных сервисов/методов и их сигнатуры. Включается явным вызовом `reflection.Register(grpcServer)` в коде сервера. Практическое применение — универсальные инструменты вроде `grpcurl`/`grpcui`, дженерик-клиенты, ad-hoc тестирование без пересборки клиента под каждую схему. Важная оговорка безопасности — reflection обычно осознанно включают в dev/stage-окружениях и явно отключают в проде (утечка структуры внутреннего API постороннему, у кого есть сетевой доступ к сервису, но нет исходников). [66]

Инструменты тестирования/отладки gRPC (в противовес наивной попытке достучаться через Postman с обычным JSON, которая не работает без явной поддержки протокола): `grpcurl` — CLI-аналог `curl` для gRPC, работает либо через reflection сервера (`grpcurl list`, `grpcurl describe`), либо с явно переданными `.proto`-файлами, вызов метода — через флаг `-d` с JSON-телом, автоматически конвертируемым в Protobuf; `grpcui` — веб-интерфейс поверх того же механизма, аналог Postman/Swagger UI именно для gRPC; современные версии Postman имеют нативную поддержку gRPC (не через JSON/HTTP-эмуляцию, а полноценный протокол); для автоматизированных тестов — интеграционные тесты с in-memory gRPC-сервером (без реального сетевого сокета) и сам `.proto`-файл как единственный источник истины (single source of truth) для контракта между сервисами. [66]
