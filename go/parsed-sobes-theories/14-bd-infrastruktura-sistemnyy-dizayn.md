## Подключение к БД и пул соединений

Важное уточнение: `sql.Open` только инициализирует пул соединений, но **не проверяет реальную доступность БД** — для проверки нужен явный вызов `PingContext`. Для продакшна обязательны: graceful shutdown, обработка миграций при старте, health-check эндпоинты. Четыре ключевых параметра настройки пула в `database/sql`: `SetMaxOpenConns` (максимум одновременных соединений), `SetMaxIdleConns` (сколько простаивающих соединений держать), `SetConnMaxLifetime` (через какое время соединение принудительно закрывается и переоткрывается), `SetConnMaxIdleTime` (автоматическая очистка долго простаивающих соединений). Для SQLite есть свои нюансы по сравнению с «настоящими» клиент-серверными БД — при синтезе стоит уточнить отдельно, в чём именно разница. [5]

Дополнительный продакшн-чек-лист инициализации БД, всплывший на код-ревью сервиса уведомлений: никогда не использовать `CREATE TABLE IF NOT EXISTS` прямо в коде приложения при старте как способ «управления схемой» в проде — вместо этого явные, версионируемые миграции схемы через отдельный инструмент (`golang-migrate`, `pressly/goose`), применяемые как отдельный контролируемый шаг деплоя, а не неявно при каждом запуске приложения. Важное разграничение health-check эндпоинтов: liveness-проба должна быть максимально дешёвой и быстрой (`SELECT 1` — просто подтверждает, что соединение с БД живо) — не должна валидировать схему или бизнес-логику, чтобы не создавать ложных срабатываний под нагрузкой; readiness-проба, наоборот, вправе быть строже (например явная проверка версии применённой схемы миграций) — сервис не готов принимать трафик, если миграции ещё не применены, даже если сама БД технически отвечает. Для часто выполняемых запросов — подготовленные выражения (prepared statements), и обязательный `context` с таймаутом на каждую операцию с БД (без него зависшее сетевое соединение с БД блокирует запрос неограниченно). Классическая уязвимость, которую стоит явно проговорить на собесе, а не считать самоочевидной — SQL injection через конкатенацию пользовательского ввода прямо в текст запроса; единственная надёжная защита — параметризованные запросы (`WHERE user_id = $1` с явно переданным параметром-биндом), никогда не строковая конкатенация значений в SQL-текст. [49]

## Управление сторонними провайдерами/интеграциями — конфигурация и отказоустойчивость

Для сервиса, зависящего от нескольких взаимозаменяемых внешних провайдеров одной и той же функции (например несколько провайдеров отправки email/SMS) — конфигурация каждого провайдера в продакшене должна включать явно: имя, тип канала, приоритет и вес (для балансировки нагрузки между несколькими одновременно активными провайдерами), политику ретраев, таймаут, отдельный rate-limit конкретно для этого провайдера, эндпоинт и токен доступа (обязательно из менеджера секретов, а не захардкоженный, см. также раздел про безопасность HTTP-хендлера выше), настройки circuit breaker именно на уровне конкретного провайдера (изоляция отказа одного провайдера от остальных). Паттерн «основной + резервный» (primary + fallback) с health-check каждого провайдера и балансировкой нагрузки между живыми — стандартная схема отказоустойчивости для этого класса интеграций, вместо жёсткой привязки ко всего одному провайдеру без альтернативы на случай его недоступности. [49]

## Типы индексов БД и диагностика медленных запросов

Индекс — вспомогательная структура, ускоряющая поиск ценой дополнительной памяти и замедления записи (индекс тоже нужно обновлять при insert/update/delete). Основные типы: **B-tree** (точнее B+tree в PostgreSQL — внутренние узлы хранят только ключи-указатели, данные лежат в листьях) — индекс по умолчанию, O(log n), поддерживает диапазонные запросы и сортировку по возрастанию/убыванию; **Hash-индекс** — O(1) в среднем, но только точное совпадение, не поддерживает диапазоны, более уязвим к коллизиям; **GiST/R-tree** — для пространственных/геометрических данных (GIS-системы, поиск «что рядом»), группировка объектов по минимальным ограничивающим прямоугольникам; **GIN** (Generalized Inverted Index) — для полнотекстового поиска и составных значений (массивы, JSONB) — инвертированный индекс, отображающий значение обратно на список строк, где оно встречается; **Bitmap-индекс** — эффективен при низкой кардинальности (мало уникальных значений, например пол/статус), но плохо ведёт себя под высокой конкурентностью записи и в OLTP-нагрузке — область применения скорее OLAP/аналитика. Дополнительно: **покрывающий индекс** (covering index) — включает не только колонки условия поиска, но и колонки, которые запрос читает в `SELECT`, что позволяет ответить на запрос вообще не читая саму таблицу (index-only scan, экономия дискового I/O); в PostgreSQL конкретно реализуется через `CREATE INDEX ... (search_col) INCLUDE (col_a, col_b)` — колонки после `INCLUDE` физически хранятся в индексе только для index-only scan, но не участвуют в самом поиске/сортировке по индексу (это не то же самое, что многоколоночный индекс из всех этих полей сразу); **частичный индекс** (partial index) — строится только по подмножеству строк, удовлетворяющих условию (например только "непроведённые" заказы), меньше объёмом и быстрее для запросов именно по этому подмножеству; **BRIN** (Block Range Index) — компактный индекс для очень больших таблиц с естественной физической корреляцией между значением колонки и порядком строк на диске (типичный случай — временные ряды, где новые строки со временем идут физически позже: индекс хранит не точные позиции, а диапазоны блоков) — на порядки меньше по объёму, чем B-tree, но эффективен только пока сохраняется эта физическая упорядоченность (после массового `UPDATE`, переставляющего строки, эффективность может деградировать). Для доступа к PostgreSQL из Go — `pgx` (низкоуровневый, быстрый, см. также файл про Append-Only модель выше) или `sqlx` (более тонкая обёртка над `database/sql` с удобным маппингом в структуры) — конкретный выбор зависит от того, нужен ли полный контроль над протоколом (pgx) или привычный API поверх `database/sql` (sqlx). [37]

Диагностика медленного SQL-запроса: `EXPLAIN` показывает план выполнения (что оптимизатор *собирается* делать, по оценке), `EXPLAIN ANALYZE` реально выполняет запрос и показывает и оценку, и фактические цифры (реальное число строк и время на каждом узле плана) — расхождение оценки и факта часто и есть источник проблемы. На что смотреть в плане: тип узла (`Seq Scan` — последовательное сканирование всей таблицы, обычно тревожный знак на большой таблице, vs `Index Scan`/`Index Only Scan`), стратегия джойна (`Nested Loop` — хорош для малого числа строк с одной из сторон, `Hash Join`, `Merge Join` — для больших отсортированных/хешируемых наборов), сильное расхождение оценки числа строк с фактическим (признак устаревшей статистики — нужен `ANALYZE`, обновляющий статистику для оптимизатора). Частая причина, по которой индекс существует, но не используется: не-SARGable условия (например `UPPER(email) = 'X'` — функция над колонкой в условии мешает использовать обычный индекс по этой колонке без функционального индекса) или несовпадение типов данных в сравнении. `Bitmap Heap Scan` — комбинирует несколько битовых индексов, но может проседать под конкурентной нагрузкой. Долгие открытые транзакции копят «мёртвые» версии строк (dead tuples, из-за MVCC) — требуется `VACUUM`/`REINDEX` для поддержания физической структуры таблицы и индексов в порядке. [20, 22] Расширенный вызов `EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)` — реально исполняет запрос (как обычный `EXPLAIN ANALYZE`), дополнительно показывает статистику буферного кэша (`BUFFERS` — сколько страниц данных было прочитано из кэша `shared_buffers` против диска, отдельный источник инсайта помимо просто времени выполнения) и отдаёт план в структурированном JSON вместо текстового вывода — удобнее для автоматического парсинга инструментами мониторинга. Поскольку `EXPLAIN ANALYZE` (в отличие от простого `EXPLAIN`) реально выполняет запрос, для `INSERT`/`UPDATE`/`DELETE` это означает реальное изменение данных — безопасный способ снять план на таком запросе без побочных эффектов — обернуть в `BEGIN; EXPLAIN ANALYZE ...; ROLLBACK;`. [52]

## Систематическая воронка диагностики медленной БД — от простого к сложному

Показательный чек-лист порядка действий при деградации производительности БД, полезный именно как структура ответа на собесе (не просто перечисление техник, а обоснованный порядок — от дешёвых и точечных решений к дорогим и архитектурным): (1) проверить индексы через `EXPLAIN`/`EXPLAIN ANALYZE` (см. выше) — самое дешёвое и часто самое эффективное действие; (2) оптимизировать сами запросы (избегать `SELECT *`, устранять N+1); (3) тюнинг параметров самой СУБД (`shared_buffers`, `work_mem` и аналоги); (4) миграция с HDD на SSD, если узкое место — диск; (5) партиционирование таблиц (по дате/диапазону); (6) репликация (read-реплики для распределения чтения); (7) шардирование (горизонтальное разделение данных между узлами); (8) кэширование (Redis/Memcached перед БД); (9) денормализация схемы, если сама реляционная модель — источник накладных расходов; (10) специализированное хранилище под конкретный паттерн доступа (колоночное — для аналитики, time-series — для метрик), если общего назначения СУБД в принципе не подходит под нагрузку. Порядок важен: переход к шардированию/специализированному хранилищу до того, как исчерпаны более дешёвые и обратимые шаги (индексы, тюнинг, кэш) — типичная поспешность, которую стоит явно избегать формулировать как решение на собесе без обоснования, почему более простые шаги не годятся. [56]

## Идемпотентность и паттерн Idempotency Key

Идемпотентная операция — повторное её выполнение с теми же входными данными не меняет итоговый результат/состояние по сравнению с однократным выполнением (в HTTP-терминах: `GET`/`PUT`/`DELETE` идемпотентны по определению протокола, `POST` — нет). Практическая проблема — распределённые системы регулярно требуют повторных попыток (retry) после сетевого сбоя, и не всегда понятно, дошла ли первая попытка до сервера (ответ мог потеряться уже после того, как операция реально выполнилась) — повторная **не**идемпотентная операция (например «списать деньги», «создать заказ») рискует продублировать эффект. Паттерн Idempotency Key: клиент сам генерирует уникальный идентификатор конкретной попытки операции (обычно UUID) и передаёт его с каждым запросом, включая повторные; сервер при первом получении такого ключа выполняет операцию и сохраняет результат вместе с ключом (обычно с TTL — не хранить вечно); при получении **уже виденного** ключа — не выполняет операцию повторно, а сразу возвращает сохранённый результат первой попытки. В PostgreSQL реализуется естественно через `INSERT ... ON CONFLICT (idempotency_key) DO NOTHING` (или `DO UPDATE` с возвратом существующей записи) — атомарная проверка-и-вставка на уровне БД, без отдельной гонки между проверкой существования ключа и вставкой новой записи. [36]

## Docker/Kubernetes/CI-CD — минимальный ожидаемый набор знаний для позиции

Компактный чек-лист инфраструктурных тем, регулярно всплывающих на Go-собесах наравне с языком (реже разбираются глубоко, но само отсутствие ответа — красный флаг): Docker — многоступенчатые сборки (multi-stage builds: один этап компилирует бинарник в полноценном образе с тулчейном, финальный образ — только сам бинарник поверх минимальной базы вроде `scratch`/`alpine`, кардинально уменьшая размер конечного образа) и осознанная работа со слоями образа (порядок инструкций в Dockerfile влияет на переиспользование кеша слоёв при пересборке). Kubernetes — базовые сущности: Pod (минимальная деплоящаяся единица, один или несколько тесно связанных контейнеров), Deployment (декларативное управление набором реплик Pod'ов, раскатка новых версий), Service (стабильная точка доступа к меняющемуся набору Pod'ов), Ingress (маршрутизация внешнего HTTP(S)-трафика в кластер); readiness probe (готов ли Pod принимать трафик прямо сейчас — временное исключение из балансировки, не рестарт) и liveness probe (жив ли процесс вообще — при провале Kubernetes перезапускает контейнер) — частая путаница именно между этими двумя видами проб. CI/CD — общее знакомство с пайплайном (сборка → тесты → деплой) как процессом, не привязанное к конкретному инструменту. Базовые облачные примитивы — объектное хранилище (S3-совместимое), очереди сообщений (SQS-подобные), виртуальные машины (EC2-подобные) — на уровне «что это и зачем», без экспертизы в конкретном облаке. [35]

Более детальная эталонная архитектура CI/CD-пайплайна (ожидаемая на сеньорском уровне, когда за конкретные пайплайны в компании отвечает отдельная DevOps/платформенная команда, но кандидат должен уметь описать её в целом): стадии — линтинг и статический анализ (`golangci-lint`, `gosec` для security-паттернов, `gofmt`), юнит/интеграционные тесты (`go test -race -coverprofile`, тестконтейнеры для интеграционных тестов с реальной БД), сборка и сканирование образа (многоступенчатая Docker-сборка, сканер уязвимостей вроде Trivy, подпись образа), деплой в staging (автоматический, в соответствующий namespace Kubernetes), деплой в прод (с ручным подтверждением, канареечные релизы через Argo Rollouts — постепенный перевод трафика на новую версию с автоматическим откатом при деградации метрик). Управление конфигурацией — инфраструктура как код (Helm-чарты или Kustomize), секреты — через HashiCorp Vault или зашифрованные переменные CI, валидация манифестов декларативной политикой (Open Policy Agent, OPA) — например запрет деплоя без заданных лимитов ресурсов. Организационная модель — либо централизованная платформенная команда (Platform Engineering: предоставляет шаблоны и владеет инфраструктурой пайплайнов для всех остальных команд), либо self-service-подход (каждая команда сама настраивает пайплайн в рамках заданных платформой рамок/guardrails). Практический ориентир по метрикам самого пайплайна — длительность прогона в пределах 15–20 минут и доля успешных прогонов выше 95%. [39]

Организационный нюанс канареечных релизов, часто упускаемый в ответе «кто вообще принимает решение катить дальше/откатывать»: технически инфраструктуру канареечного релиза (постепенный перевод трафика, автоматизированный мониторинг метрик во время раскатки) эксплуатирует DevOps/SRE-команда, но пороговые значения метрик, при превышении которых раскатка должна остановиться или откатиться (какая деградация latency/error rate — это ещё «в пределах нормы», а какая уже «явный регресс, откатываем») — задаёт именно инженерная/продуктовая команда, разрабатывающая конкретный сервис, поскольку только она понимает бизнес-контекст критичности показателей для конкретной фичи; финальное решение в критичный момент (особенно для финансовых/платёжных систем с повышенной ценой ошибки) — коллективное, на уровне SRE/тимлида, а не единолично автоматики или единолично DevOps-инженера. Ответ «раскаткой занимается DevOps» без объяснения, кто формулирует критерии успеха/отката, интервьюеры оценивают как неполный именно из-за пропуска этого организационного разграничения ответственности. [70]

Дополнительные стадии, специфичные именно для gRPC-проектов (протофайлы как контракт, а не только код): `buf lint` — статическая проверка стиля/корректности самой `.proto`-схемы (аналог `golangci-lint`, но для Protobuf); `buf breaking` — отдельная проверка, не ломает ли текущее изменение схемы обратную совместимость для уже существующих потребителей контракта (например переиспользование номера поля, смена типа существующего поля) — блокирует мерж/деплой, если breaking change не был осознанно подтверждён. Тегирование собранного образа коммит-хэшем (не `latest`) — трассируемость точно того, какой код именно задеплоен. Валидация миграций БД как отдельный шаг пайплайна перед деплоем. Для готовности gRPC-сервиса к проду в Kubernetes — `readiness`/`liveness`-пробы через специализированный `grpc_health_probe` (проверяет именно gRPC health-check протокол, а не обычный HTTP-эндпоинт, которого у чистого gRPC-сервиса может не быть). [66]

## SQL: агрегация, `WHERE` vs `HAVING`, композитные индексы

Типовая задача — «посчитать число заказов по каждому пользователю с ценой не ниже порога, отсортировать по убыванию» — стандартная связка `WHERE` (фильтр строк **до** агрегации) + `GROUP BY` + `COUNT(*)` + `ORDER BY`. Ключевое разграничение, которое часто путают: `WHERE` фильтрует исходные строки до группировки, `HAVING` — фильтрует уже сгруппированные результаты (например «оставить только пользователей с более чем 5 заказами» — это обязательно `HAVING COUNT(*) > 5`, потому что агрегированного значения `COUNT(*)` ещё не существует на этапе, где применяется `WHERE`). Композитный (составной) индекс по нескольким колонкам сразу ускоряет типичные запросы с фильтром+группировкой/сортировкой по этим же колонкам вместе — но порядок колонок в составном индексе имеет значение (индекс эффективно используется только если запрос фильтрует/сортирует по префиксу колонок индекса слева направо). Практическое правило выбора порядка колонок в композитном индексе — колонку с наибольшей селективностью (больше уникальных значений, сильнее сужает выборку) ставить первой: B-tree-индекс просматривается слева направо без «пропусков» середины, поэтому запрос с условием только по второй колонке индекса (например `WHERE first_name = 'X'` при индексе `(last_name, first_name, gender)`) вообще не сможет эффективно использовать этот индекс, а запрос по первой колонке (`WHERE last_name = 'X'`) — сможет в полной мере. Индексы не бесплатны — каждая операция записи (`INSERT`/`UPDATE`/`DELETE`) обязана обновить все существующие индексы затрагиваемой таблицы, поэтому бездумное индексирование всех колонок подряд замедляет запись без пользы для чтения; практический способ найти неиспользуемые индексы — представление `pg_stat_user_indexes`, где `idx_scan = 0` (индекс ни разу не был использован планировщиком с момента последнего сброса статистики) — явный кандидат на удаление. Обработка `NULL` требует явного внимания: `NULL` не участвует в обычных сравнениях (`WHERE x = NULL` никогда не находит строк — нужен `IS NULL`), а при агрегации `COUNT(*)` считает все строки группы, тогда как `COUNT(column)` пропускает `NULL`-значения этой колонки — если, например, `user_id` может быть `NULL` (гостевой заказ) и это критично отличать от реальных пользователей, надёжнее явный `COUNT(DISTINCT order_id)` вместо простого `COUNT(*)`, чтобы не исказить агрегат наличием технических NULL-строк. [24]

## SQL: уникальные пары после агрегирующего подзапроса + типы JOIN

Показательная задача: вернуть уникальные пары (пользователь, товар) по всем покупкам, совершённым **до** бана пользователя, отсортировав по имени и ID товара — с нюансом, что у пользователя может быть несколько банов подряд, а нужна отсечка именно по **первому** из них:

```sql
SELECT DISTINCT u.id, u.name, p.product_id
FROM purchases p
INNER JOIN users u ON p.user_id = u.id
INNER JOIN (
  SELECT user_id, MIN(ban_date) AS first_ban_date
  FROM bans GROUP BY user_id
) fb ON u.id = fb.user_id
WHERE p.purchase_date < fb.first_ban_date
ORDER BY u.name, p.product_id;
```

Подзапрос с `MIN(ban_date)` группировкой по пользователю схлопывает множественные баны до одной даты первого бана на пользователя — без этого шага джойн с таблицей банов размножил бы строки покупок на количество банов того же пользователя, и `DISTINCT` пришлось бы применять уже поверх изначально раздутого набора строк. `INNER JOIN` семантически корректен и эффективнее `LEFT JOIN` для этой задачи, потому что интересуют только пользователи, у которых бан вообще есть — `LEFT JOIN` для этого случая часто выбирают по инерции, не всегда явно объясняя, зачем: **важный нюанс** — если после `LEFT JOIN bans` в `WHERE` стоит условие, ссылающееся на колонку из `bans` (в примере — `ban_date`), это условие всё равно отсеивает строки с `NULL` в этой колонке (то есть пользователей без бана), и `LEFT JOIN` фактически начинает вести себя как `INNER JOIN` — разница между `ON`-условием (не отсеивает, сохраняет `NULL`) и `WHERE`-условием (отсеивает `NULL`-строки) — то, что часто путают на собесе, выбирая `LEFT JOIN` неявно вместо того, чтобы явно осознать, что итоговая семантика запроса и так стала INNER. Сводка типов JOIN: `INNER` — только совпавшие строки с обеих сторон; `LEFT` — все строки левой таблицы плюс совпадения справа (или `NULL`, если нет совпадения); `RIGHT` — симметрично для правой; `FULL OUTER` — все строки с обеих сторон; `CROSS` — декартово произведение (все комбинации, без условия совпадения). [41]

## Транзакции и уровни изоляции (ACID)

Транзакция — атомарная логическая единица работы с БД: либо выполняется целиком (`COMMIT`), либо откатывается целиком (`ROLLBACK`), без промежуточных частично применённых состояний. ACID: Atomicity (атомарность — всё или ничего), Consistency (согласованность — переход из одного валидного состояния данных в другое), Isolation (изоляция — конкурентные транзакции не видят «сырые» промежуточные результаты друг друга), Durability (устойчивость — после коммита изменения переживают сбой/перезапуск). Классический иллюстративный пример — денежный перевод между счетами: списание с одного и зачисление на другой должны либо оба применяться, либо ни один. Уровни изоляции (по возрастанию строгости, каждый следующий закрывает больше аномалий ценой производительности): Read Uncommitted (видны даже незакоммиченные изменения других транзакций — «грязное чтение», на практике почти нигде не используется всерьёз — в PostgreSQL этот уровень синтаксически принимается, но реально работает как Read Committed из-за архитектуры MVCC, физически «грязного чтения» там не бывает), Read Committed (видны только закоммиченные данные, но повторное чтение той же строки в рамках одной транзакции может дать другой результат — non-repeatable read; это дефолт в PostgreSQL), Repeatable Read (повторное чтение той же строки стабильно в рамках транзакции за счёт консистентного снэпшота на момент старта транзакции, но возможны «фантомные» строки — новые строки, появившиеся от чужих коммитов между двумя одинаковыми запросами с условием), Serializable (самый строгий — эквивалентно последовательному выполнению транзакций одна за другой, полностью исключает аномалии ценой наибольших накладных расходов на блокировки/повторные попытки). В PostgreSQL и Repeatable Read, и Serializable реализованы через единый механизм SSI (Serializable Snapshot Isolation) — Serializable дополнительно отслеживает предикатные блокировки (predicate locking) поверх снэпшота, чтобы ловить и фантомные аномалии тоже. Практический ориентир — Read Committed достаточен для типичной OLTP-нагрузки; более высокие уровни — там, где цена ошибки высока (финансы/биллинг), с обязательной обработкой ошибок сериализации (retry при конфликте) на прикладном уровне. В Go — работа с транзакциями через `sql.DB.BeginTx(ctx, opts)`, где `opts` позволяет явно задать нужный уровень изоляции для конкретной транзакции. [20, 25]

Практический контраргумент для конкретно банковского сценария «списать деньги со счёта» — не всегда правильный ответ автоматически «бери уровень построже» (Serializable/Repeatable Read): для точечного изменения баланса одного известного счёта часто предпочтительнее именно Read Committed (дефолт) в сочетании с явной блокировкой конкретной строки через `SELECT balance FROM accounts WHERE id = $1 FOR UPDATE` перед проверкой достаточности средств и обновлением — блокировка ложится точно на нужную строку, конкурентные транзакции над **другими** счетами продолжают работать без взаимных помех, и не возникает ошибок сериализации (`40001`), которые пришлось бы перехватывать и ретраить целиком на уровне приложения при более строгом уровне изоляции. Дополнительная защитная мера на уровне самой схемы БД — ограничение `CHECK (balance >= 0)` прямо на колонке баланса, отдельный, не зависящий от прикладной логики барьер против ухода баланса в минус даже при ошибке в коде приложения. [52]

## `GOMAXPROCS` внутри Kubernetes-контейнера с CPU-лимитом — частая ловушка

Частое непонимание: `1 CPU` в лимитах Kubernetes — это один виртуальный vCPU (логическое ядро), `0.5` — половина процессорного времени одного ядра (не «половина ядра» в смысле физического деления). Лимиты CPU в Kubernetes реализованы через Linux cgroups (CFS — Completely Fair Scheduler): процессу нарезается квота процессорного времени за период, а не буквально урезается число видимых ядер. Ловушка для Go-приложений: рантайм Go по умолчанию видит **все** ядра хост-машины через `runtime.NumCPU()` и выставляет `GOMAXPROCS` под них, даже если контейнеру по cgroup-лимиту выделена лишь часть этого CPU — в результате рантайм создаёт больше системных потоков (M), чем реально может параллельно исполняться под квотой, что приводит к CPU throttling (принудительным паузам исполнения при исчерпании квоты периода) и деградации задержки, незаметной по «средней» загрузке CPU. Решение — библиотека `go.uber.org/automaxprocs`: автоматически считывает реальный cgroup-лимит контейнера и выставляет `GOMAXPROCS` в соответствии с ним при старте приложения (обычно одной строкой импорта с side-effect `_ "go.uber.org/automaxprocs"`). [23]

Более полная картина проблемы (даже с выставленным правильно `GOMAXPROCS`): системные потоки самого рантайма Go, занятые вводом-выводом и работой GC, тоже потребляют CPU-время, но не учитываются в бюджете, который подразумевает `GOMAXPROCS` (он ограничивает число потоков, **исполняющих пользовательский Go-код**, а не вообще все потоки процесса) — то есть реальное потребление CPU процессом всегда несколько выше «чистого» `GOMAXPROCS`-бюджета. Throttling по cgroup CFS-квоте не просто линейно замедляет, а даёт скачкообразные задержки сразу по всем горутинам процесса (весь процесс «замирает» до начала следующего периода квоты). Рост очереди необработанных запросов при throttling может неожиданно проявиться как скачок потребления памяти (растущие буферы ожидания), способный спровоцировать OOM-килл пода, формально не упираясь в лимит CPU напрямую. Троттлинг может задеть и потоки netpoller'а, что проявляется как таймауты на уровне приложения, которые по симптомам выглядят как сетевая проблема, а не CPU. Практический ориентир — резервировать 10–20% CPU-бюджета контейнера сверх заявленного `GOMAXPROCS` под системные накладные расходы рантайма, а не выставлять лимиты «впритык». [34]

Конкретные метрики для диагностики именно CPU-throttling на уровне cgroup CFS (а не догадки по косвенным признакам): `container_cpu_cfs_throttled_periods_total` (сколько периодов планирования контейнер был принудительно приторможен квотой) и `container_cpu_cfs_throttled_seconds_total` (суммарное время, потраченное в throttled-состоянии) — рост этих метрик при внешне невысокой средней загрузке CPU — прямое и однозначное доказательство именно троттлинга, а не общей нехватки ресурсов. Практические меры при обнаружении: увеличить `limits.cpu`, перейти на Guaranteed QoS-класс (`requests` == `limits`, что предсказуемее делит CPU между подами на ноде), включить/настроить Horizontal Pod Autoscaler по этой метрике, либо снижать саму нагрузку через оптимизацию кода. [43]

## Виртуальная память и OOM Killer — фон для диагностики падений пода по памяти

Страницы памяти (memory pages, типичный размер — 4 КБ) — единица отображения виртуальных адресов процесса на физическую память; виртуальная память даёт процессу иллюзию большего объёма памяти, чем физически доступно (через подкачку/swapping), и изоляцию адресных пространств между процессами. Когда физическая память (с учётом лимитов cgroup для контейнера) исчерпана — ядро Linux запускает OOM Killer, который выбирает жертву для принудительного завершения (`SIGKILL`) по взвешенному показателю `oom_score` (учитывает объём используемой памяти процессом, его `nice`-приоритет, время работы и ряд других факторов) — процесс с наибольшим `oom_score` завершается первым. Показатель настраивается вручную через `/proc/<pid>/oom_score_adj` (отрицательное значение снижает шанс стать жертвой, положительное — повышает) — полезно, если в контейнере несколько процессов и один из них критичнее для сохранения. Важное разграничение при диагностике падения пода — CPU-throttling (см. выше) и OOM Killer работают на разных уровнях (CFS-планировщик CPU vs подсистема управления памятью ядра) и требуют разных метрик/логов для диагностики: throttling не убивает процесс, лишь замедляет; OOM Killer убивает процесс безвозвратно (в Kubernetes это видно как `OOMKilled` в статусе контейнера). [43]

## Контейнеризация vs виртуализация

Виртуальная машина эмулирует полноценное железо и запускает под собой отдельную ОС целиком — изоляция сильнее, но накладные расходы выше: размер образа порядка гигабайт, время старта — минуты. Контейнер разделяет ядро ОС хоста с другими контейнерами (изоляция на уровне процесса через механизмы ядра Linux — namespaces для изоляции пространств имён — процессов/сети/файловой системы/пользователей, и cgroups для ограничения и учёта потребления ресурсов — CPU/памяти/диска) — размер образа порядка мегабайт, старт — секунды; плотность размещения на одном хосте намного выше, чем у ВМ, ценой более слабой изоляции (общее ядро — потенциальная поверхность атаки при эксплуатации уязвимостей ядра). Docker — стандартная реализация контейнеризации поверх этих примитивов ядра; Kubernetes — оркестрация множества контейнеров на кластере машин (планирование, масштабирование, самовосстановление). Компромисс на собесе стоит формулировать именно как «плотность/скорость запуска vs строгость изоляции», а не абсолютное превосходство одного подхода. [20]

## Load average — метрика загрузки системы (фон для системного дизайна/эксплуатации)

Load average — усреднённое число процессов, которые в данный момент выполняются на CPU или ожидают своей очереди на выполнение (то есть не только реально работающие, но и готовые к работе), усреднённое за 1, 5 и 15 минут — три числа вместе показывают тренд (растёт/падает/стабильно). Ориентир для интерпретации: load average, примерно равный числу ядер CPU — система утилизирована полностью, но справляется; заметно выше — очередь на CPU растёт, возможна деградация задержки. Важное отличие от утилизации CPU (`%CPU`): высокий load average может быть вызван не только CPU-bound нагрузкой, но и процессами, ожидающими I/O (диск/сеть) — на некоторых системах такие процессы тоже засчитываются в load average, поэтому высокий load при низкой видимой загрузке CPU часто указывает именно на I/O-bound узкое место, а не на нехватку вычислительных ресурсов. [20]

## Диагностика деградации распределённой системы — протокол из 5 фаз

Структурированный ответ на вопрос «прод тормозит, с чего начать искать причину» — показательный сеньорский фреймворк, а не просто список инструментов: (1) **метрики (~30 сек)** — сначала посмотреть агрегированные дашборды (Grafana), чтобы быстро локализовать, какой именно сервис/компонент аномален, не тратя время на детали; (2) **логи (~2 мин)** — агрегированный поиск паттернов ошибок по уже заподозренному сервису (ELK/Loki), а не построчное чтение всего подряд; (3) **трейсинг** — найти конкретный проблемный span в цепочке вызовов запроса (какой именно хоп/сервис вносит задержку/ошибку — см. также раздел про распределённый трейсинг выше); (4) **события инфраструктуры** — проверить корреляцию по времени с деплоями/изменениями конфигурации (частая причина инцидента — что-то выкатили только что); (5) **каскадные паттерны** — проверить, не сработали ли (или не должны ли были сработать) защитные механизмы against каскадных отказов: circuit breaker, retry storms (лавинообразный рост ретраев при частичном отказе, усугубляющий проблему вместо решения), bulkhead isolation (изоляция отказа одного потребителя/раздела системы от остальных). Ключевая идея порядка фаз — идти от широкого и дешёвого (агрегированные метрики) к узкому и дорогому (конкретный трейс/лог), а не наоборот. [30]

## Наблюдаемость на практике — стек и платформенная автоматизация одной компании

Пример реального прод-стека (крупная российская компания, команда мониторинга): VictoriaMetrics — высокопроизводительная и ресурсоэффективная time-series БД для метрик (альтернатива/надстройка над классическим Prometheus TSDB для больших объёмов); ClickHouse — колоночная БД для долгосрочного хранения и аналитики (метрики/логи за длинные периоды, которые невыгодно держать в «горячей» TSDB); Prometheus — фактический стандарт сбора метрик (pull-модель, см. выше); Grafana — единая визуализация поверх всех источников; Alertmanager — маршрутизация и группировка алертов (дедупликация похожих алертов, чтобы не заваливать дежурного десятками копий одного и того же инцидента). Показательная деталь именно платформенного, а не ad-hoc подхода к observability — автоматизация «в один клик»: при создании нового сервиса на внутренней платформе мониторинг (набор дашбордов с «золотыми сигналами» — трафик/ошибки/задержка/насыщение) подключается автоматически, без отдельной настройки со стороны команды-владельца сервиса; метрики контейнеров/подов Kubernetes привязываются автоматически; общие («коммунальные») дашборды доступны всем командам сразу по стандартному шаблону; отдельная платформенная команда отвечает за retention (сколько хранить), storage и маршрутизацию алертов централизованно — команды-потребители наблюдаемости получают её «бесплатно» по умолчанию, а не как отдельную инженерную задачу при каждом новом сервисе. [31]

## Масштабирование PostgreSQL для точечных чтений по ключу на большой таблице

Задача — быстрые случайные чтения по точному ключу на таблице масштаба ~100 млн строк. На одном узле: хеш-индекс (`CREATE INDEX ... USING HASH (id)`) даёт теоретически O(1) точный поиск по ключу (в противовес O(log n) у B-tree) — но не решает саму проблему упора в диск, если рабочий набор данных не помещается в память: тюнинг `shared_buffers` (доля оперативной памяти, отведённая PostgreSQL под кэш страниц данных) — первый рычаг, прежде чем усложнять архитектуру. Партиционирование таблицы для этого конкретного паттерна доступа (точечный поиск по случайному ключу, без диапазонных запросов) не помогает — партиции полезны, когда запросы естественно ограничены диапазоном ключа партиционирования, а не при равномерно случайном доступе по всему пространству ключей. Горизонтальное масштабирование чтения — асинхронные read-реплики (распределяют нагрузку чтения и дисковый I/O по нескольким узлам; синхронная репликация вместо асинхронной — гарантия отсутствия потери данных ценой дополнительной задержки на запись), с роутером, направляющим записи всегда на primary, а чтения — на primary или реплики. Дальнейшее масштабирование — шардирование по хешу ключа (`shard = hash(key) % N`), что даёт линейное масштабирование по записи ценой сложности при перераспределении шардов (ресёрдинге); готовые инструменты — расширение Citus для PostgreSQL либо шардирование на уровне приложения. Практический тезис с этого разбора: для сценария «точечные чтения по первичному ключу» репликация PostgreSQL часто проще и надёжнее, чем добавление внешнего кэша (Redis) поверх, поскольку сохраняет ACID-гарантии в пределах кластера БД, тогда как внешний кэш добавляет отдельный класс проблем согласованности (инвалидация, staleness). [32]

## Сквозной кейс: in-memory KV-хранилище с персистентностью с нуля

Ещё один показательный «сквозной» системный дизайн — спроектировать собственное key-value хранилище в памяти с гарантией долговечности (durability) при падении процесса:

- **Конкурентный доступ к данным в памяти:** обычная map под `sync.RWMutex` (читатели не блокируют друг друга) — рабочий базовый вариант; для снижения конкуренции под нагрузкой — шардирование самой map на N независимых кусков по хешу ключа (`shards[hash(key) % 256]`), у каждого шарда — свой мьютекс, что даёт кандидату на конкурентность на два порядка больше, чем один общий лок на всё хранилище.
- **Персистентность через append-only лог (WAL-подобный подход):** каждая операция изменения (`SET key value`, `DELETE key`) дописывается в лог-файл строго последовательно (быстрая операция — только дозапись в конец файла, без произвольного доступа), опционально с контрольной суммой (CRC) на запись для обнаружения повреждения при сбое посреди записи. Восстановление после падения процесса — последовательное «переигрывание» (replay) всего лога от начала для реконструкции состояния map в памяти.
- **Компромисс durability vs производительность записи:** синхронный `fsync` после каждой операции — максимально надёжно, но медленно (каждая запись ждёт физического сброса на диск); батчинг — `fsync` раз в N операций или по таймеру — быстрее, ценой ограниченного, но ненулевого окна потери данных при падении между `fsync`; полностью асинхронная запись без `fsync` вообще — максимальная скорость, максимальный риск (обычно неприемлемо для данных, которые нельзя потерять).
- **Рост лога и компакция:** лог только растёт, поэтому периодически нужна компакция — фоновый процесс вычитывает текущий лог, сравнивает с актуальным состоянием map, пишет **только актуальные** записи (устаревшие/удалённые значения отбрасываются) в новый файл и атомарно подменяет им старый лог, не блокируя обслуживание текущих запросов (компакция под `RLock`, а не полной блокировкой). Для параллельности самой компакции — шардирование лога так же, как и map (`shardID = hash(key) % N`, отдельный файл `wal-N.log` на шард), позволяет компактить шарды параллельно и распределять дисковый I/O по нескольким файлам/дискам.
- **Ускорение восстановления через снапшоты:** периодический полный дамп состояния map целиком в файл-снапшот, с усечением (truncate) WAL-лога до точки, на которой сделан снапшот — при рестарте процесс загружает снапшот целиком (быстро) и переигрывает только «хвост» лога **после** снапшота (небольшой), а не весь лог с начала времён.
- **Вытеснение/удаление устаревших данных:** TTL-подход — периодическое сканирование map и удаление истёкших по времени ключей; альтернативно — политики вытеснения по объёму (LRU/LFU) с отдельной структурой учёта (куча/связный список) для быстрого выбора кандидата на вытеснение при достижении лимита памяти. [32]

## Сквозной кейс: платформа поддержки клиентов в реальном времени (мульти-тенантный чат)

Показательный системный дизайн — не привязан к Go специфично (применим к любому бэкенд-стеку), но содержательно полезен как ещё один сквозной кейс, дополняющий уже разобранные (сервис кликов, in-memory KV-хранилище выше):

- **Мульти-тенантность — три стратегии изоляции данных, а не одна универсальная:** общая БД + общая схема (все таблицы несут колонку `tenant_id`, простейший вариант, минимум операционных накладных расходов) — для мелких тенантов; общая БД + отдельная схема на тенанта (изоляция на уровень выше без отдельного кластера) — для средних; отдельная выделенная БД/кластер на тенанта — для крупных тенантов с высокими требованиями к изоляции/производительности. Гибридный подход (разная стратегия для тенантов разного масштаба одновременно) — практичнее, чем выбор одной стратегии для всех. Row-Level Security (RLS) на уровне PostgreSQL — механизм принудительной фильтрации строк по `tenant_id` прямо на уровне СУБД (а не только в коде приложения) для варианта с общей схемой — дополнительный барьер защиты от бага в прикладном коде, случайно вернувшего данные чужого тенанта.
- **WebSocket-гейтвей для real-time доставки сообщений:** сервер держит в памяти реестр активных соединений на комнату/чат («hub»), балансировка между инстансами шлюза — через consistent hashing по ID чата (гарантирует, что все участники одного чата попадают на один и тот же инстанс шлюза, упрощая рассылку внутри инстанса); горизонтальное масштабирование между несколькими инстансами шлюза — через Redis Pub/Sub как связующий мост (сообщение, пришедшее на один инстанс, публикуется в Redis и разлетается остальным инстансам, у которых есть локальные соединения нужных участников). Альтернативы WebSocket и их ограничения: long polling (высокая задержка, повышенная нагрузка на сервер от постоянных переоткрытий соединения), Server-Sent Events (только однонаправленный поток сервер→клиент, не годится для двустороннего чата), WebTransport/HTTP-3 (ограниченная поддержка браузерами на момент разбора).
- **Разделение профилей B2C и B2B в отдельные таблицы, а не одну общую:** хранение профилей клиентов и профилей сотрудников поддержки в одной таблице пользователей — антипаттерн: раздутая схема (много `NULL`-полей, нерелевантных для одной из ролей), конфликтующие требования к индексам между двумя сильно разными паттернами доступа, комплаенс-сложности (разные требования к персональным данным клиентов vs корпоративным данным сотрудников), да и просто на порядки разный масштаб (миллионы клиентов vs тысячи агентов поддержки в одной таблице создают взаимную деградацию производительности). Решение — раздельные таблицы `customer_profiles`/`agent_profiles` поверх общей таблицы аутентификации.
- **Стратегии разрешения конфликтов при одновременном редактировании одной записи (тикета):** оптимистичная блокировка (версионирование записи, конфликт обнаруживается по несовпадению версии при сохранении); Operational Transform (алгоритмическое слияние конкурентных правок, как в совместных редакторах текста); last-write-wins (простейший вариант, но ценой потери одной из конкурентных правок без предупреждения) — выбор зависит от того, насколько критична потеря данных при редком одновременном редактировании одной записи.
- **Плавная деградация под нагрузкой на грани SLA** — ступенчатое отключение необязательной функциональности при приближении к лимитам мощности, вместо равномерной деградации всего сразу: сначала отключить индикаторы «печатает…» (незначимо, но недёшево при большом числе одновременных чатов), затем увеличить интервалы поллинга второстепенных данных, затем отключить прочую некритичную функциональность — обязательные circuit breaker'ы на внешние зависимости работают на всех этапах.
- **Неравномерная географическая нагрузка (правило вроде 80/20 между регионами)** — планирование ёмкости и failover между зонами доступности должно закладываться именно под пиковую нагрузку самого нагруженного региона, а не по среднему значению по всем регионам сразу. [55]

## Микросервисная архитектура — паттерны из практики

Декомпозиция монолита на микросервисы: паттерн retry (повторные попытки при сбое зависимости), API Gateway (свой Go-сервис, который редьюсит/матчит/джойнит JSON из нескольких бэкендов в один ответ клиенту), разделение чтения и записи (read/write separation), осознанный выбор синхронного vs асинхронного взаимодействия сервисов. [13]

Более полный набор принципов **осознанной** декомпозиции (в противовес бездумному дроблению на множество мелких сервисов «потому что модно») — по разбору реального кейса миграции монолита (антивирус-проверка файлов как один из выделенных сервисов): доменные границы по DDD (bounded context — сервис отвечает ровно за одну связную предметную область, а не за произвольный набор функций), высокая связность внутри сервиса при слабой связанности между сервисами (high cohesion / loose coupling), независимость деплоя каждого сервиса от остальных, изоляция данных (каждый сервис владеет своей БД, не лезет напрямую в чужую схему), разные профили масштабирования и нагрузки как повод для отдельного сервиса (например CPU-тяжёлая проверка антивирусом — отдельно от лёгкого сервиса уведомлений), изоляция отказов (сбой в одном домене — например недоступность стороннего антивирус-API — не должен ронять соседние домены вроде OCR/перевода), стабильные версионированные интерфейсы между сервисами (контракт не меняется на каждый чих, а версионируется явно). Практическая иллюстрация: сервис проверки файлов/URL на вирусы вынесен отдельно именно потому, что зависит от медленного внешнего API и должен изолированно деградировать, не блокируя остальную систему — общение с остальными сервисами через message broker (асинхронно) и gRPC (синхронно, для быстрых внутренних запросов), с единым API Gateway как точкой входа для внешних клиентов. [65]

Смежное различение, часто путаемое кандидатами на практике — **stateless vs stateful** сервисы: stateless-сервис не хранит критичное для бизнес-логики состояние пользователя в памяти между запросами — благодаря этому его можно свободно масштабировать горизонтально и перезапускать без skoordinированной миграции состояния (большинство прикладных backend-сервисов и должны проектироваться именно так, вынося любое нужное состояние во внешнее хранилище — БД, Redis, брокер). Stateful-компоненты (сами БД, брокеры сообщений, хранилища сессий) — исключение из этого правила: они обязаны хранить состояние по определению, и поэтому требуют репликации и согласованной обработки отказов (кворумы, лидер-выборы) вместо простого «поднять новую копию взамен упавшей». [65]

Конкретный код-паттерн идемпотентной обработки повторяющегося события/транзакции (дополняет уже описанный выше паттерн Idempotency Key другой типовой формой реализации — проверка по естественному ключу самой сущности, а не по отдельно сгенерированному клиентом идентификатору попытки):
```go
existing, err := s.repo.GetByHash(ctx, tx.Hash)
if err != nil && !errors.Is(err, sql.ErrNoRows) {
    return fmt.Errorf("get tx: %w", err)
}
if existing != nil {
    return nil // уже обработано — идемпотентный no-op
}
```
Здесь ключом идемпотентности выступает хэш самой транзакции (естественно уникальный для данных), а не отдельно сгенерированный UUID попытки — уместно, когда сама доменная сущность уже несёт достаточно уникальности. [65]

## Append Only модель и выбор между ORM и raw SQL

Append Only (только-добавление) — модель данных, где записи не обновляются, а инкрементально добавляются; «обновление» поля реализуется через дублирование записи с новым значением, а не мутацию старой — концептуально близко к event sourcing (хранится история изменений, а не только текущее состояние). Для PostgreSQL в такой модели выбор в пользу `pgx` (низкоуровневая, быстрая библиотека-драйвер) вместо ORM — осознанный компромисс в пользу контроля и производительности в критичных по нагрузке местах, ценой более многословного кода на raw SQL. [13]

## Сквозной кейс с собеса: сервис подсчёта уникальных кликов (эволюция решения)

Показательный пример того, как один и тот же дизайн последовательно углубляют на собесе, слой за слоем:

- **In-memory → почему ломается в проде:** очевидная причина — потеря данных при рестарте процесса; но интервьюер ждёт ещё: несогласованность при горизонтальном масштабировании (несколько инстансов сервиса не видят данные друг друга — split-brain по счётчикам), отсутствие мониторинга, отсутствие graceful shutdown, отсутствие rate limiting.
- **Рост RPS — не только «добавить ядер CPU»:** балансировка нагрузки между репликами, шардирование мьютексов/данных, батчинг запросов, кэширование, lock-free атомарные операции вместо мьютекса там, где применимо, миграция на внешнее хранилище.
- **Переход на Redis:** `Redis Set` — для точного подсчёта уникальных значений, TTL — для автоматической очистки устаревших данных. Более глубокий вариант — `HyperLogLog` (вероятностная структура для подсчёта уникальных элементов) вместо точного `Set`: сильно экономит память ценой небольшой погрешности в счёте — компромисс, который стоит явно проговаривать на собесе (точность vs память). Плюс важны connection pooling и pipelining (батчинг команд в одно сетевое обращение) при работе с Redis из Go.
- **Шардирование и «горячие ключи» (hot key):** если конкретные авторы (условные «звёзды») получают на порядки больше кликов — стоит их разносить на отдельные бакеты/шарды искусственно (bucketing: разбить один ключ на N суб-ключей и агрегировать при чтении), либо выделять таким «звёздам» отдельные выделенные шарды, локальное кэширование горячих значений и динамическую перебалансировку. Асимметрия чтения/записи для горячих ключей — тоже отдельная тема для обсуждения (чтения обычно можно кэшировать агрессивнее записи).
- **Батчинг как отдельная оптимизация:** снижает RPS к шарду и дедуплицирует повторяющиеся события внутри буфера перед отправкой — но сам по себе не решает проблему неравномерного распределения нагрузки, работает в связке с шардированием/репликацией, а не вместо них.
- **Мульти-датацентровая отказоустойчивость:** пережить отказ одного дата-центра целиком — Active-Active (все ДЦ обслуживают трафик одновременно) vs Active-Passive (резервный ДЦ включается при отказе основного), Redis Sentinel/Cluster для кросс-ДЦ репликации, компромиссы теоремы CAP (при разрыве связи между ДЦ выбор между консистентностью и доступностью), плавная деградация функциональности вместо полного отказа, идемпотентность операций — важна при повторных попытках (retry) после сетевых сбоев.
- **Рост объёма хранимых данных:** обнаружение горячих ключей, политики вытеснения Redis (LRU/LFU), экономия памяти через HyperLogLog вместо точных множеств, партиционирование по диапазону в PostgreSQL для архивации «холодных» (старых, редко читаемых) данных, многоуровневое хранение (горячий слой в Redis, холодный — в реляционной БД). [16]

## Redis: назначение и компромиссы

In-memory хранилище — задержки на уровне микросекунд; типичное применение — кэш перед основной БД, чтобы снять с неё нагрузку (пример из интервью — хранение координат такси в реальном времени). Поддерживает персистентность на диск (RDB-снапшоты, AOF-журнал), но это компромисс, а не полная надёжность. Минусы: объём данных ограничен объёмом RAM (дорого для больших датасетов), асинхронная репликация несёт риск потери данных при отказе мастера до синхронизации реплики, исторически однопоточный (с Redis 7+ появилась многопоточность для I/O), нет сложных запросов/джойнов как в реляционной БД. Дополнительно стоило бы упомянуть на собесе стратегии инвалидации кэша и геопространственные возможности Redis (для того же примера с координатами). [15]

## Redis: паттерн Lazy Read-Through + Compare-And-Swap против cache stampede

Показательная задача с живого собеса — снизить задержку валидации промокода с 70 мс (прямой поход в БД на каждую проверку) до 15 мс через кэширование в Redis, с явным вниманием к «эффекту грозовой тучи» (cache stampede/thundering herd — уже описанному в контексте in-memory кэша выше, здесь тот же эффект, но на уровне распределённого кэша): при истечении TTL популярного ключа одновременно множество параллельных запросов промахиваются мимо кэша разом и все синхронно бьют в БД. Паттерн Lazy Read-Through — приложение само отвечает за заполнение кэша при промахе (в отличие от Write-Through, где запись сразу идёт и в кэш, и в БД): `GET` из Redis → при промахе читать из БД → записать результат обратно в Redis с TTL → отдать вызывающей стороне. Защита от stampede именно на этом шаге — компромисс между условной блокировкой (только одна горутина/инстанс реально идёт в БД, остальные ждут её результата — концептуально тот же принцип, что и `singleflight`/turnstile выше, только в масштабе распределённой системы, а не одного процесса) и Compare-And-Swap на уровне самого Redis (`SET key value NX` — атомарная установка значения-«замка» только если ключа ещё нет, дающая ровно одному инстансу право на поход в БД, остальные видят существующий замок и либо ждут, либо отдают чуть устаревшее значение) — оба подхода не позволяют параллельному шторму запросов одновременно долбить БД при истечении одного горячего ключа. [60]

## MVCC на уровне конкретных полей строки — `xmin`/`xmax`

Более конкретный технический уровень уже описанного выше MVCC в PostgreSQL: каждая физическая версия строки несёт служебные поля `xmin` (ID транзакции, создавшей эту версию строки) и `xmax` (ID транзакции, пометившей эту версию как устаревшую/удалённую, если применимо) — читающая транзакция видит только те версии строк, чей `xmin` завершился раньше начала её собственного снэпшота, и чей `xmax` либо не установлен, либо принадлежит транзакции, ещё не завершившейся на момент снэпшота читателя. Именно за счёт этого механизма читатели работают с согласованным снэпшотом данных, вообще не блокируя писателей (и наоборот) — старые версии строк с уже неактуальным `xmax` физически остаются на диске до прохода `VACUUM`, что и создаёт уже описанные выше «мёртвые» dead tuples. [62]

## Пессимистичная и оптимистичная блокировка — конкретная SQL-реализация обеих

Пессимистичная блокировка — `SELECT ... FROM table WHERE id = $1 FOR UPDATE`: строка физически блокируется на чтение-с-намерением-изменить сразу, удерживая лок на всё время транзакции — предотвращает конфликт заранее, ценой риска высокой конкуренции за одну и ту же строку и потенциального deadlock при неправильном порядке захвата нескольких строк разными транзакциями (см. уже описанное правило фиксированного порядка захвата локов выше). Оптимистичная блокировка — отдельное поле-версия (`version`) на строке, конфликт обнаруживается только в момент записи, а не заранее:

```sql
UPDATE accounts
SET balance = $1, version = version + 1
WHERE id = $2 AND version = $3;
```

Если запрос вернул `0` затронутых строк (`RowsAffected() == 0`) — значит между чтением и попыткой записи кто-то другой уже успел обновить эту же строку (текущая версия в БД уже не совпадает с ожидаемой `$3`) — приложение обязано перечитать актуальное состояние и повторить попытку (retry на уровне приложения, а не на уровне БД). Оптимистичная блокировка масштабируется лучше при низкой реальной конкуренции за конкретные строки (не держит лок впустую, пока никто не конфликтует), но требует явной обработки конфликта в прикладном коде — тогда как пессимистичная сразу выражает намерение через SQL и не требует отдельной retry-логики ценой худшей пропускной способности при высокой конкуренции. [62]

По умолчанию персистентность в Redis выключена — потому что она добавляет накладные расходы: `RDB`-снапшот делается через `fork()` процесса, который на момент создания снапшота фактически удваивает потребление памяти (copy-on-write); `AOF` (append-only лог всех операций) может разрастаться и требует времени на восстановление при рестарте (переигрывание всего лога). Продакшн-стандарт с Redis 7.0+ — комбинированный режим (AOF + периодический RDB) — компромисс между скоростью восстановления и накладными расходами. [16]

## Apache Kafka: назначение и сравнение с RabbitMQ

Отраслевой стандарт для асинхронного взаимодействия между сервисами — буферизует сообщения, если потребитель временно недоступен. Встроенное шардирование через партиции, consumer groups для параллельной обработки, рассчитан на большие объёмы (высокий throughput). Данные хранятся на диске (durable), реплики партиций — для отказоустойчивости. По сравнению с RabbitMQ: Kafka лучше для высоконагруженного потокового взаимодействия, RabbitMQ — для более сложной маршрутизации сообщений и приоритетов очередей. [15] Конкретный практический пример разграничения из разбора торговой платформы: Kafka — под непрерывный высокочастотный поток событий (события ордеров, рыночные котировки с частотой обновления порядка раз в 0.5 секунды — то, что нужно не терять и разбирать в строгом порядке по ключу), RabbitMQ — под разовые, менее частые задачи с более сложной маршрутизацией (email-уведомления, генерация отчётов) — выбор диктуется не абсолютным превосходством одной системы, а характером конкретного потока сообщений (непрерывный высокочастотный stream vs штучные задачи). [46]

Пример горизонтального шардирования PostgreSQL под нагрузку порядка 5 000 RPS: шардирование по `account_id` на несколько логических шардов (в разборе — 3 шарда, у каждого — 2 реплики для отказоустойчивости чтения), несколько инстансов приложения (от единиц до полутора десятков, в зависимости от нагрузки) за балансировщиком, с отдельным пулом соединений на каждый шард и асинхронной публикацией событий об изменениях в очередь сообщений, а не синхронно в рамках запроса. [46]

Гарантия порядка сообщений в Kafka действует **только в рамках одной партиции** (монотонно возрастающий offset внутри партиции) — глобального порядка по всему топику с несколькими партициями нет. Чтобы связанные сообщения обрабатывались строго по порядку — задавать им одинаковый ключ (key) при отправке: консистентное хеширование ключа гарантированно направляет все сообщения с одним ключом в одну и ту же партицию, а внутри партиции сообщения разбирает только один поток одного консьюмера в группе (что и защищает от гонки при обработке связанных событий). Смежные настройки надёжности: `min.insync.replicas` — минимальное число реплик-подтверждений записи перед тем, как она считается зафиксированной (защита от потери данных при отказе брокера-лидера); `enable.idempotence=true` у продюсера — присваивает сообщениям порядковые номера и защищает от дублей при повторных отправках после сетевого сбоя (retry самого продюсера не создаёт дублирующихся сообщений); Kafka-транзакции — атомарная запись сразу в несколько партиций/топиков одним махом. В Go — типичная библиотека `segmentio/kafka-go`, маршрутизация по ключу через `kafka.Hash`-балансировщик. [25]

Обработка сообщений, которые не удалось корректно обработать (в противовес наивному «залогировать ошибку и просто продвинуть offset дальше», что на практике означает молчаливую потерю сообщения) — паттерн Dead Letter Queue именно для Kafka: проблемное сообщение публикуется в отдельный топик-DLQ с сохранением исходного контекста (топик/партиция/offset оригинала, текст ошибки, счётчик уже сделанных попыток), а не просто отбрасывается. Важное разграничение перед retry — фатальная ошибка (например неразбираемый формат сообщения — повторная попытка ничего не изменит, сразу в DLQ) против временной (сетевой таймаут, недоступность зависимости — имеет смысл ограниченное число ретраев с отступом, часто через отдельные retry-топики с растущей задержкой, прежде чем окончательно уйти в DLQ). Offset коммитится только после успешной обработки или осознанной отправки в DLQ — не автоматически при простом получении сообщения. Гарантия доставки по умолчанию — at-least-once (то же сообщение может прийти повторно), поэтому обработчик обязан быть идемпотентным (см. паттерн Idempotency Key выше); exactly-once достижимо только через транзакционный API Kafka. Эксплуатационная часть — отдельный мониторинг глубины DLQ-топика (растущая глубина — сигнал систематической проблемы, а не единичного сбоя) и явная процедура переигрывания (reprocessing) накопленных в DLQ сообщений после исправления причины сбоя. [68]

Отдельный практический вопрос — зачем вообще строить свой конвейер сбора метрик (например HTTP → Kafka → колоночная БД вроде QuestDB) поверх низкоуровневых библиотек (`prometheus/client_golang`) вместо использования готового стека Prometheus/Grafana целиком «из коробки»: типичные причины — push-модель доставки метрик там, где pull-модель Prometheus неудобна (например метрики от короткоживущих задач, которые не успевают дожить до следующего опроса `/metrics`), необходимость multi-tenant изоляции метрик разных клиентов на уровне протокола (не просто через label, а на уровне отдельного пайплайна), гарантии доставки в духе at-least-once там, где обычный Prometheus-скрейп такого не даёт, и поддержка кастомной схемы/протокола событий, выходящей за рамки классической модели «метрика = число + labels». [69]

## Transactional Outbox — паттерн против рассинхрона БД и брокера сообщений (расширенно)

Проблема, которую решает паттерн (уже упомянута выше кратко в контексте кейса с кликами): двойная запись (dual write) — нельзя атомарно и записать в БД, и опубликовать в Kafka одной операцией, поэтому при сбое между двумя шагами возможна либо потеря события, либо его публикация без соответствующего изменения в БД. Решение — событие и бизнес-изменение пишутся **в одной локальной ACID-транзакции** в саму БД: бизнес-таблица обновляется и в ту же транзакцию добавляется строка в отдельную outbox-таблицу (поля обычно включают `aggregate_id`, `event_type`, `payload` (JSONB), `status`, счётчик попыток доставки, индекс по `(status, created_at)` для эффективной выборки необработанных). Отдельный фоновый процесс (poller/relay) периодически вычитывает необработанные записи из outbox-таблицы и публикует их в Kafka, помечая как отправленные после успеха; для горизонтального масштабирования нескольких инстансов такого relay-процесса без дублирования работы — `SELECT ... FOR UPDATE SKIP LOCKED` (каждый инстанс блокирует и забирает свою порцию строк, не мешая другим инстансам, вместо конкуренции за одни и те же строки; тот же самый приём независимо всплывал на другом собесе как решение задачи «несколько инстансов сервиса безопасно разбирают общий пул задач без гонки» — предпочтительная альтернатива хрупким схемам разбиения по offset/диапазону между инстансами, поскольку не требует заранее фиксировать, какой инстанс какой диапазон обрабатывает, и позволяет просто добавлять новые инстансы для горизонтального масштабирования). [68] Гарантии доставки: at-least-once (простая версия — надёжно, но консьюмер обязан быть идемпотентным, то есть безопасно обрабатывать возможный дубль) достижимо сразу; exactly-once требует либо использования транзакционного API самой Kafka, либо перехода на подход CDC (Change Data Capture, например через Debezium) — при CDC отдельная outbox-таблица и polling вообще не нужны: инструмент читает журнал транзакций самой БД (WAL в PostgreSQL / binlog в MySQL) напрямую и публикует события из него, снимая накладные расходы на ручной polling. [25]

## Монолит vs микросервисы — практический ориентир выбора

Монолит: проще стартовать, лучше производительность (вызовы в процессе, без сетевых задержек), проще тестировать, полноценные ACID-транзакции без распределённой согласованности. Микросервисы: автономность команд, гранулярное масштабирование каждого сервиса отдельно (в интервью приводили пример Авито — порядка 1000 деплоев в день по всем сервисам), изоляция отказов — ценой сетевой сложности. Практический совет с собеса: начинать с монолита, переходить к микросервисам только при реальной, а не гипотетической необходимости («start with monolith, split when it hurts»). Промежуточные варианты — модульный монолит или паттерн Strangler Fig (постепенный вынос кусков монолита в отдельные сервисы). [15]

## CQRS и Event Sourcing — разделение модели чтения и записи

CQRS (Command Query Responsibility Segregation) — разделение модели записи (команды, меняющие состояние) и модели чтения (запросы, только читающие) на отдельные пути, вплоть до отдельных хранилищ данных под каждую: путь записи оптимизирован под целостность и бизнес-правила, путь чтения — под скорость конкретных запросов (например денормализованные материализованные представления, заранее посчитанные под конкретный экран/отчёт, вместо тяжёлых JOIN'ов на лету). Event Sourcing — смежный, но отдельный паттерн: состояние системы хранится не как текущий снимок (обычная таблица с перезаписью строк), а как последовательность неизменяемых событий изменения состояния (`OrderCreated`, `OrderPaid`, `OrderShipped` и т.п.), а текущее состояние — производное значение, вычисляемое проигрыванием (replay) всех событий по порядку; даёт полный аудиторский след и возможность восстановить состояние на любой момент времени, ценой более сложной модели чтения (обычно требует CQRS поверх, чтобы не пересчитывать всю историю событий на каждый запрос). Оба паттерна часто применяются вместе именно в финансовых/учётных доменах, где важен полный, неизменяемый аудиторский след движений (тот же класс задачи, что и паттерн двойной записи/`ledger`-таблицы, см. код-ревью `processPayment` выше), но добавляют архитектурную сложность — оправданы не по умолчанию, а именно там, где эта сложность окупается требованиями предметной области. [44]

Конкретный распространённый на практике вариант того же принципа «отдельное хранилище под чтение» без полноценного CQRS/Event Sourcing — связка MongoDB (или любая другая документная/реляционная БД) как источник истины (source of truth, где реально живут и меняются данные) + Elasticsearch как денормализованный поисковый индекс поверх тех же данных, оптимизированный именно под полнотекстовый/фасетный поиск, а не под транзакционную целостность. Важный нюанс, который путают кандидаты — это не «Elasticsearch хранит данные в MongoDB» (в такой формулировке смысл направления теряется) и не два равноправных хранилища одних и тех же данных: основное хранилище остаётся единственным источником истины, а поисковый индекс — вторичная, намеренно денормализованная проекция данных с eventual consistency (индекс обновляется через отдельный конвейер синхронизации — CDC/очередь событий/периодическая переиндексация — с задержкой относительно основного хранилища, а не синхронно в той же транзакции). [70]

## SQL: оконные функции и CTE для аналитических запросов

Оконные функции (window functions) — в отличие от обычной агрегации с `GROUP BY` (схлопывающей строки группы в одну), считают агрегат **для каждой строки** относительно её «окна» (партиции), не схлопывая набор строк: `ROW_NUMBER() OVER (PARTITION BY ... ORDER BY ...)` — присваивает каждой строке в своей партиции порядковый номер (типичное применение — «топ-N по каждой категории», через обёртку внешним запросом `WHERE row_num <= N`); `RANK()`/`DENSE_RANK()` — аналогично, но с обработкой повторяющихся значений (RANK оставляет «дыры» в нумерации после связки одинаковых значений, DENSE_RANK — нет). CTE (Common Table Expression, `WITH ... AS (...)`) — именованный временный результат подзапроса, читаемый по имени в основном запросе (в том числе рекурсивно через `WITH RECURSIVE` — для иерархических структур вроде дерева категорий/оргструктуры) — не меняет план выполнения принципиально по сравнению с эквивалентным подзапросом, но делает сложный многошаговый SQL-запрос значительно более читаемым и поддерживаемым, разбивая его на именованные логические шаги. ⚠ Уточнение по версиям PostgreSQL: до PostgreSQL 12 CTE исторически были **барьером оптимизации** (materialization fence) — планировщик всегда материализовал результат CTE как отдельный временный набор строк перед использованием во внешнем запросе, не «протаскивая» условия внешнего запроса внутрь CTE; начиная с PostgreSQL 12 по умолчанию поведение стало адаптивным (простые CTE могут быть заинлайнены планировщиком как обычный подзапрос), но старое поведение обязательной материализации доступно явно через ключевое слово `NOT MATERIALIZED`/`MATERIALIZED` в самом объявлении CTE — стоит явно проверять план (`EXPLAIN`) при использовании CTE в аналитических запросах, если критична производительность, а не полагаться на предположение о поведении по умолчанию для конкретной версии СУБД. Типичная задача, где всё это применяется вместе — отчёт «топ-N покупателей по каждому месяцу»: `CTE` агрегирует продажи по месяцу и покупателю, `ROW_NUMBER() OVER (PARTITION BY month ORDER BY total DESC)` ранжирует покупателей внутри каждого месяца, внешний запрос отсекает `row_num > N`. [44]

## Saga — распределённые транзакции без единого ACID

Паттерн для управления распределёнными "транзакциями" через границы нескольких микросервисов, где нет единой БД для обычного `ROLLBACK`. Два вида: **Orchestration (оркестрация)** — центральный координатор явно вызывает шаги по порядку и знает, как компенсировать (откатить) каждый шаг при сбое; проще проследить логику, но плотнее связанность сервисов. **Choreography (хореография)** — децентрализовано, каждый сервис реагирует на события от других сам по себе, без центрального дирижёра; слабее связанность, событийно-ориентированно, но сложнее отлаживать и восстанавливать полную картину происходящего. В обоих случаях — только eventual consistency (согласованность в конечном счёте), настоящего ACID через границы сервисов не бывает; вместо отката — компенсирующие действия (compensating actions). [15]

## `sql.NullTime` вместо голого `*time.Time`/нулевого значения для NULL-колонок

Частая ошибка маппинга опционального (может быть `NULL` в БД) поля времени — использовать голый `time.Time` и полагаться на его нулевое значение (`0001-01-01 00:00:00`) как признак «значения нет»: нулевое значение Go-типа и `NULL` в БД — семантически разные понятия, их отождествление создаёт риск незаметно спутать «явно указанное давнее время» с «значение отсутствует», а при работе через указатель (`*time.Time`) — риск паники на разыменовании без явной проверки на `nil`. Правильный инструмент — `sql.NullTime` (или аналогичные `sql.NullString`/`sql.NullInt64` и т.п. из `database/sql`, либо самодельный тип с полями `Time`/`Valid` и реализованными интерфейсами `sql.Scanner`/`driver.Valuer` для кастомной логики маппинга) — явно различает «есть значение» и «значения нет» на уровне типа, а не полагается на договорённость about нулевого значения. [53]

## Генерация идентификаторов транзакций под высокую нагрузку

Частая ошибка — генерировать ID транзакции через `time.Now().UnixNano()`: на высоком RPS реальны коллизии, потому что системные часы и планировщик ОС имеют ограниченную гранулярность (округление до микро-/миллисекунд на многих платформах), и at that же значение не гарантирует уникальность между разными узлами распределённой системы — для платежей это прямое нарушение идемпотентности (два разных платежа могут получить одинаковый ID). Продакшн-альтернативы: **ULID/KSUID** — сортируемые по времени идентификаторы, сочетающие временную метку (обычно 48 бит) с криптографически случайной частью (обычно 80 бит) для гарантии уникальности даже при коллизии по времени; **UUID v7** — более новый вариант UUID, тоже сортируемый по времени за счёт встроенной временной метки в старших битах, при этом сохраняющий случайность младших битов классического UUID v4. Последовательности (`SEQUENCE`) самой СУБД — годятся для внутренних технических ID, но не годятся напрямую как публичный идентификатор транзакции (предсказуемость, отсутствие смысла вне контекста одной БД). Отдельно от самого ID транзакции — idempotency key на стороне клиента (см. уже описанный паттерн Idempotency Key выше) — сознательно отдельная сущность от внутреннего ID транзакции, а не одно и то же значение: idempotency key defends от повторной отправки клиентом одного и того же запроса, тогда как ID транзакции — это идентификатор уже созданной записи внутри системы. [53]

## Безопасная обработка вебхуков платёжного провайдера (на примере Stripe)

Показательный код-ревью обработчика вебхука от внешнего платёжного провайдера — типичный набор критичных пробелов:

- **Отсутствие проверки подписи** — без верификации заголовка подписи (`Stripe-Signature` у Stripe, аналоги у других провайдеров) через официальный SDK провайдера кто угодно может отправить произвольное поддельное событие на публичный эндпоинт вебхука, выдав его за настоящее.
- **Отсутствие защиты от replay-атаки** — без проверки временной метки события (с разумным окном допуска, например 5 минут — `Tolerance` в терминологии Stripe SDK) перехваченное и повторно отправленное легитимное событие обрабатывается заново, как будто оно новое.
- **Неидемпотентная обработка события** — то же событие может прийти от провайдера повторно (гарантия доставки провайдера обычно at-least-once, а не exactly-once) — без дедупликации по ID события (отдельная таблица уже обработанных ID событий) повторная доставка приводит к повторной обработке (двойное зачисление/списание).
- **Синхронная тяжёлая бизнес-логика внутри самого HTTP-обработчика вебхука** — блокирует ответ провайдеру, рискуя таймаутом со стороны провайдера (который в ответ может счесть доставку неуспешной и начать retry, усугубляя проблему); правильный паттерн — как можно быстрее сохранить событие (в очередь/outbox) и вернуть `200 OK`, саму бизнес-обработку вынести в асинхронный обработчик отдельно от HTTP-хендлера приёма вебхука.
- Дополнительно — явный разбор типа события **до** приведения типов (не пытаться слепо распарсить payload под ожидаемую структуру для неизвестного/неожиданного типа события) и игнорирование неизвестных типов событий вместо падения с ошибкой; логирование ID события, типа и временной метки для последующей трассируемости инцидентов. [53]

## Код-ревью функции обработки платежа (`processPayment`) — сборный чек-лист ошибок

Показательное упражнение с собеса: дают функцию обработки платежа и просят найти проблемы — хорошо ложится в конспект как готовый чек-лист «что проверить в коде, работающем с деньгами и распределёнными системами»:

- **Порядок отката и коммита перепутан** — откат (rollback) вызывался уже после коммита транзакции, то есть фактически не мог ничего откатить (транзакция уже необратимо зафиксирована); правильно — сначала проверять ошибку и откатывать до коммита, коммитить только на пути успеха.
- **`float64`/`float32` для денег** — потеря точности на дробных операциях с плавающей запятой недопустима для денежных сумм; правильно — целочисленный тип в минимальных единицах валюты (например `int64` в копейках/центах) либо специализированный decimal-тип. Конкретная иллюстрация масштаба проблемы: ошибка округления, ничтожная на одной операции, накапливается на масштабе (наглядный пример с одного из собесов — прибавление `0.1` миллион раз через float не даёт ровно `100000` из-за неточного двоичного представления десятичных дробей) — детерминированная целочисленная арифметика не подвержена такому накоплению ошибки. [17, 21]
- **Один глобальный мьютекс на все платежи** — сериализует вообще все платёжные операции в системе (все ждут друг друга), убивая конкурентность; правильно — блокировка на уровне конкретной записи/счёта (row-level locking в БД), а не общий мьютекс уровня процесса.
- **Отсутствие `SELECT ... FOR UPDATE`** — без блокировки строки на чтение перед изменением баланса возможна гонка: два конкурентных платежа читают один и тот же баланс до того, как любой из них его обновит, и оба совершают операцию над устаревшим значением (classic read-modify-write race на уровне БД).
- **Запись в Kafka внутри той же БД-транзакции** — держит блокировки БД открытыми на время сетевого похода в Kafka (потенциально медленного/ненадёжного), удлиняя критическую секцию и раздувая шанс конфликтов и таймаутов; правильный паттерн — **Transactional Outbox**: запись события кладётся в отдельную outbox-таблицу в той же локальной транзакции с изменением баланса (атомарно, без сети), а отдельный фоновый процесс асинхронно вычитывает outbox-таблицу и публикует события в Kafka — так основная транзакция БД не зависит от доступности брокера.
- **Отсутствие поддержки `context`** — функция не принимает/не прокидывает `context.Context`, то есть не может быть отменена по таймауту или при отмене вышестоящего запроса.
- **Нет проверки на отрицательный баланс** — списание может увести баланс в минус без валидации перед применением изменения.
- **Нет идемпотентности** — при повторной попытке (retry после сетевого сбоя, повторная доставка сообщения) один и тот же платёж может провестись дважды; нужен идемпотентный ключ (idempotency key), по которому повторный запрос с тем же ключом распознаётся и не проводит операцию заново.
- **Недостаточно логирования и метрик** — для платёжного пути ожидаются структурированные логи и метрики на каждом шаге (не просто общий лог на всю функцию).
- **Область действия `defer` для отката/закрытия транзакции** — рекомендация оборачивать весь жизненный цикл транзакции в `defer` сразу после её открытия (например `defer tx.Rollback()`, которое становится no-op после успешного `tx.Commit()`), а не расставлять откат вручную по отдельным веткам ошибок — надёжнее против забытых веток. [17]
- **Дополнительные детали с другого разбора той же задачи** — конкретный SQL-тип для денег: `NUMERIC(19, 4)`/`DECIMAL` (точный, в отличие от `FLOAT`/`DOUBLE PRECISION`, которые дают ошибки округления вроде `0.1 + 0.2 ≠ 0.3`); уровень изоляции `sql.LevelSerializable` на транзакции перевода само по себе не спасает без обработки — конкурирующие транзакции при конфликте получают ошибку сериализации (код `40001` в PostgreSQL), приложение обязано перехватывать именно эту ошибку и делать retry транзакции целиком, а не считать её обычным сбоем; отдельная таблица-леджер (audit table, `ledger`/`transactions_log`) с записью `INSERT` **до** обновления баланса — паттерн двойной записи (double-entry bookkeeping), дающий независимый от текущего состояния баланса аудиторский след всех движений денег. [26]

## Пример схемы хранения результатов проверок (health-check/мониторинг за URL)

Показательный пример дизайна таблицы для хранения результатов регулярных проверок (взято из разбора сервиса health-check по списку URL): колонки под URL, статус (успех/ошибка/таймаут), HTTP-код, задержку (latency), текст ошибки, временную метку и счётчик попыток (retry count); композитный индекс по `(url, timestamp)` — под типичный запрос «последние N проверок конкретного URL, отсортированные по времени». Смежная практика — собирать не только факт успеха/ошибки, но и перцентили задержки (p95/p99, а не только среднее — среднее скрывает хвостовые задержки, которые обычно и есть главная проблема), долю ошибок по типам (сетевая ошибка vs HTTP-код ошибки — разные причины, разная реакция), и средние времена ответа как часть той же системы мониторинга. [33]

## Наблюдаемость (observability): метрики, логи, трейсы

Классический стек: Grafana для визуализации метрик/логов (дашборды на десятки графиков — нагрузка на диск, сетевые сокеты и т.п.), Prometheus как источник метрик, Jaeger для трейсинга запросов между сервисами, Kibana для полнотекстового поиска по логам. Современный подход — не собирать все четыре сигнала (метрики/логи/трейсы) разрозненными агентами, а унифицировать через OpenTelemetry. Практика для алертинга — метрики по методологии RED (Rate/Errors/Duration, для сервисов-запросчиков) или USE (Utilization/Saturation/Errors, для ресурсов); correlation ID, прокидываемый через весь путь запроса — то, что связывает конкретную строку лога с конкретным трейсом. Расхожая мнемоника для разграничения ролей трёх сигналов: метрики отвечают на вопрос «что именно сломалось» (агрегированные числа), логи — «почему» (детали конкретного события), трейсинг — «где именно в цепочке вызовов» (какой сервис/хоп внёс задержку или ошибку). [15, 23]

Более глубокие детали, всплывающие на сеньорских разборах: у Prometheus — pull-модель сбора метрик (сервер сам с заданным интервалом опрашивает `/metrics`-эндпоинт каждого инстанса) в противовес push-моделям других систем — компромисс между простотой обнаружения новых инстансов (push) и отсутствием необходимости держать открытым входящий порт на каждом сервисе (pull); высокая кардинальность меток (labels) метрик (например если в метрику добавить `user_id` как label) — практический риск: каждое уникальное сочетание значений labels создаёт отдельный временной ряд, и их бесконтрольный рост может привести к исчерпанию памяти самого Prometheus (тот же принцип независимо всплывал в контексте маркировки метрик задержки БД именно сырым SQL-текстом запроса как label — тоже высококардинальная и потому опасная практика, стабильные лейблы вроде типа операции/статуса безопаснее). [69]

Практический выбор типа метрики для измерения задержки операции (например время доступа к БД, измеренное через `defer` вокруг вызова — `start := time.Now(); defer func(){ dur.Observe(time.Since(start).Seconds()) }()`) — конкретно **Histogram**, а не **Summary**: Histogram считает попадания в заранее заданные бакеты (например экспоненциально растущие от 1мс до 2с — `prometheus.ExponentialBuckets(0.001, 2, 12)`) и позволяет агрегировать перцентили постфактум на стороне сервера запросов (можно пересчитать p95/p99 по любому произвольному временному окну и просуммировать данные с разных инстансов); Summary считает квантили уже на стороне клиента метрики в момент наблюдения — они не агрегируются корректно между несколькими инстансами (нельзя просто усреднить уже посчитанные на разных инстансах перцентили и получить корректный общий перцентиль), поэтому для метрик, которые нужно агрегировать по всему флоту инстансов сервиса — Histogram предпочтительнее почти всегда, Summary имеет смысл только для метрик по одному конкретному процессу без потребности сравнивать/агрегировать между инстансами. Для распределённого трейсинга — стандарт W3C Trace Context (заголовок `traceparent`) для сквозной передачи ID трейса между сервисами независимо от конкретного инструмента; стратегии сэмплирования трейсов — head-based (решение сэмплировать/нет принимается сразу на входе в систему, дёшево, но не знает заранее, будет ли трейс интересным) vs tail-based (решение откладывается до завершения всего трейса — можно осознанно оставлять именно медленные/ошибочные трейсы, но дороже по инфраструктуре, требует буферизации). Непрерывное профилирование в проде (continuous profiling, отдельная категория поверх обычных метрик/логов/трейсов) — инструменты вроде Pyroscope/Parca, снимающие профиль CPU/памяти на постоянной основе с минимальным оверхедом (в дополнение к разовому ручному `pprof`, см. файл 13). Специфичные для Go-рантайма метрики для мониторинга: `go_memstats_gc_cpu_fraction` (доля CPU-времени, съеденного сборщиком мусора — рост говорит о GC-давлении), число живых горутин (`goroutines`, резкий/монотонный рост — сигнал утечки, см. файл 08), использование файловых дескрипторов (истощение — типичный признак сетевого узкого места/утечки соединений); `sync/atomic.Value`/`sync/atomic.Pointer` упоминались как примитивы для построения lock-free структур в контексте той же беседы про производительность мониторинга. [24]

Расширенный набор для очередей/асинхронной обработки: consumer lag (разница между последним записанным и последним обработанным консьюмером offset в Kafka/Pulsar — растущий лаг сигнализирует, что консьюмер не успевает за продюсером), время обработки одного сообщения, доля сообщений, ушедших в dead-letter queue (DLQ). Синтетические проверки (synthetic checks) — периодическое автоматическое прохождение реального пользовательского сценария целиком (логин → добавление в корзину → оформление заказа) как отдельный вид мониторинга, ловящий деградацию, которую пассивные метрики могут не поймать; принцип «отсутствие данных метрики — это тоже сигнал отказа» (blackbox monitoring: если метрика вообще перестала поступать, это не значит «всё хорошо», это может значить «сломался сам сборщик метрик»). [26]

## Оптимизация стоимости обращения к платному внешнему API

Расширение уже описанных выше паттернов retry/circuit breaker/rate limiting применительно конкретно к **платным** внешним API, где каждый лишний вызов стоит денег напрямую, а не только нагрузки: приоритет тактик по порядку — сначала вообще избежать вызова (кэширование), затем сгруппировать неизбежные вызовы (батчинг), затем ограничить частоту (throttling), и только в последнюю очередь — контролируемо деградировать при сбоях (resilience-паттерны), а не наоборот.

Многоуровневое кэширование: L1 — in-memory (`sync.Map` или сторонние `ristretto`/`bigcache`) для «горячих» данных с TTL и лимитом по объёму:
```go
cache := ristretto.NewCache(&ristretto.Config{
    NumCounters: 1e7,
    MaxCost:     1 << 30, // 1 ГБ лимит
    BufferItems: 64,
})
cache.Set("user_123", response, 1)
```
L2 — распределённый кэш (Redis/Memcached), общий на все инстансы сервиса, чтобы разные реплики не дублировали одни и те же дорогие запросы. Отдельно — негативное кэширование: кратковременно кэшировать и сами ошибки (`404`/`400`), чтобы не платить повторно за заведомо несуществующий ресурс.

Батчинг: слияние идентичных одновременных запросов через `golang.org/x/sync/singleflight` — несколько горутин, одновременно запросивших один и тот же ключ, получают результат одного реального похода в API вместо N отдельных оплаченных вызовов:
```go
var g singleflight.Group
func GetUserData(ctx context.Context, id string) (Result, error) {
    v, err, _ := g.Do(id, func() (interface{}, error) {
        return doFetch(ctx, id)
    })
    return v.(Result), err
}
```
Отдельно — батчинг по очереди: буферизация запросов и отправка одной пачкой по таймеру или по достижении порога размера, снижая стоимость с N·C до C (где C — цена одного batched-вызова, если API поддерживает bulk-эндпоинт).

Продвинутый rate limiting: token bucket с раздельными приоритетными квотами (например 100 req/sec для пользовательских запросов, 10 req/sec для фонового обновления кэша) — критичный трафик не блокируется фоновым; адаптивный throttling — отслеживание заголовков ответа API (`X-RateLimit-Remaining`, `Retry-After`) и упреждающее снижение фоновой нагрузки до того, как сервис начнёт отвечать `429`.

Отказоустойчивость: circuit breaker (например пакет `gobreaker`) — при росте доли ошибок или задержек (которые сами по себе стоят денег на потраченных впустую таймаутах/ретраях) временно полностью отключать вызовы на период восстановления; retry с экспоненциальным backoff и джиттером — ограниченное число попыток, разнесённых по времени, вместо шторма одновременных повторов при массовом сбое (тот же принцип, что уже описан выше применительно к обычным ретраям, но здесь оправдание — прямая экономия денег, а не только нагрузка).

Наблюдаемость и бюджетирование конкретно под затраты: теговые метрики стоимости по операциям (`api.cost.search`, `api.cost.validate`) выявляют, какая именно фича генерирует основную часть счёта; программный «мягкий» бюджет (например не больше 10 000 запросов/час) с плавной деградацией при исчерпании — отдавать закэшированные (пусть и не совсем свежие) данные вместо живого запроса, а не просто блокировать функциональность целиком. [38]

## Сквозной кейс системного дизайна: видеоплатформа (YouTube-подобный сервис)

Ещё один сквозной кейс системного дизайна (дополняет уже описанные выше кейсы KV-хранилища, мульти-тенантной чат-платформы), на этот раз из домена медиа-стриминга — область, ранее не встречавшаяся в конспекте:

- **Транскодирование видео** — необходимо не ради самого процесса, а ради совместимости с разными устройствами/сетевыми условиями: разные разрешения и битрейты под адаптивный стриминг, разные форматы/кодеки под разные декодеры устройств, подготовка контента к последующему монтажу/лицензированию.
- **Протоколы доставки видео** — распространённое смешение вживую разных протоколов под разные сценарии: `UDP/RTP` — минимальная задержка (IP-камеры, WebRTC-подобные сценарии реального времени); `RTMP` (поверх TCP) — легаси-протокол приёма потока от энкодера (до сих пор используется для приёма потока от OBS в сторону платформы); `HLS`/`MPEG-DASH` (поверх HTTP) — стандарт для видео по запросу (VoD) именно благодаря совместимости с обычным HTTP-CDN-кэшированием, обходу NAT и встроенной поддержке адаптивного битрейта — доминируют именно для VoD, а не потоков реального времени; `WebRTC` — для полностью интерактивных сценариев (видеозвонки), где задержка критичнее гарантированной доставки.
- **Кодеки** — компромисс между эффективностью сжатия и совместимостью декодеров: `H.264` — универсальная базовая совместимость почти на любом устройстве; `H.265/HEVC` — на ~50% эффективнее по сжатию, но лицензионные отчисления и не универсальная поддержка декодирования на старых устройствах; `VP9` — открытый, бесплатный по лицензии, стандарт для одной конкретной экосистемы (YouTube/Chromium); `AV1` — наилучшее сжатие (примерно на 30% эффективнее HEVC) и отсутствие лицензионных отчислений, ценой самой требовательной к CPU/времени кодировки на сегодняшний день. Практическая рекомендация — мульти-кодек стратегия (отдавать разным устройствам разные кодеки по возможностям декодирования), а не ставка на один кодек сразу для всех.
- **Сервис оптимизации/транскодирования** как отдельный обособленный компонент архитектуры: принимает исходное видео, валидирует, кодирует в несколько разрешений параллельно через очередь воркеров (масштабируется горизонтально добавлением воркеров), генерирует адаптивные манифесты (HLS/DASH-плейлисты) и превью-миниатюры, публикует результат в CDN.
- **Выбор БД под метаданные видео** — конкретный практический пример компромисса между реляционной и документной БД внутри одной системы: реляционная (PostgreSQL) — сильна в сложных JOIN'ах и ACID-транзакциях (уместна для учётных записей/платежей), но хуже горизонтально масштабируется и менее гибка к изменению схемы; документная (MongoDB) — гибкая схема и лёгкое горизонтальное шардирование, высокая пропускная способность на чтение/запись, но более слабые транзакционные гарантии — уместна именно для метаданных видео/аналитики, где гибкость схемы и объём важнее строгой транзакционности. Практический вывод — гибридный подход в рамках одной системы (не «или-или» на весь проект): NoSQL под высокообъёмные, часто меняющиеся по структуре данные (метаданные видео, аналитика просмотров), реляционная БД — под данные, где консистентность и связи критичны (учётные записи, платежи). [75]

Отдельно на смежном источнике — конкретная связка ClickHouse (колоночная OLAP-БД для аналитики) как потребитель Kafka напрямую через движок `Kafka Engine` (таблица-обёртка, читающая топик как источник строк) и последующие материализованные представления (materialized view), автоматически трансформирующие/агрегирующие данные по мере поступления, без отдельного внешнего ETL-процесса — типичный паттерн реалтайм-аналитики поверх потока событий. Частая путаница в терминологии на этом стыке — представление типа Kafka Connect (отдельный внешний коннектор-фреймворк для интеграции с внешними системами) не то же самое, что механизм materialized view внутри самого ClickHouse (внутренний механизм трансформации данных на лету при вставке) — это два разных, не взаимозаменяемых понятия, которые кандидаты иногда путают между собой. [74]
