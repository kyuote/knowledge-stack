## Моки в тестах — инструменты и терминология

Мокирование зависимостей в юнит-тестах реализует принцип инверсии зависимостей (Dependency Inversion, последняя буква в SOLID) — тестируемый код зависит от интерфейса, а не от конкретной реализации, поэтому в тесте можно подставить фейковую реализацию. Популярные инструменты: `testify/mock` (мок вручную, без кодогенерации), `mockery` (генератор моков по интерфейсу), `gomock`/`uber-go/mock` (тоже генератор, от Uber), `miniredis` (тестовый Redis-совместимый сервер в памяти), `httptest` (тестовый HTTP-сервер/клиент из стандартной библиотеки), `sqlmock` (мок SQL-драйвера для `database/sql`). Терминологическое уточнение: мок проверяет **поведение** (что метод действительно был вызван нужное число раз с нужными аргументами), а стаб просто **возвращает заданные значения** без проверки самого факта вызова — разные инструменты для разных целей теста. [15]

## Тестируемый HTTP-код через интерфейс вместо конкретного `*http.Client`

Идиоматичный приём для тестируемости HTTP-клиентского кода — принимать зависимость не как конкретный `*http.Client`, а как минимальный интерфейс с единственным нужным методом (`type HTTPClient interface { Do(*http.Request) (*http.Response, error) }`), которому `*http.Client` уже соответствует «из коробки» (см. также принцип «интерфейс на стороне потребителя» в файле 06). Это открывает три уровня тестовых замен по возрастанию гибкости: (1) **fake-клиент** — простая структура с захардкоженными полями возврата, для самых базовых сценариев; (2) **мок с программируемым полем-функцией** (`DoFunc func(*http.Request) (*http.Response, error)`) — поведение задаётся замыканием прямо в тесте, гибче фиксированного fake; (3) **`http.RoundTripper`** — подмена на уровне транспорта пониже, когда нужно эмулировать что-то ближе к реальному сетевому уровню (задержки, конкретные заголовки ответа), но без реального сетевого вызова; отдельно — **`httptest.Server`** — поднимает по-настоящему работающий локальный HTTP-сервер на случайном порту для интеграционных тестов, когда фейка/мока уже недостаточно и нужен реальный HTTP-роундтрип целиком. [33]

## Табличные тесты (table-driven) и подтесты через `t.Run`

Идиоматичный Go-паттерн для покрытия множества сценариев одной функцией: слайс/срез структур-кейсов (входные данные + ожидаемый результат) и цикл, где каждый кейс запускается как именованный подтест через `t.Run(caseName, func(t *testing.T) {...})` — даёт отдельный, независимо запускаемый и легко идентифицируемый в выводе тест на каждый кейс, вместо одной большой функции с кучей отдельных `if`/`t.Errorf`. Типичный набор кейсов для HTTP-клиентского кода, показательный своей полнотой: успешный ответ 200, серверная ошибка 500, сетевой таймаут, отмена через контекст, циклический редирект, задержка ответа больше таймаута, «нестандартные» успешные коды (например 204). Для конкурентного кода — отдельный вид теста: запустить сотню горутин, каждая бьёт по своему URL, и проверить, что все завершились, число реальных запросов совпадает с числом горутин, и обязательно прогнать с флагом `-race` для проверки отсутствия гонок данных. [33]
