## Зачем нужны интерфейсы и как проверяется соответствие

Интерфейс — набор сигнатур методов, контракт поведения без реализации; реализация в Go неявная (нет ключевого слова `implements`) — тип автоматически удовлетворяет интерфейсу, если имеет все нужные методы с совпадающими сигнатурами (лишние методы сверх требуемых не мешают удовлетворению). Даёт абстракцию, тестируемость (моки через интерфейсы) и полиморфизм. Проверка соответствия — статическая, на этапе компиляции. [1]

## Внутреннее устройство интерфейсного значения

Интерфейсное значение хранится как структура `iface` из двух указателей: указатель на `itab`/itable (таблица методов конкретного типа — «type + method table») и указатель на сами данные — пара `(itab, data)`. Именно эта пара обеспечивает динамическую диспетчеризацию вызова метода в рантайме. (Тот же механизм лежит в основе «ловушки nil-интерфейса» — typed-nil, положенный в интерфейс, даёт `iface` с ненулевым `itab`, поэтому сам интерфейс не равен nil, даже если данные внутри — nil указатель.) [1, 7]

Важное уточнение, разграничивающее **пустой** интерфейс (`interface{}`/`any`, без методов) и **непустой** (с хотя бы одним методом в наборе): у непустого интерфейса внутреннее представление — именно пара `(itab, data)`, поскольку рантайму реально нужна таблица методов конкретного типа для диспетчеризации вызова. У пустого интерфейса диспетчеризировать нечего (набор методов пуст) — поэтому вместо `itab` его представление устроено как пара «указатель на дескриптор типа (`*_type`), указатель на данные» напрямую, без промежуточной таблицы методов вообще. Оба представления по-прежнему двухсловные (два указателя), но смысл первого слова разный — на практике это объясняет, почему присвоение конкретного значения пустому интерфейсу «дешевле» с точки зрения диспетчеризации (нет косвенного обращения через itab), но не меняет стоимость самого копирования данных/боксинга. [67]

## Value receiver vs pointer receiver для целей удовлетворения интерфейса

Подробный разбор этого нюанса — в файле 05 «Указатели» (там же код-пример): если у типа все методы объявлены с value receiver — интерфейсу удовлетворяют и сам тип, и указатель на него; если хотя бы один метод — с pointer receiver, интерфейсу удовлетворяет только указатель. [9 — см. файл 05]

## Сравнение интерфейсных значений через `==` — паника при несравнимом динамическом типе

Два значения типа `interface{}`/`any` сравниваются через `==`, только если их **динамический тип сравним**. `int`, `string`, `bool`, указатели, массивы (если элементы сравнимы), структуры (если все поля сравнимы) — сравнимы; слайсы, map, функции — нет. Если оба интерфейсных значения хранят `int` — сравнение отработает нормально; если хотя бы одно хранит слайс (`[]int`) — сравнение `==` **паникует в рантайме** (`runtime error: comparing uncomparable type []int`), а не просто возвращает `false` — частая ловушка, компилятор не может отследить это статически для `any`, потому что конкретный динамический тип известен только в момент выполнения. Альтернативы для слайсов — `slices.Equal()` (пакет `slices`, Go 1.21+) или `reflect.DeepEqual()` (универсальнее, но через рефлексию — медленнее). [19]

## Интерфейс объявляется на стороне потребителя, а не производителя

Идиоматичное правило размещения интерфейсов в Go (в противовес практике многих других языков, где интерфейс объявляется рядом с реализацией): интерфейс должен жить в пакете, который его **использует** (принимает как параметр, зависит от него), а не в пакете, который его реализует. Реализующий тип/пакет вообще не обязан знать о существовании интерфейса — благодаря неявному (структурному) удовлетворению интерфейса это просто работает. Практическая польза — пакет-потребитель объявляет ровно тот минимальный интерфейс, который ему нужен (часто на 1 метод меньше, чем «полный» интерфейс поставщика), что упрощает мокирование в тестах и снижает связанность между пакетами. [23]

## Сужение доступных методов после type assertion к другому интерфейсу — завязано на статический, а не динамический тип

Нюанс, часто упускаемый при type assertion не к конкретному типу, а к **другому интерфейсу**: после успешной assertion `ab.(BC)` (где `AB`/`BC` — интерфейсы с частично разными наборами методов) доступны **только** методы целевого интерфейса `BC`, даже если реальный (динамический) тип, лежащий внутри, реализует значительно больше методов, включая методы исходного интерфейса `AB`.

```go
type A interface { MethodA() }
type B interface { MethodB() }
type C interface { MethodC() }
type AB interface { A; B }
type BC interface { B; C }

type T struct{}
func (T) MethodA() {}
func (T) MethodB() {}
func (T) MethodC() {}

var ab AB = T{}
bc := ab.(BC) // успешно: динамический тип T реализует и B, и C
bc.MethodA()  // ОШИБКА КОМПИЛЯЦИИ: интерфейс BC не включает A
```

Assertion срабатывает успешно, потому что рантайм проверяет соответствие по **динамическому** типу (`T` реально реализует всё, что требует `BC`) — но после присвоения переменной `bc` статическим типом становится именно `BC`, и компилятор разрешает вызывать только то, что объявлено в этом статическом типе, независимо от того, что́ ещё умеет исходный конкретный тип. Практическое следствие — если нужен доступ сразу к нескольким наборам методов одновременно, стоит явно определить составной интерфейс, включающий все нужные методы (как `AB`/`BC` в примере), а не полагаться на то, что assertion «магически» откроет что-то за пределами целевого интерфейса. Безопасная форма assertion — всегда двузначная (`bc, ok := ab.(BC)`), чтобы не паниковать на неуспешном приведении; при необходимости проверить сразу несколько альтернативных интерфейсов — `switch v := ab.(type) { case BC: ...; case AB: ... }`. [41]

## ООП в Go: без классов и наследования

В Go нет классов — «ООП» реализовано неявно: методы привязываются к структурам через receiver, композиция вместо наследования — через встраивание (embedding) одной структуры в другую, с продвижением методов (method promotion: методы встроенного типа становятся доступны у внешней структуры напрямую). Полиморфизм — через интерфейсы и структурную типизацию (duck typing): тип удовлетворяет интерфейсу автоматически при совпадении методов, без явного `implements`. [15]
