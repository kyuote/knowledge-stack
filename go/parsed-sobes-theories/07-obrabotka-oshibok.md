## Паника и восстановление (`panic`/`recover`)

`recover()` работает только будучи вызванным напрямую внутри отложенной (`defer`) функции — перехватывает панику и предотвращает аварийное завершение программы. Возвращает значение типа `any`/`interface{}` — если нужно понять, что именно "запаниковало", требуется type assertion к этому значению. Рекомендуемая практика — ставить `recover` на верхнем уровне приложения (например в middleware HTTP-сервера или в обёртке над обработчиком воркера), а не разбрасывать по всему коду. Критичный нюанс: `recover` работает только в той горутине, где произошла паника — каждой горутине, где в принципе может случиться паника (особенно воркерам в пуле), нужен свой собственный `defer`+`recover`; необработанная паника в любой горутине убивает **весь процесс** целиком, а не только эту горутину. Смысловое разграничение panic vs обычный `error`: `panic` — для нарушения инвариантов программы (программистских ошибок, не должных происходить в принципе), `error` — для ожидаемых, «штатных» сбоев (не найден файл, не прошла валидация, недоступна сеть) — не стоит использовать panic как замену обычной обработке ошибок в пользовательском/бизнес-коде. [15, 21]

## Оборачивание ошибок: `%w`, `errors.Is`, `errors.As`

Начиная с Go 1.13, `fmt.Errorf` поддерживает глагол `%w` для «оборачивания» одной ошибки в другую с сохранением цепочки (в отличие от `%v`, который просто форматирует текст ошибки без сохранения структуры-обёртки). Интерфейс `error` минимален — единственный обязательный метод `Error() string`; `nil` тоже удовлетворяет этому интерфейсу (отсюда классическая ловушка с typed-nil в интерфейсе, см. файл 06). Две функции пакета `errors` для работы с цепочкой обёрнутых ошибок: `errors.Is(err, target)` — проверяет, есть ли конкретное ожидаемое значение ошибки (например `sql.ErrNoRows`) где-либо в цепочке оборачиваний (аналог `==`, но проходящий по всей цепочке через `Unwrap()`); `errors.As(err, &target)` — находит в цепочке ошибку конкретного **типа** и извлекает её в `target` (аналог type assertion, но тоже проходящий по всей цепочке). Кастомные типы ошибок — обычные структуры с методом `Error() string`, могут нести дополнительный контекст через свои поля (например код ошибки, ID сущности, исходную причину). Ошибки в Go принято считать неизменяемыми значениями — если к ошибке обращаются из нескольких горутин конкурентно (например, копят в общий слайс ошибок воркер-пула), запись в общую структуру требует обычной синхронизации (мьютекс), как и любые другие shared-данные. [22]

## Продакшн-стратегия ошибок для высоконагруженного сервиса — доменные коды вместо текста

Показательный код-ревью платёжного сервиса (несколько тысяч RPS) — типичная недоработка: ошибки разбросаны по разным слоям без единой стратегии, текст ошибки дублируется в разных HTTP-ответах, тесты вынуждены сравнивать строки текста ошибки (хрупко — падают при любой правке формулировки), в самой ошибке нет операционного контекста (`TraceID`, имя операции) для последующей диагностики по логам. Продакшн-паттерн — доменные типы ошибок с явным **кодом**, а не только текстом (`ErrNotFound`, `ErrInvalidArgument` и т.п. как отдельные сравниваемые значения/константы, а не строки), при этом сама валидация входных данных — часть доменного контракта (обязанность бизнес-логики), а не транспортного слоя (HTTP-хендлера); в JSON-ответе клиенту передаётся именно код ошибки, локализация текста для конечного пользователя — уже на стороне клиента, а не зашита в сообщение с бэкенда. Отдельное централизованное middleware отвечает за маппинг доменного кода ошибки в конкретный HTTP-статус — в одном месте, а не разбросанной по каждому хендлеру логикой; `TraceID` и имя операции стоит прокидывать в саму структуру ошибки (или через `context`) для сквозной трассируемости конкретного инцидента по логам/трейсам. [53]
