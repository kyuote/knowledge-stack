## Go всегда передаёт по значению (call-by-value)

Ключевая рамка для всей темы: в Go нет «передачи по ссылке» — всегда копируется какое-то значение, вопрос лишь в том, *что именно* копируется. `func Modify(s MyStruct)` копирует всю структуру на стек функции — исходная переменная снаружи не меняется. `func ModifyPtr(s *MyStruct)` копирует только указатель (8 байт на 64-бит) — но по этому указателю можно менять оригинал. То же самое верно для передачи через канал: канал не «передаёт по ссылке», просто кладёт в себя копию того, что в него отправили — структуру целиком или указатель. [5, 9]

## Value vs pointer receiver у методов

Метод с value receiver (`func (u User) SetName(name string)`) получает копию структуры — изменения внутри метода не видны вызывающей стороне, даже для примитивных типов-алиасов (`type Counter int`, `func (c Counter) Inc()` не мутирует оригинал). Метод с pointer receiver (`func (u *User) SetName(...)`) получает указатель на оригинал и может его мутировать. Частая ошибка кандидатов — ожидать мутацию от value receiver. [9]

## Shallow copy vs deep copy при копировании структур

Копирование структуры («вся структура копируется целиком») не означает, что копируются и данные внутри слайсов/map-полей: они копируются мелко (shallow) — дублируется только заголовок (указатель+len+cap для слайса, указатель для map), а не сами данные. Обе копии структуры продолжают ссылаться на одни и те же исходные данные слайса/map — изменение элемента через одну копию видно через другую. `append`, если требует реаллокации, разрывает эту связь. Если нужны независимые копии — нужно явно хранить указатели (`map[K]*V`, `[]*T`) или делать глубокое копирование вручную. [9]

## `new(T)` vs `make(T, ...)`

`new(T)` работает для любого типа, возвращает `*T` — указатель на обнулённую память. `make(T, args)` работает только для слайсов/map/каналов, возвращает саму инициализированную структуру `T` (не указатель), с уже выделенными внутренними буферами. `new([]int)` даёт `*[]int`, указывающий на nil-слайс — использовать напрямую нельзя, нужна инициализация. Важно: то, окажется ли значение на стеке или в куче, решает escape analysis, а не то, через `new` или `make` оно создано. [9]

```go
p := new(int)           // *int, значение 0
s := make([]int, 0, 10) // []int, готов к использованию
```

## Нельзя взять адрес элемента map

`ptr := &m[key]` — ошибка компиляции. Причина: map — хеш-таблица, при рехешировании бакеты перевыделяются и элементы физически перемещаются в памяти; сохранённый указатель стал бы висячим (dangling). Обходные пути: (а) читать-изменять-записывать значение целиком, либо (б) хранить в map сами указатели (`map[K]*V`), тогда мутировать можно через разыменование, а адрес самого указателя не «плавает». [9]

## Interface satisfaction: value vs pointer receiver — критичный нюанс

Если у типа `T` **все** методы объявлены с value receiver — интерфейсу удовлетворяют и `T`, и `*T`. Если хотя бы один метод объявлен с pointer receiver — интерфейсу удовлетворяет **только** `*T`, не голое значение `T`. Частая ошибка на собесе — считать value- и pointer-receiver взаимозаменяемыми для целей удовлетворения интерфейса; на практике кандидаты часто верно объясняют разницу в теории, но не могут сразу сказать, обязательно ли передавать именно `&structVar` (а не голую переменную) при присвоении интерфейсной переменной — ответ: да, обязательно, если среди методов есть хоть один pointer receiver. [9, 19]

```go
type I interface { Do() }
func (t T) Do() {}   // T и *T оба удовлетворяют I
func (t *T) Do() {}  // удовлетворяет только *T
```

## Размер указателя не зависит от размера типа, на который он указывает

Указатель — это всегда просто адрес: 4 байта на 32-битной платформе, 8 байт на 64-битной, независимо от того, указывает ли он на `int8` или на структуру в мегабайт весом — сам указатель не «весит» больше от размера цели. Смежная тема — `unsafe.Pointer` как способ обойти систему типов и делать явные преобразования указателей между несовместимыми типами (используется точечно во внутренностях стандартной библиотеки, например в `strings.Builder`/конвертации `string`↔`[]byte`, см. файл 01) — в обычном прикладном коде считается кодом-запахом и признаком того, что стоит поискать типобезопасную альтернативу. [20]

## Escape analysis — что решает стек или куча

Взятие адреса переменной (`&x`) само по себе не гарантирует, что она уйдёт в кучу. Компилятор анализирует, «убегает» ли переменная из функции (возвращается ли, сохраняется ли глобально, передаётся ли в горутину/канал) — если нет, она может остаться на стеке даже если её адрес был взят внутри функции. Указатели повышают риск ухода в кучу, но не гарантируют его. Посмотреть решения компилятора: `go build -gcflags="-m"`. [9]

## Автоматическое разыменование и адресуемость (addressability)

Go неявно подставляет `&` при вызове pointer-receiver метода — но только у адресуемых значений (переменных). Временные значения (литералы структур, результат вызова функции) неадресуемы — вызов pointer-receiver метода на них не компилируется. Обход — присвоить временное значение переменной перед вызовом. [9]

```go
User{}.SetName("X")  // ошибка компиляции: нельзя взять адрес литерала
u := User{}
u.SetName("X")       // ок: Go неявно делает (&u).SetName("X")
```

## Захват переменной цикла в замыкании/через указатель — версия Go 1.22+

До Go 1.22 все итерации `for` делили одну и ту же переменную цикла — если брать её адрес (`&v`) или захватывать в замыкании на каждой итерации, все указатели/замыкания в итоге видели одно и то же (последнее) значение. С Go 1.22 на каждой итерации через `:=` создаётся новая переменная — `&v` на разных итерациях указывает на разные ячейки памяти, каждая с верным значением своей итерации. Обходной путь для старых версий Go — вручную затенить переменную: `v := v` внутри тела цикла. [9]

```go
// Go 1.22+: выведет указатели на 10, 20, 30, 40 — каждый на своё значение
for _, v := range []int{10, 20, 30, 40} {
    ptrs = append(ptrs, &v)
}
// Go ≤1.21: все указатели видели одно и то же — итоговое значение 40
```
