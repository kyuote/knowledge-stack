## I/O через `io.Reader`/`io.Writer`

I/O-операции в Go — это не только «чтение/запись запроса на сервере» (частый узкий ответ кандидатов): файлы, сеть, сжатие, кодирование — всё абстрагировано через интерфейсы `io.Reader`/`io.Writer` из пакета `io`. Хороший пример того, как стандартная библиотека построена на маленьких композируемых интерфейсах (см. также файл 06). [1]

## Бинарный поиск и `sort.Search`

Бинарный поиск по отсортированным данным — O(log n); в stdlib есть готовая `sort.Search` вместо ручной реализации. При ручной реализации: предпочтительнее итеративный вариант (безопаснее по стеку, чем рекурсия); середину диапазона считать как `low + (high-low)/2`, а не `(low+high)/2` — защита от переполнения `int` при больших значениях. Для очень маленьких массивов (< ~20 элементов) линейный поиск на практике может быть быстрее бинарного (меньше оверхеда, лучше предсказуемость для CPU cache/branch predictor) — нюанс скорее про производительность, чем про язык. [3]

## Приоритетная очередь и `container/heap`

Приоритетная очередь — структура, где элементы извлекаются по приоритету, а не по порядку вставки (в отличие от обычной FIFO-очереди). Способы реализации и их сложность: бинарная куча (heap) — вставка/извлечение O(log n), стандартный выбор; отсортированный массив — вставка O(n) (сдвиг для сохранения порядка), извлечение минимума/максимума O(1); связный список — без явной сортировки вставка O(1), но извлечение приоритетного O(n); сбалансированное дерево поиска (BST) — O(log n) на обе операции, но с большими константными накладными расходами, чем у кучи. В стандартной библиотеке Go — пакет `container/heap`: не готовая структура данных «из коробки», а набор функций (`heap.Push`/`heap.Pop`/`heap.Init`/`heap.Fix`), работающих поверх пользовательского типа, реализующего интерфейс `heap.Interface` (`sort.Interface` + `Push`/`Pop`) — идиоматично, но требует своей обвязки, в отличие от, например, `PriorityQueue` из stdlib других языков. Классические примеры применения: алгоритм Дейкстры (кратчайшие пути во взвешенном графе — куча хранит вершины по текущей известной дистанции), планировщики задач по приоритету. [20]

## Генерация уникальных случайных чисел: `math/rand` vs `crypto/rand`, парадокс дней рождения

Задача «сгенерировать N уникальных случайных чисел» наивно решается циклом «генерируем — кладём в map для проверки уникальности — повторяем, пока не наберём N» — рабочий подход, но с нюансами уровня продакшна: (1) выбор пакета — `math/rand`/`math/rand/v2` детерминирован по seed и предназначен для некриптографических случаев (тесты, шаффл, игры); там, где случайность имеет значение для безопасности (токены, идентификаторы, к которым не должно быть возможности подобрать значение) — обязателен `crypto/rand`, дающий криптографически стойкую энтропию ценой меньшей производительности; (2) глобальный генератор пакета `math/rand` не потокобезопасен для конкурентного использования из нескольких горутин без дополнительной синхронизации (в новых версиях есть автоматическая внутренняя блокировка, но это стоит явно проверять для конкретной версии Go); (3) «парадокс дней рождения» — вероятность коллизии двух случайных значений растёт нелинейно и заметно быстрее интуиции по мере роста числа попыток относительно размера пространства значений — если запрашиваемое N приближается к существенной доле максимально возможных значений (например больше половины), наивный цикл «генерируй и проверяй» становится всё менее эффективным по числу отбрасываемых повторов; в этом случае эффективнее развернуть задачу — сгенерировать/перемешать весь диапазон возможных значений через алгоритм Фишера-Йетса (Fisher-Yates shuffle, равномерная случайная перестановка за O(n)) и просто взять первые N элементов результата. [24]

## Кросс-компиляция — частое заблуждение

Ошибочное мнение: скомпилированный Go-бинарник запускается на любой ОС без пересборки. На деле бинарник платформозависим — Go компилируется в нативный машинный код под конкретную пару ОС/архитектура. «Кросс-компиляция» — это пересборка с другими значениями переменных окружения `GOOS`/`GOARCH` (например, `GOOS=linux GOARCH=amd64 go build`), а не один универсальный бинарник, работающий везде. [8]

## `encoding/binary` — перевод чисел в байты с явным порядком байт

Задача «превратить `int32` в срез байт» наивно решается ручными битовыми сдвигами (`byte(x >> 24)`, `byte(x >> 16)` и т.д.) — рабочий, но низкоуровневый подход, уместный разве что для совсем специфичных протоколов; идиоматичнее — пакет `encoding/binary` с явным указанием порядка байт: `binary.BigEndian.PutUint32(buf, uint32(x))` или `binary.LittleEndian.PutUint32(buf, uint32(x))` (и обратные `Uint32`/`Uint64` для разбора байт обратно в число). Явный выбор функции вместо неявного поведения платформы — важно, потому что порядок байт не определяется языком/рантаймом произвольно, а обязан быть согласован по контракту конкретного бинарного протокола/формата файла. Big Endian — самый значимый байт числа записывается первым (сетевой порядок байт, network byte order, стандарт для большинства сетевых протоколов); Little Endian — наоборот, младший байт первым (нативный порядок для x86/x86-64 и большинства ARM-конфигураций). Несовпадение ожидаемого порядка байт у отправителя и получателя — частый источник трудноуловимых багов при интеграции с внешними бинарными протоколами/legacy-форматами файлов, где значение читается технически без ошибки, но получается совершенно другим числом. [63]
