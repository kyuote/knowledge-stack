Глава 12

HTTP-сервер

Мини-проект, который собирает вместе структуры, методы, мьютексы, JSON и net/http из прошлых глав — простой REST API для списка задач.

12.1Модель и хранилище

In-memory хранилище на map, защищённое мьютексом (глава 8) — вместо настоящей БД, но с тем же принципом:

store.go
type Task struct {
    ID   int    `json:"id"`
    Text string `json:"text"`
    Done bool   `json:"done"`
}

type Store struct {
    mu     sync.Mutex
    tasks  map[int]Task
    nextID int
}

func NewStore() *Store {
    return &Store{tasks: make(map[int]Task), nextID: 1}
}

func (s *Store) Add(text string) Task {
    s.mu.Lock()
    defer s.mu.Unlock()
    t := Task{ID: s.nextID, Text: text}
    s.tasks[t.ID] = t
    s.nextID++
    return t
}

func (s *Store) All() []Task {
    s.mu.Lock()
    defer s.mu.Unlock()
    out := make([]Task, 0, len(s.tasks))
    for _, t := range s.tasks {
        out = append(out, t)
    }
    return out
}

func (s *Store) Get(id int) (Task, bool) {
    s.mu.Lock()
    defer s.mu.Unlock()
    t, ok := s.tasks[id]
    return t, ok
}
Подробнее: почему All() возвращает копии, а не ссылку на карту medium

All() собирает срез из значений карты внутри критической секции и возвращает уже готовый срез — это принципиально: если бы метод возвращал саму карту s.tasks по ссылке, вызывающий код мог бы читать и писать её уже вне мьютекса, что превратило бы весь механизм защиты в фикцию (см. главу 8 про гонки данных). Возврат копии данных, а не доступа к внутреннему состоянию — стандартный способ безопасно «выпустить» защищённые мьютексом данные наружу.

Этот же Store — простая иллюстрация паттерна repository: обработчики HTTP ничего не знают о том, что данные лежат в map в памяти, а не в PostgreSQL — они видят только методы Add/All/Get. Замена map на реальную БД в проде не потребует менять код обработчиков вообще, если интерфейс хранилища выделить отдельно (см. 11.4, тестируемость через интерфейсы).

12.2Обработчики

handlers.go
type API struct{ store *Store }

func (a *API) listTasks(w http.ResponseWriter, r *http.Request) {
    w.Header().Set("Content-Type", "application/json")
    json.NewEncoder(w).Encode(a.store.All())
}

func (a *API) createTask(w http.ResponseWriter, r *http.Request) {
    var in struct{ Text string `json:"text"` }
    if err := json.NewDecoder(r.Body).Decode(&in); err != nil {
        http.Error(w, "некорректный JSON", http.StatusBadRequest)
        return
    }
    task := a.store.Add(in.Text)
    w.WriteHeader(http.StatusCreated)
    json.NewEncoder(w).Encode(task)
}

func (a *API) getTask(w http.ResponseWriter, r *http.Request) {
    id, err := strconv.Atoi(r.PathValue("id"))
    if err != nil {
        http.Error(w, "некорректный id", http.StatusBadRequest)
        return
    }
    task, ok := a.store.Get(id)
    if !ok {
        http.Error(w, "не найдено", http.StatusNotFound)
        return
    }
    json.NewEncoder(w).Encode(task)
}
Подробнее: почему Content-Type нужно ставить до WriteHeader deep

Первый вызов w.Write(...) (или неявный первый вызов внутри json.NewEncoder(w).Encode(...)) неявно посылает статус-код 200 OK, если WriteHeader ещё не был вызван явно, — и в этот момент фиксируются все заголовки, выставленные к тому моменту. Установка заголовка (w.Header().Set(...)) после первой записи в тело ответа ни на что не повлияет — заголовки уже отправлены клиенту. Поэтому в listTasks заголовок ставится первой строкой, а в createTask порядок ещё строже: WriteHeader(http.StatusCreated) вызывается явно и до Encode, иначе тело ответа отправило бы неявные 200 вместо нужного 201.

Ещё один частый промах в таком коде: ошибка от json.NewEncoder(w).Encode(...) в конце обработчика почти никогда не проверяется — на практике к этому моменту заголовки уже отправлены, и сделать полноценный http.Error уже нельзя, поэтому обычно её как минимум логируют, а не молча игнорируют.

Подробнее: http.Handler vs http.HandlerFunc, и чем плох nil вторым аргументом в ListenAndServe medium

http.Handler — интерфейс с единственным методом ServeHTTP(w http.ResponseWriter, r *http.Request). Методы a.listTasks/a.createTask выше — обычные функции с такой сигнатурой, а не значения, реализующие интерфейс напрямую; связывает их с интерфейсом тип-обёртка http.HandlerFunc — она сама реализует ServeHTTP, просто вызывая себя как функцию. Именно поэтому mux.HandleFunc(...) (принимающий обычную функцию) и mux.Handle(...) (принимающий готовый Handler) — по сути один и тот же механизм с разным уровнем адаптации.

Отдельная ловушка — вызов http.ListenAndServe(addr, nil) с nil вместо явного мультиплексора: тогда используется http.DefaultServeMux — единый глобальный экземпляр роутера пакета net/http, в который пишет любой импортированный в процесс пакет, вызвавший пакетные функции http.HandleFunc/http.Handle (в том числе сторонние зависимости, регистрирующие туда отладочные хендлеры). В отличие от кода выше, явно создающего свой mux := http.NewServeMux(), использование DefaultServeMux в проде считается плохой практикой — риск незаметного конфликта путей между независимыми частями кода и невозможность держать несколько независимых серверов в одном процессе. (источник: t.me/go_interview_lib)

12.3Маршрутизация

main.go
func main() {
    store := NewStore()
    api := &API{store: store}

    mux := http.NewServeMux()
    mux.HandleFunc("GET /tasks", api.listTasks)
    mux.HandleFunc("POST /tasks", api.createTask)
    mux.HandleFunc("GET /tasks/{id}", api.getTask)

    log.Println("слушаем :8080")
    http.ListenAndServe(":8080", mux)
}
собес

Свежая деталь: запись метода прямо в паттерне ("GET /tasks") и path-параметры вроде {id} с r.PathValue("id") — это возможности http.ServeMux, добавленные в Go 1.22. До этого стандартный роутер не различал методы и параметры пути — ради этого тянули сторонние библиотеки (chi, gorilla/mux).

Подробнее: почему до 1.22 тянули chi/gorilla, и приоритет более конкретного паттерна medium

До Go 1.22 http.ServeMux умел маршрутизировать только по точному совпадению пути или по префиксу, заканчивающемуся на / (например, "/tasks/" ловил всё, что начинается с этого префикса), и совсем не различал HTTP-методы — GET /tasks и POST /tasks обрабатывались бы одним и тем же паттерном "/tasks", а различать методы и вытаскивать path-параметры ({id}) приходилось руками внутри обработчика (r.Method == "GET", ручной парсинг r.URL.Path) или сторонними роутерами вроде gorilla/mux и chi, которые умели это из коробки. С 1.22 методы и {param} вошли в сам стандартный http.ServeMux, и многим проектам сторонний роутер стал не нужен вообще.

Когда несколько зарегистрированных паттернов могут совпасть с одним и тем же запросом, побеждает более конкретный — например, "GET /tasks/{id}" выигрывает у "GET /tasks/" для запроса GET /tasks/7, даже если оба зарегистрированы. Специальный синтаксис {id...} (с многоточием) ловит «хвост» пути произвольной длины — аналог wildcard-сегмента в сторонних роутерах.

Подробнее: httptest вместо реального curl/сервера medium

Проверка через curl на живом сервере удобна руками, но не автоматизируется в CI. Стандартный пакет net/http/httptest позволяет протестировать обработчик без реального сетевого сокета: httptest.NewRequest строит *http.Request напрямую в памяти, а httptest.NewRecorder() даёт http.ResponseWriter, который просто записывает всё в память вместо отправки по сети — обработчик вызывается как обычная функция, без поднятия сервера и порта.

handlers_test.go
func TestGetTask(t *testing.T) {
    api := &API{store: seedStore()}
    req := httptest.NewRequest("GET", "/tasks/1", nil)
    req.SetPathValue("id", "1")
    rec := httptest.NewRecorder()

    api.getTask(rec, req)

    if rec.Code != http.StatusOK {
        t.Errorf("код = %d, хотим %d", rec.Code, http.StatusOK)
    }
}

Для тестов, покрывающих весь стек включая маршрутизацию (а не один изолированный обработчик), поднимают httptest.NewServer(mux) — настоящий сервер на случайном свободном порту, который живёт только на время теста.

12.5Что дальше в проде

Для реального сервиса этому примеру не хватает: таймаутов (http.Server{ReadTimeout, WriteTimeout}), graceful shutdown через context и Server.Shutdown, middleware для логирования и восстановления после паники в хендлере, настоящей БД вместо map и более строгой валидации входных данных. Каждый пункт — материал для отдельной темы, здесь важно было собрать воедино синтаксис из прошлых глав.

Подробнее: graceful shutdown целиком deep

Grace­ful shutdown — это остановка сервера, при которой уже принятые запросы успевают доработать, а новые соединения перестают приниматься сразу после сигнала завершения. http.Server.Shutdown(ctx) делает именно это: закрывает слушающий сокет (новые соединения больше не принимаются), но ждёт завершения уже идущих обработчиков, пока не истечёт дедлайн переданного context.Context — если дедлайн истекает раньше, чем все обработчики закончили, Shutdown возвращает ошибку контекста, а незавершённые соединения обрываются принудительно.

graceful.go
srv := &http.Server{Addr: ":8080", Handler: mux}

go func() {
    if err := srv.ListenAndServe(); err != nil && err != http.ErrServerClosed {
        log.Fatalf("ListenAndServe: %v", err)
    }
}()

stop := make(chan os.Signal, 1)
signal.Notify(stop, syscall.SIGINT, syscall.SIGTERM)
<-stop // блокируемся, пока не придёт сигнал

ctx, cancel := context.WithTimeout(context.Background(), 10*time.Second)
defer cancel()
if err := srv.Shutdown(ctx); err != nil {
    log.Printf("принудительное завершение: %v", err)
}

Важная деталь: сам ListenAndServe() нужно запускать в отдельной горутине именно потому, что он блокирует вызывающую горутину до остановки сервера — если запустить его в основной горутине, код после него (ожидание сигнала, вызов Shutdown) никогда не выполнится. После успешного Shutdown, ListenAndServe в фоновой горутине вернёт специальную, ожидаемую ошибку http.ErrServerClosed — её явно исключают из «настоящих» ошибок, иначе штатная остановка сервера выглядела бы как сбой.

Код выше — «ручной» вариант через signal.Notify и отдельный канал. Более современная альтернатива — signal.NotifyContext (с Go 1.16): ctx, stop := signal.NotifyContext(context.Background(), os.Interrupt, syscall.SIGTERM) сразу возвращает обычный context.Context, который отменяется при получении сигнала, — тогда весь остальной код (в том числе части, уже написанные с оглядкой на ctx.Done(), например через errgroup) реагирует на завершение единым образом, без отдельного канала сигналов и ручного select. Обязателен defer stop() сразу после получения — он освобождает регистрацию обработчика сигнала в рантайме; без него регистрация продолжает висеть до конца процесса. (источник: t.me/go_interview_lib)

Подробнее: SQL-инъекция и XSS — минимально необходимая защита medium

«Более строгая валидация входных данных», упомянутая выше, на практике в первую очередь означает защиту от двух классических атак.

От SQL-инъекции защищают исключительно параметризованные запросы — плейсхолдеры ($1 в PostgreSQL, ? в MySQL/SQLite), где значения передаются драйверу отдельно от текста запроса, а не подставляются в строку конкатенацией или через fmt.Sprintf. Драйвер и СУБД в этом случае гарантированно интерпретируют переданное значение как данные, а не как часть SQL-синтаксиса, какие бы кавычки или ключевые слова оно ни содержало.

От XSS (внедрения чужого JS/HTML через пользовательский ввод, впоследствии отображаемый другим пользователям) защищает контекстно-зависимое экранирование при рендеринге. Стандартный пакет html/template делает это автоматически — экранирует значение по-разному в зависимости от того, куда именно оно подставляется в шаблоне (тело HTML-тега, атрибут, URL, встроенный <script>). Пакет text/template с виду тождественен по API, но не экранирует ничего вообще — использовать его для генерации HTML-страниц из непроверенных пользовательских данных небезопасно, это только для обычного текстового вывода. (источник: t.me/go_interview_lib)
