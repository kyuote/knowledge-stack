Глава 01

Базовый синтаксис

Коротко и по делу: как устроен файл на Go, переменные, типы, константы, операторы и видимость. Отдельно — что из этого чаще всего спрашивают на собеседовании.

1.1Анатомия файла

Любой файл начинается с объявления пакета, затем идут импорты, затем объявления. Точка входа программы — функция main в пакете main.

main.go
package main

import "fmt"

func main() {
    fmt.Println("Привет, Go!")
}
камень

Неиспользуемый импорт или неиспользуемая локальная переменная — это ошибка компиляции, а не предупреждение. Go нарочно не даёт мусору копиться в коде.

Подробнее про сборку файла medium

Пакет может состоять из нескольких файлов в одной директории — все они делят одно пространство имён, ничего не нужно импортировать друг у друга. Условие одно: у всех файлов одинаковый package.

Особая функция func init() запускается автоматически перед main, без явного вызова. В пакете таких функций может быть несколько, даже в разных файлах: сначала инициализируются все переменные уровня пакета, затем по порядку (файл за файлом) выполняются все init().

1.2Переменные

Три способа объявить переменную — с явным типом, с выводом типа и «короткое» объявление:

vars.go
var a int = 10     // явный тип
var b = 20         // тип выводится из значения — int
c := 30            // короткое объявление, только внутри функции

var (              // групповое объявление
    name    = "gopher"
    age int = 3
)
собес

Чем := отличается от var? := работает только внутри тела функции, требует хотя бы одну новую переменную слева и сам выводит тип. var работает и на уровне пакета, и позволяет объявить переменную без инициализации — тогда она получит zero value.

Подробнее: затенение переменных (shadowing) medium

:= внутри вложенного блока (if, for, просто { }) создаёт новую переменную, даже если снаружи уже есть переменная с таким же именем — внешняя на время блока просто «затеняется».

shadow.go
x := 1
if true {
    x := 2          // это НОВАЯ x, видна только внутри if
    fmt.Println(x)  // 2
}
fmt.Println(x)      // 1 — внешняя x не изменилась
Ещё глубже: почему это частый источник багов deep

Особенно коварно с ошибками — легко случайно затенить err из внешней области видимости:

shadowerr.go
var err error
if x, err := f(); x > 0 { // := создаёт новую err!
    _ = err
}
// внешняя err так и осталась nil, даже если f() вернула ошибку

Встроенный go vet это не ловит — нужен отдельный анализатор shadow (например, через golangci-lint).

собес

Зачем нужен zero value? Чтобы в языке в принципе не было неинициализированной памяти — любая переменная сразу в валидном состоянии, без UB как в C.

Byte vs rune? byte = uint8, один байт UTF-8. rune = int32, один символ Unicode. Индексация строки s[i] даёт байт, а range — руну.

камень

Строки в Go неизменяемы: s[0] = 'H' не скомпилируется. Чтобы менять — приводите к []byte или []rune и обратно.

Подробнее: усечение при конвертации medium

Явное приведение к меньшему типу не паникует — оно молча обрезает лишние биты:

truncate.go
var big int32 = 300
var small int8 = int8(big) // 300 не влезает в int8 (-128..127)
fmt.Println(small)          // 44 — молчаливое переполнение

Конвертация string ↔ []byte/[]rune — это всегда копирование памяти (O(n)), а не бесплатный reinterpret: строки в Go неизменяемы, слайсы — нет.

Подробнее: string изнутри — заголовок, графемы и zero value stringmedium

Внутри строка — не сами байты, а компактный заголовок (stringHeader) из двух слов: указатель на данные (Data) и длина в байтах (Len) — без поля ёмкости (Cap), в отличие от заголовка слайса. Именно поэтому len(s) всегда O(1) и всегда считает байты, а не «символы».

Байт (byte) — единица хранения UTF-8, руна (rune) — один code point Unicode, а то, что человек интуитивно называет «одним символом» — графема — может состоять из нескольких рун сразу (например «é», набранное как «e» + акцент, — это 2 руны, но 1 графема). Ни len(s), ни utf8.RuneCountInString графемы не считают — оба останавливаются на уровне байт/рун; для графемно-осознанного подсчёта нужны сторонние библиотеки (например rivo/uniseg).

Отдельная тонкость: zero value строки — всегда пустая строка "", а не nil, в отличие от слайса/map/канала. В этом смысле string ведёт себя как обычный value type (сравнима через ==, у неё нет «пустого/неинициализированного» состояния, отличного от "") — хотя физически внутри неё лежит указатель на данные.

Подробнее: почему float — плохой выбор для денег float32 / float64medium

float32/float64 следуют стандарту IEEE 754 — двоичному представлению, которое точно хранит далеко не все десятичные дроби (та же проблема, что и в большинстве других языков со стандартным float). Классический пример — сложение 0.1 миллион раз через float64 не даёт ровно 100000: мелкие ошибки округления накапливаются на масштабе.

money.go
var total float64
for i := 0; i < 1_000_000; i++ {
    total += 0.1
}
fmt.Println(total) // НЕ ровно 100000 — накопленная погрешность

// правильно — целые единицы валюты (копейки/центы)
var totalCents int64
for i := 0; i < 1_000_000; i++ {
    totalCents += 10 // 0.10 → 10 копеек
}

Практическое правило: для денег — либо целочисленный тип в минимальных неделимых единицах валюты (int64 в копейках/центах), либо тип NUMERIC/DECIMAL на уровне БД/специализированная decimal-библиотека, но не «голый» float32/float64. Дробный литерал без явного приведения (3.14) в Go по умолчанию имеет тип именно float64, а не float32 — это стоит держать в голове при работе со сторонними API, ожидающими float32.

Подробнее: правда ли, что rune — знаковый int32 специально ради -1 как признака ошибки? runemedium

⚠ Популярное, но неточное объяснение — встречается в разных обучающих материалах: якобы rune сделали знаковым (int32, а не uint32) специально для того, чтобы функции декодирования могли возвращать -1 как признак «невалидного символа». Это не так на практике: стандартная библиотека для этого использует не -1, а специальную руну utf8.RuneError (U+FFFD) — unicode/utf8.DecodeRuneInString возвращает (RuneError, 0) для пустой строки и (RuneError, 1) для невалидной кодировки, но никогда -1. Официальный блог-пост Go про строки лишь констатирует факт: «rune — это алиас для int32, чтобы в коде было явно видно, где значение представляет code point», не объясняя выбор знаковости.

Более скромное и проверяемое объяснение: одного code point Unicode достаточно 21 бита, поэтому естественным выбором стал 32-битный тип — а int32, а не uint32, просто следует общему соглашению Go по умолчанию использовать знаковые целые (как int для длин/индексов), а не потому что отрицательные руны специально задуманы как сигнал ошибки. byte (uint8), для сравнения, беззнаковый естественно — это просто единица хранения байта (0..255), а не Unicode-значение. (проверено в этой сессии: go.dev/blog/strings, pkg.go.dev/unicode/utf8)

Подробнее: когда использовать byte, а когда rune byterunemedium

byte — для сырых данных, без понятия «символа»: ввод/вывод (io.Reader/io.Writer работают с []byte), хеширование, шифрование, бинарные протоколы, индекс строки s[i]. rune — для текста, когда важен именно символ: перебор строки посимвольно (for i, r := range s), подсчёт длины в символах, а не в байтах (utf8.RuneCountInString(s) вместо len(s)), регистр и классы символов (unicode.ToUpper, unicode.IsLetter).

Правило простое: поток байт — byte; юникод-осознанный анализ текста — rune. Для ASCII разница незаметна, а вот кириллица (2 байта на символ в UTF-8) или эмодзи (обычно 4 байта) её сразу проявляют: len("привет") — это 12, а не 6. Резать строку по s[:n] безопасно, только если точно известно, что байт n не разрезает многобайтовый символ пополам.

1.4Константы и iota

Отдельного типа enum в Go нет — его эмулируют через const и счётчик iota, обнуляемый в каждом новом блоке:

weekday.go
type Weekday int

const (
    Sunday Weekday = iota // 0
    Monday                // 1
    Tuesday               // 2
    Wednesday             // 3
)
собес

Есть ли enum в Go? Нет ключевого слова — есть идиома «именованный тип + const + iota». Типобезопасность обеспечивает именно именованный тип (Weekday), а не сам iota.

Подробнее: iota с выражениями и битовые флаги medium

iota можно подставлять в произвольное выражение — классика: степени двойки для битовых флагов:

flags.go
const (
    Read  = 1 << iota // 1 << 0 = 1
    Write              // 1 << 1 = 2
    Exec               // 1 << 2 = 4
)
perms := Read | Write // 3 — комбинация флагов

Пропустить значение — подчёркивание вместо имени: const (a = iota; _; c) — c получит 2, хотя имени под 1 не было.

1.5Приведение типов

В Go нет неявных преобразований — даже между int и float64. Только явный вызов T(v):

convert.go
var i int = 42
var f float64 = float64(i) // явно
var u uint = uint(f)

// var f2 float64 = i      // ошибка компиляции:
                           // cannot use i (int) as float64
собес

Почему нет неявного приведения? Разработчики Go сознательно пожертвовали удобством ради явности: скрытая потеря точности или неожиданный оверфлоу — частый источник багов в C/C++/JS.

Подробнее: ловушка string(int) medium

string(n), где n — число, не переводит число в текстовую запись — Go воспринимает его как код Unicode-символа:

strconv_trap.go
s := string(65)       // "A" — код символа, НЕ "65"!
n := strconv.Itoa(65) // "65" — вот так правильно

Для чисел нужен пакет strconv: Itoa/Atoi — число в строку и обратно. С недавних версий go vet предупреждает про такое string(int), если явно не имелся в виду rune.

&^ — уникальный для Go оператор «AND NOT» (bit clear): a &^ b обнуляет в a те биты, где в b стоит 1.

++ и -- — это statement, а не выражение: x = i++ не скомпилируется, только i++ отдельной строкой.

Подробнее: приоритет операторов и переполнение medium

Целочисленное деление отбрасывает дробную часть, округляя к нулю: 7 / 2 == 3, -7 / 2 == -3. Остаток % берёт знак делимого.

Переполнение знаковых и беззнаковых целых не паникует — значение «оборачивается» по модулю (math.MaxInt8 + 1 == math.MinInt8). Единственное исключение среди целых — деление на 0: это паника в рантайме (runtime error: integer divide by zero), кроме случая, когда оба операнда — константы: тогда это ошибка компиляции, а не рантайм-паника.

У float64/float32 деление на 0 ведёт себя принципиально иначе — не паникует вообще: по IEEE 754 результат +Inf, -Inf или NaN (для 0.0/0.0). Частая ловушка на собеседовании — ответить «паника» и для float тоже, забыв про эту асимметрию между целыми и плавающей точкой. (источник: t.me/go_interview_lib)

1.7Экспорт и видимость

В Go нет private/public. Видимость идентификатора за пределами пакета решает регистр первой буквы:

shapes.go
package shapes

type Circle struct { // экспортируется — с заглавной
    Radius float64    // экспортируется
    color  string      // НЕ экспортируется — со строчной
}

func NewCircle(r float64) *Circle { … } // экспортируется
func (c *Circle) area() float64 { … }    // НЕ экспортируется

(c *Circle) перед именем функции — это receiver: он делает функцию методом, привязанным к типу Circle (грубо — как self/this в других языках, только явно указанный). Вызывается как c.area(). Подробно про методы — в главе 6, здесь важно только одно: видимость метода вне пакета решает та же заглавная буква — area строчная, значит метод приватный для пакета.

собес

Как в Go устроена инкапсуляция без private? На уровне пакета, а не класса: правило регистра действует для всех файлов пакета сразу и проверяется компилятором, а не соглашением.

Подробнее: видимость и encoding/json medium

Пакеты вроде encoding/json работают через рефлексию, а рефлексия не может ни прочитать, ни записать неэкспортируемое поле из другого пакета. Поэтому color string из примера выше просто молча пропускается при json.Marshal/Unmarshal — без ошибки, как будто поля не существует.

1.8Комментарии

Обычные — // и /* */. Комментарий прямо перед объявлением становится doc-комментарием и попадает в godoc:

doc.go
// Circle описывает круг с заданным радиусом.

Соглашение godoc: doc-комментарий начинается с имени сущности (Circle описывает…) — так его проще парсить и читать в сгенерированной документации.
