Глава 05

Указатели

Единственный законный способ изменить оригинал, если Go всё передаёт по значению — и заодно самая частая паника в проде.

5.1& и *

& берёт адрес переменной, * — разыменовывает указатель:

pointer.go
x := 10
p := &x    // p — *int, адрес x
*p = 20     // разыменование — меняем x через указатель
fmt.Println(x) // 20

Это и есть способ обойти «всё передаётся по значению» из главы 3 — указатель тоже копируется, но копия указывает на тот же адрес:

double.go
func double(n int)  { n *= 2 }   // копия — x не изменится
func doublePtr(p *int) { *p *= 2 } // указывает на x — x изменится

x := 10
double(x)          // x всё ещё 10
doublePtr(&x)      // x стало 20
Подробнее: копирование структуры — не то же самое, что копирование её данных deep

Присвоение структуры (без указателя) копирует всю структуру целиком — но если внутри есть поле-слайс или поле-map, копируется только их заголовок (shallow copy): обе копии продолжают ссылаться на одни и те же исходные данные:

shallow.go
type Order struct {
    ID    int      // обычное поле — копируется полностью
    Items []string // слайс — копируется только заголовок (ptr+len+cap)
}

a := Order{ID: 1, Items: []string{"хлеб"}}
b := a               // копия структуры

b.ID = 99            // меняет только b — a.ID остаётся 1 ✓
b.Items[0] = "молоко" // меняет общий массив — a.Items[0] тоже "молоко" ✗
fmt.Println(a.ID)        // 1    — обычное поле скопировалось честно
fmt.Println(a.Items[0])  // "молоко" — слайс разделяет данные!

append разрывает эту связь — но только если не хватает ёмкости (cap) и нужна реаллокация:

append_break.go
// cap есть — append пишет в ТОТ ЖЕ массив, обе копии видят изменение
a := Order{Items: make([]string, 1, 10)} // len=1, cap=10
a.Items[0] = "хлеб"
b := a
b.Items = append(b.Items, "молоко") // места хватило — старый массив
fmt.Println(a.Items[1])             // "молоко" — a видит! (сюрприз)

// cap исчерпан — append выделяет новый массив, связь рвётся
a2 := Order{Items: []string{"хлеб"}} // len=1, cap=1 — места нет
b2 := a2
b2.Items = append(b2.Items, "молоко") // реаллокация → b2.Items новый массив
fmt.Println(len(a2.Items))            // 1 — a2 про "молоко" не знает

Если нужны по-настоящему независимые копии — только глубокое копирование вручную (copy() для слайса). []*T — это не решение, а другая стратегия: явное управляемое шаринг объектов через указатели.

5.2new() vs &T{}

new.go
p1 := new(int)        // *int → 0, базовый тип
p2 := new(Point)      // *Point → {0, 0}, поля — zero value
p3 := &Point{1, 2}    // *Point → {1, 2}, сразу с нужными полями — так пишут почти всегда
собес

new(T) просто выделяет память под zero value T и возвращает *T. &T{...} делает то же самое, но с инициализацией полей на месте — поэтому на практике new почти не встречается вне учебников.

Для полей структуры компилятор сам разыменовывает — p.X вместо (*p).X:

autoderef.go
p := &Point{1, 2}
p.X = 10   // сахар для (*p).X = 10
Подробнее: new() для слайса/map/канала обычно бесполезен medium

new(T) работает для любого типа, но для слайса/map/канала он даёт указатель на zero value этого типа, то есть на nil — использовать сразу нельзя, нужна отдельная инициализация:

new_nil.go
p := new([]int) // *[]int, указывает на nil-слайс
(*p)[0] = 1      // panic: index out of range — слайс всё ещё пуст

s := make([]int, 0, 10) // так — сразу с выделенным буфером

Поэтому make, а не new — стандартный способ создать эти три типа. Отдельная деталь: то, окажется ли значение на стеке или в куче, решает escape analysis (разбор ниже), а не то, через new или make оно создано.

5.3Указатель на локальную переменную

В отличие от C, возвращать адрес локальной переменной в Go совершенно безопасно:

newpoint.go
func newPoint(x, y int) *Point {
    p := Point{x, y}
    return &p // безопасно! компилятор перенесёт p на heap
}
собес

А как же dangling pointer, как в C? Невозможен — сработает тот же escape-анализ, что и с замыканиями в главе 3: раз на p остаётся живая ссылка после возврата, компилятор размещает её на heap вместо стека.

Подробнее: взятие адреса не гарантирует уход на heap medium

Частое заблуждение — считать, что раз у переменной взяли &, она автоматически окажется в куче. На самом деле компилятор анализирует, «убегает» ли переменная из функции (возвращается, сохраняется глобально, передаётся в горутину/канал) — если нет, она вполне может остаться на стеке, даже если её адрес был взят внутри функции:

noescape.go
func sum(a, b int) int {
    p := &a  // адрес взят, но p никуда не "убегает" из функции
    return *p + b // компилятор вполне может оставить a на стеке
}

Посмотреть, что решил компилятор для конкретной функции — go build -gcflags="-m": он печатает решения escape-анализа построчно (moved to heap / does not escape). Полезно при профилировании — лишние аллокации на горячем пути часто оказываются неожиданным «убеганием» переменной туда, где её не ждали.

5.4nil-указатель

nilptr.go
var p *Point
p.X = 1 // panic: runtime error: invalid memory address or nil pointer dereference
камень

Разыменование nil-указателя — одна из самых частых паник в проде, особенно если указатель пришёл откуда-то извне (не найденная запись, несработавший поиск). Проверка if p == nil перед использованием — не паранойя, а норма.

собес

Есть ли в Go арифметика указателей? Нет (кроме экзотического unsafe.Pointer). Указатель либо валиден, либо nil — это упрощает сборщик мусора и делает памятную модель Go безопаснее, чем в C.

Подробнее: unsafe.Pointer и почему указатель всегда весит одинаково deep

Указатель — это всегда просто адрес: 4 байта на 32-битной платформе, 8 байт на 64-битной, независимо от того, указывает он на int8 или на мегабайтную структуру — сам указатель не «весит» больше от размера цели.

unsafe.Pointer — способ обойти систему типов и явно приводить указатели между несовместимыми типами; точечно используется во внутренностях стандартной библиотеки (например в strings.Builder/конвертации string↔[]byte без копирования). В обычном прикладном коде это считается кодом-запахом — почти всегда есть типобезопасная альтернатива, а любая ошибка в ручной арифметике с unsafe.Pointer — потенциальный SIGSEGV, который компилятор уже не может предотвратить.

5.5Антипаттерны

камень

Никогда не берите указатель на интерфейс (*io.Reader). Интерфейс уже сам по себе содержит указатель на данные — добавляя ещё один уровень косвенности, вы ломаете методы и получаете путаный код. Почти всегда это ошибка в рассуждении «мне нужен указатель, чтобы изменить значение».

iface_ptr.go
// ❌ НЕПРАВИЛЬНО — почти никогда не нужно
func process(r *io.Reader) {
    (*r).Read(buf) // лишнее разыменование
}

// ✓ ПРАВИЛЬНО — интерфейс передаётся по значению, внутри уже есть указатель
func process(r io.Reader) {
    r.Read(buf)
}

// Единственный легитимный случай *io.Reader — когда нужно
// заменить саму переменную интерфейса (редко):
func resetReader(r *io.Reader, new io.Reader) {
    *r = new
}
камень

Двойной указатель (**T) — почти всегда лишний. Встречается как «out-параметр» для изменения указателя снаружи, но в Go для этого обычно лучше просто вернуть новый указатель.

double_ptr.go
// ❌ C-стиль out-параметр через **T
func initNode(n **Node) {
    *n = &Node{Val: 42}
}
var n *Node
initNode(&n)

// ✓ Go-стиль — просто возвращаем значение
func newNode() *Node {
    return &Node{Val: 42}
}
n := newNode()

// Легитимный случай **T — linked list или дерево,
// где нужно изменить корень (head) снаружи:
func pushFront(head **Node, val int) {
    *head = &Node{Val: val, Next: *head}
}
