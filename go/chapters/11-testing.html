Глава 11

Тестирование

Пакет testing, идиома table-driven tests и то, как маленькие интерфейсы из главы 6 делают код тестируемым без библиотек для моков.

11.1Базовый тест

Файл *_test.go, функция TestXxx(t *testing.T), запуск — go test:

math_test.go
func TestAdd(t *testing.T) {
    got := Add(2, 3)
    want := 5
    if got != want {
        t.Errorf("Add(2, 3) = %d, хотим %d", got, want)
    }
}
собес

t.Errorf vs t.Fatalf? Errorf помечает тест проваленным и продолжает выполнение (можно собрать несколько ошибок за один прогон), Fatalf сразу останавливает текущий тест — используйте его, когда без прерванного шага (например, без успешного открытия файла) продолжать бессмысленно.

Подробнее: почему Fatalf нельзя вызывать не из горутины теста deep

t.Fatalf (и t.FailNow, на котором он основан) внутри вызывает runtime.Goexit() — специальную функцию, которая завершает текущую горутину, предварительно прогнав все её defer, но не завершая всю программу. Именно поэтому Fatalf нельзя вызывать из горутины, запущенной внутри теста (например, воркера), а не из горутины самого теста — Goexit просто «убьёт» ту горутину, где был вызван, но не остановит и не провалит тест из горутины, где он в реальности исполняется; в лучшем случае это приведёт к зависшему тесту или гонке на завершении, а не к ожидаемой ошибке.

Практическое правило: t.Fatal/t.FailNow вызываются только из той же горутины, в которой выполняется тело TestXxx (или его подтеста, запущенного через t.Run). Если ошибку нужно сообщить из воркер-горутины — используют канал с результатом или t.Errorf после wg.Wait() в основной горутине теста.

11.2Table-driven tests

Де-факто стандарт в Go: один кейс — одна строка таблицы, t.Run даёт каждому кейсу свой независимый подтест:

table_test.go
func TestAdd(t *testing.T) {
    tests := []struct {
        name string
        a, b int
        want int
    }{
        {"положительные", 2, 3, 5},
        {"с нулём", 0, 5, 5},
        {"отрицательные", -1, -1, -2},
    }

    for _, tt := range tests {
        t.Run(tt.name, func(t *testing.T) {
            got := Add(tt.a, tt.b)
            if got != tt.want {
                t.Errorf("Add(%d, %d) = %d, хотим %d", tt.a, tt.b, got, tt.want)
            }
        })
    }
}
собес

Зачем именно так? Новый кейс — это одна строка в срезе, а не новая функция. t.Run(tt.name, …) даёт каждому кейсу отдельное имя в выводе — сразу видно, какой конкретно провалился, и можно перезапустить только его через -run.

камень

Тот же подвох, что и с range в горутинах (глава 2): до Go 1.22 переменную цикла tt нужно было перехватывать явно (tt := tt) внутри тела, иначе при запуске подтестов параллельно (t.Parallel()) все они видели последнее значение tt. С 1.22 каждая итерация получает свою копию.

Подробнее: t.Parallel() и golden-файлы medium

Вызов t.Parallel() первой строкой внутри тела подтеста сигнализирует go test, что этот подтест можно выполнять параллельно с другими такими же подтестами — сам родительский тест при этом приостанавливается до тех пор, пока не будут запущены все его подтесты, после чего они реально исполняются одновременно (ограничено флагом -parallel, по умолчанию равным GOMAXPROCS). Это ускоряет большие table-driven наборы, но требует, чтобы кейсы были независимы друг от друга и не делили изменяемое состояние без синхронизации.

Для тестов со сложным ожидаемым выводом (сгенерированный код, большой JSON/HTML-ответ) вместо литералов в самом тесте часто используют golden-файлы — эталонный вывод сохраняют в отдельный файл (testdata/case.golden) и сравнивают фактический результат с его содержимым; флаг вида -update (соглашение, не встроено в testing) позволяет перегенерировать golden-файлы одной командой при осознанном изменении ожидаемого поведения.

11.3Бенчмарки

bench_test.go
func BenchmarkAdd(b *testing.B) {
    for i := 0; i < b.N; i++ {
        Add(2, 3)
    }
}
собес

Кто выставляет b.N? Не вы — сам testing подбирает его автоматически, постепенно увеличивая, пока не наберётся достаточно повторов для стабильного по времени измерения. Запуск: go test -bench=. -benchmem.

Подробнее: -benchmem, b.ReportAllocs и защита от компилятора medium

Флаг -benchmem добавляет в вывод бенчмарка число аллокаций на операцию (allocs/op) и байт на операцию (B/op) — часто именно эти две цифры интереснее сырого времени, потому что аллокации напрямую нагружают GC. Опасность, о которой часто спрашивают: компилятор умеет заметить, что результат вызова внутри цикла бенчмарка нигде не используется, и убрать сам вызов через dead code elimination — тогда бенчмарк «измеряет» пустой цикл и врёт о производительности. Стандартная защита — сохранять результат в пакетную переменную:

bench_safe_test.go
var result int // пакетная переменная — компилятор не уберёт запись в неё

func BenchmarkAdd(b *testing.B) {
    var r int
    for i := 0; i < b.N; i++ {
        r = Add(2, 3)
    }
    result = r // предотвращает "оптимизацию до пустоты"
}

Ещё один стандартный приём — b.ResetTimer() сразу после дорогой подготовки данных внутри самой функции бенчмарка, чтобы время на setup не попадало в измерение самой операции.

11.4Тестируемость через интерфейсы

Маленькие интерфейсы и структурная типизация (глава 6) позволяют подставлять фейки без библиотек для моков:

fake_test.go
type Store interface {
    Get(id int) (string, error)
}

type fakeStore struct{}
func (f *fakeStore) Get(id int) (string, error) { return "тест", nil }

func TestHandler(t *testing.T) {
    h := NewHandler(&fakeStore{}) // подменяем реальную БД фейком
    // ...
}
Подробнее: fake vs mock, и когда всё же нужны библиотеки моков medium

В экосистеме Go принято различать «fake» — упрощённую, но реально работающую альтернативную реализацию интерфейса (например, in-memory хранилище вместо реальной БД) — и «mock» — объект, который не реализует логику, а только проверяет, что к нему обратились с ожидаемыми аргументами в ожидаемом порядке. Идиоматичный Go-подход исторически предпочитает ручные fake-и (как в примере выше) генерации моков через рефлексию или кодогенерацию — маленькие интерфейсы (глава 6) делают ручное написание fake дешёвым, а сама структурная типизация не требует специального фреймворка для подмены зависимости.

Тем не менее для больших проектов с десятками зависимостей и точной проверкой поведения вызовов (сколько раз вызван метод, с какими именно аргументами, в каком порядке) распространены и генераторы моков — gomock (с mockgen) и testify/mock — они генерируют код, реализующий интерфейс, с настраиваемыми ожиданиями (EXPECT()) и встроенными проверками вызовов. Выбор между ручным fake и сгенерированным mock — это компромисс между простотой/читаемостью и точностью контроля над поведением зависимости в тесте.

КомандаЧто делает

Подробнее: build-теги для интеграционных тестов и -short medium

Быстрые юнит-тесты и медленные интеграционные (поднимающие реальную БД, обращающиеся по сети) принято разделять, чтобы CI мог гонять их отдельными этапами. Два стандартных способа: build-тег в начале файла (//go:build integration, файл компилируется только при go test -tags=integration) — или проверка флага testing.Short() внутри самого теста с ранним t.Skip("пропускаем в -short режиме"), если тест запущен с go test -short.

integration_test.go
func TestDatabaseIntegration(t *testing.T) {
    if testing.Short() {
        t.Skip("пропускаем интеграционный тест в -short режиме")
    }
    // ... реальное подключение к БД
}

go test -cover считает покрытие по строкам/блокам, но не гарантирует качество тестов — 100% покрытия достижимо и без единой проверки утверждения (assertion) внутри теста, поэтому в реальных проектах процент покрытия — ориентир, а не самоцель.
