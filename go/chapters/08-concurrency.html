Глава 08

Конкурентность

Визитная карточка Go: горутины, каналы, select, sync — и где именно прячутся гонки данных.

8.1Горутины

goroutine.go
go func() {
    fmt.Println("работает в фоне")
}()
собес

Горутина — это поток ОС? Нет. Это лёгкая «зелёная» нить: рантайм Go сам мультиплексирует множество горутин на меньшее число настоящих потоков ОС (планировщик M:N). Стартовый стек горутины — около 2 КБ и растёт по мере надобности, тогда как поток ОС обычно резервирует мегабайты. Поэтому горутин легко запустить тысячи и десятки тысяч.

камень

Когда main() завершается, все горутины обрываются без предупреждения — даже недописанные:

gotcha.go
func main() {
    go fmt.Println("привет") // main может завершиться раньше — и это не напечатается
}
Подробнее: модель планировщика GMP и до какого предела растёт стек deep

Планировщик Go — модель GMP: G (горутина), M (поток ОС), P (логический процессор, число = GOMAXPROCS, по умолчанию — число ядер). У каждого P — своя локальная очередь горутин; когда она опустеет, P ворует горутины из чужой очереди (work stealing), забирая обычно половину, чтобы не создавать лишней конкуренции за одну очередь.

Стартовый стек горутины — 2 КБ, растёт динамически до ~1 ГБ по умолчанию — упереться в этот лимит почти всегда признак неограниченной рекурсии, а не легитимной глубокой нагрузки. Именно за счёт лёгкого старта на типичном железе можно держать миллионы горутин одновременно, хотя практический ориентир для одного инстанса — не превышать 500 тыс.–1 млн, с запасом по памяти и с использованием worker pool (8.7) для контроля нагрузки, а не бесконтрольного спавна.

С Go 1.14 планировщик умеет асинхронно вытеснять горутину, которая слишком долго не отдаёт управление добровольно (сигнал SIGURG) — до этого «тяжёлый» вычислительный цикл без операций ввода-вывода мог надолго занять поток целиком.

Три штатных способа остановить горутину (в отличие от потока ОС, у горутины нет метода вроде Kill() — остановить можно только «изнутри», кооперативно):

  1. завершение main() — обрывает вообще все горутины программы разом, без каких-либо гарантий завершённости;
  2. закрытие канала, который слушают горутины — close(ch) будит разом всех, кто ждёт на нём, стандартный «широковещательный» сигнал;
  3. отмена через context — все горутины держат один и тот же ctx и проверяют ctx.Done(), обычно в select (подробнее о самом context — в 8.3 ниже).

Управление ресурсами планировщика — не только GOMAXPROCS как переменная окружения: идиоматичный явный вызов runtime.GOMAXPROCS(runtime.NumCPU()) фиксирует число P равным числу логических ядер (это и есть значение по умолчанию, явный вызов нужен, только если до этого кто-то его переопределил). runtime.Gosched() — добровольно уступить текущий поток, поставив свою горутину в конец очереди на выполнение, не блокируясь при этом ни на чём; в проде почти не нужен благодаря вытесняющему планировщику с Go 1.14, но всплывает в вопросах про кооперативную многозадачность. (источник: habr.com/ru/articles/670974/)

8.2Каналы

channel.go
ch := make(chan int)      // небуферизованный
bch := make(chan int, 3)  // буферизованный на 3

ch <- 5      // отправка
v := <-ch    // получение
close(ch)    // сигнал "больше данных не будет"

v, ok := <-ch // ok == false — канал закрыт и пуст
камень

Отправка в закрытый канал — паника (send on closed channel). Повторное close — тоже паника. А вот читать из закрытого канала можно всегда — вернётся zero value и ok == false.

Подробнее: nil-канал не паникует — он блокируется навсегда deep

Полная таблица поведения по трём состояниям канала — частый вопрос-«аксиома», который путают: nil-канал — и чтение, и запись блокируются навсегда (вечный deadlock, если это единственный путь горутины), не паника; открытый канал — обычная семантика рандеву/буфера; закрытый канал — чтение продолжает отдавать оставшиеся данные, затем zero value без блокировки, запись — паника.

СостояниеЧтениеЗапись

закрытоставшиеся данные, затем zero value без блокапаника

Это специально используют в select: присвоив каналу nil, соответствующий case больше никогда не сработает — способ динамически «выключить» одну из веток, например при реализации конечного автомата состояний (разбор — в 8.3 ниже). Внутри канал — структура hchan с очередями ожидающих отправителей/получателей (sendq/recvq); каждая заблокированная горутина паркуется там в обёртке sudog, не «крутясь в цикле», и будится через рантайм-функцию goready(), когда появляется встречная сторона.

Подробнее: почему chan struct{}, а не chan bool, для канала-сигнала medium

Когда через канал не передаётся полезных данных, а важен только сам факт получения значения или закрытия («стоп», «готово», «разбудить») — идиоматичный тип канала: chan struct{}, а не chan bool. Причина не только стилистическая: struct{} — тип нулевого размера, не занимает памяти вообще, тогда как bool физически занимает байт и создаёт ложное впечатление, что переданное значение (true/false) само по себе что-то значит. chan struct{} явно говорит читателю кода: этот канал — только для синхронизации.

Тот же тип struct{} — идиоматичная реализация множества (set) как map[T]struct{} вместо map[T]bool ровно по той же причине нулевого размера значения. (источник: t.me/go_interview_lib)

8.3select

select.go
select {
case v := <-ch1:
    fmt.Println("из ch1:", v)
case v := <-ch2:
    fmt.Println("из ch2:", v)
case <-time.After(time.Second):
    fmt.Println("таймаут")
default:
    fmt.Println("ни один канал не готов")
}
собес

Что если готовы сразу два case? select выберет один из готовых случайно — намеренно, чтобы код не мог незаметно положиться на порядок case'ов как на приоритет.

Подробнее: time.After в цикле — незаметная утечка памяти deep

Частая ошибка на собеседовании и в проде: time.After(d) создаёт новый таймер (и канал под него) при каждом вызове. Если вызвать её внутри select, который крутится в цикле, — на каждой итерации создаётся новый таймер, а старые продолжают жить в памяти до срабатывания (таймер не собирается GC, пока не истечёт). При частых итерациях это ощутимая утечка.

select_leak.go
// плохо: новый таймер на каждой итерации цикла
for {
    select {
    case v := <-ch:
        process(v)
    case <-time.After(5 * time.Second):
        return
    }
}

// хорошо: один таймер, переиспользуется через Reset
t := time.NewTimer(5 * time.Second)
defer t.Stop()
for {
    if !t.Stop() {
        <-t.C
    }
    t.Reset(5 * time.Second)
    select {
    case v := <-ch:
        process(v)
    case <-t.C:
        return
    }
}

Ещё один нюанс: nil-канал в select никогда не готов — этим пользуются, чтобы динамически «выключать» case, присвоив переменной канала nil (см. 8.2), вместо того чтобы городить дополнительный bool-флаг и ветвление.

Подробнее: основы context.Context — Background/TODO и три способа отмены medium

context.Background() и context.TODO() возвращают технически идентичный пустой контекст — разница чисто смысловая, для читаемости кода. Background() — канонический корень дерева контекстов, с которого стартуют в точке входа программы (main, обработчик верхнего уровня). TODO() — временная заглушка для мест, где ещё не решено, какой контекст должен быть на самом деле, либо родительский контекст пока объективно неоткуда взять — сигнал «здесь чего-то не хватает», а не альтернативный «корень».

Три конструктора производного отменяемого контекста, у каждого из которых обязательно нужно вызвать возвращаемую функцию отмены (обычно через defer cancel()), даже если дедлайн/таймаут уже успел сработать сам — иначе связанные с контекстом ресурсы (например горутина внутри самого пакета context, отслеживающая дедлайн) не освобождаются сразу:

КонструкторКогда сработает отмена
WithCancel(parent)только вручную — когда вызывающий сам решит и позовёт cancel()
WithDeadline(parent, t)автоматически в конкретный момент времени t
WithTimeout(parent, d)автоматически через интервал d от текущего момента (по сути обёртка над WithDeadline)
ctxselect.go
select {
case res := <-resultCh:
    return res, nil
case <-ctx.Done():
    return nil, ctx.Err() // context.Canceled или context.DeadlineExceeded
}

Канал ctx.Done() закрывается ровно один раз при отмене (см. широковещательную семантику close из 8.2) — поэтому его можно безопасно слушать сразу в нескольких горутинах и в select вперемешку с другими каналами; ctx.Err() после закрытия возвращает конкретную причину — context.Canceled (позвали cancel()) либо context.DeadlineExceeded (истёк срок). (источник: habr.com/ru/articles/670974/)

8.4sync.WaitGroup

waitgroup.go
var wg sync.WaitGroup
for i := 0; i < 3; i++ {
    wg.Add(1)
    go func() {
        defer wg.Done()
        fmt.Println("worker", i)
    }()
}
wg.Wait()
камень

Add(1) вызывается до запуска горутины, а не внутри неё — иначе Wait() может успеть завершиться раньше, чем горутина вообще успеет вызвать Add.

Подробнее: errgroup — WaitGroup + ошибки + отмена контекста medium

Голый sync.WaitGroup не умеет собирать ошибки из горутин и не умеет остановить остальные при первой ошибке — обе задачи приходится решать вручную (общий error под мьютексом, канал ошибок). Пакет golang.org/x/sync/errgroup закрывает именно этот пробел: g, ctx := errgroup.WithContext(ctx) создаёт группу, привязанную к контексту — как только любая горутина вернёт ненулевую ошибку, этот ctx отменяется, и остальные горутины (если написаны с оглядкой на ctx.Done()) могут завершиться раньше срока; g.Wait() возвращает первую полученную ошибку.

errgroup.go
g, ctx := errgroup.WithContext(context.Background())
g.SetLimit(10) // не более 10 горутин одновременно

for _, url := range urls {
    url := url
    g.Go(func() error {
        return fetch(ctx, url)
    })
}
if err := g.Wait(); err != nil {
    log.Fatal(err)
}

SetLimit(n) дополнительно превращает группу в готовый пул с ограничением параллелизма — не нужно вручную городить буферизованный канал-семафор.

Подробнее: как счётчик и число ожидающих упакованы в одно 64-битное слово deep

Внутреннее состояние WaitGroup — не два отдельных поля-счётчика, а одно упакованное uint64: старшие 32 бита — счётчик незавершённых задач (то, что меняют Add/Done), младшие 32 бита — число горутин, заблокированных в Wait(). Упаковка в одно слово — не экономия памяти, а способ менять оба значения одной атомарной инструкцией CPU (atomic.Add/CAS) без отдельного мьютекса: если бы это были два независимых int32, между их обновлениями возможна была бы гонка.

Отсюда и историческое требование выравнивания WaitGroup на границу 8 байт на 32-битных платформах — атомарная операция над 64-битным словом невозможна, если оно не выровнено, а несоблюдение этого требования на старых версиях Go могло приводить к панике именно на 32-битных архитектурах. (источник: t.me/go_interview_lib)

8.5sync.Mutex

mutex.go
var mu sync.Mutex
var counter int

func increment() {
    mu.Lock()
    defer mu.Unlock()
    counter++
}
собес

Зачем Mutex, если есть каналы? Девиз Go — «не делитесь памятью через общение, общайтесь через каналы», но это не догма: для защиты простого счётчика или поля структуры Mutex часто проще и быстрее, чем городить канал ради одного значения.

Подробнее: normal- и starvation-режим мьютекса deep

С Go 1.9 sync.Mutex внутри (internal/sync/mutex.go) — не просто один бит блокировки, а конечный автомат с двумя режимами. В normal mode горутина, не сумевшая захватить мьютекс сразу, несколько раз активно крутится в спин-цикле (busy-wait) в надежде, что владелец вот-вот освободит блокировку — это дёшево на многоядерных машинах, если критическая секция короткая, и только после нескольких неудачных попыток горутина паркуется в очереди ожидания. Из-за этого разбуженная горутина конкурирует за захват наравне с новоприбывшими и может проигрывать им много раз подряд — это несправедливо, но быстро в среднем.

Если конкретная горутина ждёт в очереди дольше порога starvationThresholdNs = 1мс, мьютекс переключается в starvation mode: захват передаётся строго первой горутине из очереди FIFO, новоприбывшие вообще не пытаются захватить мьютекс сразу, а встают в конец очереди — спин-цикл в этом режиме отключается. Это гарантирует прогресс долго ждавшим ценой пиковой пропускной способности. Как только очередь опустевает или последняя разбуженная горутина ждала меньше 1мс, мьютекс возвращается в normal mode.

RWMutex добавляет к этому разделение read/write-блокировок: несколько читателей могут держать RLock() одновременно, но писатель, ожидающий Lock(), блокирует новых читателей от захвата (чтобы не голодал бесконечно) — типичное практическое правило: RWMutex оправдан, когда чтений на порядок больше записей (грубая эвристика — 10:1 и выше), иначе накладные расходы на его более сложную логику не окупаются по сравнению с обычным Mutex.

Подробнее: sync.Once и sync.Cond — соседи Mutex, о которых часто забывают medium

sync.Once гарантирует, что переданная в Do(f) функция выполнится ровно один раз за весь жизненный цикл программы, даже если Do вызывают конкурентно из множества горутин одновременно — остальные вызовы просто дождутся завершения первого и вернутся, ничего не выполнив повторно. Типичное применение — ленивая потокобезопасная инициализация синглтона или общего подключения без ручной возни с мьютексом и флагом «уже инициализировано».

once.go
var once sync.Once
var conn *Connection

func getConn() *Connection {
    once.Do(func() { conn = connect() }) // выполнится только у первого вызвавшего
    return conn
}

sync.Cond — условная переменная поверх блокировки (обычно *sync.Mutex), нужна, когда горутине важно не просто дождаться освобождения лока, а дождаться конкретного условия. Методы: Wait() — атомарно освобождает лок и паркует горутину, при пробуждении сама же снова захватывает лок перед возвратом; Signal() — будит ровно одну ожидающую горутину; Broadcast() — будит все разом. Классическое правило использования — проверять условие в цикле for, а не в if: между пробуждением и повторным захватом лока условие могла успеть изменить другая горутина (или сработало «паразитное» пробуждение), поэтому после Wait() нужно перепроверять условие заново, а не считать пробуждение доказательством его истинности. (источник: habr.com/ru/articles/658623/)

8.6Гонки данных

race.go
counter := 0
var wg sync.WaitGroup
for i := 0; i < 1000; i++ {
    wg.Add(1)
    go func() {
        defer wg.Done()
        counter++ // ГОНКА — инкремент не атомарен
    }()
}
wg.Wait()
fmt.Println(counter) // не гарантированно 1000
камень

counter++ — это чтение, инкремент и запись тремя отдельными шагами; горутины могут перемежать их как угодно. Всегда гоняйте тесты с детектором гонок: go test -race / go run -race — он ловит именно такие гонки, а не полагайтесь только на глазомер.

Подробнее: дедлок, livelock, голодание — не путать medium

Три разных отказа конкурентной программы, которые часто путают на собеседовании:

ТерминСуть
Дедлок (deadlock)все участники заблокированы навсегда, взаимно ожидая друг друга — прогресса нет вообще; рантайм Go умеет обнаружить дедлок всех горутин сразу (тогда паникует с "all goroutines are asleep — deadlock!"), но не частичный дедлок подмножества горутин
Livelockгорутины не заблокированы, активно выполняются и реагируют друг на друга, но система в целом не продвигается — классический пример: два человека в коридоре синхронно уступают дорогу друг другу и одновременно шагают в одну сторону
Голодание (starvation)какая-то горутина в принципе может продвинуться, но ей систематически не даёт этого сделать более «агрессивный» сосед (см. normal-mode мьютекса в 8.5, где именно от этого защищает starvation mode)

Классические четыре условия Коффмана (Coffman conditions), при одновременном выполнении которых возможен дедлок: взаимное исключение (ресурс нельзя разделить), удержание-и-ожидание (процесс держит один ресурс и ждёт другой), отсутствие принудительного отбора ресурса, и циклическое ожидание (A ждёт B, B ждёт A). Убрать хотя бы одно условие — например, всегда захватывать несколько мьютексов в фиксированном глобальном порядке, убирая циклическое ожидание — стандартный способ гарантированно избежать дедлока при работе с несколькими блокировками.

Детектор гонок (-race) работает по алгоритму vector clocks поверх реальных запусков и замедляет выполнение примерно в 5–10 раз и увеличивает потребление памяти в разы — поэтому его держат во включённом виде в CI на тестах, но не в проде.

Подробнее: lock-free vs wait-free — чем CAS-цикл отличается от более строгой гарантии deep

sync/atomic позволяет писать алгоритмы вообще без блокировок — типичный паттерн: прочитать текущее значение, вычислить новое, попытаться атомарно подменить через CompareAndSwap, при неудаче (кто-то успел изменить значение первым) — повторить цикл заново.

cas_loop.go
for {
    old := atomic.LoadInt64(&x)
    n := f(old) // например, old*2 или max(old, candidate)
    if atomic.CompareAndSwapInt64(&x, old, n) {
        break
    }
    // проиграли гонку — old устарел, повторяем с начала
}

Это lock-free, но не wait-free — важное различие в строгости гарантии прогресса. Lock-free гарантирует лишь, что хотя бы одна горутина из всех конкурирующих продвинется вперёд за конечное время (система в целом не зависает) — но конкретная отдельная горутина в теории может проигрывать CAS сколь угодно много раз подряд при очень высокой конкуренции («живое голодание» одного участника при общем прогрессе системы). Wait-free — более сильная гарантия: каждая горутина завершает операцию за ограниченное число шагов независимо от того, что делают остальные — на практике такие структуры данных сложнее в реализации и применяются реже, чем lock-free с CAS-ретраем.

8.7Мини-паттерн: worker pool

Несколько воркеров разбирают одну очередь заданий и пишут результат в общий канал:

pool.go
func worker(id int, jobs <-chan int, results chan<- int) {
    for j := range jobs { // выходит из цикла, когда jobs закрыт и пуст
        results <- j * 2
    }
}

func main() {
    jobs := make(chan int, 5)
    results := make(chan int, 5)

    for w := 1; w <= 3; w++ {
        go worker(w, jobs, results)
    }
    for j := 1; j <= 5; j++ {
        jobs <- j
    }
    close(jobs) // сигнал воркерам — заданий больше не будет

    for i := 0; i < 5; i++ {
        fmt.Println(<-results)
    }
}
собес

Что означают <-chan int и chan<- int? Направленные типы каналов: jobs в сигнатуре worker — только для чтения, results — только для записи. Компилятор не даст перепутать направление — это защита от ошибок на уровне типов, а не просто соглашение.

Подробнее: кто закрывает канал результатов и как остановиться по контексту deep

Пример выше жёстко знает, что результатов будет ровно 5, поэтому читает результаты фиксированное число раз без закрытия results. В реальном пуле воркеров так не получится — читателю нужно знать, когда результаты закончились, а закрывать канал из нескольких воркеров одновременно нельзя (повторное закрытие — паника). Стандартное решение — отдельная «координирующая» горутина, которая через sync.WaitGroup дожидается завершения всех воркеров и только затем закрывает канал результатов:

pool_shutdown.go
var wg sync.WaitGroup
for w := 1; w <= 3; w++ {
    wg.Add(1)
    go func() {
        defer wg.Done()
        for j := range jobs {
            select {
            case results <- process(j):
            case <-ctx.Done():
                return // корректная остановка по отмене контекста
            }
        }
    }()
}
go func() {
    wg.Wait()
    close(results) // закрывает ровно ОДНА горутина, когда все воркеры точно завершились
}()
for r := range results { // читаем, пока канал не закроется
    fmt.Println(r)
}

Второй нюанс — грациозная остановка: воркер, слепо читающий из jobs в бесконечном for range, не отреагирует на отмену контекста, пока не придёт следующее задание или канал не закроется. Чтобы пул можно было остановить по таймауту/сигналу немедленно, каждую отправку/приём внутри воркера оборачивают в select с case <-ctx.Done(): return, как показано выше.

Подробнее: сколько воркеров заводить — CPU-bound и I/O-bound требуют разного ответа medium

Универсального числа воркеров не существует — правильный размер пула прямо зависит от того, чем именно занята задача внутри воркера:

Для CPU-bound задач (чистые вычисления, без ожидания сети/диска) оптимум обычно близок к runtime.NumCPU() (то есть к GOMAXPROCS) — больше воркеров, чем логических ядер, лишь увеличивает переключение контекста между горутинами, не давая реального прироста параллелизма, поскольку одновременно исполняться может ровно столько горутин, сколько есть P.

Для I/O-bound задач (сеть, диск, ожидание ответа БД) воркеров осмысленно заводить в разы или на порядки больше числа ядер — большую часть времени такая горутина не потребляет CPU вообще, а простаивает в ожидании ответа, дешёво занимая лишь несколько КБ стека. Здесь ограничивающий фактор — не число ядер, а внешние лимиты: число одновременных соединений, которое выдержит удалённый сервис/пул соединений БД, и под них подбирается размер пула (часто эмпирически, через нагрузочное тестирование), а не под NumCPU().
