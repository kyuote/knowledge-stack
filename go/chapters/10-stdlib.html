fmt.go

Подробнее: Stringer и почему %v сам вызывает String() medium

Пакет fmt перед выводом любого значения проверяет через приведение типа, реализует ли оно интерфейс fmt.Stringer (String() string) — если да, %v, %s и Println используют именно этот метод вместо вывода полей структуры по умолчанию. Это тот же механизм, что и с error (интерфейс с Error() string) — fmt одинаково умеет распознавать оба.

stringer.go
type Status int

const (
    StatusOK Status = iota
    StatusError
)

func (s Status) String() string {
    switch s {
    case StatusOK:
        return "ok"
    case StatusError:
        return "error"
    }
    return "unknown"
}

fmt.Println(StatusOK) // выведет "ok", а не "0"

Частая опасность: если внутри String() случайно форматировать сам получатель через %v (например, fmt.Sprintf("%v", s) вместо явного разбора полей) — получится бесконечная рекурсия и переполнение стека, потому что %v снова вызовет тот же String().

10.2strings / strconv

strings.go
strings.Contains(s, "go")
strings.Split(s, ",")
strings.Join(parts, "-")
strings.TrimSpace(s)

n, err := strconv.Atoi("42")        // строка → int
s := strconv.Itoa(42)                // int → строка
f, err := strconv.ParseFloat("3.14", 64)
камень

Строки неизменяемы (глава 1) — конкатенация через + в цикле каждый раз создаёт новую строку, это O(n²) на больших объёмах. Для многих склеек — strings.Builder:

builder.go
var b strings.Builder
for i := 0; i < 1000; i++ {
    b.WriteString("x")
}
result := b.String() // одна финальная аллокация вместо тысяч
Подробнее: почему Builder быстрее, и разница строка/[]byte/[]rune deep

strings.Builder внутри — просто растущий []byte (с той же логикой роста, что и у слайсов, глава 4), плюс защита от копирования через встроенный noCopy-детектор (паника при go vet, если Builder скопировали по значению после первой записи). В отличие от s += "x", где каждая конкатенация выделяет новую строку целиком и копирует старое содержимое, Builder переиспользует один и тот же буфер и лишь изредка перевыделяет его при росте — отсюда амортизированная O(n) вместо O(n²).

Ещё один частый вопрос на собеседовании — разница между []byte(s) и []rune(s): строка в Go — это последовательность байт в UTF-8, а не рун. []byte(s) просто копирует сырые байты (длина совпадает с len(s)); []rune(s) декодирует UTF-8 и даёт по одному элементу на кодовую точку Unicode — для строки с кириллицей или эмодзи len([]rune(s)) обычно меньше, чем len(s), потому что не-ASCII символы занимают 2–4 байта, но всего одну руну. Индексирование строки s[i] всегда возвращает байт, а не символ — для посимвольного (по рунам) прохода нужен for i, r := range s или явное приведение к []rune.

10.3time

time.go
d := 2 * time.Second
time.Sleep(d)

now := time.Now()
later := now.Add(time.Hour)
diff := later.Sub(now) // time.Duration

fmt.Println(now.Format("2006-01-02 15:04:05"))
собес

Почему формат — «2006-01-02», а не «YYYY-MM-DD»? В Go форматы строятся не буквами-плейсхолдерами, а через опорную дату: Mon Jan 2 15:04:05 MST 2006. Мнемоника — это просто числа по порядку: 01/02 03:04:05PM '06 -0700 → месяц-день-час-минута-секунда-год-таймзона, 1 2 3 4 5 6 7. Запоминаете один раз — и подставляете нужные части этой даты в любом порядке.

Подробнее: time.Time vs time.Duration, и почему нельзя сравнивать время через == medium

time.Duration — это просто int64-наносекунды с собственным типом и методом String() (отсюда красивый вывод вроде 1h30m0s), а time.Time — структура, хранящая момент времени с точностью до наносекунды плюс информацию о часовом поясе (*time.Location) и, для времён, полученных через time.Now(), ещё monotonic-компонент — отдельный «счётчик тиков» ядра, не привязанный к настенным часам.

Именно из-за monotonic-компонента t1 == t2 для двух значений time.Time — плохая идея: у двух логически одинаковых моментов может отличаться представление часового пояса или отсутствовать monotonic-часть (например, после Round/десериализации), и == сравнит все поля структуры буквально. Правильный способ сравнения — метод t1.Equal(t2), который сравнивает именно момент времени, игнорируя представление зоны; для упорядочивания — t1.Before(t2) / t1.After(t2).

Подробнее: коды выхода, сигналы и os.Exit vs return из main medium

os.Exit(code) завершает процесс немедленно — в отличие от обычного выхода из main(), он не выполняет отложенные defer ни в текущей, ни в других горутинах: если в коде есть defer file.Close() или defer wg.Wait(), они просто не сработают при вызове os.Exit. Поэтому os.Exit используют только в самом конце main, когда все важные defer уже точно отработали (типичный паттерн — вынести логику в отдельную функцию, которая возвращает код ошибки, и вызвать os.Exit только в самом main, после того как эта функция вернула управление).

По конвенции код 0 — успех, любое ненулевое значение — ошибка (конкретное число обычно не стандартизировано в самой программе, кроме общеупотребимых 1 — общая ошибка, 2 — неверные аргументы). Пакет os/signal с signal.Notify позволяет перехватить сигналы вроде SIGINT/SIGTERM и грациозно завершить работу (закрыть соединения, дождаться текущих запросов) вместо мгновенного убийства процесса.

10.5encoding/json

json.go
type User struct {
    Name string `json:"name"`
    Age  int    `json:"age,omitempty"`
}

u := User{Name: "Аня", Age: 25}
data, _ := json.Marshal(u)   // {"name":"Аня","age":25}

var u2 User
json.Unmarshal(data, &u2)    // JSON → struct
камень

Снова регистр первой буквы (главы 1 и 4): неэкспортированное поле encoding/json просто не увидит через reflect — ни при Marshal, ни при Unmarshal, без единой ошибки.

Подробнее: теги, omitempty, и почему Marshal/Unmarshal медленнее, чем кажется deep

Теги вида `json:"name,omitempty"` — это обычная строка в бэктиках, синтаксически часть объявления поля структуры, но не проверяемая компилятором семантически (опечатка в имени тега просто тихо не сработает). omitempty опускает поле при сериализации, если оно равно zero value своего типа — важный нюанс: для указателей, слайсов, map и интерфейсов «пусто» означает nil, а не «пустая, но не nil» коллекция; пустой, но не-nil слайс ([]int{}) всё равно попадёт в JSON как [], если явно не сравнить его отдельно.

json_tags.go
type Config struct {
    Name    string `json:"name"`
    APIKey  string `json:"-"`           // никогда не сериализуется
    Tags    []string `json:"tags,omitempty"`
    Timeout int      `json:"timeout_ms,omitempty"`
}

encoding/json из стандартной библиотеки исторически работает через reflect и заметно медленнее, чем кодогенерируемые альтернативы (easyjson, ffjson) или основанные на unsafe/SIMD библиотеки вроде json-iterator/go и segmentio/encoding/json — на высоконагруженных сервисах с большим объёмом JSON это частая точка оптимизации. В сообществе Go давно обсуждается переработанная версия пакета (нацеленная в том числе на производительность и более гибкую настройку тегов) — стоит свериться с актуальной документацией, попала ли она уже в стандартную библиотеку на момент собеседования.

10.6net/http

server.go
func handler(w http.ResponseWriter, r *http.Request) {
    fmt.Fprintln(w, "Привет из Go!")
}

func main() {
    http.HandleFunc("/", handler)
    http.ListenAndServe(":8080", nil)
}
собес

Почему у обработчика именно такая сигнатура? http.Handler — интерфейс с одним методом ServeHTTP(w, r) (привет, глава 6). http.HandlerFunc — тип-обёртка над обычной функцией, который сам реализует этот метод, вызывая внутри себя саму функцию. Так обычная func(w, r) становится валидным http.Handler без лишнего кода.

Подробнее: middleware как обёртка над http.Handler medium

Именно потому, что http.Handler — обычный интерфейс, middleware в Go — это не отдельный механизм фреймворка, а просто функция, принимающая один http.Handler и возвращающая другой, который что-то делает до/после вызова исходного:

middleware.go
func Logging(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        start := time.Now()
        next.ServeHTTP(w, r)
        log.Printf("%s %s — %v", r.Method, r.URL.Path, time.Since(start))
    })
}

http.Handle("/", Logging(http.HandlerFunc(handler)))

Несколько middleware комбинируются вложенной оборачиваемостью (Logging(Auth(RateLimit(handler)))) — порядок оборачивания определяет порядок выполнения «до» вызова и обратный порядок «после». http.ListenAndServe в проде почти никогда не используют напрямую без обёртки: базовый net/http-сервер по умолчанию не задаёт тайм-ауты чтения/записи, что уязвимо к Slowloris-атакам — production-код обычно явно настраивает http.Server{ReadTimeout: ..., WriteTimeout: ..., IdleTimeout: ...} вместо голого ListenAndServe.
