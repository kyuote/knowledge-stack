Глава 13

Идиомы и best practices

Как отличить код, написанный «на Go», от кода, просто скомпилированного компилятором Go. И чек-лист всех ловушек из прошлых глав в одном месте.

13.1Именование

naming.go
const MaxRetries = 3 // MixedCaps, не MAX_RETRIES и не max_retries

func (u User) Name() string { return u.name } // геттер — без "Get"

type Stringer interface { // интерфейс на один метод — по методу + "-er"
    String() string
}
собес

В маленькой области видимости — короткие имена (i, n, err в цикле из трёх строк), в широкой — говорящие. Обратная пропорция удивляет новичков из других языков, но это осознанное соглашение Go, а не небрежность.

Подробнее: инициализмы, и почему не GetName() medium

Официальный гайд Go по именованию требует единый регистр для инициализмов целиком: URL, ID, HTTP, API — а не Url, Id. Отсюда userID, ServeHTTP, parseURL — и характерная проблема при переходе с других языков, где принято Id/Url. golangci-lint и staticcheck отдельно проверяют это правило (линтер ST1003/revive).

Отказ от префикса Get для геттеров — тоже не случайность, а официальная рекомендация: если метод Name() просто возвращает поле без побочных эффектов, приставка Get ничего не добавляет к пониманию кода и только удлиняет каждый вызов. Исключение — когда операция реально что-то «получает» с side-эффектом (сходить в сеть, за файл), там `Get`-подобное имя уместно, потому что сигнализирует, что вызов не бесплатный.

13.2Accept interfaces, return structs

accept.go
// хорошо: принимает узкий интерфейс — подойдёт любой источник данных
func Copy(dst io.Writer, src io.Reader) (int64, error)

// хуже: требует конкретный тип, хотя нужен только один метод
func Save(f *os.File, data []byte) error
собес

Принимая интерфейс, функция работает с чем угодно, реализующим нужное поведение — включая фейки в тестах (глава 11). Возвращая конкретный тип, а не интерфейс, вы даёте вызывающему доступ ко всем его методам, а не только к урезанному подмножеству.

Подробнее: почему возврат интерфейса «на будущее» обычно вредит medium

Соблазн вернуть интерфейс из конструктора («а вдруг понадобится другая реализация») на практике почти всегда лишний: вызывающий код теряет доступ к конкретным методам и полям возвращаемого типа, которых нет в интерфейсе, а сам интерфейс приходится расширять при каждом новом методе — то есть интерфейс, объявленный «на стороне поставщика», в итоге пытается предугадать все нужды потребителей и либо разрастается, либо режет функциональность. Согласуется с идиомой из главы 6 («interface declared on consumer side»): именно потребитель кода должен объявить у себя узкий интерфейс под свои нужды, а не поставщик — заранее «широкий» интерфейс от поставщика.

Практическое правило: возвращать интерфейс из функции стоит только тогда, когда действительно нужно скрыть за одной сигнатурой несколько взаимозаменяемых реализаций уже сейчас (фабрика, возвращающая разные бэкенды по конфигу) — а не «про запас».

Подробнее: SOLID применительно к Go — без классов, но не без принципов medium

В Go нет классов и наследования, но все пять принципов SOLID переносятся на структуры/интерфейсы почти без искажений:

ПринципКак выглядит в Go
S — Single Responsibilityпакет или тип решает одну узкую задачу и решает её хорошо — в духе Unix-философии, а не «богатого» типа на всё сразу
O — Open/Closedкод открыт расширению через добавление новой реализации интерфейса и закрыт для модификации уже написанных и протестированных реализаций
L — Liskov Substitutionбез иерархии классов принцип превращается в требование к контракту интерфейса: реализация не должна вести себя так, что нарушает ожидания вызывающего кода (не паниковать там, где интерфейс это не предполагает, не менять смысл метода)
I — Interface Segregationровно идиома этой главы (13.2, выше) — маленькие интерфейсы на стороне потребителя лучше одного большого «на все случаи»
D — Dependency Inversionзависеть от интерфейсов, а не от конкретных реализаций; зависимости явно передаются через конструктор (constructor injection), а не создаются внутри самого типа

На практике I и D в Go получаются «бесплатно» из-за самой структурной типизации и идиомы «интерфейс объявляется у потребителя» (глава 6.3) — именно поэтому Go-код часто выглядит SOLID-совместимым, даже когда никто сознательно не следовал этой аббревиатуре. (источник: habr.com/ru/articles/658623/)

13.3gofmt

terminal
gofmt -l .      # показать неотформатированные файлы
gofmt -w .      # отформатировать на месте
goimports -w .  # + сортирует импорты, добавляет/убирает неиспользуемые
собес

В Go нет холивара про табы/пробелы или расположение скобок — gofmt один на весь язык и не настраивается. Это часть тулчейна, а не линтер на вкус проекта.

Подробнее: gofmt работает по AST, а не по текстовым правилам deep

gofmt не «причёсывает» исходный текст построчно регулярками, а полностью парсит файл в абстрактное синтаксическое дерево (AST) и заново печатает его в канонической форме — поэтому он не может случайно сломать код (в отличие от текстовых автоформаттеров, у которых бывают крайние случаи с некорректным результатом), и попутно нормализует то, что находится за пределами «стиля» в узком смысле — например, автоматически выравнивает соседние строки в блоке констант/структур по табуляции.

gofmt -s дополнительно упрощает код там, где это возможно без потери смысла (убирает избыточные преобразования типов, упрощает []T{T{...}} до []T{{...}}). Именно потому, что форматирование детерминировано и не настраивается, ревью в Go-командах почти никогда не тратит время на обсуждение стиля кода — весь этот класс споров устранён на уровне тулчейна.

13.4go vet и линтеры

terminal
go vet ./...        # неверные verb'ы в Printf, копирование Mutex и т.п.
golangci-lint run   # агрегатор: staticcheck, errcheck, unused…
собес

go vet — часть официального тулчейна и автоматически запускается перед go test. golangci-lint — отдельный инструмент поверх, объединяющий десятки линтеров с одной конфигурацией.

Подробнее: чем vet отличается от линтера, и что ловит staticcheck medium

Разница в философии: go vet проверяет только конструкции, которые компилируются, но почти гарантированно являются ошибкой — неверное число или тип аргументов в Printf-подобной функции, копирование значения, содержащего sync.Mutex (что делает копию мьютекса независимой блокировкой — классическая скрытая гонка), недостижимый код после return. Поэтому он входит в официальный тулчейн и запускается автоматически. Сторонние линтеры (golangci-lint как агрегатор поверх staticcheck, errcheck, unused, gosec и десятков других) идут дальше и ловят стилистические и потенциально проблемные, но не гарантированно ошибочные вещи — неиспользуемые переменные и импорты, непроверенные ошибки, потенциальные уязвимости, избыточно сложные функции.

staticcheck отдельно славится проверками уровня «это технически работает, но почти наверняка не то, что вы хотели» — например, бесполезное сравнение x != nil для типа, который не может быть nil, или неиспользуемый результат вызова без побочных эффектов.

13.6Организация пакетов

packages.go
// плохо: package util / common / helpers — свалка всего подряд

// хорошо: имя пакета — то, что он предоставляет
package validator

func Email(s string) error { /* … */ }
// снаружи читается как validator.Email(...)
собес

Имя пакета — неявный префикс для всего экспортированного из него. validator.Email(...) читается как связное предложение; utils.ValidateEmail(...) — нет. Пакеты util/common обычно сигнал, что модуль не нашёл своей ответственности.

Подробнее: internal/, layout проекта и циклические импорты deep

Каталог с зарезервированным именем internal/ — единственный механизм видимости пакетов на уровне модуля, встроенный прямо в тулчейн: пакет myapp/internal/db можно импортировать только из кода, лежащего внутри myapp (точнее — внутри дерева, корень которого — родитель internal); попытка импортировать его из другого модуля — ошибка компиляции, а не просто соглашение об именовании. Это единственный официальный способ пометить пакет как «не для внешнего использования».

Общепринятый (хотя формально не навязанный тулчейном) layout — неофициальный стандарт golang-standards/project-layout: cmd/ — точки входа (main-пакеты, обычно тонкие), internal/ — приватная бизнес-логика, pkg/ — код, специально предназначенный для переиспользования извне модуля (спорная директория — многие проекты обходятся без неё, если ничего действительно не рассчитано на внешних потребителей).

Циклический импорт (пакет A импортирует B, а B — A) — ошибка компиляции, а не предупреждение; типичное лечение — выделить общий код, от которого зависят оба, в третий пакет, либо объединить A и B в один пакет, если они настолько тесно связаны, что тянут друг на друга.
